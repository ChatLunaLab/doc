# 术语表

ChatLuna v2 涉及多个核心技术概念与系统边界。在控制台界面和日常交流中，相同的中文词汇可能对应完全不同的底层实现。在排查故障、编写插件或调用接口时，请以本表声明的具体语义与系统实体为准。

## 配置与运行时

| 术语 | 定义与职责 | 边界与区别（不等于） |
| --- | --- | --- |
| **instance / 实例** | 独立的完整运行环境，拥有自己的 `package`、根清单与运行时数据。 | 单个机器人账号或浏览器标签页。 |
| **launcher** | 全局 `chatluna` 命令行工具，负责管理实例选择、进程调度、依赖包与故障恢复。 | 所有业务服务本身的实现集合。 |
| **manifest / 清单** | Cordis 加载的插件配置树，支持通过 `include` 引入外部配置。 | 完整的环境变量集合或运行时数据库。 |
| **entry / 配置条目** | 清单中带有固定 `id` 的插件或配置组项。 | 会话日志中的 `SessionEntry`。 |
| **fiber** | Cordis 中单次挂载插件时的生命周期与资源所有权边界。 | 操作系统线程或物理机、容器级隔离环境。 |
| **inject** | 插件声明所需依赖服务的注入机制，以及对应的依赖子树挂载流程。 | 运行时对服务可用性的主动轮询。 |
| **HMR** | 开发环境下的模块热重载机制，仅卸载受影响的插件并重新构建其生命周期。 | 保证所有正在运行的执行上下文不受中断。 |
| **config transaction** | 包含配置写入、静态校验并安全应用到运行时的完整变更流程。 | 跨数据库、跨网络或跨节点的分布式事务。 |
| **safe mode / 安全模式** | 由 supervisor 提供的最小化恢复启动环境，用于排查启动故障。 | 抵御任意恶意插件代码的安全沙箱。 |

## 对话与执行

### 核心对象与生命周期

| 术语 | 定义与边界说明 |
| --- | --- |
| **conversation** | 面向用户交互或业务路由的逻辑会话。索引维护、主线切换与活跃执行调度统一由 `conversations` 服务负责。 |
| **head** | 当前业务对话所指向的 `Session` 引用，并非历史日志条目的快照副本。 |
| **Session** | 有序且仅追加（append-only）的会话日志与视图对象。持久化存储由底层的 `SessionStore` 实现承担。 |
| **SessionEntry** | 构成 `Session` 日志的基础条目联合类型，包含 `message`、`cut`、`mark` 三类；字段 `n` 为递增的日志绝对序号。 |
| **message** | 已正式提交保存的聊天消息记录，不包括流式生成中尚未完成的临时文本。 |
| **cut** | 上下文截断点与关联摘要。用于调整后续构建上下文时的视图，不会物理删除历史日志。 |
| **mark** | 带有特定名称的状态标记或追踪记录。仅用于系统内部流转，不会作为对话消息直接提供给模型。 |
| **draft** | 正在生成且尚未正式提交的草稿内容。系统不保证此类中间状态具备落盘持久化能力。 |
| **committed** | 已被 `Session` 接收并成功追加的条目。具体的落盘时机与容灾保证取决于所选用的 store 实现。 |
| **Agent** | 拥有独立运行状态、输入队列与驱动循环的活跃执行体，区别于存储中静态保存的 `Session` 数据。 |
| **turn** | Agent 的单次业务执行轮次。一次 turn 可以按需包含多次模型推理步骤与工具调用过程。 |
| **step** | 单次模型推理请求及其前后的上下文处理边界。 |
| **Run** | 针对单次 chat 模型推理请求的流式传输与最终结果封装，不代表包含工具调用的完整 Agent 闭环。 |

### 调度控制与上下文管理

| 术语 | 定义与边界说明 |
| --- | --- |
| **receive next** | 将新输入放入 Agent 的待处理缓冲队列，等待当前轮次结束后在下一轮（turn）执行。 |
| **receive now** | 在当前步骤（step）的执行边界插入新输入，不会强行打断正在等待响应的外部网络请求。 |
| **receive quiet** | 仅将输入写入日志而不唤醒空闲的 Agent，也不能作为输入已被消费的业务凭证。 |
| **abort** | 向当前执行流程发送中断请求。已发送至外部的网络请求、写入操作或已推送消息无法撤回或回滚。 |
| **branch / fork** | 从指定日志位置派生出新的子 `Session`。创建分支日志本身不会自动切换业务主线 `head`，需由上层 conversation 协同切换。 |
| **lane** | 路由层用于划分消息流向的逻辑通道，不同于 `Session.branch` 机制，也不具备安全隔离能力。 |
| **compaction** | 通过生成摘要并在日志中插入 `cut` 标记来缩减上下文长度的过程，与模型供应商提供的 prompt cache 机制无关。 |

> **标识符与序列号说明**：
> `Session` 日志序号 `n` 与前端渲染的消息列表索引并不等价：插入 `mark`、`cut` 或是界面合并展示时，都会导致视觉计数与底层日志序号产生偏移。在系统集成与排查故障时，切勿将 HTTP 查询参数 `seq`、SSE 传输中的 `id`、前端 UI 的 `revision` 与数据库内部主键直接混用或相互替代。

## 模型

- **provider**：具体的接入协议或供应商适配实现。在系统中配置完成平台与密钥，仅代表凭据就绪，并不代表远端推理端点已经连通或当前可用。
- **model address**：模型寻址标识符。在运行时通常写作 `provider:model` 格式；部分预设元数据也允许使用 `provider/model`，系统会根据具体接口的参数边界分别解析。
- **role / 模型角色**：逻辑角色与用途的绑定标识，例如 `@small`、`@medium`、`@large`、`@decide` 等。角色只代表能力映射策略，并不绑定特定供应商品牌、计费单价或绝对能力等级。
- **modality / 模态**：系统支持的交互模态定义，包括 `chat`、`embed`、`rerank`、`draw`、`speak`、`listen`、`decide`。其中 `decide` 是专用于结构化裁决的独立模态，其调用协议与行为不同于普通的聊天 JSON 格式化输出。
- **verb / 动词**：模型调用的统一 API 入口方法，包含 `ask`、`chat`、`extract`、`embed`、`rerank`、`draw`、`speak`、`listen`、`decide`、`decideOne` 以及 `judge`。
- **resolve / bind / call**：单次模型调用的三个独立生命周期阶段：
  - *resolve*：根据规则解析并确定目标模型；
  - *bind*：将当前调用的运行参数绑定到具体的适配器实现；
  - *call*：正式发起网络通信并向端点发送请求。
  需要注意，在早期的模型寻址或参数校验阶段，调用同样可能因为不合规而抛出异常并失败。
- **generation**：Provider 适配器在生命周期中重新挂载或热重载时递增的代际编号。请不要将它与提示词或缓存维度的 prompt/cache epoch 混淆。
- **usage**：标准化后的 Token 消耗计量数据。不同供应商返回的总输入、缓存读取、缓存写入以及推理计算 Token 之间可能存在交集或统计包含关系，计算业务用量时不能直接简单相加。

## 上下文与缓存

- **preset / 预设**：由系统统一管理的 Markdown 源文件及其配套元数据、片段与配置集合。常见的「人设伪装」只是预设定义角色人设、行为约束和记忆检索规则的一种具体应用形式，并非一种独立的新模型协议。
- **prompt zones**：提示词构建时的区域划分，分为 `system`、`context` 和 `input` 三个区：
  - `system`：放置高稳定性的前缀内容，便于利用供应商的提示词缓存；
  - `context`：用于承载动态注入的外部数据与历史会话记录；
  - 这种逻辑分区仅用于组织提示词结构，不能作为区分可信内容与不可信内容的安全防御边界。
- **mutable variable**：取值会随调用轮次频繁变化的可变变量。在严格要求静态内容的 `system` 区中使用此类变量会直接抛出 `MutableVariableError`，系统不会静默降级或保留变量原文本。
- **epoch**：提示词模板或工具定义前缀的缓存生命周期边界。它只表示缓存切片边界，既不代表业务层面的会话分叉（branch），也不代表底层模型实现版本的迭代。
- **cache break**：向模型供应商协议显式声明的缓存分段断点。底层是否真正命中缓存以及具体的计费优惠，完全由该模型协议与供应商服务端的机制决定。
- **memory scope**：长期记忆的作用域分级，涵盖全局共享、预设、群聊、用户与对话等维度。在构建群聊上下文时，系统可能会合并引入近期活跃发言者的用户维度记忆。
- **memory index**：系统在上下文中自动注入的主题摘要索引，而非所有记忆条目的原始正文。开启会话隔离（`conversation isolation`）只会收窄上下文自动注入的索引范围，并不限制拥有权限的 `memory_search` 工具在获得授权后检索其他范围的记忆数据。

## 能力与权限

| 术语 | 定义与边界说明 |
| --- | --- |
| **tool** | 注册给模型调用的动作单元，声明有参数结构 `args` 与执行方法 `run`。模型在上下文中接收到 tool schema 仅代表感知到该动作，不代表系统已预先批准执行。 |
| **tool search** | 工具的动态检索机制。通过按需发现并延迟挂载工具来减少初始请求的提示词体积，不能作为绕过权限策略的手段。 |
| **MCP** | 即 Model Context Protocol，用于连接外部工具与上下文资源的通信协议。对端进程自身的安全性、凭据有效性以及网络连通性仍需独立配置和授信。 |
| **skill** | 能够被系统检索与激活的工作规范说明或复合能力资源。加载说明性文本本身不会让执行环境自动获取额外的系统调用权限。 |
| **tool auto / ask / off** | 工具策略层提供的三种行为选项：自动运行（auto，仍受能力权限规则约束）、人工审批（ask）与完全禁用（off）。这与全局权限策略中的 `permission mode` 是不同维度的概念。 |
| **permission mode** | 系统统一的权限求值策略，包括 `read-only`、`files`、`auto`、`allow` 等模式。最终权限由主体身份、规则列表与操作等级综合计算决定。 |
| **machine** | 由 `computer` 服务统一管理的外部执行后端，例如 `local`、`ssh`、`docker`、`e2b`。 |
| **sandbox** | 具体执行环境所提供的隔离机制。沙箱隔离能力完全依赖底层 machine 后端的配置与实现，无法单纯通过在配置中勾选「启用工具」自动获得。 |
| **background** | 异步任务调度与结果追踪管理器。系统不保证宿主进程在异常崩溃重启后能恢复未完成任务的内存现场。 |
| **subagent** | 由父级任务衍生出的子执行对象。即使配置了上下文继承隔离（`inherit none`），也不代表它在操作系统或文件系统层面上拥有安全隔离。 |
| **settled** | 执行流程进入最终确定状态。该终态包含执行失败（failed）或主动取消（aborted），并不等同于业务执行成功。 |

## 诊断与协议

- **trace / 轨迹**：依据系统日志与执行上下文记录生成的诊断视图，用于追溯输入数据、工具调用链、模型输出以及错误堆栈。trace 是对底层事实数据的排查呈现，并非独立于日志系统之外的第二套状态数据。
- **reconstruct / 请求重建**：根据历史记录的边界数据还原当时的请求载荷结构。该过程仅在本地拼装结构，不会重新请求模型端点，亦不执行任何工具逻辑。
- **replay / 重放**：基于指定的历史边界重新向模型发起新的推理调用用于结果比对。重放操作会真实消耗网络与模型配额并产生计费，但不会自动重新执行原历史中的工具调用，亦不会修改原 `Session` 日志。
- **durable SSE**：用于向客户端推送已正式提交的 `Session` 条目流，支持客户端携带 `sessionId:n` 游标实现断线追溯恢复。该命名仅表明协议支持持久化条目的断点重传，在未配置持久化 store 的内存模式下，不具备抗进程崩溃或断电的能力。
- **live SSE**：用于向客户端实时展示尚未提交的生成内容快照与增量分块。传输中的 `revision` 字段仅用于前端渲染视图同步，不能作为 durable SSE 的历史恢复游标使用。
- **state / action**：管理 WebUI 所使用的强类型状态快照与操作动作协议，与传输对话流的 SSE 通道职责相互独立。
- **access token / 访问口令**：用于验证访问当前实例权限的静态安全口令，不是模型供应商的 `provider key`。登录鉴权成功后签发的会话凭据（session credential）与访问口令在结构和用途上互不相同。
- **owner / 主人**：经应用确认的平台管理身份。已单独设置的权限等级仍应以具体权限记录为准；不同于标准 Web 系统的多租户账号体系，WebUI 目前直接使用实例所有者的访问口令进行统一认证。
- **idempotency / 幂等**：针对相同业务操作请求的防重复提交约束机制。当前 HTTP 层的内存幂等记录表具备时间窗口限制，且在进程重启后丢失，系统不承诺提供跨多进程的绝对分布式 exactly-once 保证。

想了解更多底层机制，请继续阅读[架构总览](/architecture/)；若想快速开始操作，请前往[首次配置](/manual/usage/webui)。

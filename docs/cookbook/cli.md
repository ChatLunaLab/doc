# 命令行诊断

::: tip
控制台打不开、实例起不来、会话数据可疑时，终端里的几条命令往往比界面更管用。
:::

当 Web 控制台无法访问、实例无法启动或会话数据出现异常时，控制台往往已经无法提供有效线索。此时你可以使用终端里的诊断命令进行排查。

## 两个入口

### 全局启动器

安装后可以直接在终端使用 `chatluna` 命令。

它负责管理 `~/.chatluna` 目录下的所有实例，涵盖创建、启动、停止、升级与修复等操作。

### 实例内命令

实例自身的 `chatluna` 命令（通常在项目目录内借助包管理器执行）专注于深度诊断与数据导出。

它不负责启动实例——启动实例始终需要使用外部的全局启动器。

::: tip
分不清两者的区别时，可以直接查看帮助信息。

全局启动器的命令面向「实例」，而实例内命令面向「数据」。
:::

## 实例管理

| 命令 | 作用 |
| --- | --- |
| `create <名字>` | 创建实例（可选模板、包管理器、目录） |
| `start [名字]` | 启动（可后台运行） |
| `list` | 列出实例与运行状态 |
| `stop [名字]` | 停止 |
| `restart [名字]` | 重启 |
| `dev [目录]` | 开发模式启动（热更新，不做恢复与安全模式） |

### 默认实例

执行命令时不指定实例名称，启动器会自动启动默认实例。

默认实例记录在全局启动器配置中。首次创建实例时，它会被自动写入配置作为默认项。

### 后台运行

在服务器环境下，通常不需要将进程常驻在前台。使用 `start` 命令并附加后台参数时，进程会脱离终端在后台运行，日志会自动写入指定的日志目录。

这种方式适合部署在远程服务器或无人值守的环境中。

### 开发模式

`dev` 会以源码方式启动实例，并支持代码热更新。

开发模式下关闭了快照恢复与安全模式。在本地开发时，你可以直接看到完整的错误调用栈，而不会被容灾机制自动掩盖。

## 依赖管理

| 命令 | 作用 |
| --- | --- |
| `add <包...>` | 为实例安装插件 |
| `remove <包...>` | 卸载插件 |
| `link <目录>` | 链接本地插件目录 |
| `unlink <名字>` | 取消链接 |

插件安装走的是与控制台完全相同的包管理队列，即使并发操作也不会与界面产生冲突。

`link` 适用于本地开发调试：直接把本地代码目录软链接进来，修改源码后实例即可即时生效；调试结束后，执行 `unlink` 取消链接即可。

## 维护

### update

用于更新启动器本身以及各实例中的插件。

它的标准执行流程为：创建快照 → 执行更新 → 健康检查 → 失败自动回滚。更新失败时会自动回滚，确保升级过程安全可控。

### repair

当实例发生严重异常、无法启动时使用。

它会在现场收集详细的诊断信息，调度本地 Agent 尝试执行一次自动修复，并生成一份完整的诊断报告。

### report

查看最近一次执行修复后的详细报告，其中包含了启动失败现场的日志尾部。

::: warning
`repair` 并不是万能的。

它解决的是「配置格式错误」或「依赖版本异常」这类环境问题，不能修复业务层面的逻辑错误。自动修复未解决时，报告里的原始日志才是人工排查的关键。
:::

### new

在实例、项目或仓库中快速生成标准的插件脚手架。

当你准备着手开发自定义插件时，用它能省去手动搭建目录结构的麻烦。

## 诊断

### 配置检查

用于验证实例配置与运行环境的基础契约是否健康。

- **检查什么**：插件清单是否合法、包契约依赖是否满足、受保护路径配置是否正确，以及控制台入口资源是否完整。
- **通过说明什么**：插件依赖完整、路由配置合规，Web 控制台具备正常加载运行的基础条件。
- **失败先看哪**：查看控制台输出中是否有插件名拼写错误、缺失的 npm 依赖包，以及受保护路径（如控制台路径）是否配置缺漏。

### 会话检查

用于针对特定会话进行数据链与状态完整性检查。

- **检查什么**：指定会话的日志不变量，确认上下文消息是否有断档、索引与内容是否一致，以及各类状态标记是否成对闭合。
- **通过说明什么**：该会话的上下文记录完整无损，状态机与历史消息可被正常回放与追加。
- **失败先看哪**：查看最近几条消息的写入记录、数据库日志，以及是否存在意外中断导致的未闭合标记或索引错位。

### 缓存检查

深入分析指定会话的模型缓存周期与上下文复用状况。

- **检查什么**：会话的上下文缓存周期、Prompt 前缀命中情况以及缓存失效或切换的具体原因。
- **通过说明什么**：会话消息前缀保持稳定，上下文缓存正在有效工作，未发生意外的缓存击穿或前缀颠簸。
- **失败先看哪**：若发现每轮均未命中缓存，先看报告中记录的上下文切换点，排查是哪次提示词改动或动态注入破坏了公共前缀。

### 提供商检查

探测各模型服务提供商的连通性与服务响应。该命令需要实例保持在运行状态，会通过运行接口向外发起实时探测。

- **检查什么**：已配置的各模型提供商 API 端点连通性、网络延迟以及认证凭据有效性。
- **通过说明什么**：实例到模型服务提供商的网络通路畅通，API Key 与鉴权配置完全正常。
- **失败先看哪**：检查网络代理配置、本地 DNS 解析，以及各提供商对应的 API Key 与 Base URL 是否配置正确或已过期失效。

### 导出

将指定会话的完整历史记录导出为结构化的 JSONL 格式文件。

- **检查什么**：目标会话在存储层中的数据可读性与记录序列的完整性，并提取出全量记录。
- **通过说明什么**：该会话的全部历史数据已完整导出，可以直接复现对话过程与调用链。
- **失败先看哪**：确认会话 ID 是否输入正确，或者会话对应的本地数据文件是否存在读写权限异常与损坏。

::: tip
导出的内容是包含工具调用与系统消息在内的完整日志。在分享给他人或公开发布前，请务必确认其中没有包含敏感配置或隐私信息。
:::

## 输出与退出码

诊断命令在终端中会输出易于阅读的排版报告。

如果编写脚本或将其接入自动化工作流，请务必关注命令的退出码：执行成功退出码为 0，检测到异常或错误时则会返回非零值。此外，修复报告采用了统一的结构化格式，遇到疑难问题时可以直接复制并附在 Issue 中求助。

## 部署中的用法

### 服务器

在独立服务器上，通常使用后台模式启动实例，并交由系统服务管理器（如 systemd）进行进程托管。

升级维护时先执行 `update`，依靠自动健康检查把关；一旦升级失败，便可根据报告快速回滚。

### 容器

在容器化部署环境下，容器的入口脚本通常直接启动实例进程。

容器健康检查建议直接探测 Web 控制台端口；实例起不来时，直接查看容器的标准输出日志即可。

### CI

在持续集成流程中，可以利用实例内命令快速完成各项自动化冒烟检查：

- 校验配置清单是否合法合规
- 确认全部包依赖是否完整可用
- 验证会话日志存储是否能正常读取

## 与 supervisor 的关系

通过命令行启动实例时，进程全程由内置的 supervisor 监管：

- 进程意外崩溃时自动拉起重启
- 健康检查失败时自动进入恢复流程
- 连续恢复失败后自动降级进入安全模式

命令行本身只是操作的发起者与控制端；真正保障服务持续稳定运行的，是底层的 supervisor 守护进程。

## 排查

这里总结了日常使用中最常见的几类排查场景：

**命令找不到实例**  
确认实例名字拼写无误，并检查 `~/.chatluna/instances` 目录下是否存在对应的实例目录。

**start 后立刻退出**  
先看日志尾部。端口被占用、配置格式错误、核心依赖缺失是最常见的三大诱因。

**list 显示运行中，但打不开**  
可能是后台刚启动，健康检查尚未完全通过；也有可能是监听端口被本地防火墙或反向代理拦截。

**update 后起不来**  
使用 `repair` 命令尝试本地修复，或者直接回滚到更新前自动创建的快照。报告中会有具体的失败原因。

**doctor 报路径保护错误**  
控制台路由路径未被包含在受保护前缀中。这属于危险的配置缺陷，必须立即修正。

**导出失败**  
通常是会话 ID 错误，或者对应的会话数据文件损坏。建议先运行会话检查确认会话状态。

# 从 ChatLuna v1 迁移到 v2

ChatLuna v2 基于 Cordis 4 架构全面重构，演进为一个独立的应用程序。因此，你无法直接在原有的 Koishi 实例中对 v1 插件进行就地升级。

如果你正在运行 v1，最稳妥的迁移路线是全新部署一套独立的 v2 实例：使用独立的运行目录、独立的数据库以及独立的数据根目录。在完整迁移配置与相关资产并完成全链路验证后，再将生产聊天平台平滑切换过来。

如果你需要查阅旧版的部署配置或历史说明，可以随时访问 [v1.chatluna.chat](https://v1.chatluna.chat)。

---

## 迁移前准备：资产清单与备份

在部署新实例之前，建议先梳理一份清晰的 v1 运行资产清单：

- **平台与账号**：当前接入的聊天平台类型、机器人账号及身份标识。
- **模型与 Provider**：已接入的服务商、模型名称、自定义端点地址及访问凭据。
- **预设与世界书**：自定义的 YAML 预设文件、角色卡、世界书及配套静态资源。
- **规则与行为**：已配置的场景规则、消息路由策略、触发词与激活条件、会话归属。
- **能力扩展**：日常使用的自定义扩展工具、外部插件及必须保留的业务逻辑。

### 备份安全与隔离规范

在备份与规划环境隔离时，请遵循以下规范：

1. **彻底物理隔离**：切勿让 v2 直接打开、读取或写入旧版 v1 的数据库文件。两套系统也严禁挂载或复用同一个正在写入的数据目录。
2. **执行完整冷备份**：完整备份 v1 的 Koishi 配置文件、数据库、媒体资源及环境凭据。若使用在线数据库，请通过其原生导出工具生成一致性备份副本；备份完成后，确认备份文件大小正常且可独立读取。
3. **保留清晰的回退链**：完整记录 v1 当前运行的依赖版本与锁定文件，并整理一份明确的回滚步骤清单，确保在新环境遇到问题时能随时恢复旧实例。
4. **妥善保管凭据与私密数据**：导出的备份中通常包含明文 API Key 和用户聊天记录，请务必设置严格的文件权限，切勿直接提交到公开代码仓库中；确认备份存放在受保护的私有目录中。

## 资产迁移与重建对照

下表列出了两代版本间各类资产的迁移与重建对照：

| 旧资源类型 | v2 处理方式 | 重点检查项 |
| --- | --- | --- |
| **Provider 与模型** | 按照对应 v2 Schema 重新配置 | SDK 依赖是否安装、端点 URL 格式、模型标识符（如 `provider:model`）、凭据有效性与真实推理测试。 |
| **聊天平台** | 安装对应的 Satori adapter，重建连接 | 上行消息接收、下行消息发送、平台身份标识（Bot ID 与平台账号）、命令前缀识别。 |
| **YAML 预设与内容资产** | 使用 v2 已支持的导入入口，检查转换后的源码 | 变量占位符、`include` 引用路径、世界书触发器、Few-shot 示例、`system` 与 `context` 的显式划分。 |
| **人格与运行状态** | 按照 v2 character 与记忆契约重新构建 | 记忆归属范围（scope）、首次主人确认机制、自动提取开关状态、管理操作权限划分。 |
| **Koishi 插件** | 寻找明确的 v2 移植实现，或按新扩展点重新开发 | 严禁仅因存在 command 与 session 兼容层就假设任意旧插件完全兼容。 |
| **历史会话数据** | 保留 v1 数据作为只读副本供人工参考 | 不可据此伪造 v2 的请求 mark、工具调用因果链或计费 Token 记录。 |

### 关于历史会话迁移的限制说明

目前没有通用的自动化流程能将任意 v1 历史会话无损转换为可精确重建请求的 v2 Session。

v1 的消息历史通常只是扁平的消息数组，并没有记录调用模型时的请求参数、工具调用的中间思考因果链以及 Token 消耗。如果强行将旧消息写入 v2 的运行引擎，会破坏底层完整的状态审计与调度上下文。

旧会话文本仍可作为纯文本参考资料归档，或在需要时提取关键提示词，但请不要直接将其挂载为底层的运行态 Session。

## 部署独立的 v2 实例

准备就绪后，即可开始搭建全新的 v2 环境。关于全新实例的具体安装步骤，请参考 [选择安装方式](/manual/starter/) 与 [快速上手](/manual/quickstart)。

初次启动新实例时，**切勿直接连接生产聊天平台**。建议先利用内置的 Web 聊天窗口或受控的测试账号，在安全的本地沙箱中完成全部调试。

### 检查配置与目录结构

在确认新环境健康状态时，应先核对配置文件的语法与目录结构。

在部署目录中运行实例诊断命令：

执行 `chatluna doctor config --dir .`（若处于源码工作区，可执行 `yarn chatluna doctor config --dir .`）。运行后，确认控制台输出的各项校验均已通过。

关于诊断结果，有两点需要注意：
- 诊断命令返回成功仅代表本地配置格式与文件路径有效，并不代表远端模型端点或平台网络已连通。
- 当前工作目录、受管实例名与 `--dir` 参数分属不同层级，请仔细核对目标目录，避免将配置写入错误路径。

### 网络安全与访问控制

在网络规划与访问控制方面，需要提前配置好访问鉴权与端口约束：
- 外部网络与内部服务互通时，Docker 容器内部网络、宿主机端口映射、`allowRemote` 配置项与反向代理 HTTPS 分属不同层级，切勿直接套用源码仓库中的本地回环地址默认配置。
- 确保 `/api` 与 `/console` 等管理入口均已开启网络防护与身份验证。配置完成后，确认未授权或口令错误时的访问会被正确拦截；目前系统采用实例共享口令，而非各端点独立配置口令。

## 重新配置模型、平台与场景规则

实例搭建完成后，即可在新架构中逐一重建模型能力、聊天渠道与对话逻辑。

### 1. 模型与 Provider 配置

根据 v2 规范重新填写 Provider 密钥、端点地址与所需模型，并安装对应的客户端 SDK 依赖。

保存配置后，必须发起一次真实的端到端对话推理调用。确认控制台能收到模型返回的流式文本且计费统计正常，不要仅凭模型列表刷新成功就判定配置完成。

模型标识符在不同位置的表示格式有所不同：
- 运行时调用与场景引用中，通常采用形如 `provider:model` 的冒号分隔格式。
- API 交互与数据对象中，通常表现为独立的 `provider` 与 `model` 两个字段。
- 预设文件的元信息中，通常采用 `provider/model` 的斜杠格式。

### 2. 聊天平台接入

前往扩展管理页面，安装目标聊天平台对应的 Satori adapter，并按照提示填入鉴权参数。

v2 虽然提供了面向 Koishi 风格指令的兼容层，但这并不意味着可以直接运行任意旧插件。完成平台配置后，请按链路分段验证以下环节：
- 平台用户发送测试消息，确认 v2 能正常接收上行消息。
- 检查机器人的基础指令前缀能否被正确识别与触发。
- Agent 推理生成的回复能否顺利投递，平台端下行展示正常。

### 3. 场景规则重建

v2 对场景规则进行了命名空间重构，用于统一管理 engine 调度、模型选择、预设绑定、会话归属、激活方式以及渲染策略。

不要直接从旧配置中复制 `routingRules` 或 `patch` 等字段，这些键名并非统一标准，直接粘贴会导致解析失败。建议对照实际业务需求，在控制台中逐条手动配置规则。

配置完成后，使用「规则预览」功能仔细确认各字段在匹配链路上的来源与最终生效值，切勿凭「规则更具体」的直觉猜测匹配优先级。

## 迁移预设、角色与记忆

### 预设迁移检查清单

v2 提供了针对旧版 YAML 预设等格式的导入入口。导入完成后，请打开生成的 Markdown 源码、系统诊断信息与渲染预览，逐项核对以下内容：

1. **Frontmatter 格式校验**：检查文档头部的元数据字段，确认模型名称与运行参数完全符合 v2 Schema 规范；确认元数据能在预览面板中正确解析。
2. **静态与动态内容严格分离**：
   - 静态角色人设必须写入 `system` 字段。
   - 随对话推进的人物状态、动态检索资料等易变数据必须写入 `context` 字段。
   - 将 `mutable` 变量误填入 `system` 会直接抛出解析错误，系统不会静默容错；请确认字段归属准确。
3. **外部引用资源有效性**：核验预设中 `include` 引用的相对文件路径与静态资源链接；确认所有引用的外部资源均可正常读取，且内容安全可靠。
4. **世界书与 Few-shot 示例**：检查世界书词条的匹配触发规则；确认示例对话落入正确的上下文位置（`context` 或 `system`），与原始设定保持一致。
5. **绑定关系与版本一致性**：确认目标会话或场景已绑定至新导入的预设；核对保存后的预设修订版本号（revision）保持一致，且实际交互中渲染出的 Prompt 结构符合预期。

### 角色（Character）与记忆体系

v1 中的伪装群友插件数据、角色卡记录和旧版记忆不会自动转换为 v2 的运行状态，需要按照新体系重新梳理：

- **记忆存储与提取策略**：v2 的长期记忆系统默认采用 Markdown 主题后端，自动提取开关默认处于关闭状态。
- **重新规划记忆作用域**：理清记忆的作用范围（scope），不要假定每个用户的个人记忆天然仅在私聊中隔离可见。
- **主人身份绑定流程**：首次启动引导中的主人权限绑定，必须通过真实聊天平台的私聊绑定码或手动填写用户 ID 完成；系统不会将群聊或私聊中「第一个发言的用户」推断为主人。
- **权限降级安全保护**：若账号曾被管理员显式降级，即使重新执行主人确认流程，系统也不会自动恢复其最高管理权限。完成身份确认后，在后台核对权限列表记录是否准确。

## 扩展能力：工具、MCP 与自定义插件

### 启用工具与协议扩展

接入扩展能力时，建议遵循「按需启用、逐个验证」的原则：

- 逐一接入所需的工具服务、MCP 协议端点与技能（Skills），切勿在未经充分测试的情况下将未知工具的执行策略批量设为 `auto`。
- 配置完成后，仔细检查工具的参数 Schema 与权限边界，确认人工审批通道能正常拦截敏感操作。
- 区分不同协议的权限范围：技能描述文本本质上只是 Prompt 提示，不会赋予模型额外的底层操作权限；而本地启动的 MCP 进程会直接继承宿主服务的运行身份，需防范越权风险。

### 自定义插件迁移路径

如果你在 v1 中维护了自定义插件，建议将其拆解并对齐至 v2 的标准扩展点：

- 按照标准扩展点拆分重构：将旧业务拆解为**自定义工具（Tool）**、**提示词模板（Prompt）**、**路由策略（Router）**、**推理引擎（Engine）** 或 **消息中间件**。
- 严禁将旧版基于 LangChain 的适配器接口直接套用到新的模型运行时中。
- 不要为了兼容单个插件的特殊行为而修改 Agent 的公共核心接口。详细规范请参阅 [插件开发](/guide/develop/first-plugin)。
- 重构完成后，确认单元测试与模拟调用均可正常运行，业务输出符合预期。

### 运行环境隔离与任务清理

- **执行沙箱隔离**：代码执行环境与子代理需显式配置隔离级别。上下文隔离不等于文件系统隔离，直接暴露宿主机器的 Docker socket 会带来系统级安全隐患。
- **定时任务清理与重建**：旧版的定时任务需在 v2 中手动重新创建。配置完成后，确认定时任务的执行时间与推送目标准确无误，避免切换上线时一次性补发离线期间积压的通知。

## 验收核对与平台切换

### 切换前最终验收清单

在断开旧环境连接前，请逐项确认以下条件均已满足：

- [ ] 目录、数据库、数据根目录及只读备份完全物理独立，路径清晰。
- [ ] 真实端点模型推理通过，默认角色回复质量与异常回退逻辑均符合预期。
- [ ] 测试平台的上行、下行收发正常，规则匹配、激活条件、预设加载与会话归属准确。
- [ ] 会话控制行为（`stop`、`new`、`fork`、`compact`）与预期完全一致，长期记忆作用域清晰可解释。
- [ ] 针对工具调用至少完成一次「允许」「拒绝」与「询问审批」的全流程测试，未审核工具保持关闭。
- [ ] 服务网络策略、管理口令、反向代理转发以及控制台与 API 接口的访问防护校验完毕。
- [ ] v1 运行环境、配置文件及只读数据库处于随时可启动状态，回滚步骤与应急方案记录完备。

### 流量切换步骤

验收清单全部确认完毕后，按以下步骤进行平滑切换：

1. **停用旧连接**：在 v1 运行环境中彻底断开生产聊天平台的适配器连接。操作后确认旧实例已停止收发消息；**严禁让 v1 和 v2 同时连接同一个机器人账号**。
2. **启用新连接**：在 v2 实例中启用对应的平台 Satori adapter。操作后确认平台后台显示连接已成功建立，且机器人上线状态正常。
3. **监控全链路状态**：在生产聊天环境中发送测试指令，观察实时运行日志与模型推理轨迹，确认用户端能正常收到回复。需要注意的是：ChatLuna 消息 API 返回的 HTTP 202 仅表示服务端已接受分发请求，并不代表模型已生成完毕或平台消息已实际投递成功。

### 紧急回退流程

若切换上线后遇到严重故障，可执行以下应急回滚流程：

1. **切断新实例**：立即停止 v2 实例中对应的平台 adapter 连接，确认 v2 已完全释放平台通道。
2. **启动旧环境**：重新启动准备好的 v1 运行环境，载入原始配置文件与旧数据库，确认 v1 机器人恢复正常响应。
3. **保持数据隔离**：**严禁将 v2 测试运行期间产生的任何数据写回 v1 数据库**，以免破坏旧版数据完整性。
4. **保留历史备份**：在整套系统的迁移验证彻底收尾前，切勿删除 v1 的历史备份与旧环境副本。确认旧环境稳定运行后，再继续排查问题。

如果在排查与迁移过程中遇到问题，可以随时查阅 [排错与诊断](/cookbook/troubleshooting) 获取帮助。

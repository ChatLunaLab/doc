# 从 ChatLuna v1 迁移到 v2

ChatLuna v2 是基于 Cordis 4 构建的独立应用，不支持在原 Koishi 实例中对 v1 插件执行原位升级。迁移时必须使用独立的目录、数据库和数据根目录进行部署，逐项迁移配置与资产，完成全链路验证后再切换生产平台的连接。

原版使用说明请参考 [v1.chatluna.chat](https://v1.chatluna.chat)。

---

## 迁移前准备：资产清单与备份

在开始部署 v2 前，应全面梳理并导出 v1 现有的资产清单：

- **平台与账号**：当前接入的聊天平台、Bot 账号与身份标识。
- **模型与 Provider**：已接入的 Provider、模型名称、端点地址与凭据。
- **预设与世界书**：YAML 预设、角色卡、世界书以及相关静态资源。
- **规则与行为**：场景规则、路由、触发与激活条件、会话归属。
- **能力扩展**：正在使用的工具、插件以及必须保留的自定义业务逻辑。

### 备份安全与隔离规范

1. **完全隔离**：不要让 v2 直接打开、读取或写入 v1 的数据库；严禁让两套系统复用同一个正在写入的数据目录。
2. **完整备份**：备份 v1 的完整 Koishi 配置文件、数据库、媒体资源及凭据。对于在线运行的数据库，请使用其原生备份机制生成一致性副本。
3. **保留回退链**：完整保留可用的 v1 运行环境版本、依赖锁定文件以及明确的回退步骤记录。
4. **安全保护**：备份内容通常包含明文 API Key 和用户会话数据，必须严格限制文件访问权限，严禁提交到公开 Git 仓库。

## 资产迁移与重建对照

| 旧资源类型 | v2 处理方式 | 重点检查项 |
| --- | --- | --- |
| **Provider 与模型** | 按照对应 v2 Schema 重新配置 | SDK 依赖、端点 URL、模型标识符（如 `provider:model`）、凭据有效性、真实端到端推理测试。 |
| **聊天平台** | 安装对应的 Satori adapter，重建连接 | 上行消息接收、下行消息发送、平台身份标识（Bot ID/平台账号）、命令前缀识别。 |
| **YAML 预设与内容资产** | 使用 v2 已支持的导入入口，检查转换后的源码 | 变量占位符、`include` 路径、世界书触发器、Few-shot 示例、`system` 与 `context` 区分。 |
| **人格与运行状态** | 按照 v2 character 与记忆契约重新构建 | 记忆归属范围（scope）、首次主人确认机制、自动提取开关、操作权限划分。 |
| **Koishi 插件** | 寻找明确的 v2 移植实现，或按新扩展点重新开发 | 严禁仅因存在 command/session 兼容层就假设任意旧插件完全兼容。 |
| **历史会话数据** | 保留 v1 数据作为只读副本供人工参考 | 不可据此伪造 v2 的请求 mark、工具调用因果链或计费 Token 记录。 |

### 关于历史会话迁移的限制说明

当前没有将任意 v1 历史会话无损转换为可精确重建请求的 v2 Session 的通用流程。

v1 的消息数组通常缺乏记录当时模型请求参数、工具调用链路、中间思考过程和上下文控制标记的元数据，无法据此伪造完整的 v2 日志链路。但这并不意味着历史文本无法利用：普通文本资产依然可以作为人工参考材料或明确标注的导入内容载入，只是不能直接充当引擎底层的运行态 Session。

## 部署独立的 v2 实例

参考 [安装与启动](/manual/quickstart) 文档建立新的运行实例。初次部署时**切勿直接连接生产聊天平台**，应优先使用内置的 Web 聊天和受控测试身份进行功能验证。

### 检查配置与目录结构

运行诊断命令核查目标目录与实际根清单：

```sh
chatluna doctor config --dir .
```

*若处于源码工作区，可执行：*

```sh
yarn chatluna doctor config --dir .
```

> **注意**：
> - 诊断命令通过仅代表配置格式与路径语法符合规范，并不证明上游模型端点或平台网络已经连通。
> - 注意严格区分当前工作目录、受管实例名以及 `--dir` 指定的目录，避免将配置写入错误路径。

### 网络安全与访问控制

- Docker 容器内网络、宿主机映射端口、`allowRemote` 配置项与反向代理 HTTPS 分属不同层级，不可直接套用源码仓库的回环地址默认配置。
- 确保 `/api`、`/console` 及其他管理端点均受实例认证与网络访问限制保护；当前使用实例共享口令，不是每个端点一套独立口令。

## 重新配置模型、平台与场景规则

### 1. 模型与 Provider 配置

- **区分配置格式**：Provider 名称相似不代表配置可以直接复用。按 v2 配置规范保存密钥、端点以及模型地址，并安装对应的 SDK 依赖。
- **格式对应**：
  - 运行时调用与引用常用格式为 `provider:model`。
  - API 交互中通常表示为独立的 `provider` 和 `model` 对象字段。
  - 预设元信息中则以特定的 `provider/model` 字符串格式存在。
- **真实推理验证**：端点能够成功列出模型列表或配置保存成功只是中间状态，必须通过触发一次真实的推理调用，确认模型输出与计费链路正常。

### 2. 聊天平台接入

- 安装目标平台对应的 Satori adapter 并填写 Schema 配置。
- v2 提供了面向 Koishi 风格命令的兼容层，但**并不**提供承载任意 v1 插件运行的完整依赖环境。
- 按链路分别测试：消息上行到达、命令系统识别、Agent 推理生成、平台消息下行投递。

### 3. 场景规则重建

- 场景规则配置已全面切换为当前命名空间，用于管理 engine、模型选择、预设绑定、会话归属、激活方式以及渲染策略。
- **禁止直接复用旧键**：其他历史实现中出现的 `routingRules`、`patch` 等键并非 v1 统一格式，严禁将旧配置整块复制粘贴至 v2。必须对照实际业务逻辑逐项手工重建。
- **规则生效预览**：使用规则预览功能检查各个字段的实际来源与最终锁定值，切勿仅凭“规则更具体”的经验直觉推断优先级结果。

## 迁移预设、角色与记忆

### 预设迁移检查清单

v2 提供了针对旧 YAML 预设等受支持格式的导入入口。导入完成后，必须以最终生成的 Markdown 源码、系统诊断信息和渲染预览为准，重点核查：

1. **Frontmatter 格式**：模型名称与运行时行为字段是否符合 v2 Schema。
2. **静态与动态内容隔离**：
   - 静态人设必须放置在 `system` 字段。
   - 每轮对话的人物运行状态、动态检索数据等易变内容必须放置在 `context` 字段。
   - `mutable` 变量若误填入 `system` 会直接抛出错误，系统不会静默保留或自动容错。
3. **资源有效性**：核验 `include` 引用的相对路径与静态资源链接是否有效，确认外部引入内容的安全性。
4. **世界书与 Few-shot 示例**：检查触发规则、落点上下文位置（context/system）是否符合原始设定。
5. **绑定与版本一致性**：确认目标对话已经绑定到新预设，预设保存后的修订版本号（revision）保持一致。

### 角色（Character）与记忆体系

- v1 的伪装群友插件状态、角色卡数据库和旧版记忆数据不会自动转换为 v2 的 character 运行状态。
- **记忆后端与提取**：v2 的记忆系统默认使用 Markdown 主题后端，自动提取功能默认关闭。
- **作用域（Scope）设计**：重新规划记忆的作用域和共享范围，不要预设用户的个人记忆天然仅私聊可见。
- **主人身份确认**：首次设置向导中的主人绑定必须通过真实聊天平台的私聊绑定码完成，系统不会根据群聊或私聊中“第一个发送消息的用户”推断所有权。
- **权限降级保护**：被显式降低过权限等级的账号，不会因为重新走一遍主人确认流程而自动恢复为最高权限。

## 扩展能力：工具、MCP 与自定义插件

### 启用工具与协议扩展

- 遵循按需启用原则逐个接入工具、MCP 服务与技能（Skills），严禁在未充分测试的情况下将未知工具的执行策略批量设为 `auto`。
- 逐项审查工具的参数 Schema、调用权限要求和人工审批通道。
- **权限边界区分**：
  - 技能描述文本仅作为 Prompt 提示，不会向模型赋予额外的执行权限。
  - 本地运行的 MCP 进程会继承宿主服务的运行用户权限，存在潜在越权风险。

### 自定义插件迁移路径

- 自定义 v1 插件应拆解并迁移至 v2 标准扩展点：**自定义工具（Tool）**、**提示词模板（Prompt）**、**路由策略（Router）**、**推理引擎（Engine）** 或 **消息中间件**。
- 严禁将旧版 LangChain 的适配器接口直接移植到新的模型运行时中。
- 不得为了兼容单一插件的功能而随意修改 Agent 的公共核心接口。详细规范请参阅 [插件开发](/guide/develop/first-plugin)。

### 运行环境隔离与任务清理

- **执行隔离**：代码执行环境与子代理需显式配置。上下文继承不等于文件系统隔离；暴露宿主 Docker socket 将带来宿主机级别的安全漏洞。
- **定时任务清理**：所有定时任务必须在 v2 重新创建，并重新核验对应的执行 Job 与目标，避免切换生效瞬间重复触发由于系统离线期间积压的旧通知消息。

## 验收核对与平台切换

### 切换前最终验收清单

在切断旧环境连接前，逐项确认满足以下条件：

- [ ] 目录、数据库、数据根目录及只读备份完全独立且归属明确。
- [ ] 真实端点模型推理测试通过，默认角色行为与异常回退逻辑符合预期。
- [ ] 测试平台的上行、下行收发正常，规则匹配、激活条件、预设加载及会话归属准确。
- [ ] 会话控制行为（`stop`、`new`、`fork`、`compact`）与当前版本插件表现完全一致，长期记忆作用域清晰可解释。
- [ ] 针对工具调用至少完成一次“允许”、“拒绝”与“询问审批”的全流程触发，未知/未审核工具保持关闭。
- [ ] 服务网络策略、管理口令、代理转发与管理接口（Console/API）的访问防护检查完毕。
- [ ] v1 运行环境、配置文件及只读数据库处于可用状态，切换步骤与回退方案已记录完备。

### 流量切换步骤

1. **停用旧连接**：在 v1 环境中彻底断开生产聊天平台的连接。**严禁让 v1 和 v2 两个实例同时连接同一个机器人账号。**
2. **启用新连接**：在 v2 中启用对应的平台 Satori adapter。
3. **监控链路状态**：观察实时日志、推理轨迹及平台接收端的真实消息下发。**注意：ChatLuna 消息 API 的 HTTP 202 只表示接受分发，不代表模型回复或平台投递完成。**

### 紧急回退流程

若切换后出现严重异常需要回滚：

1. 立即停止 v2 实例的平台 adapter 连接。
2. 重新启动原有的 v1 运行环境、载入原配置与旧数据库。
3. **严禁尝试将 v2 运行期间产生的数据逆向写回 v1 数据库。**
4. 在迁移验证完全收尾前，切勿删除 v1 的历史备份。

若遇到故障，可查阅 [排错与诊断](/cookbook/troubleshooting) 获取定位支持。

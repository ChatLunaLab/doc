# 反向代理与网络接入

::: tip
这一页只谈网络接入这一层：怎么把控制台放到反向代理后面、代理层需要注意哪些关键细节，以及不同接入方式的权衡取舍。

至于访问令牌、允许远程访问、受保护前缀等具体的安全配置，请参考[公网部署](/manual/recipe/server)。
:::

当你完成了机器人的基础部署后，下一步通常就是考虑如何从外部网络稳定且安全地访问控制台。

很多小伙伴在初次配置时，可能会直觉地想把实例的端口直接映射到公网上。但这种做法不仅缺乏灵活的路由控制，还会把内部服务毫无防护地暴露在复杂的公网环境中。更稳妥且优雅的思路，是通过反向代理来统一接管外部流量。

## 代理必须做到的四件事

先说结论：无论你使用的是 Nginx、Caddy 还是 Traefik，只要是把外部请求转发给实例端口，就必须满足下面这四个基本条件。

1. **保留真实来源**：反向代理必须把访问者的真实地址以转发请求头的形式传给实例。
   实例正是靠这些请求头来判断请求到底来自哪里的。如果不传递，在实例看来所有的请求都来自代理所在的本机回路地址。这会导致两方面的问题：一是访问日志里无法记录真实访客 IP，二是后续所有基于来源地址的安全策略和频率限制都会完全失效。
2. **支持协议升级**：控制台依赖长连接来向浏览器实时推送状态与数据。
   这就要求代理服务器在转发 HTTP 请求时，必须能够识别并透传协议升级请求头，把初始的 HTTP 连接顺利升级为 WebSocket 等长连接。如果代理未配置协议升级支持，浏览器与实例之间的握手就会失败，控制台也就无法建立实时双向通信。
3. **关闭响应缓冲**：长连接上传输的数据必须在产生的瞬间立刻下发，绝不能在代理层被排队或缓冲。
   反向代理在默认情况下常常会为了提升网络吞吐而开启响应缓冲，把上游发来的小数据包攒成一批再发送给客户端。但对于聊天流式输出、调用轨迹和运行日志来说，这种缓冲机制会带来灾难性的体验——用户看到的不再是实时打字，而是界面卡死几秒钟后，所有内容一次性「蹦」出来。
4. **保持足够超时**：空闲长连接很容易被代理服务器按默认超时掐断，必须显式调大超时时间。
   普通的网页请求通常在几百毫秒到几秒内就会结束，因此反向代理默认的读写超时往往设置得较短（比如 30 秒或 60 秒）。但控制台的长连接在用户不进行操作时可能会持续处于空闲等待状态。一旦超过了默认超时，代理就会强行掐断连接，导致前端频繁报错并不断发起重连。

::: warning
最常见的配置失败并不是页面打不开，而是「明明能登录、页面也在，但数据就是不刷新」。

出现这种情况时，请优先检查协议升级与响应缓冲设置。因为普通的静态资源与登录请求走的都是标准 HTTP，完全不受影响；只有依赖长连接推送的实时数据，才会在代理配置不当时悄悄「停摆」。
:::

## HTTPS

先说结论：最推荐的做法是将 TLS 证书完全交由反向代理统一管理，而实例自身只在本地回路地址上保持明文 HTTP 监听即可。

为什么推荐这种架构呢？这样做可以将证书自动申请、定期续期、加密套件协商以及 HTTP/2 等现代协议特性全部收敛在代理这一层。实例程序本身只需要专注处理业务逻辑，完全不必关心复杂的 TLS 握手细节。

如果你选择使用支持自动签发证书的现代代理（例如 Caddy 的自动 HTTPS 功能，或是 Traefik 配合 Let's Encrypt 的证书解析器），你甚至完全不需要手动下载和替换证书文件，一切都会自动化运行。

## 子路径部署

如果你打算把控制台部署在某个域名的子路径下（例如将某个特定的前缀路径转发到控制台），需要同时处理好代理与实例两边的路径约定。

为什么子路径往往比独立域名更让人头疼？因为在独立域名下，所有的资源请求都是从网站根目录开始计算的；而一旦挂载到了子路径下，前端页面的资源定位逻辑就会变得相对敏感。

在反向代理这一侧，你需要根据实际需求明确路径转发规则：是将外部访问的子路径前缀剥除后再转发给实例端口，还是原封不动地将完整路径传过去。与此同时，实例侧也必须配置对应的基础路径参数，确保它在返回页面时，内部引用的脚本、样式以及接口请求都能带上正确的子路径前缀。如果两端的路径预期不匹配，请求就会全盘错位。

那么在配置完成后，我们该怎么确认子路径是否正常工作呢？

部署后请立刻打开浏览器的开发者工具，切换到网络面板观察是否有请求返回了 404 状态码。子路径配置的问题几乎都会在这一步暴露出来：如果路径少拼了一层，前端拿不到入口脚本，通常会直接遭遇白屏；而如果路径多拼了一层，页面骨架虽然可能还在，但所有的样式和图标都会因为加载失败而全盘走样。

## 三种接入方式

面对不同的使用环境，我们需要在安全性、便利性与维护成本之间做出权衡。在深入每种方案的具体细节之前，我们先通过下表快速了解它们各自的定位：

| 方式 | 适用场景 | 代价 |
| --- | --- | --- |
| 反向代理 + 域名 | 长期对外提供服务 | 需要证书、需要维护代理配置 |
| SSH 隧道 | 临时远程排错 | 只在那台机器上临时可用，用完即断 |
| 内网 / VPN | 家用 NAS、公司内网 | 外网访问需要先连 VPN |

从表格中可以看出，并没有哪一种方案能够在所有维度上都做到完美，适合当下需求的才是最好的。接下来让我们逐一看看后两者的具体用法。

### SSH 隧道

先说结论：如果你只是临时需要对远程服务器上的机器人进行排错或修改设置，SSH 隧道往往是成本最低且最安全的选择。

它的工作原理非常直观：通过 SSH 在本地电脑与远程服务器之间建立一条加密通道，把远程服务器上实例监听的端口直接映射为你本地的一个端口。

这样一来，你只需要在本地浏览器中直接访问映射后的本地端口，体验就和直接在远程服务器本机打开控制台一模一样。

这种方式最大的好处在于「零额外负担」：你既不需要事先申请域名与 SSL 证书，也不需要改动实例现有的任何监听配置，更不需要在云服务商的安全组或系统防火墙上对外暴露端口。排查工作结束后，只要断开 SSH 会话，外部访问通道便会立刻关闭，不留任何安全隐患。

### 内网直连

先说结论：如果你的服务器与访问设备原本就位于同一个局域网内，直接通过局域网地址访问就是最高效的途径。

这在家用 NAS、家庭软路由或者公司内部办公网络中非常普遍。客户端与服务器之间直接互通，无需经过公网绕行，既快速又私密。

然而，如果你出门在外，需要通过手机或外网笔记本访问家中的控制台，这时候该怎么办呢？

最省事的办法是把端口直接映射到公网，但我们强烈不建议这么做。更稳妥的做法，是在家庭路由器或内网主机上搭建通往内网的安全通道（例如基于 WireGuard 或 Tailscale 的 VPN 接入方式）。在外网时先连入 VPN，再像在家里一样直接访问内网地址，这样就能在兼顾移动访问的同时，避免把控制台暴露给公网扫描工具。

## 代理之后的配置项

配置好反向代理并打通网络，仅仅是完成了一半的工作。很多用户往往容易忽略：反向代理把流量送到了实例面前，但如果实例自身的一系列安全与访问策略没有调整，这些请求依然会被拒绝。

为了让反向代理能够顺利与实例对接，我们需要在实例侧核对以下四个关键配置项：

| 项目 | 位置 | 说明 |
| --- | --- | --- |
| 监听地址与端口 | 服务插件配置 | 默认只监听本机 |
| 允许远程访问 | 服务插件配置或环境变量 | 不开时，即使代理正确请求也会被拒 |
| 访问令牌 | 配置 / 环境变量 / 数据目录 | 公网环境必须用固定强口令 |
| 受保护前缀 | 服务插件配置 | 接口与控制台路径必须在其中 |

在这四个项目中，最容易让人踩坑的是「允许远程访问」选项。许多小伙伴在配置完代理后，满心欢喜地打开网页，却发现浏览器提示连接被拒绝，原因通常就在于实例还处在严格的本地限制之中。

关于上述配置项的具体含义、环境变量优先级以及检查方法，请参考[公网部署](/manual/recipe/server)一节。

## 上线前自检

在把控制台正式投入日常使用之前，建议大家按照下面的自检清单逐条测试，确保整条数据链路不仅「能通」，而且「通得稳定」：

1. **公网连通性**：从另一台完全脱离当前内网的设备（例如断开 Wi-Fi、直接使用手机蜂窝网络）尝试打开控制台，确认能够顺利加载并展示登录页面。
2. **实时消息推送**：登录控制台并发起一轮对话，仔细观察机器人回复的流式输出是否即时出现，确认消息没有在代理层被成批积攒后才一次性显示。
3. **轨迹实时刷新**：在对话进行的同时切到轨迹页面，观察内部各个执行步骤是否在实时滚动刷新，而不是等整轮对话彻底结束才刷出结果。
4. **断网重连韧性**：尝试在服务器上临时停止反向代理服务，此时前端控制台的长连接应当及时断开；待代理恢复后，页面应当能够自动重连并恢复正常状态。
5. **健康诊断确认**：在实例中运行配套的诊断指令，确认系统配置没有任何报错或潜在的监听警告。

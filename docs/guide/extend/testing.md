# 测试插件

::: tip
测试要验证行为，而不是复述实现。能用一个真实的服务组合跑通，就不要用一堆 mock 把它包起来。
:::

ChatLuna 的测试风格是「组装真实的部件，替换最外层的边界」。

数据库用内存实现，模型用假提供商，会话用内存存储——其余都是真实代码。

<!-- 开发指南，可以使用代码 -->

## 先跑起来

```bash
yarn build
yarn test
```

新包在构建前跑测试会报模块找不到：输出是按包生成的，构建之前不存在。

## 最小测试

```ts
const ctx = new Context()
ctx.plugin(SessionService, { store: new MemorySessionStore() })
ctx.plugin(AIService)
ctx.plugin(MyPlugin)

const result = await ctx.chatluna.ask({ prompt: 'hi' })
```

要点：

- 每个测试建一个新的上下文。
- 只加载被测插件与它真正依赖的服务。
- 测试结束释放上下文，避免定时器与监听泄漏。

## 假模型

用 mock 提供商代替真实模型：

- 固定回复，便于断言。
- 可以注入错误，测试失败路径。
- 不产生网络请求与费用。

需要测试流式输出时，让假提供商按分片返回。

## 假时间

定时、超时、退避这类逻辑，用可控时钟。

不要用真实等待——既慢又不稳定。

## 断言什么

- **行为**：输入之后，输出、事件、日志条目是什么。
- **边界**：失败时返回什么错误，是否留下半截状态。
- **生命周期**：卸载后是否释放监听、是否清理定时器。

不要断言内部实现细节，那会让重构变成改测试。

## 集成测试

需要多个服务协作时，写集成测试：

- 一条消息从进入到投递的完整链路。
- 工具调用被权限拦截。
- 定时任务触发一次唤醒。

集成测试更能发现真实问题，但也要控制规模：一个测试只验证一条主线。

## 常见陷阱

**共享上下文。** 测试之间状态串了。每个测试新建上下文。

**没等异步收尾。** 事件是并行广播，断言前要等待空闲。

**依赖顺序。** 测试顺序变化后失败。让每个测试自包含。

**真实的网络。** 单测里不要连外网，用假提供商。

## 调试

- 打开 trace，按 span 看每一步。
- 用 `ctx.logger` 输出关键状态，而不是到处 `console.log`。
- 失败时先看断言前的最后一条事件，而不是整个日志。

## 提交前

- 相关测试全部通过。
- 新增行为有对应测试。
- 没有引入无关的依赖或生成文件。

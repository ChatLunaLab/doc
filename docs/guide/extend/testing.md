# 测试插件

::: tip
测试的核心是验证行为，而不是复述实现。能用真实服务跑通的场景，尽量不要用大量的 mock 去包裹。
:::

ChatLuna 推荐的测试风格是「组装真实的部件，替换最外层的边界」。

在测试环境中，数据库与会话存储均可使用内存实现，模型由假提供商接管，而其余链路全部运行真实代码。

## 先跑起来

在运行测试前，请先确保项目已完成构建：

```bash
yarn build
yarn test
```

如果未构建就直接运行测试，新包会提示找不到模块。这是因为产物文件是按包生成的，在构建之前并不存在。

## 最小测试

编写插件的最小测试很简单，只需在独立的上下文中加载必要服务即可：

```ts
const ctx = new Context()
ctx.plugin(SessionService, { store: new MemorySessionStore() })
ctx.plugin(AIService)
ctx.plugin(MyPlugin)

const result = await ctx.chatluna.ask({ prompt: 'hi' })
```

编写此类测试时需要注意：

- **隔离上下文**：每个测试都应该创建全新的上下文实例。
- **按需加载**：只加载待测插件与真正依赖的服务，避免无关插件干扰。
- **及时清理**：测试结束后释放上下文，避免定时器与监听器发生泄漏。

## 假模型

在单元测试中，我们推荐使用 mock 提供商替代真实模型：

- **确定性输出**：回复内容完全固定，便于编写精确断言。
- **模拟错误**：可以主动注入异常，测试错误处理逻辑。
- **零网络开销**：不产生任何网络请求与 API 调用费用。

需要测试流式输出时，也可以让假提供商按分片逐步返回数据。

## 假时间

针对定时任务、超时判定或退避重试等时间敏感的逻辑，应当统一使用测试框架的可控时钟。

尽量避免在测试中使用真实的延时等待。这既会拖慢整体执行速度，也容易产生不稳定的测试结果。

## 断言什么

编写断言时，请把重点放在可观测的外部行为上：

- **行为**：传入特定输入后，插件的输出、派发的事件或记录的日志是否符合预期。
- **边界**：遇到失败或异常时会返回什么错误，是否会残留不一致的中间状态。
- **生命周期**：插件卸载后，事件监听是否已注销，定时器是否已被清理。

切忌断言内部的私有实现细节，否则后续重构代码时将不得不频繁修改测试。

## 集成测试

当需要验证多个服务之间的协作效果时，可以编写集成测试：

- 消息从接收、处理到最终投递的完整链路。
- 带有权限校验的工具调用是否被正确拦截。
- 定时任务触发后执行的一次会话唤醒。

集成测试更容易发现真实的模块装配问题，但也需要合理控制规模：确保每个测试只验证一条核心链路。

## 常见陷阱

编写测试时，有几个常见陷阱需要留意：

- **共享上下文**：在不同测试之间复用上下文会导致状态相互干扰。请务必为每个测试新建独立的上下文。
- **未等待异步收尾**：事件通常是并行广播的，在执行断言前必须等待异步队列清空。
- **依赖执行顺序**：测试因执行顺序改变而失败，说明用例之间存在隐式依赖。务必保证每个测试独立且自包含。
- **请求真实网络**：单测中切勿直连外网，请始终使用假提供商在本地模拟。

## 调试

测试未通过时，可以借助以下方式排查问题：

- 开启 trace，按调用 span 逐层检查每一步的执行状态。
- 使用 `ctx.logger` 打印关键状态，避免在代码各处散落临时的 `console.log`。
- 遇到失败时，优先查看断言触发前的最后一条事件，而不是通读全部日志。

## 提交前

向仓库提交代码前，请确认已完成以下检查：

- 相关测试用例已全部通过。
- 所有新增或变更的行为均有对应的测试覆盖。
- 未引入无关的临时依赖或构建产物文件。

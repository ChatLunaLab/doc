# 测试插件

::: tip
测试的核心是验证行为，而不是复述实现。能用真实服务组合跑通的场景，尽量不要用大量的 mock 去包裹它。
:::

ChatLuna 推荐的测试风格是「组装真实的部件，替换最外层的边界」。

在测试环境中，数据库与会话存储均可使用内存实现，模型由假提供商接管，而其余链路全部运行真实代码。

## 先跑起来

在运行测试前，请先确保项目已完成构建：

```bash
yarn build
yarn test
```

如果新包在构建前直接跑测试会报错找不到模块。这是因为产物文件是按包生成的，在构建之前并不存在。

## 最小测试

编写一个插件的最小测试非常简单，只需在一个独立的上下文里加载必要服务即可：

```ts
const ctx = new Context()
ctx.plugin(SessionService, { store: new MemorySessionStore() })
ctx.plugin(AIService)
ctx.plugin(MyPlugin)

const result = await ctx.chatluna.ask({ prompt: 'hi' })
```

编写此类测试时需牢记以下要点：

- **隔离上下文**：每个测试都应当创建全新的上下文实例。
- **按需加载**：只加载待测插件与它真正依赖的服务，避免无关插件干扰。
- **及时清理**：测试结束后释放上下文，避免定时器与监听器发生泄漏。

## 假模型

在单测中，我们推荐使用 mock 提供商替代真实模型：

- **确定性输出**：回复内容完全固定，便于编写精确断言。
- **模拟错误**：可以主动注入异常，充分测试失败容错路径。
- **零网络开销**：不产生任何网络请求与 API 调用费用。

当需要测试流式输出特性时，也可以让假提供商按分片逐步返回数据。

## 假时间

针对定时任务、超时判定或退避重试等时间敏感的逻辑，应当统一使用测试框架的可控时钟。

尽量避免在测试中使用真实的等待延时——既拖慢整体执行效率，又容易引发不稳定的测试结果。

## 断言什么

编写断言时，请把重点放在可观测的外部行为上：

- **行为**：给予特定输入后，插件产出的输出、派发的事件或记录的日志是否符合预期。
- **边界**：遇到失败或异常时返回什么错误，是否会残留不一致的半截状态。
- **生命周期**：插件在卸载之后，事件监听是否已释放，定时器是否已被清理。

切忌去断言内部的私有实现细节，那会让未来的重构变成痛苦地修改测试。

## 集成测试

当需要验证多个服务之间的协作效果时，就应当编写集成测试：

- 一条消息从接收、处理到最终投递的完整链路。
- 带有权限校验的工具调用被正确拦截。
- 定时任务触发后执行的一次会话唤醒。

集成测试更能发现真实的模块装配问题，但也需要合理控制规模：确保每个测试只验证一条核心主线。

## 常见陷阱

在编写测试时，有几个常见的陷阱需要留意：

- **共享上下文**：在不同测试之间复用上下文会导致状态相互串扰。请务必为每个测试新建上下文。
- **未等待异步收尾**：事件通常是并行广播的，在执行断言之前必须等待异步队列进入空闲。
- **依赖执行顺序**：测试因顺序变化而失败，说明用例之间存在隐式依赖。务必让每个测试自包含。
- **请求真实网络**：单测中绝不要直连外网，请始终使用假提供商进行本地替代。

## 调试

当测试未按预期通过时，可以借助以下方式进行排查：

- 打开 trace，按调用 span 逐层检查每一步执行状态。
- 使用 `ctx.logger` 输出关键状态，避免在代码各处散落临时的 `console.log`。
- 遇到失败时，优先查看断言触发前的最后一条事件，而不是通读整个日志。

## 提交前

在向仓库提交代码之前，请确认已完成以下检查：

- 相关的测试用例已全部通过。
- 所有新增或变更的行为均有对应的测试覆盖。
- 未引入无关的临时依赖或构建产物文件。

# 扩展路由命名空间

::: tip
如果你的插件需要支持「按群」「按用户」或「按特定条件」差异化配置，无需自行实现一套配置存储系统。只需注册一个路由命名空间，后续的继承、覆盖、优先级匹配与界面渲染都会由路由系统统一处理。
:::

场景规则页面中的每个配置标签，背后都对应一个独立的路由命名空间。

无论是工具策略、记忆、渲染，还是权限与子代理，在核心实现中都是通过这种方式接入的。你的插件也可以使用完全相同的方式扩展场景规则。

## 一个命名空间包含什么

在深入代码前，我们先来看看一个命名空间由哪些核心要素构成：

- **名字**：读取配置时使用的唯一键名。
- **结构**：定义该命名空间下包含的一组字段类型及其默认值。
- **界面位置**：决定该配置块展示在场景规则页面的哪一个大标签下。
- **生效方式**：提示前端界面「这些配置修改后大概何时生效」。

## 注册

注册命名空间非常简单。在插件中声明依赖 `schemas` 服务后，调用 `ctx.schemas.section()` 即可完成注册：

```ts
import { Schema } from '@chatluna/schema'
import type {} from '@chatluna/ui-schema-registry'

export const name = 'my-plugin-routing'
export const inject = ['schemas']

export function apply(ctx: Context) {
  ctx.schemas.section({
    surface: 'routing',
    key: 'myFeature',
    id: 'my-feature',
    title: '我的功能',
    tab: 'rules.capabilities',
    order: 60,
    schema: Schema.object({
      enabled: Schema.boolean().default(true).label('启用'),
      level: Schema.union(['low', 'high'] as const).default('low').label('强度'),
    }),
    applies: 'live',
    plugin: 'my-plugin',
  })
}
```

得益于上下文生命周期管理，注册的行为会被自动清理：当插件卸载时，对应的标签也会随之移除，无需手动注销。

### 字段说明

| 字段 | 含义 |
| --- | --- |
| `surface` | 固定为 `routing`（路由规则页）或 `settings`（快捷设置页） |
| `key` | 命名空间名称，读取配置时使用 |
| `id` | 唯一 ID，用于记录界面折叠状态 |
| `title` | 标签标题 |
| `tab` | 挂载的大标签 |
| `order` | 排序顺序 |
| `schema` | 字段结构 |
| `applies` | `live` 或 `session`，用于界面提示 |
| `plugin` | 来源插件标识 |

## 读取值

在执行业务逻辑时，可以通过 `valuesAt` 获取合并计算后的最终配置：

```ts
const routing = ctx.get('routing')
const values = routing?.valuesAt(subjectOf(agent), 'myFeature')

const enabled = values?.['enabled'] ?? true
const level = values?.['level'] ?? 'low'
```

`valuesAt` 会自动处理继承与覆盖：它会先读取全局默认值，再按当前上下文中更具体的目标逐层合并。

::: warning
请不要尝试自行读取底层配置文件或数据库来解析规则。

直接解析规则会绕过路由系统内置的优先级裁决、配置锁、多级缓存与诊断机制，导致运行时行为与控制台界面的展示效果不一致。
:::

## subject 从哪来

调用 `valuesAt` 时，第一个参数需要传入 `subject`。在绝大多数情况下，你都可以直接通过现成的转换函数推导出来：

- 从当前会话或 Agent 对象直接推导出对应的 `subject`。
- 如果需要指定特定的路由上下文，将 `route` 一并传入即可。

如果你有自定义的身份或过滤维度，也可以在 `subject` 上扩展自定义字段，前提是对应的规则匹配逻辑能够识别并处理该字段。

## 默认值写在两处

默认值通常会出现在两个地方：

- **Schema 定义中的 `.default()`**：用于控制台界面的默认展示与表单提交校验。
- **业务代码读取时的 `?? fallback`**：用于运行时的空值兜底。

务必保证这两处的默认值保持一致。如果只在一处指定了默认值，容易导致「界面显示为已开启，但运行时实际却按关闭处理」等隐蔽问题。

## 处理器与子字段

如果你的命名空间规则需要根据目标动态判断是否生效，可以向系统注册自定义谓词处理器：

```ts
ctx.routing.predicate('my-plugin:enabled', {
  evaluate: (_args, input) => input.subject?.guild === '...',
})
```

当谓词函数返回 `true` 时，包含该条件的规则才会匹配当前会话。

需要注意的是，谓词逻辑应当尽量保持轻量与纯粹：在单次路由解析与多规则匹配过程中，谓词可能会被频繁调用。

## 缓存

为了保证性能，路由计算的结果默认会按 `subject` 进行缓存。

只有当系统检测到规则中包含「内容相关」的谓词（例如需要读取具体的实时消息文本）时，才会跳过缓存重新求值。

因此，如果你的配置取值或过滤逻辑依赖于消息内容，在注册谓词时务必显式标记为内容相关，否则系统将直接复用缓存，导致读取到旧的评估结果。

## 优化界面

想要让插件的配置项在控制台中更清晰易用，可以参考以下几点建议：

- 字段的 `description` 会显示为帮助文本，建议写清楚「什么时候该改」。
- 善用 `role('ms')`、`role('slider')`、`role('element')` 这类角色修饰符，让界面使用更合适的表单控件。
- 将逻辑相关的字段放在同一个子对象中，界面会自动分组显示。

## 测试

在完成插件路由配置的开发后，建议按以下步骤验证功能的完整性：

1. 注册两个命名空间，确认数据读写互不干扰。
2. 创建一条全局规则和一条群规则，确认群规则能够覆盖全局规则。
3. 在群规则中只覆盖一个字段，确认其他字段仍沿用全局配置。
4. 卸载插件，确认标签消失，且读取时返回 `undefined`。

## 常见问题

**标签不出现**
检查 `inject` 是否包含 `schemas`，`surface` 是否为 `routing`，`tab` 是否是已存在的标签 ID。

**读不到值**
检查 `key` 与注册时是否一致；检查 `subject` 是否为空——空的 `subject` 只能匹配全局规则。

**值没有按预期覆盖**
检查规则目标是否更具体；检查是否有配置锁阻止了覆盖；可以使用诊断接口查看最终来源。

**改了规则没生效**
配置在何时被读取，决定了何时生效。缓存型字段需要等待下一次读取，引擎型字段则需要开启新会话。

# 定时与后台任务

定时任务用于描述「条件满足时做什么」，后台任务用于管理「已经开始但不必占住当前回合的工作」。两者可以协作，但具有完全不同的持久化机制与取消语义：创建日程不代表下游消息已经成功发出，后台任务返回占位结果也不代表该任务最终已成功执行。

## 任务类型选型

| 需求场景 | 对应机制 | 完成凭证 | 持久化与运行时载体 |
| --- | --- | --- | --- |
| 延迟提醒、周期执行 | Schedule（`at` / `every` / `cron`） | Job 定义与触发记录 | Job 保存在数据库表 `chatluna_schedule`，执行历史保存在 `chatluna_schedule_run` |
| 观察特定消息或状态条件后再介入 | 条件唤醒（`watch` / `wakeup`） | 条件命中记录与实际投递状态 | 依赖事件流评估与调度表记录 |
| 耗时较长的命令、子代理或重型工具调用 | Background 工作池 | 任务终态状态码与最终结果输出 | 进程内执行句柄与内存环形缓冲；不承诺服务重启后恢复或接管先前的进程 |

## 在管理面板配置日程

在控制台创建日程时，必须先指定目标聊天会话，再配置触发器与关联动作。目标聊天必须绑定至已实际接入的机器人身份与会话上下文。创建完成后，需核对平台类型、机器人实例、群组/频道 ID 以及解析出的下一次执行时间（next run）。

### 1. 触发器类型

每次创建日程仅能指定一种触发器类型：

| 触发器类型 | 格式与示例 | 规则与注意事项 |
| --- | --- | --- |
| `at` | 相对时间（如 `+30m`）、当地时间（如 `18:30`）或带时区的完整 ISO 时间 | 若仅指定 `HH:mm`，表示匹配下一次出现的该时刻；若该时刻已过则顺延至次日，跨日执行需核查基准日期。 |
| `every` | 持续时间单位（如 `30m`、`2h`） | 按固定的相对时间间隔触发，不等于每天固定的当地自然时刻。 |
| `cron` | 标准五段式表达式（如 `0 9 * * 1-5`） | 依次为：分、时、日、月、周。支持指定 IANA 时区（如 `Asia/Shanghai`）。Cron 指定的时区与宿主容器系统时区相互独立，涉及夏令时或跨时区场景时，必须核对下一次触发时间列表。 |
| `watch` | 条件表达式（如 `silence > 30 * 60 && !selfSaid`） | 基于 JavaScript 表达式（js-expr）评估，变量类型与时间单位严格受限于关注域作用域。 |

### 2. 执行动作

- `wake`（会话唤醒）：向目标会话注入一条唤醒原因（reason），交由当前会话绑定的聊天引擎接管处理。系统不会将 `reason` 字段直接作为最终消息发送给用户。
- `run`（主动执行）：使用指定的 Prompt 运行任务。可指定特定的模型引擎或子代理 Profile，并配置结果投递策略：
  - `send`：将执行结果直接投递至聊天。
  - `notice`：作为系统通知呈现。
  - `none`：仅静默运行，不向会话推送文本。
  *注意：`run` 动作会实际调用模型、运行工具并可能触发外部系统，产生相应的 API 配额和运行开销。*

### 3. 控制台管理操作

管理页面支持对日程执行**暂停**、**恢复**、**取消**和**手动触发**：
- 手动触发为实际执行操作，并非只读预览。是否调用模型、执行工具或发送消息，取决于任务动作、执行结果与投递策略。
- 测试任务时，建议配置专用测试会话及无外部副作用的动作载荷。

## 模型工具驱动的日程管理

当允许模型自主管理日程时，系统向模型暴露四个核心工具：`schedule_create`、`schedule_list`、`schedule_cancel` 与 `wakeup`。

这些工具的执行依赖真实的会话绑定上下文，并需要 Observer 机制解析调用目标；无上下文的纯模型调用无法执行这些工具。

### `schedule_create` 参数示例

以下为 `schedule_create` 的内部参数结构示意（非直接发往后端的原始 HTTP 载荷）：

```json
{
  "when": { "cron": "0 9 * * 1-5" },
  "tz": "Asia/Shanghai",
  "reason": "工作日上午检查今天的计划",
  "times": 5
}
```

- **动作转换**：若在参数中传入 `prompt` 字段，任务动作将从默认的 `wake` 转换为 `run`。
- **权限边界**：跨会话投递、极短间隔执行以及执行高危命令具有不同的权限鉴权机制。当前会话内获得的一般性提醒授权，不能作为向任意外部群组发送内容或调用特权工具的凭据。
- **完成凭据**：工具返回的内容必须包含底层持久化生成的实际 Job 实体数据，模型仅回复「已安排好」不可作为创建成功的凭据。
- **幂等与覆盖**：服务层同一会话使用相同 `key` 可覆盖旧 Job；`set` 按 key 更新，相同定义保留。`schedule_create` 模型工具没有 key 参数，`wakeup` 工具可设置 key。业务 key 不能撤销已发生的外部副作用。

## 条件唤醒机制（`wakeup`）

`wakeup` 允许针对特定会话事件或环境状态注册监听规则，满足条件后再触发处理流程。

### 参数定义

| 参数名 | 语义说明 |
| --- | --- |
| `after` / `at` | 最早允许触发的时间阈值，支持相对时间或绝对时间。 |
| `when` | 状态判断表达式；若省略，则到达最早允许时间时立即触发。 |
| `expires` | 规则有效期，从注册时起算。默认值为 24 小时。 |
| `fallback` | 规则到期仍未命中条件时的降级动作：`drop`（丢弃，默认）或额外执行一次 `wake`。 |
| `times` | 允许触发的最大次数。默认值为 1 次。 |
| `gap` | 连续两次触发之间的最小冷却时间（退避间隔）。默认值为 `10m`。 |
| `cancelOn` | 自动取消策略。例如设为 `reply` 时，若机器人在该会话内主动发言，该监听规则自动作废。 |

### 消息条件可用变量

在编写 `when` 表达式时，js-expr 求值器提供以下上下文变量；这不是任意 JavaScript 程序的执行环境，也不是操作系统沙箱：

- **统计与环境量**：`messages`（上次触发以来的消息数组，并非完整历史）、`message`（当前消息）、`count`（匹配计数）、`speakers`（发言者集合）、`selfSaid`（机器人本轮是否已发言）、`mentioned`（是否提及机器人）、`silence`（会话静默持续秒数）、`selfSilence`（机器人自身静默持续秒数）、`hour`（当前本地小时数）。
- **消息对象属性**：`messages` 与 `message` 内的单条消息包含以下只读字段：`text`、`user`、`name`、`self`、`images`、`at`、`mentionsMe`、`quotesMe`、`time`。
- **语法限制**：表达式由内置 js-expr 引擎解析，不支持任意外部 JavaScript 语法或沙箱外调用。管理界面提供表达式语法校验工具，可用于定位具体的语法错误与符号位置。

## 调度限制、运行配额与故障恢复

### 默认资源配额

针对模型侧工具调用，系统实施以下限额保护：

- **会话配额**：每个会话最多同时保持 20 个处于活动状态的 Job，最多挂载 5 个活动的 `wakeup` 监听器。
- **触发频率**：单个会话每日最大允许触发 100 次。
- **间隔限制**：`every` 触发器的常规最小时间间隔为 `300000 ms`（5 分钟）。
- **轮询开销**：包含时间动态变量的 `watch` 条件表达式，系统默认按 `10000 ms`（10 秒）的周期执行轮询求值。
- **语义求值预算**：当表达式内调用 `judge(...)` 进行模型语义判定时，默认调用 `@decide` 模型；单个频道内判定最小调用间隔为 `30000 ms`（30 秒），全局每日判断预算上限为 200 次。

### 延迟跳过与状态合并（Grace Period）

- **宽限期**：系统为定时触发配置了宽限期机制，默认 Grace 阈值为 1 小时。若节点离线导致任务触发时间落后于当前时间超过该阈值，调度器将直接跳过本次执行。系统重启后不会无限制补发所有离线期间错过的任务。
- **唤醒合并**：同一路由终点在同一执行周期内到期的多个唤醒任务会自动合并为一个事件处理。单次触发也可以被会话内的事件监听器拦截或取消。
- **历史归档**：每个 Job 仅在 `chatluna_schedule_run` 中保留最近 50 条运行记录，不提供永久审计历史存储保证。

## 后台工作机制（Background Tasks）

后台服务用于隔离高耗时工作流，避免长耗时阻塞模型主对话交互。

### 任务启动与输出捕获

- **创建模式**：通过 `start` 接口派生新任务，或通过 `adopt` 接口接管当前已在执行的工作，接管过程不重置任务执行上下文。
- **输出机制**：
  - `out`：结构化输出内容，专门提供给模型上下文读取。
  - `log`：运行日志，供运维人员核查。
  - **内存环形缓冲区**：捕获的标准输出与日志保存在定长环形内存缓冲区内，旧输出会被自动覆盖淘汰。重要任务数据必须明确转存至外部存储或物理文件。
  - **进度显示**：提供单行简略状态进度字段用于即时轮询。

### 超时拦截与后台转换

- 工具的同步等待上限默认配置为 `180000 ms`（3 分钟）。
- 支持在工具元数据中使用 `traits.timeout` 单独覆盖默认超时配置。
- 当系统启用了后台服务时：
  - 支持后台化的工具达到超时上限后，执行引擎将中断当前的等待状态，向会话返回占位结果（Placeholder），底层工作单元自动脱离并转入后台静默运行。
  - 若工具明确声明 `traits.background: false`，则超时后直接宣告失败并中止执行，绝不转入后台运行。

### 模型控制与通知模式

模型通过系统工具查看与干预自身归属的后台任务：
- `background_list`：列出当前归属的活动后台任务及运行状态。
- `background_read`：读取特定任务的最新输出缓冲区与日志。
- `background_stop`：向指定任务句柄发送终止信号。

任务终态通知策略支持以下三类：
- `wake`：任务完成后，自动触发一次会话唤醒，通知模型整合产出。
- `next`：不主动唤醒，将结果挂起在会话上下文中，合并至用户的下一次交互回合。
- `silent`：静默完成，不向对话流注入通知。

*去重保障：若在当前交互回合内，模型已经通过显式执行 `wait` 或 `background_read` 消费了该任务结果，后续不会重复投递完成通知。*

### 生命周期与销毁

- **属主生命周期**：当前任务的拥有者（Owner）关闭或会话销毁时，其名下关联的所有后台任务将被级联发送取消信号。
- **服务卸载**：当底层插件或服务卸载时，服务管理器会触发取消逻辑并等待进程退出。
- **副作用边界**：取消操作仅负责终止进程执行句柄，无法自动回滚任务已经写入的本地文件系统修改或已向外部 API 产生的远程调用副作用。

## 故障排查流程

1. **确定失效阶段**：
   - 区分是调度层未产生触发事件（Job 未触发）、执行逻辑异常报错（任务失败），还是下游通道推送受阻（投递失败）。
2. **核对调度元数据**：
   - 检查任务目标身份（Target Identity）、时区偏移、解析出的下一次触发时间（`next`）、Job 活动状态以及触发时间是否已超出 Grace 宽限期。切忌盲目重复创建副本任务。
3. **检查执行记录与关联态**：
   - 检查 `chatluna_schedule_run` 历史日志及对应的会话实例。
   - 排查模型推理额度、工具调用错误以及外部鉴权拦截记录。
4. **验证配额与判定条件**：
   - 确认当前会话活动 Job 数、Wakeup 监听器数及每日调用次数是否触碰硬性上限。
   - 检查 `watch` 条件表达式求值结果，核实 `judge(...)` 是否耗尽每日判定预算。
5. **核查服务重启影响**：
   - 明确持久化 Job（数据库驱动）与纯内存执行项（后台任务缓冲区）的恢复差异。服务重启后，不能假设进行中的后台任务或已退避的瞬态状态能够自动恢复运行。

# 轨迹与用量

排查一次交互问题，需要区分不同环节的状态：平台是否收到输入、引擎是否启动、模型实际接收了什么上下文、工具是否执行，以及最终回复是否成功送达平台。仅检查最后一条输出文本，无法定位完整的调用链路。

---

## 定位单次运行记录

排查时，应先从目标聊天记录进入轨迹页，核验以下基础字段：

- `sessionId` 与时间戳
- 使用的 provider 与 model
- 消息归属与当前回合（Turn）

在核对调用链路时，需注意以下行为特征：

- **群聊消息聚合**：群聊中的连续输入可能被合并归入同一回合。
- **后台与衍生调用**：后台通知、记忆提取/判断、子代理调用等均可能触发独立的模型请求，这些调用与用户发送的消息并非严格的一对一关系。
- **存储与展示状态的差异**：轨迹页展示的数据基于 `Session entries` 推导生成，并非独立且可任意篡改的历史记录。会话内部的 `message`、`mark`、`cut` 与前端实时的流式增量不同；客户端界面出现增量渲染，并不保证该内容已成功写入持久化条目。

---

## 检查链路与排查顺序

排查调用时，建议遵循「先看执行结果，再反推请求上下文」的顺序：

1. **核对完成状态**：判断请求属于正常成功、主动取消、模型报错还是工具执行失败。
2. **核对运行时标识与结束标志**：检查实际生效的 `provider`/`model`、产生的 `warning` 以及 `finish` 状态（流式连接关闭不代表请求成功）。
3. **核查模型请求上下文**：检查实际发出的 `system` 提示词、挂载的工具 schema、生效的模型调用参数以及最终组装的消息序列。
4. **定位规则命中与覆盖**：核对命中的路由或处理规则，检查逐字段来源，判断配置是否被更具体的上下文规则覆盖或锁定。
5. **排查工具执行细节**：检查工具调用的输入参数、执行权限、执行结果、运行机器环境以及执行耗时。
6. **核查渲染与平台投递**：验证前端渲染与目标平台的实际投递状态（模型生成完毕不代表平台已完成推送）。

### 错误类型辨析

遇到异常时，应区分处理：

- **错误根因定位**：Token 超限、认证失败、额度耗尽与协议不兼容属于不同层面的问题，需分别处置，不应依赖无限制的重试逻辑掩盖异常。
- **工具调用真实性**：严格以工具实际返回的数据为准，不能以模型在生成文本中声称的「我已经完成」替代真实的工具执行结果。

## 请求重建与重放实验

Session 的 `prompt mark` 中保存了发起调用时的请求 header。结合对应的历史消息与切点（`cut`），系统可以重建该次调用的完整模型输入。

> **注意**：请求重建的目标是还原**发起请求当时**的模型输入，并不保证在当前外部环境或外部依赖变更后重新执行仍能得到完全一致的输出。

轨迹页支持基于历史上下文创建请求草稿。用户可手动修改 `system` 提示词、挂载工具、模型参数或上下文消息，并执行重放实验。

### 重放操作边界

| 操作 | 是否调用远端模型 | 是否自动执行工具 | 是否追加原会话日志 |
| :--- | :--- | :--- | :--- |
| **查看重建请求** | 否 | 否 | 否 |
| **编辑请求草稿** | 否 | 否 | 否 |
| **执行重放实验** | 是（可能产生计费） | 否 | 否 |

### 重放执行说明

- **执行路径**：重放操作直接调用远端模型接口，不进入完整的 Agent 决策与事件循环。如果模型在重放中返回了 `tool call`，系统**不会**自动执行对应工具。
- **观测记录**：重放实验会以 `purpose=replay` 记录观测数据。在配置了数据库的环境中，数据将保存至 `chatluna_replay_experiments` 表。
- **安全检查**：在向模型服务商提交重放请求前，必须人工审查草稿内的消息内容、工具定义及包含的敏感字段。

## 用量统计与监控指标

用量统计依赖独立的 billing 插件进行采集与持久化：

- `chatluna_usage`：记录单次模型调用明细，单次调用占用一行，调用失败亦会记录。明细数据默认保留 90 天。
- `chatluna_usage_daily`：保存每日汇总统计，长期保留。超出 90 天的数据仅保留汇总指标，因此历史长期数据不再支持明细级 P95 统计。

### 监控指标与筛选维度

用量页面提供以下指标与分析视图：

- **统计指标**：请求数、RPM、Token 计数、TPM、成本估计、首 Token 延迟（TTFT）、P95 耗时、成功率、模型性能表现以及历史趋势。
- **筛选维度**：支持按 `provider`、`model`、`plugin`、`purpose`、`platform`、`guildId`、`userId`、`sessionId`、`status`、`rule`、`tag` 进行联合检索。

### 成本分析与实时状态

- **多阶段成本归因**：排查异常费用时，应优先按 `purpose` 或 `plugin` 进行拆解。主会话聊天、记忆提取、记忆召回、逻辑判断、子代理（Sub-agent）以及重放实验均会独立发起模型调用，总成本并非仅由主聊天的回复长度决定。
- **内存中的活跃任务**：用量页展示的「正在运行的调用列表」基于内存追踪维护。调用在触发 `ai/model-bound` 时加入，在 span 结束时移除。该列表反映当前实时状态，并非具备进程崩溃恢复能力的任务持久化队列。

## Token 统计与性能指标口径

在分析用量与吞吐量时，需遵循以下计算口径：

- **输入 Token 构成**：严格区分未缓存输入、缓存读取（Cache Read）与缓存写入（Cache Write）。ChatLuna 归一化后的 `input` 字段并不等同于各供应商 SDK 原始返回的 `total` 字段。
- **输出 Token 构成**：供应商报告的输出总数可能已包含思维链数据（reasoning tokens），统计时不能将两者二次相加。
- **缺失值含义**：指标字段为空或缺失，表示服务商或协议层未上报该数据，不应视为测量值为 0。
- **价格基准**：页面显示的计费金额基于预设模型目录与定价算法进行估算，最终财务成本请以对应服务商的实际出账账单为准。
- **吞吐量计算**：页面展示的吞吐速率基于思考耗时结束后的纯生成耗时（`generationMs`）以及扣除 reasoning 后的最终答案输出 Token 计算。只有在流式传输产生至少两个答案/工具增量，且统计窗口达到 100ms 时才会启动计量；过短的突发传输（burst）吞吐将显示为 `—`。
- **实际返回模型**：`responseModel` 记录远端接口实际生效并返回的模型名称。当其与请求模型名称不一致时，界面会单独标注展示，这并不意味着本地的默认模型配置被修改。

首 Token 延迟、思考时间、生成吞吐量与总耗时分别描述调用链路的不同阶段。当存在较长的工具等待或大体量深度推理时，不能仅凭单一的整体 `tokens/s` 评估性能。

## 数据导出与统计重建

### 明细导出

- **API 接口**：`GET /api/usage/export.csv`
- **说明**：接口使用与用量页面一致的时间跨度与筛选条件导出调用明细，请求需要认证登录。
- **安全注意**：导出的 CSV 文件包含用户身份标识、会话 ID 及自定义标签等潜在敏感信息，对外共享前需完成数据脱敏。

### 统计数据重建

当明细数据与每日汇总（`chatluna_usage_daily`）出现不一致时，可触发重建操作，系统将依据当前数据库中保留的明细记录重新计算汇总。已经由于超过保留期而被清理的旧明细记录无法通过该操作凭空恢复，重建操作不属于数据备份恢复机制。

### 日志导出

会话维度的完整日志可通过 CLI 工具执行 `export <id>` 导出为 JSONL 文件，具体参数见 [CLI 参考](/reference/cli)。

> **说明**：请求重建、会话日志导出与用量 CSV 导出分别对应不同的排查与审计场景，不能仅依赖用量明细表格来替代或恢复完整的会话上下文。

## 问题反馈与证据收集

向维护者反馈异常或提交 Issue 时，为便于定位根因，建议提供以下完整信息：

- ChatLuna 版本号与系统部署方式。
- 脱敏后的 `sessionId` 与问题发生的具体时间范围。
- 确定性的复现步骤与触发上下文。
- 实际生效的 `provider` 与 `model`。
- 终止状态标识（`finish`）或系统抛出的完整异常日志（`error`）。
- 命中的路由规则及相关系统调用日志。
- 环境作用域说明：明确故障是仅发生于特定接入平台、仅出现于全新会话，还是仅在特定交互模态下触发。

**安全须知**：请勿在公开渠道张贴访问口令、平台 API Key、包含用户私聊内容的完整请求体或敏感的宿主机配置。若排查必须提供原始载荷，需先确认共享范围并做好脱敏处理。通用的排错检查清单与诊断流程，参见[排错与诊断](/guide/troubleshooting)。

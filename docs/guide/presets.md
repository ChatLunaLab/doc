# 预设与角色

预设决定机器人如何被描述、如何组织提示词与示例，不是插件配置的副本。普通聊天预设与角色引擎预设是不同 kind：先选择引擎，再选择它能够消费的预设。

## 从文件到生效

托管目录默认是应用根目录下的 `data/chatluna/presets/`。新目录保持为空，不会自动复制旧预设或生成示例。可以在预设页导入、创建或复制，也可以由首次 setup 明确创建。

编辑器以源码为主，提供格式诊断和补全。预览会解析未保存内容而不写盘；保存后仍保持原格式。revision 是内容 SHA-256，用于防止旧页面覆盖新文件；遇到冲突先刷新并合并自己的改动，不要覆盖另一处更新。

目录有文件监听、200ms 去抖和内容哈希去重。解析失败时会显示 error，并保留上一次成功数据供已有装载使用；因此页面中的错误源码与正在使用的最后成功版本可能不同。先修复诊断，再确认新的 revision 已加载。

路由中的预设切换由引擎在下一个回合开始时应用，不应期待中途改变已发出的网络请求。切换不抹掉历史；需要干净上下文时另开对话。

## 普通 Markdown 聊天预设

以下是一个不依赖远端模型名的最小示例，保存为 `.md`：

````markdown
---
name: 技术助手
description: 解释步骤，区分事实与推测
input: '{prompt}'
---

你是一位技术助手。回答要列出前置条件、操作和验证方法。
不知道的信息要明确指出，不编造已经执行的操作。

<!-- @section name=style order=20 -->
先给结论，再解释原因。涉及破坏性操作时先说明影响。

<!-- @context name=clock -->
当前时间：{time}

<!-- @example -->
用户：保存成功是不是代表模型能调用？
助手：不是。还需要发送真实请求，检查认证、额度和协议。
````

第一条指令之前是 system 区的 persona 块。`@section` 新开一个块，`@context` 放变化内容，`@example` 放用户/助手示例。分区指令必须是单独一行的 HTML 注释；`@include` 则单独写一行，不加 HTML 注释。普通 Markdown 标题不会自动改变 zone。

| 写法 | 规则 |
| --- | --- |
| `@section name=X order=N` | 默认 system 区，默认 order 10 |
| `@context name=X order=N` | context 区，默认 order 1000 |
| `zone=system` / `zone=context` | 显式选择区段 |
| `role=system` / `user` / `assistant` | 声明块角色；system 区的 user/assistant 作为 prelude 消息 |
| frontmatter `input:` 或 `@input` | 输入模板必须含 `{prompt}`；同时设置时指令优先并产生警告 |
| `@include ./partial.md` | 展开同目录文件，只允许一层包含 |

不同区段的 name 不要重复。示例按 `用户：` / `User:`、`助手：` / `Assistant:` 分行；非角色开头的后续行并入上一条示例，不是独立消息。

### 把变化内容放到 context

system 区只允许不可变变量。时间、随机数等变化内容应放进 `@context` 或输入模板，否则会出现 `variable.mutable` 等诊断，渲染也可能拒绝。

这项限制用于保持请求前缀稳定，不是提示词的安全边界。可用的一键修复会把包含变化变量的段落移到 context；采用修复后仍应检查段落含义与顺序。机制见[上下文与缓存](/architecture/context-cache)。

### 工具、技能和模型建议

frontmatter 可声明 tools/skills 的 allow/deny 策略。这些策略只收窄能力，不替代用户权限、机器访问权限或每次审批。没有允许列表与显式空列表的含义不同。

普通 Markdown 加载器的 `model:` 目前用 `provider/model` 解析为模型建议，与运行时精确地址 `provider:model` 不同。这是文件格式边界，不要在提供商、场景规则中照抄斜杠写法；也不要把建议等同于已经选定当前请求模型。初次使用可先省略它，通过界面明确选择并验证实际模型。

## 角色引擎预设

角色预设使用 frontmatter `kind: character`，由 character 加载器处理。它与普通聊天预设并存，不能只改文件扩展名就假定语义相同。

````markdown
---
kind: character
name: 小溪
nick: [小溪]
interests: [天文, 游戏]
mute: [安静点]
status:
  - key: mood
    label: 心情
    initial: calm
    hint: calm / happy / tired
---

你是小溪，一位喜欢分享日常的聊天伙伴。

<!-- @style -->
用简短自然的中文，不假装完成了尚未执行的操作。

<!-- @example -->
用户：今晚看星星吗？
小溪：<message>先看看天气，再决定去哪儿</message>
````

输出元素说明、状态字段、工具说明和可用群档案由能力插件注入，不需要把整套运行时协议重复粘贴进人格正文。角色通过 `prepare → generate → deliver → settle` 四段流程运行；页面上的能力流程图表示当前配置，不是某一回合的真实执行轨迹。

### 状态、短期 memo 与长期记忆

- 状态字段是结构化数据。模型写增量，合法字段经过 schema 检查，不是把整段状态文本无条件覆盖。
- 内置频道/按人 memo 依赖状态能力，是角色短期状态的一部分。
- 长期记忆属于独立记忆服务，群资料也要有实际来源；没有服务时不能声称已经写入记忆。
- Judge 类状态更新会额外调用模型，默认关闭；开启前核对模型角色与成本。

节奏、禁言、动作、工具和唤醒等按当前引擎设置生效。规则值优先于引擎缺省。工具模式未指定时，角色引擎默认 delegate；不能套用普通 Agent 的默认模式。

## 旧格式与迁移

旧普通预设与旧角色预设由各自加载器处理。角色 v1 加载器识别 `nick_name`、`input`、`status` 等旧字段；旧 input 模板不会原样执行，会给出诊断和转换修复。历史、状态和触发原因由新引擎提供，不应把旧占位符机械复制到新模板。

引擎配置中 schema 不认识的旧键可能在挂载与保存时被剪除并记录日志，这不是自动等价迁移。先备份原文件，在小范围测试消息、元素输出、工具和状态，再替换正在使用的角色。

## 常见问题

| 现象 | 检查 |
| --- | --- |
| 文件存在但下拉列表没有 | 加载器、扩展名、kind、文件诊断与 id 重名 |
| 保存后仍像旧人格 | 是否绑定到正确范围、revision 是否成功、下一回合是否开始、旧历史是否仍在 |
| 变量报 mutable | 移出 system，检查输入模板或 context |
| 角色说已排程却没有任务 | 定时服务与权限是否在场，查看真实工具结果 |
| 预览和生效内容不同 | 未保存预览、解析失败保留旧数据、并发编辑冲突 |

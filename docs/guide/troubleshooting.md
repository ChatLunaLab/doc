# 排错与诊断

先确定失败在哪个边界，再改动单项配置。一次成功的 HTTP 请求、保存提示、模型列表或流式文字，都不能代替整个对话链路的完成证据。本页按现象排查，不要求先删除数据库、重装所有依赖包或放开所有权限。

## 先收集最小证据

记录发生时间、运行版本、部署方式、当前实例名/目录、出错页面或平台、会话 ID、完整错误码以及最近一次改动。保留服务端日志与浏览器控制台错误；对外提供前必须移除 `Authorization`、口令、API key、平台身份、用户消息和工具输出。

```sh
chatluna list
chatluna doctor config --dir .
```

以上命令在已有实例目录中执行；源码工作区可通过 `yarn chatluna` 运行同一入口。`doctor config` 是本地配置静态检查，不会替你测试全部远端模型。不要通过直接输出整个运行环境或私人 `chatluna.yml` 分享诊断资料。

## 启动失败或读错配置

1. **检查启动目标**：`--dir` 选项优先；显式传入实例名会选择受管目录，不跟随当前工作目录。
2. **检查根清单选择顺序**：查找优先级依次为 `cordis.yml`、`cordis.yaml`、`chatluna.yml`、`chatluna.yaml`。查看文件中的 `include` 关系，确认编辑的是实际生效的来源。
3. **逐项检查语法与依赖**：依次检查 YAML 语法、稳定 `id`、插件包是否安装、条目的 `disabled` 状态，以及必需的 `inject` 服务依赖。
4. **验证构建产物**：新包或依赖改动后必须先执行 `yarn build`；运行时抛出 `ERR_MODULE_NOT_FOUND` 也可能是包的 `lib` 编译产物未生成，而非 TypeScript 路径声明缺失。
5. **排查 HMR 泄漏**：若在热重载（HMR）后出现重复事件监听或工具重名，检查对应资源是否已绑定当前生命周期，不要使用全局 `Set` 掩盖泄漏。

开发命令 `chatluna dev .` 会使用当前根清单并启用 `dev` 配置组，但它不自动加载 `cordis.dev.yml`，且不启用生产 supervisor 的恢复与安全模式。启动恢复报告与普通业务异常要分开查看。

若尝试运行 `chatluna repair`，必须先阅读现有报告并备份数据。`repair` 可能会修改工程文件；`chatluna report` 用于查看已有报告和 issue 草稿，不等于把诊断资料自动发送到社区。

## 页面打不开、一直加载或离线

| 现象 | 优先检查 |
| --- | --- |
| TCP 连接拒绝 | 检查对应进程、实际监听地址、端口占用，以及 Compose 服务是否已启动 |
| HTTP 401 | 检查登录会话是否过期、口令是否发生变化、反向代理是否保留认证头 |
| HTTP 403 | 检查 `allowRemote` 来源限制或操作权限，不应先判定为密码错误 |
| HTTP 404 | 检查访问路径、插件挂载点、静态资源产物、代理路径前缀；不一定是网络断开 |
| 首屏有旧数据但无法操作 | 检查 WebSocket 是否断开，页面当前快照可能仍保留上次的数据 |
| 只有某个页面打不开 | 检查对应页面包、入口编译产物、所依赖的基础服务与 action/state 错误 |

可在受信任的本机检查健康端点：

```sh
curl --fail http://127.0.0.1:5028/api/health
```

`5028` 是默认示例端口，请替换为实际部署地址。`health` 端点返回成功只证明该 HTTP 服务正常响应，不证明远端模型、聊天平台、数据插件和 WebSocket 全部处于健康状态。

反向代理需正确转发 WebSocket，并避免对流式接口开启长时间缓冲。检查浏览器 Network 选项卡中的实际连接状态和响应码，不因旧快照仍有内容显示就认为服务在线。管理界面的 state/action、对话 durable SSE 与 live SSE 属于不同的协议通道，故障处理不能只尝试重连其中一条。

Docker 镜像内部允许容器网络互通，而官方 Compose 在宿主机上默认只将端口映射到回环地址（`127.0.0.1`）。配置远程访问时，需同时检查宿主机的发布地址、HTTP 监听配置、来源限制、认证设置和 HTTPS 终止，不能将关闭认证作为连通性解决方案。

## 忘记访问口令

先确认口令的提供来源：`server` 配置、`CHATLUNA_TOKEN` 环境变量或文件模式（file mode）。

- **固定口令**：若通过配置文件或环境变量固定口令，必须在对应来源中修改；此时删除 `auth.json` 并不能覆盖依然存在的固定配置。
- **文件模式**：在文件模式下，`auth.json` 仅保存哈希和签名密钥，无法从哈希反算原口令。在备份并停止实例后，可由可信管理员重置该认证文件再重启实例，从本机标准输出的启动日志中取得新生成的口令；原有的已签名会话将全部失效。
- **弱口令回退**：若传入了过弱的固定口令，该口令会被忽略并回退到文件模式；此时应直接查看启动诊断日志，而不是反复尝试同一个密码。切勿删除整个数据目录，也不要在公共渠道公开首次登录链接。

## 模型存在却无法回复

按以下顺序逐步排查：

1. **Provider 注册**：Provider 扩展包是否已成功安装和注册？缺少底层 SDK 时，配置项不会自动变成可调用的模型实现。
2. **模型定位**：当前规则、预设和会话具体选择的是哪一个 `provider:model`？检查设置来源，不要只看全局默认项。
3. **凭据与端点**：API key、endpoint、模型标识、组织或区域配置是否符合该 provider 的要求？在配置界面保存凭据时，空白输入可能表示保留已有值，并非删除。
4. **推理连通性**：列出模型或 discover 调用成功，仅证明元数据探测通过；必须执行一次明确的真实推理测试。
5. **能力匹配**：该模型是否支持请求所需的输入模态、工具调用（tool calls）或文件附件？`chat`、`embed`、`decide` 属于不同的接口契约，不能直接混用或替代。
6. **供应商状态**：查看请求的 `finish_reason`、错误码、调用超时、供应商限额与账单余额，不要将所有调用异常都归咎于“模型不存在”。

```sh
chatluna doctor providers --dir .
```

执行该命令需要应用处于运行状态，默认访问本机 `5028` 端口；通过 `CHATLUNA_BASE` 与 `CHATLUNA_TOKEN` 指定目标地址与认证口令，不要在排错工单中输出这些值。请注意，停止、客户端取消或超时的调用，供应商侧已经产生的计算仍可能计费。

## 平台在线但机器人不回复

平台在线仅表示 adapter 与聊天服务平台的连接处于存活状态。排查时应先确认消息是否成功进入命令解析或中间件链路，再检查场景规则中的 engine、预设、模型、会话归属与激活条件：

- **激活条件判定**：@机器人、昵称匹配、引用消息、随机回复和私聊直回属于相互独立的控制项。通用激活 schema 中的 `allowQuoteReply` 默认值为 `false`，不可假定引用消息必然唤醒机器人。
- **逻辑抑制**：检查冷却时间（cooldown）、机器人自身消息过滤逻辑以及角色引擎判定是否抑制了响应。
- **Observer 行为**：Observer 记录非唤醒消息只用于上下文维护，不代表该消息会触发一次模型调用。
- **会话路由**：多机器人、多平台或群聊/私聊可能被路由解析到不同的会话 ID；应逐一检查命中规则与每个上下文字段的实际来源。
- **投递阶段错误**：排查末端 `renderer` 或 `transport` 的发送错误；模型生成成功不代表平台已完成消息投递。

建议使用专用的测试账号与独立会话进行验证，切勿让 v1 和 v2 两个实例同时连接同一个平台机器人账号。首次人格设置流程限定了主人私聊等触发条件，在群聊中未进入访谈流程并不属于模型故障。

## 绑定码或首次向导卡住

向导的标准执行顺序为：模型配置 -> 聊天平台配置 -> 用途设定。在模型步骤中点击“继续”需要真实推理测试通过；在平台步骤中点击“继续”要求已挂载非 Web 的在线 bot 实例；选择“跳过”或“稍后”不等于这些依赖项测试已通过。

绑定码的使用规则如下：

- 必须在真实聊天平台的私聊对话中发送 `bind <code>`（指令前缀是否需要带 `/` 取决于系统的指令配置），不能在 Web 聊天界面中认领。
- 系统使用实际 `sender` 的平台标识与用户身份完成校验与绑定。
- 绑定码有效期为 10 分钟，生成新码后旧码立即作废；连续输入 5 次错误将直接导致当前码失效。
- 第一个向机器人发送私聊消息的用户不会自动取得主人身份。

主人确认状态、向导完成状态、模型就绪状态、当前预设以及人格状态分别保存在不同的数据结构中。显式执行 `setup` 命令后，系统会从下一条消息开始进入访谈流程；排查时应以命令的实际返回和路由走向为准，不要反复清空预设数据库。

## 预设保存后未生效

保存后若未达到预期，应按顺序检查预设源文件诊断、`include` 路径、当前绑定关系与版本号（revision）。文件在外部被修改或发生并发保存时可能触发冲突；此时应重新加载并合并改动，不能强制覆盖未载入的变更。

- **变量作用域**：`system` 区域仅允许不可变变量，动态渲染值必须放置在 `context` 区域。若抛出 `MutableVariableError`，必须修正区域划分或变量声明；系统不会自动保留原文继续渲染。
- **包含语法**：独立的包含行语法为 `@include ./partial.md`，使用其他不受支持的语法格式将无法解析。
- **生效时机**：已生效的修改只作用于其后规定的轮次与生命周期边界，不会逆向改写已经发送给模型的历史请求。
- **缓存状态**：文件监听器（watcher）解析失败时会保留上一个有效版本，因此磁盘上存在新文件并不代表内存中已成功加载新内容。

## 工具不见了、一直问或被拒绝

按照“可见性 -> 选择过滤 -> 执行环境”逐层排查：

1. **注册状态**：对应的插件与底层依赖服务是否正常挂载？工具是否已完成注册？
2. **规则过滤**：当前预设或场景中的允许列表（allowlist）与 tool policy 是否隐藏了该工具？空配置的 allow 与未设置 allow 可能对应完全不同的策略行为。
3. **延迟加载**：检查工具是否属于延迟加载；应先触发搜索机制，不要将未直接出现在首轮请求中的工具判定为不存在。
4. **参数校验**：工具入参是否通过了 Schema 校验？检查实际传递的结构化参数，而不是参考模型生成的自然语言口头解释。
5. **鉴权机制**：能力权限、主体安全等级（level）、调用目标范围与 `ask` 询问通道是否满足要求？配置为 `auto` 并不代表能绕过安全权限限制。
6. **运行时策略**：runtime policy 当前是处于 `inspect` 还是 `off`？即便设置为 `full`，系统也仍可能需要显式确认。
7. **执行层故障**：宿主环境、MCP 服务或下游接口是否可用？调用失败可能来自真实执行阶段的异常，而非框架层拒绝。

当审批超时或对应通道不存在时，系统将默认按拒绝处理。切勿为了消除审批确认提示而将所有工具无差别设为 `auto`、将所有用户权限设为最高级别 `5`，或直接向容器挂载宿主机的 Docker socket。

## 记忆、定时与后台异常

- **长期记忆边界**：新建对话不会清空全局长期记忆；需明确区分当前 `scopes`、自动索引机制与检索返回结果三者的差异。
- **索引机制**：自动提取功能默认关闭；系统发出的 `index` 通知仅代表检测到主题变动，不代表全文已被直接注入提示词。开启会话隔离（conversation isolation）并不等于工具搜索具有绝对的私有化边界。
- **定时任务执行**：定时任务必须存在真实的 Job 实例与执行日志记录，不能仅凭对话中“已安排好”的自然语言回复断定生效。排查时检查任务的时区、暂停状态、`when` 表达式、`grace` 容忍窗口、执行预算以及结果投递目标。
- **唤醒消息范围**：`wakeup` 的 `messages` 上下文仅覆盖上次唤醒触发之后产生的新消息；表达式引擎不是通用的任意 JavaScript 执行环境。
- **后台作业终态**：后台任务（Background）的终态可能包含 `failed` 或 `cancelled`；收到占位响应或任务状态处于 `settled` 并不保证业务逻辑执行成功，实例重启也不保证能重新接管历史未完成的进程。
- **容器生命周期**：Docker `pause` 操作会保留容器及其状态，而 `close` 操作将销毁容器；在执行恢复流程前，必须确认工作区（workspace）与生成产物是否已持久化导出。

## 历史、轨迹与用量对不上

- **索引定义区别**：`Session n` 代表存储序列中的条目序号，并不是前端展示页面中的消息数组下标。
- **视图过滤**：消息渲染视图排除了系统内部的 `mark`，并会受到 `cut` 摘要机制的影响；分支分叉（fork）复制采用半开区间，业务层的逻辑 head 与底层存储的 Session 分支处于不同层级。
- **历史回放机制**：请求重建（reconstruct）不会重新调用模型；而 `replay` 操作属于一次新的模型推理请求，会产生新的计费，但系统不会自动重新执行原流程中关联的工具调用。
- **流式状态转换**：SSE 输出的 `live` 实时文字不属于最终确认的 `committed` 消息。若 SSE 传输过程中发生 `truncated`，应拉取 `messages` 完整快照以恢复当前视图，不能将截断的尾部数据当作完整对话保存。
- **统计数据差异**：Token 用量、实际账单金额、成本估算与管理界面上的实时 `active` 列表在统计口径上并不完全一致。供应商返回的 input/output 数据中可能已经包含了缓存抵扣或推理阶段的 reasoning token，重复累加会导致数据偏大。请先核对 billing 插件配置、模型单价基准与统计周期范围，再判断是否存在数据统计故障。

## 提交问题前

准备 issue 或向社区反馈时，必须提供以下内容：

- 最小且可复现的完整操作步骤。
- 预期行为与实际出现的结果。
- 发生时间、详细运行版本号与相关错误码。
- 相关的插件清单及经过脱敏处理的服务端/控制台日志。
- 说明该现象是否能在干净的独立测试实例中复现、系统是否刚完成版本升级，以及故障是否能通过回退版本消除。

切勿提交真实数据库文件、`auth.json` 认证文件、全量运行环境导出、私人配置文件或完整的用户对话隐私记录。如需了解更多背景，请继续查看[配置参考](/reference/configuration)、[安全与权限](/guide/security)和[轨迹与用量](/guide/observability)。

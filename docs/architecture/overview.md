# 架构总览

ChatLuna v2 是基于 Cordis 4 的可组合聊天与 Agent 框架。Cordis 负责管理插件、服务与生命周期，Satori 负责接入各类聊天平台。应用的 React WebUI 提供系统管理与对话交互界面，文档站则采用独立的 Vue/VitePress 工程构建。

理解 ChatLuna v2 的运行时架构，核心在于解耦并厘清三组正交概念：
1. **业务对话（Conversation）**：平台的业务归属、上下文目录与当前活跃分支指针。
2. **会话日志（Session）**：持久化、版本化、按序号追加的事件记录与切点视图。
3. **活跃执行对象（Agent）**：运行时的执行上下文、输入缓冲与状态推进循环。

在明确上述对象边界的基础上，系统进一步向下调度单步模型推理与受控工具执行。

## 一条消息的路径

从消息接入到平台响应，整体调用关系如下：

```text
Satori / Web 输入
  → 注册命令与中间件
  → chat 分发、场景规则与激活
  → conversations 协调业务对话与当前 head
  → engine 接入 Agent
  → Agent 默认循环：准备请求 → 模型步骤 → 工具 → 下一步骤
  → Session 追加 message / mark / cut
  → renderer / transport 投递平台回复
```

上述路径描述的是一次标准交互的处理链条，并非每条消息都严格经历整套线性流水线：
- **中间件与命令拦截**：已注册的命令可以在中间件层直接消费消息并提前返回，不再向下传递至对话路由。
- **旁路观察**：启用 `Observer` 时，系统可记录非唤醒状态下的输入内容。
- **特定接管**：`setup` 引擎仅在满足特定主人私聊规则的前提下接管执行流程。
- **异步与可见性边界**：模型流式输出（Streaming）已经展示，仅表示当前步骤的部分生成内容可用，不代表最终完整的 `SessionEntry` 已提交写入，更不代表平台端传输已完成投递。

## 三个不同的对话对象

系统在业务层、存储层与执行层分别定义了职责清晰的独立对象，避免职责混淆：

| 对象 / 服务 | 负责职责 | 明确边界（不负责） |
| --- | --- | --- |
| **conversation**<br>`ctx.conversations` | 业务目录管理、维护当前业务 head 指针、主线切换、协调绑定活跃 Agent 实例。 | 不单独复制一份独立的消息实体作为真相源。 |
| **Session**<br>`ctx.sessions` | 有序日志条目管理、消息切片视图、截断切点（cut）与分支（branch）；根据配置委托给底层 store 持久化。 | 不持有各聊天平台的业务归属逻辑，不参与模型与工具的执行循环。 |
| **Agent**<br>`ctx.agents` | 运行状态机、输入缓冲队列调度、模型单步请求与工具调用循环。 | 不直接等同于数据库中保存的某一条静态 Session 记录。 |

### Session 条目结构与分支机制

- **条目联合类型**：`SessionEntry` 是 `message`、`cut`、`mark` 三类条目的联合。每个条目均包含递增日志序号 `n`。
  - `cut`：在当前位置建立逻辑切点，改变后续可见的消息切片视图，但不会硬删除历史条目。
  - `mark`：用于记录控制信息、调试数据与请求上下文标记，不作为普通聊天消息参与模型上下文构建。
- **分支边界与协调**：分支头通过 `parent` 与 `at` 字段标记分叉位置，复制历史条目的有效区间为半开区间 `[0, at)`。分支创建仅处理日志层级的条目拓扑，上层业务 `head` 指针的切换必须由 `ctx.conversations` 协调完成，`Session.branch` 不会自动切换业务归属。
- **提交与持久化**：条目标记为 `committed` 仅表示当前 `Session` 实例接受了该追加操作。实际的数据落盘与容灾恢复取决于具体配置的 `SessionStore` 实现。默认组合采用独立的 SQLite 持久化插件；在未挂载持久化 store 的运行模式下，不能因类名包含 `append-only` 或 `durable` 字样推断系统具备抗断电的物理落盘保证。

详细设计参见[会话、消息与分支](/architecture/sessions)。

## Agent 与默认执行循环

默认执行循环位于 `packages/agent/core/src/loop/`，与 Agent 契约同属于 `@chatluna/agent` 包，并非独立的外部包。

- **Turn 与 Step**：用户的一次交互唤醒称为一次 turn。在一个 turn 内部，Agent 可执行多次模型单步推理（step）和工具调用。循环负责处理停止条件判定、并行工具调度以及并发输入缓冲的合并逻辑。
- **输入注入策略**：通过 `receive` 接口接入输入，支持三种模式：
  - `next`：放入缓冲，等待当前 turn 结束后在下一轮处理。
  - `now`：在当前步骤的执行边界立即合入。
  - `quiet`：作为不主动唤醒的输入，若 Agent 处于空闲状态则不启动执行；不是已经提交的日志或处理回执。
  三种模式均用于控制调度时机，并非每条消息投递的成功回执。执行中断（`abort`）仅能终止后续未执行的步骤，无法回滚已经产生外部副作用的工具调用。
- **核心服务依赖**：默认循环的完整运行依赖 `trace`、`presets`、`tool_search` 等服务。这些服务以独立包形式组织，但若从运行环境中移除，将导致默认循环功能缺失；不同的 Agent 运行时实现允许声明自身专用的依赖集合。
- **扩展原则**：扩展 Agent 行为时，应当通过请求准备、单步拦截、提交等既有扩展缝隙（seams）介入，避免因单个插件的需求随意扩大核心接口表面。

详细执行机制参见[Agent 执行](/architecture/agents)。

## 模型与单次请求

ChatLuna 将模型抽象拆分为规范定义层与执行运行时：
- **`@chatluna/ai`**：定义独立的模型协议元语与抽象接口。
- **`@chatluna/ai-runtime`**：提供 `ctx.ai` 服务，负责 provider 的注册管理、寻址解析、客户端绑定、中间件拦截以及具体调用分发。
- **`@chatluna/core`**：在顶层封装业务动词，暴露为 `ctx.chatluna`。

### 模态与调用动词

- **支持模态**：`chat`、`embed`、`rerank`、`draw`、`speak`、`listen`、`decide`。
- **业务动词**：`ask`、`chat`、`extract`、`embed`、`rerank`、`draw`、`speak`、`listen`、`decide`、`decideOne`、`judge`。

### 运行时调用特征

- **单步 Run**：对 `chat` 模态的一次调用返回一个 `Run` 对象，仅代表单个模型推理步骤（Step），其内部不包含 Agent 的完整工具执行循环。
- **Provider Generation**：Provider 实例上的 `generation` 字段用于追踪服务热重载与实现重绑定的代际计数，并非用于标记模型提示词缓存的 epoch。
- **调用链故障域**：注册有效、目录寻址匹配、运行时参数绑定与最终底层 API 调用是四个互相解耦的阶段。模型出现在配置目录中仅表示协议注册成功，不等于推理接口具备可用性。
- **依赖与用量计算**：各底层模型 SDK 必须按需安装和加载，系统不会仅因配置文件中指定了名称便自动具备对应的协议实现。统计规范化用量（Usage）时，必须注意供应商缓存命中字段与思考推理（reasoning）字段的包含关系，不能直接将所有返回的 token 计数进行简单相加。

详细模型交互参见[模型与请求运行时](/architecture/models)。

## 场景规则、预设与上下文

### 场景规则解析

场景规则负责将请求路由到对应的配置与引擎。其解析遵循以下机制：
1. **合并与校验**：先合并全局配置与所有命中规则的配置层，再按所属命名空间的 Schema 执行完整校验。
2. **规则排序优先级**：依次按规则特异度（Specificity）、`priority` 字段、创建时间戳及唯一 `id` 进行确定性排序。
3. **引擎隔离解析**：解析时先确定生效的 `engine`，再行校验该引擎专属的下属配置。禁止直接复用或沿用此前其他引擎留存的过期字段。字段锁定、数组全量替换以及默认值注入的时机均会影响最终合并结果。

### 预设装配与动态分区

预设由受管理的 Markdown 源文件、元信息（Metadata）及片段模板组成。`ctx.prompt` 服务将内容分拣装配至三个独立区域（Zone）：
- **`system` 区**：仅允许注入全局不可变变量。若在 `system` 区声明或传入动态/易变变量，系统将直接抛出 `MutableVariableError`。
- **`context` 区**：用于存放运行时装配的动态数据、截取切片及检索结果。
- **`input` 区**：承载当前轮次的用户实际输入与即时状态。

### 缓存边界与生命周期

- **稳定前缀与 Cache Break**：系统通过稳定前缀构建与插入 `cache break` 来提升供应商协议层提示词缓存的复用效率。该机制仅为缓存性能优化手段，不构成内容安全可信边界，亦不能作为供应商必命中缓存的绝对保证。
- **生命周期解耦**：系统内不同层级的版本控制生命周期各自有不同的意义与推进条件，不应混用；一次配置变动也可能同时影响其中多个生命周期：
  - `prompt/cache epoch`：由 `system` 提示词内容、挂载工具列表及核心模型参数变更驱动刷新。
  - `provider generation`：由 Provider 服务热重载与插件重挂载驱动。
  - `session branch`：由对话交互中的显式切片、分叉操作驱动。
  - `preset revision`：由预设源文件的编辑与版本追踪驱动。

详细机制参见[上下文与缓存](/architecture/context-cache)。

## 能力、授权与执行环境

### 工具调度与权限体系

工具通过 `args`（通常采用 `Schema.args`）与执行函数 `run` 声明。一次实际的工具调用必须依次经过以下管道：
`工具存在性过滤` → `参数 Schema 校验` → `执行中间件拦截` → `能力权限判定` → `底层 run 执行`。

系统将工具控制细化为三个正交的约束层级：
1. **工具可用状态**：`auto`（允许自动调用）、`ask`（需要确认）、`off`（禁用）。
2. **权限模式（Permission Mode）**：管控工具调用的主体资质与范围。
3. **运行时策略（Runtime Policy）**：约束工具在宿主运行时的执行边界与具体上下文。

### 执行抽象与隔离边界

- **MCP 扩展**：MCP（Model Context Protocol）协议负责将外部工具投影到统一的工具调用平面内。
- **技能（Skills）**：仅提供关于能力的语义描述、操作说明与静态上下文资源，挂载技能不等于自动授予底层工具的执行权限。
- **执行环境分工**：
  - `machine`：管理系统命令与底层文件操作的具体执行后端。
  - `subagent`：管理子级派生任务的状态与上下文分发。
  - `background`：负责后台异步长任务的执行调度。
  上下文继承与异步任务调度仅为执行方式的分离，不代表底层宿主环境具备物理机或容器级别的安全隔离。
- **模块分级原则**：组件分为“核心默认实现”、“核心默认依赖”与“可选扩展”。外部 MCP 传输适配器、Forge、特定的底层机器后端、动态插件/守护进程管理、附加追踪导出器（Trace Sinks）以及账单聚合器均为按需挂载的可选扩展，不能将默认系统依赖直接视作可无缝剥离的可选模块。

## 插件与数据的所有权

### 目录与依赖约束

工程在物理目录上明确划分了可复用库与终端插件：
- **`packages/<domain>/<name>`**：可直接导出的公共库、通用服务与类型契约包。
- **`plugins/<domain>/<name>`**：仅能通过清单（Manifest）加载的终端业务插件。

Cordis 服务的生命周期管理遵循以下规范：
- 业务服务必须使用 `inject` 声明静态或运行时服务依赖。
- 业务逻辑中的事件注册与钩子必须绑定到当前调用方的 `ctx` 上下文。
- 监听外部资源或占用句柄时，必须通过 `effect` 返回明确的释放回调（disposer）。
- 模块热重载（HMR）能够自动清理并回收持有者的注册资源，但无法保证依赖发生剧烈重载时对正在执行中的会话上下文完全透明。

### 运行时配置与数据隔离

运行时配置事务负责处理配置清单校验、磁盘写入与受控应用（apply）。该事务机制的保证仅限于配置系统内部，**不承诺**跨底层数据库、远程网络调用与外部工具环境的分布式全局原子性。

各个服务独立维护各自的文件记录或数据库表结构。禁止将配置快照（Config Snapshot）视作全系统业务数据的备份替代方案。详细约束参见[插件、运行时与数据](/architecture/extensions)。

## 从记录到诊断

### 请求重建与模型 Replay

- **静态请求重建**：基于 `Session entries` 与记录在日志中的 `prompt mark`，系统可以在不发起实际模型推理、不执行任何工具的前提下，严格依据当时记录的切片边界重建完整的历史请求输入。轨迹（Trace）系统是此类事实数据的可观测性视图，并非另一套并行的消息存储库。
- **动态 Replay**：Replay 是明确发起的新模型实验。该操作会调用底层模型 API 并产生真实计费，系统不会自动重新执行原会话中的外部工具，亦不会隐式改写历史的 `SessionEntry` 记录。

### 实时协议分层

系统为不同场景提供两套独立的 Server-Sent Events (SSE) 同步协议：
- **Durable SSE**：同步已提交的 Session 条目，并按游标恢复有限历史；超出恢复上限时需要重新拉取消息快照，落盘保证由 store 决定。
- **Live SSE**：用于实时推送尚未提交的流式生成内容（Token 流、临时状态更新）。

两者分别针对持久事实与临时流设计，采用不同的恢复协议与断线重连逻辑。详细定义参见[HTTP 和实时协议](/development/api-reference)与[轨迹与用量](/guide/observability)。

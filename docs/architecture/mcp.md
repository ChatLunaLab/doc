# MCP 接入

::: tip
MCP (Model Context Protocol) 是一个开放协议，用于把外部服务提供的工具无缝接入模型上下文。接入后，这些外部工具在模型眼中与内置工具没有任何区别。
:::

在实际开发中，并不是所有扩展能力都值得单独编写一个 ChatLuna 插件。

比如现成的数据库查询服务、GitHub 客户端，或是企业内部的工单系统——它们本身就拥有完善的独立实现，我们往往只需要一种标准、统一的接入方式将它们连入 Agent。

MCP 正是为此而生的桥梁。

## 服务定义

在 ChatLuna 中，一个 MCP 服务通过配置对象进行声明：

```ts
servers: {
  github: {
    transport: 'stdio',
    command: 'npx',
    args: ['-y', '@modelcontextprotocol/server-github'],
    env: { GITHUB_TOKEN: process.env.GITHUB_TOKEN },
    timeoutMs: 120_000,
  },
  internal: {
    transport: 'http',
    url: 'https://mcp.example.com/mcp',
    headers: { Authorization: 'Bearer ...' },
  },
}
```

配置项中的键名即为服务 ID（如上述配置中的 `github` 和 `internal`）。这个服务 ID 也会直接作为后续投影工具名称的前缀组成部分。

### 字段说明

每个服务支持配置以下字段：

| 字段 | 说明 |
| --- | --- |
| `transport` | 传输协议类型，支持 `stdio` 或 `http` |
| `enabled` | 实例启动时是否自动建立连接 |
| `command` / `args` / `cwd` | `stdio` 模式下的启动命令、运行参数及工作目录 |
| `env` | `stdio` 子进程的环境变量键值对 |
| `url` / `headers` | `http` 模式下的服务端点 URL 与请求头 |
| `timeoutMs` | 单次工具调用的超时时间（毫秒） |

需要注意的是，配置中填写的环境变量与请求头会被系统作为敏感凭据妥善加密保存，绝不会在前端界面或配置导出时回显明文。

## 两种传输协议

ChatLuna 支持两种不同的通信传输方式，分别适应本地与远程场景：

### stdio

`stdio` 传输模式会在宿主机本地启动一个子进程，双方通过标准输入输出（stdin/stdout）进行数据通信。

这种模式非常适合本地开发工具、命令行 CLI 封装，或是需要直接读写宿主机本地文件的服务。子进程的生命周期与服务状态强绑定：服务启用时启动进程，服务停用或插件卸载时安全终止。

::: warning
`stdio` 模式启动的子进程拥有与 ChatLuna 宿主进程完全一致的系统访问权限。请切勿直接接入来源不明的服务，尤其是包含任意命令执行或系统写权限的外部进程。
:::

### http

`http` 传输模式通过网络连接远端 MCP 端点，并支持基于流式传输的交互。

这种模式特别适合已经独立容器化或集群部署的服务，也便于多个 ChatLuna 实例共同复用同一个后端能力。不过需要注意，远端 HTTP 端点必须完整实现 MCP 协议规范所要求的流式传输语义；否则即使握手连接成功，后续的数据交互也可能无法正常进行。

## 连接生命周期

每个 MCP 连接都拥有一套清晰明确的运行时状态流转机制：

| 状态 | 含义 |
| --- | --- |
| 已停用 | 服务配置已保留，但连接开关处于关闭状态 |
| 连接中 | 正在与端点建连并尝试握手拉取工具清单 |
| 已连接 | 连接建立成功，导出的工具已就绪 |
| 出错 | 握手失败、连接中断或远端进程异常退出 |
| 缺少传输支持 | 当前运行环境中未加载对应传输协议所需的支撑插件 |
| 空闲 | 服务已开启，但尚未满足触发建连的条件 |

### 什么时候会触发重连

在以下几种典型场景下，系统会自动或手动触发服务的重新连接：

- 保存并更新了服务配置；
- 安装、更新或卸载了相关的底层传输插件；
- ChatLuna 实例启动或插件上下文热重载；
- 开发者在控制台手动点击了「重连」操作。

触发重连时，系统会重新向服务端拉取完整的工具列表，并自动替换已注册的工具定义。在此期间正在执行中的历史工具调用并不会被强制打断——旧调用会平稳等待执行结束，而后续发起的新调用则会立即采用刷新后的最新定义。

### 失败隔离机制

MCP 服务在设计上严格遵循了故障隔离原则：

哪怕某一个外部服务发生网络抖动或崩溃报错，也完全不会波及其他正常运行的服务，更不会导致整个机器人实例崩溃。连接失败的服务会保持在「出错」状态，并在界面与日志中清晰呈现具体的错误原因。

## 工具投影

外部服务接入后，其声明的能力必须经过一层「投影」机制，转换成 ChatLuna 内部通用的标准工具定义。

### 命名规则

外部工具在投影到内部注册表时，其命名遵循统一的命名空间规范：

```text
mcp__<服务 id>__<工具名>
```

例如在服务 ID 为 `github` 的配置下，名为 `search_repos` 的工具投影后就会变成 `mcp__github__search_repos`。

为了保证兼容性，工具名中包含的非法字符会被统一替换为下划线，且名称总长度会被截断在 64 个字符以内。如果替换或截断后的名称不幸与已有工具冲突，系统会直接跳过该工具的注册，并记录一条警告日志。

::: tip
统一命名前缀并不仅仅是为了美观。有了 `mcp__` 前缀，我们就可以借助通配规则一次性批量治理所有外部工具，例如统一将全部 MCP 工具配置为「按需动态发现」或「调用前需管理员审批」。
:::

### 参数结构转换

外部 MCP 工具使用 JSON Schema 来定义其入参规范，系统在注册时会将其转换为 ChatLuna 内部的 Schema 结构。

在转换过程中：

- 受支持的标准字段会被直接解析并正常映射；
- 暂未支持的非标准扩展字段会被安全忽略，并记录到调试日志中；
- 若整个入参 Schema 出现解析异常或结构损坏，该工具将被直接跳过。

因此，当你遇到「服务已成功连接，但工具列表空空如也」的情况时，往往是因为该服务所声明的工具入参格式与内部 Schema 转换规范不兼容。

### 执行结果返回

外部工具执行完毕后，返回的内容会被序列化为文本直接注入到模型的对话上下文中。

如果外部服务在协议响应中明确将结果标记为失败（isError），系统则会向外抛出执行异常，使外层的 Agent 执行循环能准确感知到本次调用的失败并执行重试或补救逻辑。

## 清单刷新机制

ChatLuna 本地缓存的外部工具清单本质上是一份运行时快照。

当外部 MCP 服务端动态新增、变更或删除了某些工具后，这些修改并不会自动广播推送过来，必须经历一次刷新流程才能生效。由于每次重连都会重新抓取清单，因此当你在服务端调整了暴露接口却未见生效时，最简单的解决方式就是手动点击一次重连。

## 与工具系统的关系

需要明确的是，外部能力一旦完成投影，在内部就完全等同于一个普通的内置工具：

- 统一受到工具策略的管控；
- 统一受到场景规则的过滤与调度；
- 统一受到权限与审批系统的约束；
- 支持被配置为按需加载（动态工具发现）。

服务提供方只负责声明并提供原生能力，至于哪些用户、在哪些场景下能够调用这些能力，完全由 ChatLuna 的工具管理体系统一裁决。

::: warning
请不要将 MCP 协议当成安全隔离的权限边界。所谓「这个 MCP 服务只暴露了只读能力」，仅仅是服务端自己的声明，无法代替宿主系统的安全防护。真正可靠的权限管控必须在 ChatLuna 自身的工具策略与权限规则中明确配置。
:::

## 安全考量

### 凭据保护

所有与外部服务交互涉及的环境变量及 HTTP Headers 均作为机密凭据进行持久化。无论是在日常配置查看还是在导出排查日志时，这些明文均受到严格脱敏保护，避免意外泄露。

### 超时防护

为避免外部挂起导致整个会话卡死，MCP 工具单次调用的默认超时为 120 秒，初始建连与握手超时为 30 秒。你可以根据服务的实际网络环境与计算开销，在配置中单独调整各个服务的超时时长。

### 进程管控

对于本地 `stdio` 服务，由于其本质是宿主机上的原生子进程，我们建议在部署时遵循以下规范：

- 仅连接来自官方或深度信赖的工具源；
- 在启动参数中尽量锁定依赖的确定版本，避免使用不受控的「始终拉取最新版本」；
- 若涉及高危操作或高隔离需求，建议将服务运行在独立的 Docker 容器或远端服务器中。

## 常见服务类型

社区中常见的 MCP 服务通常涵盖以下典型场景：

| 类型 | 典型能力 |
| --- | --- |
| 文件与代码 | 读写本地代码仓库、符号索引检索、隔离沙盒命令执行 |
| 数据库 | 表结构与 Schema 读取、只读 SQL 查询与元数据统计 |
| 搜索与网页 | 联网搜索抓取、网页核心正文解析与摘要提取 |
| 项目管理 | GitHub/GitLab Issue 与 PR 查询、敏捷看板协作 |
| 内部系统 | 企业内部 ERP、CRM、库存管理及工单系统联动 |

## 常见问题排查

遇到 MCP 服务无法正常工作时，可以对照下方的排查清单逐步确认：

**服务一直停留在出错状态：**

首先检查控制台的具体报错日志：常见原因包括本地 command 可执行程序路径不存在、运行参数错误、远端网络端点不通、Authorization 鉴权失败，或是协议版本不兼容。对于 `stdio` 服务，建议先在终端命令行中手动执行启动指令；对于 `http` 服务，则优先检查连通性与 Headers 配置。

**连接成功了，但找不到可用工具：**

确认服务端是否真的声明了 Tools（部分服务可能只提供 Resources 或 Prompts）；或者该服务暴露的工具入参 JSON Schema 不符合内部解析规范。可查看系统日志中被跳过的工具条目与具体原因。

**模型在对话中看不到特定的 MCP 工具：**

请按顺序依次排查：服务是否处于「已连接」状态；该工具是否因重名或 Schema 错误被跳过；全局工具策略中是否禁用了该工具；当前会话场景规则是否将其过滤；或者该工具是否被设置为了「按需加载」而模型尚未主动检索它。

**提示工具名称冲突：**

如果多个服务提供了同名工具，且投影规则发生重合，建议直接在配置中修改服务 ID（例如将 `git` 改为 `github_corp`），或者在工具策略中显式禁用其中一方。

**工具调用超时报错：**

适当增大该服务配置中的 `timeoutMs` 阈值；检查外部服务端是否发生了死锁或长时间阻塞；若该工具执行的是耗时极长的异步作业，建议将工具改造为支持轮询或转后台任务模式。

# MCP

::: tip
MCP 是一个开放协议，用来把外部服务提供的工具接进模型上下文。接进来之后，这些工具和内置工具在模型眼里没有区别。
:::

不是所有能力都值得写一个 ChatLuna 插件。

一个数据库查询服务、一个 GitHub 客户端、一个公司内部的工单系统，它们本来就有自己的实现，只需要一个统一的接入方式。

MCP 就是那个方式。

## 服务定义

一个 MCP 服务由一份配置描述：

```ts
servers: {
  github: {
    transport: 'stdio',
    command: 'npx',
    args: ['-y', '@modelcontextprotocol/server-github'],
    env: { GITHUB_TOKEN: process.env.GITHUB_TOKEN },
    timeoutMs: 120_000,
  },
  internal: {
    transport: 'http',
    url: 'https://mcp.example.com/mcp',
    headers: { Authorization: 'Bearer ...' },
  },
}
```

配置里的键就是服务 id，同时也是工具名前缀的一部分。

### 字段

| 字段 | 说明 |
| --- | --- |
| `transport` | `stdio` 或 `http` |
| `enabled` | 启动时是否自动连接 |
| `command` / `args` / `cwd` | stdio 模式的启动方式 |
| `env` | stdio 子进程的环境变量 |
| `url` / `headers` | http 模式的端点与请求头 |
| `timeoutMs` | 单次工具调用的超时 |

环境变量与请求头会被当作凭据保存，不回显在界面上。

## 两种传输

### stdio

在宿主机上启动一个子进程，通过标准输入输出通信。

适合本地工具、命令行封装、需要访问本机文件的服务。

生命周期与服务状态绑定：启用时启动，卸载时终止。

::: warning
子进程拥有与 ChatLuna 进程相同的系统权限。

来源不明的服务不要用 stdio 方式接，尤其是需要执行命令的那种。
:::

### http

连接一个远程端点，支持流式传输。

适合已经独立部署的服务，或者多个实例共享同一个服务。

远程端点必须完整支持协议要求的流式规范，否则可能连上但无法正常交互。

## 连接生命周期

连接有明确的状态：

| 状态 | 含义 |
| --- | --- |
| 已停用 | 配置保留，但开关关闭 |
| 连接中 | 正在建连并拉取工具 |
| 已连接 | 工具已就绪 |
| 出错 | 连接或握手失败 |
| 缺少传输支持 | 没有对应的传输插件 |
| 空闲 | 启用但尚未建立连接 |

### 什么时候重连

- 修改服务配置。
- 安装或卸载相关插件。
- 实例启动或插件重载。
- 手动点击重连。

重连会重新拉取工具清单，并替换工具定义。

正在执行中的工具调用不会被打断——旧的调用跑完，新的调用用新的定义。

### 失败隔离

一个服务连接失败，不会影响其他服务，也不会让机器人整体不可用。

它会停留在出错状态，并在界面上显示原因。

## 工具投影

外部工具需要变成 ChatLuna 能识别的工具定义。

### 命名

投影后的名字是：

```text
mcp__<服务 id>__<工具名>
```

例如服务 `github` 的工具 `search_repos`，投影后是 `mcp__github__search_repos`。

非法字符会被替换成下划线，整体截断到 64 个字符。

如果替换或截断后与已有工具重名，这个工具会被跳过，并记录一条警告。

::: tip
前缀不是装饰性的。

它让「所有 MCP 工具」可以被一条通配规则统一管理，例如统一设为按需加载或需要审批。
:::

### 参数结构

外部工具的参数是 JSON Schema，需要转换成内部的 Schema。

转换过程中：

- 支持的字段正常映射。
- 不支持的字段被丢弃，并记录日志。
- 整个结构无法解析时，这个工具被跳过。

所以「连接成功但没有工具」是很常见的现象，通常意味着参数结构不兼容。

### 结果

外部工具的返回被序列化成文本交给模型。

如果服务把结果标记为错误，系统会抛出错误，让 Agent 循环知道这次调用失败了。

## 刷新

工具清单是快照。

服务端新增或删除工具后，需要一次刷新才能反映到 ChatLuna。

刷新会在重连时发生，所以「改了服务端配置没生效」时，手动重连一次即可。

## 与工具系统的关系

MCP 工具一旦投影进来，就只是普通工具：

- 受工具策略控制。
- 受场景规则控制。
- 受权限系统控制。
- 可以设为按需加载。

服务本身不决定谁能用什么，它只负责提供能力。

::: warning
不要把 MCP 当成权限边界。

「这个服务只暴露了只读工具」是服务端的承诺，不是 ChatLuna 的保证。真正的限制要写在工具策略和权限规则里。
:::

## 安全

### 凭据

环境变量与请求头按凭据保存。

配置里不会出现明文，导出配置时也不会。

### 超时

单次调用默认 120 秒；建连超时是 30 秒。

超时可以按服务单独设置。

### 进程

stdio 服务是子进程，需要认真对待：

- 只接可信来源。
- 尽量用固定版本，不要用「永远最新」。
- 需要隔离时，把服务放进容器或远程主机。

## 常见服务类型

| 类型 | 典型能力 |
| --- | --- |
| 文件与代码 | 读写文件、检索代码、在沙盒中执行 |
| 数据库 | 表结构查询、只读查询 |
| 搜索与网页 | 联网搜索、抓取正文 |
| 项目管理 | Issue、PR、看板 |
| 内部系统 | 订单、库存、工单 |

## 排查

**服务一直出错。**

看错误信息：命令不存在、参数错误、端点不通、鉴权失败、协议版本不兼容。

stdio 先用终端手动跑一遍；http 先检查网络与请求头。

**连上了但没有工具。**

服务本身没暴露工具，或者所有工具的参数结构都不兼容。看日志里被跳过的工具与原因。

**模型看不到某个 MCP 工具。**

依次检查：服务是否连接、工具是否被跳过、工具策略是否禁用、场景规则是否过滤、是否被设为按需而模型还没搜索。

**工具名冲突。**

改服务 id，或者禁用其中一个冲突工具。

**调用超时。**

调大该服务的超时；检查服务端是否卡住；如果是长任务，考虑让工具支持转后台。

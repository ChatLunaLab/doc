# MCP 接入

::: tip
MCP (Model Context Protocol) 是一个开放协议，用于将外部服务提供的工具接入模型上下文。接入后，这些外部工具对模型而言与内置工具完全一致。
:::

在实际使用中，并不是所有扩展能力都需要专门编写 ChatLuna 插件。

例如现成的数据库查询服务、GitHub 客户端，或是内部工单系统——它们本身已有完整的独立实现，只需要一种标准方式接入 Agent 即可。

MCP 正是为此设计的接入方案。

## 服务定义

在 ChatLuna 中，MCP 服务通过配置对象来声明：

```ts
servers: {
  github: {
    transport: 'stdio',
    command: 'npx',
    args: ['-y', '@modelcontextprotocol/server-github'],
    env: { GITHUB_TOKEN: process.env.GITHUB_TOKEN },
    timeoutMs: 120_000,
  },
  internal: {
    transport: 'http',
    url: 'https://mcp.example.com/mcp',
    headers: { Authorization: 'Bearer ...' },
  },
}
```

配置项中的键名即为服务 ID（例如上述配置中的 `github` 和 `internal`）。后续生成的投影工具名称会使用该服务 ID 作为前缀。

### 字段说明

每个服务支持配置以下字段：

| 字段 | 说明 |
| --- | --- |
| `transport` | 传输协议类型，支持 `stdio` 或 `http` |
| `enabled` | 实例启动时是否自动建立连接 |
| `command` / `args` / `cwd` | `stdio` 模式下的启动命令、运行参数及工作目录 |
| `env` | `stdio` 子进程的环境变量键值对 |
| `url` / `headers` | `http` 模式下的服务端点 URL 与请求头 |
| `timeoutMs` | 单次工具调用的超时时间（毫秒） |

注意：配置中填写的环境变量与请求头属于敏感信息，系统会加密保存，不会在前端界面或导出配置时显示明文。

## 两种传输协议

ChatLuna 支持两种传输协议，分别用于本地与远程场景：

### stdio

`stdio` 模式会在本地启动子进程，通过标准输入输出（stdin / stdout）进行通信。

这种模式适合本地开发工具、命令行 CLI 封装，或是需要读写本地文件的服务。子进程的生命周期与服务状态绑定：启用服务时启动进程，停用服务或卸载插件时终止进程。

::: warning
`stdio` 模式启动的子进程拥有与 ChatLuna 完全相同的系统权限。请不要接入来源不明的服务，尤其是具有命令执行或文件写入权限的外部程序。
:::

### http

`http` 模式通过网络连接远端 MCP 端点，支持流式传输交互。

这种模式适合已容器化或独立部署的服务，也方便多个 ChatLuna 实例复用同一后端。需要注意，远端 HTTP 端点必须完整实现 MCP 协议的流式传输规范；否则即使连接成功，后续数据交互也可能异常。

## 连接生命周期

MCP 连接具有以下运行时状态：

| 状态 | 含义 |
| --- | --- |
| 已停用 | 服务配置已保留，但连接处于关闭状态 |
| 连接中 | 正在建立连接并拉取工具清单 |
| 已连接 | 连接成功，导出的工具已就绪 |
| 出错 | 握手失败、连接中断或远端进程异常退出 |
| 缺少传输支持 | 当前运行环境缺少对应传输协议所需的插件 |
| 空闲 | 服务已开启，但尚未满足连接条件 |

### 触发重连的时机

以下情况会触发服务的自动重连或手动重连：

- 保存或更新了服务配置
- 安装、更新或卸载了传输协议相关的插件
- ChatLuna 实例启动或插件热重载
- 在控制台手动点击「重连」

触发重连时，系统会重新拉取完整的工具列表，并更新已注册的工具定义。重连不会打断正在执行的调用：旧调用会等待执行结束，后续的新调用则使用刷新后的定义。

### 故障隔离

MCP 服务遵循故障隔离原则。

单个外部服务发生网络波动或报错，不会影响其他正常运行的服务，更不会导致整个机器人实例崩溃。连接失败的服务会保持在「出错」状态，并在界面和日志中显示具体错误原因。

## 工具投影

外部服务接入后，系统会通过「投影」机制将其声明的能力转换为内部通用的工具定义。

### 命名规则

外部工具投影到内部注册表时，遵循统一的命名规范：

```text
mcp__<服务 id>__<工具名>
```

例如，在服务 ID 为 `github` 的配置下，名为 `search_repos` 的工具投影后会命名为 `mcp__github__search_repos`。

为保证兼容性，工具名中的非法字符会被替换为下划线，名称总长度会截断在 64 个字符以内。如果处理后的名称与已有工具冲突，系统会跳过该工具的注册，并记录警告日志。

::: tip
统一命名前缀便于批量管理。借助 `mcp__` 前缀和通配规则，你可以一次性配置所有外部工具，例如统一设置为「按需动态发现」或「调用前需管理员审批」。
:::

### 参数结构转换

外部 MCP 工具使用 JSON Schema 定义入参规范，注册时系统会将其转换为 ChatLuna 内部的 Schema 结构：

- 标准字段会被直接解析并映射
- 暂不支持的非标准扩展字段会被忽略，并记录到调试日志中
- 若入参 Schema 解析异常或结构损坏，该工具会被直接跳过

如果遇到「服务已成功连接，但工具列表为空」的情况，通常是因为该服务声明的入参格式与内部 Schema 转换规范不兼容。

### 执行结果返回

外部工具执行完毕后，返回内容会序列化为文本直接注入到模型的对话上下文中。

如果外部服务在协议响应中将结果标记为失败 (`isError`)，系统会抛出执行异常，供外层 Agent 感知失败并执行重试或补救逻辑。

## 清单刷新机制

ChatLuna 本地缓存的外部工具清单是一份运行时快照。

当外部 MCP 服务端新增、修改或删除了工具时，改动不会自动推送到本地，需要刷新后才能生效。每次重连都会重新抓取工具清单。如果在服务端调整了接口后没有生效，在控制台手动点击一次「重连」即可。

## 与工具系统的关系

外部工具完成投影后，与内置工具的处理方式完全一致：

- 统一受工具策略管控
- 统一受场景规则过滤与调度
- 统一受权限与审批系统约束
- 支持配置为按需加载（动态工具发现）

服务提供方只负责声明和提供能力，具体哪些用户、在哪些场景下可以使用这些能力，完全由 ChatLuna 的工具管理体系决定。

::: warning
不要将 MCP 协议本身作为安全隔离的边界。服务端的只读声明无法替代宿主系统的安全控制，可靠的权限管控仍需在 ChatLuna 的工具策略与权限规则中明确配置。
:::

## 安全考量

### 凭据保护

外部服务涉及的环境变量与 HTTP Headers 均作为机密凭据存储。无论是在配置界面查看还是导出日志排查，系统都会对这些内容进行脱敏处理，避免明文泄露。

### 超时保护

为防止外部服务挂起导致会话卡死，MCP 工具单次调用的默认超时时间为 120 秒，建立连接与握手的默认超时时间为 30 秒。你可以根据实际网络情况和耗时需求，在配置中单独调整各个服务的超时时长。

### 进程管控

本地 `stdio` 服务会在宿主机上启动子进程，建议在部署时注意以下事项：

- 仅连接来自官方或可信来源的服务
- 尽量在启动参数中锁定明确的依赖版本，避免使用动态拉取最新版本的命令
- 涉及高危操作或强隔离需求时，建议将服务运行在独立的 Docker 容器或远端服务器中

## 常见服务类型

社区中常见的 MCP 服务通常涵盖以下典型场景：

| 类型 | 典型能力 |
| --- | --- |
| 文件与代码 | 读写本地代码仓库、代码符号检索、沙盒命令执行 |
| 数据库 | 表结构与 Schema 读取、只读 SQL 查询、元数据统计 |
| 搜索与网页 | 网页搜索抓取、正文解析与摘要提取 |
| 项目管理 | GitHub / GitLab 的 Issue 与 PR 查询、看板协作 |
| 内部系统 | 企业内部 ERP、CRM、库存管理及工单系统对接 |

## 常见问题排查

遇到 MCP 服务无法正常工作时，可以对照下方的排查清单逐步确认：

**服务一直停留在出错状态**

检查控制台的具体报错日志。常见原因包括：本地 `command` 可执行文件路径不存在、运行参数错误、远端网络端点不通、鉴权失败，或是协议版本不兼容。对于 `stdio` 服务，建议先在终端中手动执行启动命令进行验证；对于 `http` 服务，优先检查网络连通性与 Headers 配置。

**连接成功，但找不到可用工具**

确认服务端是否声明了 Tools（部分服务可能只提供 Resources 或 Prompts）；也可以查看系统日志，确认工具是否因入参 JSON Schema 不符合规范而被跳过。

**模型在对话中看不到特定的 MCP 工具**

按以下顺序依次排查：

1. 服务是否处于「已连接」状态。
2. 该工具是否因重名或 Schema 解析错误被跳过。
3. 全局工具策略中是否禁用了该工具。
4. 当前会话场景规则是否过滤了该工具。
5. 该工具是否被设置为「按需加载」，而模型尚未主动检索它。

**提示工具名称冲突**

当多个服务提供了同名工具且投影规则冲突时，可以在配置中修改服务 ID（例如将 `git` 改为 `github_corp`），或者在工具策略中显式禁用其中一方。

**工具调用超时报错**

可以在配置中适当增大该服务的 `timeoutMs` 阈值；同时检查外部服务是否出现阻塞。若该工具执行的是耗时较长的异步作业，建议将工具改造为支持轮询或后台任务模式。

# 定时与后台任务

在 ChatLuna 中，大部分交互都发生在一个完整的回合（Turn）内部：从收到消息、调用模型、触发工具到最终回复。

然而，还有两类工作无法局限在单一交互回合中：

- **未来时刻触发**：例如早报推送、日程提醒，或在群聊冷场时主动搭话。
- **需要耗时处理**：例如代码编译、文件下载、长时间运行的脚本或委派的子代理任务。

这两类工作在架构上分别由**定时任务**与**后台任务**提供支持。

::: tip
这是两套截然不同的运行时机制：定时任务的核心是「到点了再开始」，而后台任务则是「现在开始，但不在当前回合中同步等待」。
:::

## 定时任务

定时任务负责在约定的时刻或满足特定条件时触发预设动作。

### 任务模型

每一个定时任务在底层都由以下几个核心部分构成：

| 部分 | 说明 |
| --- | --- |
| 目标 | 在哪个会话、哪个路由触发 |
| 触发 | 什么时候触发 |
| 动作 | 触发后做什么 |
| 重复 | 执行几次、到什么时候为止 |
| 状态 | 活跃、暂停、完成、失败 |
| 归属 | 谁创建的 |

任务的「目标」绑定的是环境的身份快照，而非单一固定的会话 ID。这样即使后续角色改名或群聊升级，任务依然能够精确投递到预期的交互位置。

### 触发方式

根据调度逻辑的不同，定时任务支持四种触发方式：

| 类型 | 含义 |
| --- | --- |
| `at` | 某个具体时间点 |
| `every` | 固定间隔重复 |
| `cron` | 日历表达式，可带时区 |
| `watch` | 持续观察一个条件 |

其中，前三种类型由定时器直接驱动，而 `watch` 则由消息到达与定时轮询共同驱动。

### 动作

任务被触发后，可以执行以下两类动作：

- **唤醒**：模拟有人向机器人发起交互，在目标会话中触发一次正常的对话回合。
- **运行**：使用指定的流程引擎或子代理，在后台静默运行一段提示词。

针对「运行」类动作的执行结果，系统提供了三种投递方式：

- **发送**：将结果作为普通聊天消息投递到目标会话中。
- **通知**：仅将结果推送到控制台，不打扰群聊中的普通用户。
- **不发送**：完全不向外投递消息，仅在内部记录执行结果。

::: tip
在选择投递方式时，建议明确「谁需要看到这个结果」：直接发往群聊的消息会打扰所有人，而面向管理员的通知或审计日志使用控制台推送更为合适。
:::

### 状态

任务在其生命周期中包含四种状态：

- **活跃**：任务处于正常调度中，正在等待下一次触发。
- **暂停**：保留任务配置但暂时不触发。
- **完成**：一次性任务已顺利执行完毕，或周期任务已达到设定的重复上限。
- **失败**：任务执行出错且未能恢复。

任务的状态变更均会被实时持久化，系统重启后仍可继续运行。

## 执行保证

定时任务在设计上追求的是「尽量准时」，而不是物理意义上的绝对准时。

真正触发执行时，调度系统会依次进行四道前置检查：

1. **是否到期**：核对当前系统时间是否已经超过了预定的计划时间。
2. **是否还在宽限内**：默认允许延迟一小时。若超过宽限期则直接跳过本次执行，避免在半夜补发白天的消息。
3. **是否超过每日上限**：默认单会话每天最多触发 100 次。
4. **是否超过任务数量**：默认单会话最多允许 20 个活跃任务。

需要说明的是，因检查未通过而被跳过并不等同于失败。系统只是放弃了这一次执行，后续的周期触发仍会照常进行。

::: warning
如果你发现「任务偶尔不执行」，请优先检查最大延迟宽限与每日触发上限。服务器重启、长时间停机或任务堆积，都可能使任务超出宽限期而被判定为不适宜补发。
:::

### 频率约束

为了保障宿主环境的稳定性，调度系统内置了一组频率约束：

| 配置 | 默认 |
| --- | --- |
| 最短触发间隔 | 5 分钟 |
| 单会话活跃任务 | 20 |
| 单会话一次性唤醒 | 5 |
| 单会话每日触发 | 100 |
| 单次定时最长 | 24 小时 |
| 最大延迟 | 1 小时 |

任何触发间隔低于最短间隔的任务，都必须经过显式审批才能成功创建。

这项限制主要是为了防止配置失误：一个被误设为「每 10 秒触发一次」的任务，足以在几分钟内耗尽全天的 API 调用额度。

## 关注条件

与固定按时间点等待不同，`watch` 触发方式会持续观察预设的环境条件是否达成。

关注条件支持读取以下上下文数据：

- 最近接收到的消息列表。
- 发言人身份与权限。
- 会话当前的沉默时长。
- 积累的消息条数。
- 当前系统时间。
- 该任务已累计触发的次数。

根据条件所依赖的数据源，系统的检查机制分为两类：

- **消息驱动**：仅依赖消息内容的条件，每当会话接收到新消息时就立即判断一次。
- **轮询驱动**：依赖时间推移或沉默时长的条件，系统会按照固定间隔进行定期检查，默认轮询间隔为 10 秒。

### 意图判定

对于无法用简单规则表达的场景，关注条件中允许调用判定模型来回答一个二元（是/否）问题。

为了避免高频调用带来不可控的模型开销，意图判定设定了严格的成本配额：

- 单个频道两次判定之间至少必须间隔 30 秒。
- 全局每天最多允许执行 200 次意图判定。

一旦超出上述预算限制，判定请求将直接返回「否」，并不会挂起或排队等待。

::: tip
判定模型适合用于「聊到某个话题时插话」等语义理解条件。对于纯粹基于消息数量或固定时长的规则，请不要使用判定模型，避免产生不必要的开销。
:::

## 一次性唤醒

角色系统大量使用了「唤醒」类任务，用于约定「等会儿再说」。

与常规的定时任务相比，一次性唤醒具有以下特点：

- 可以设置超时过期时间。
- 过期时可以根据配置选择「放弃」或「强行唤醒」。
- 可以设置最小触发间隔，避免频繁自言自语。
- 可以在角色因别的原因开口后自动取消。

这些约束让角色的主动行为更加拟人自然，而不是像机械的时钟定时器。

## 后台任务

后台任务用于解决长耗时操作的阻塞问题，确保对话交互的流畅响应。

### 什么时候转后台

工具在定义时通常会声明同步等待的耗时上限。当实际执行时间超出这一上限时：

- **允许转后台**：交由后台任务继续执行，先向当前回合返回占位结果。
- **不允许转后台**：直接判定为调用超时并失败。

除了工具超时触发外，委派的子代理也可以主动申请转入后台运行。

### 状态

后台任务在生命周期中具有以下五种状态：

- **运行中**
- **停止中**
- **完成**
- **失败**
- **取消**

### 两条输出流

后台任务将输出严格拆分为两路流，兼顾模型消费与调试观测：

- **模型可读结果**：仅包含任务完成后的有效业务产出，任务完成后会回到会话上下文。
- **人类可读日志**：包含详细的执行跟踪日志，仅在控制台展示，不进入模型输入。

两路输出相互隔离，可以有效避免冗长的调试日志污染模型的上下文窗口。

### 缓冲区

为了保护系统资源，后台任务的输出缓冲区设有明确的上限：

- 控制台的日志输出设有 256KB 上限：超过后仅保留最新的尾部内容，并打上截断标记。
- 最终写回模型上下文的业务结果部分，则被单独限制在 8KB 以内。

此外，日志读取接口支持从指定偏移量增量拉取，因此控制台界面可以实现「仅展示新增内容」。

::: warning
当缓冲区满触发截断时，系统虽然会打上标记，但不会产生报错。如果模型反馈「收到的结果不完整」，请先排查是否触发了 8KB 的结果截断，而不是工具本身的逻辑问题。
:::

### 完成通知

当后台任务执行完毕后，系统提供了三种通知方式：

- **唤醒**：任务完成后，立即在当前对话中插入一条助手消息展示结果。
- **下一轮**：安静排队等待，在用户的下一次对话中再合入结果。
- **静默**：仅在控制台记录状态，不向聊天流投递通知。

选择的关键在于「这个结果在当前对话中是否具有即时性」。

### 取消

调用取消操作时，系统会通知底层任务停止，并立即截断后续结果向对话流的回流。

尽管部分外部任务可能无法做到瞬间停止，但系统保证绝不会再向会话中写入已过期的执行结果。

## 持久化

定时任务与后台任务在生命周期持久化上有明确的区分：

- **定时任务会落盘**：重启后会自动恢复调度。
- **后台任务不一定会恢复**：运行中的任务属于进程状态，进程重启后通常会被标记为中断。

这是架构上的有意取舍：定时任务代表系统向用户作出的承诺，必须可靠守住；而后台任务代表当前正在进行的工作，进程重启意味着其宿主执行环境已经不复存在。

## 与权限的关系

定时任务经常在无人值守的场景下触发工具执行。

在此类场景中，工具调用的审批流程依然照常生效。若操作需要审批而无人处理，系统将统一按未批准处理。因此，将一个需要人工审批的命令放入无人值守的定时任务中，实际效果往往是「每次都执行失败」。

::: warning
设计自动化任务时，推荐优先选用只读操作。如果确实需要执行写入或高权限操作，请提前在权限规则中为对应的自动化场景授予权限，而不是指望半夜有人手动审批。
:::

## 排查

在开发和调试任务时，如果遇到问题可以按照以下思路进行排查：

**任务到点了没执行。**

检查任务状态是否为活跃；排查是否超出最大延迟宽限，或单会话已达到每日 100 次的触发上限；确认单会话活跃任务数是否已达到 20 个的上限；确认实例在计划时间附近是否发生过停机。

**关注条件一直不成立。**

先用最简单的基础条件进行验证；确认条件中引用的字段属性确实存在；检查轮询驱动的检查间隔是否配置过长。

**判定模型没有调用。**

检查频道的 30 秒冷却间隔以及每日 200 次的全局调用预算；确认判定模型本身的可用性。

**后台任务一直运行。**

查看控制台的日志输出是否仍在滚动；确认底层任务是耗时较长还是陷入了死锁；必要时通过取消方法手动终止。

**后台结果没回到对话。**

检查任务的完成通知方式设置；静默模式下结果不会出现在聊天流中，只会在控制台保留记录。

**重复任务突然停了。**

检查任务是否已达到预设的重复次数上限，或者是否因执行出错已被系统标记为完成或失败。

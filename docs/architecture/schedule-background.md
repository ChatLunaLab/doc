# 定时与后台任务

::: tip
这是两套不同的机制：定时任务是「到点了再开始」，后台任务是「现在开始，但不在这一轮等它」。
:::

ChatLuna 的大多数工作发生在回合内部：收到消息、调模型、调工具、回复。

但有两类工作不属于任何回合。

一类是「未来的某个时刻该做点什么」——早报、提醒、冷场时搭话。

另一类是「现在开始，但可能要跑很久」——编译、下载、长脚本、子代理。

它们分别对应定时任务和后台任务。

## 定时任务

### 任务模型

一个任务包含：

| 部分 | 说明 |
| --- | --- |
| 目标 | 在哪个会话、哪个路由触发 |
| 触发 | 什么时候触发 |
| 动作 | 触发后做什么 |
| 重复 | 执行几次、到什么时候为止 |
| 状态 | 活跃、暂停、完成、失败 |
| 归属 | 谁创建的 |

目标是身份快照，而不是一个会话 id。这样即使角色改名、群升级，任务仍然能落到正确的位置。

### 触发方式

| 类型 | 含义 |
| --- | --- |
| `at` | 某个具体时间点 |
| `every` | 固定间隔重复 |
| `cron` | 日历表达式，可带时区 |
| `watch` | 持续观察一个条件 |

前三种由定时器驱动，最后一种由消息与轮询共同驱动。

### 动作

两种：

- **唤醒**：模拟有人叫了机器人，触发一次正常的对话回合。
- **运行**：用指定的引擎或子代理，在后台跑一段提示词。

运行的结果有三种投递方式：

- **发送**：作为普通消息发到目标会话。
- **通知**：只推送到控制台，不打扰聊天。
- **不发送**：只记录结果。

::: tip
选择投递方式时想清楚「谁需要看到这个结果」。

发给群里的消息会打扰所有人；只给管理员看的通知不会。
:::

### 状态

- **活跃**：等待下一次触发。
- **暂停**：保留配置但不触发。
- **完成**：一次性任务已执行，或达到重复上限。
- **失败**：执行出错且未恢复。

状态变化会持久化，重启后继续。

## 执行保证

定时任务不是「准时闹钟」，而是「尽量准时」。

真正执行时会经过几道检查：

1. **是否到期**：当前时间是否已经过了计划时间。
2. **是否还在宽限内**：默认允许延迟一小时。超过就跳过本次，避免半夜补发白天的消息。
3. **是否超过每日上限**：默认每个会话每天最多触发 100 次。
4. **是否超过任务数量**：默认每个会话最多 20 个活跃任务。

跳过不是失败，只是这一次不执行，下一次照常。

::: warning
如果你发现「任务偶尔不执行」，先检查宽限与每日上限。

服务器重启、长时间停机、任务堆积，都会让补发变得不合适。
:::

### 频率约束

| 配置 | 默认 |
| --- | --- |
| 最短触发间隔 | 5 分钟 |
| 单会话活跃任务 | 20 |
| 单会话一次性唤醒 | 5 |
| 单会话每日触发 | 100 |
| 单次定时最长 | 24 小时 |
| 最大延迟 | 1 小时 |

低于最短间隔的任务需要经过审批才能创建。

这条限制主要是防止误配：一个「每十秒触发一次」的任务，足以在几分钟内烧掉一整天的额度。

## 关注条件

`watch` 不按时间去等，而是持续检查一个条件。

条件可以读取：

- 最近的消息。
- 发言人身份。
- 沉默时长。
- 消息条数。
- 当前时间。
- 已触发次数。

检查分两种：

- **消息驱动**：只看消息内容的条件，每来一条消息就判断一次。
- **轮询驱动**：涉及时间、沉默的条件，按固定间隔检查，默认 10 秒。

### 意图判定

条件里可以调用判定模型，回答一个二元问题。

判定有严格的成本约束：

- 单个频道两次判定之间至少间隔 30 秒。
- 全局每天最多 200 次。

超过预算的判定直接返回「否」，不会排队等待。

::: tip
判定模型适合「聊到某个话题时插话」这类语义条件。

纯数量、纯时间的条件不要用判定模型，没有意义还费钱。
:::

## 一次性唤醒

角色系统大量使用「唤醒」这种任务：约定「等会儿再说」。

它和普通定时任务的区别在于：

- 可以设置过期时间。
- 过期时可以选择「放弃」或「强行唤醒」。
- 可以设置最小间隔。
- 可以在角色因别的原因开口后自动取消。

这些约束让角色的主动行为更像人，而不是定时器。

## 后台任务

### 什么时候转后台

工具声明了同步等待上限。超过上限时：

- 允许转后台：交给后台继续跑，先返回占位结果。
- 不允许：直接超时失败。

子代理也可以主动转后台。

### 状态

- **运行中**
- **停止中**
- **完成**
- **失败**
- **取消**

### 两条输出流

后台任务有两路输出：

- **模型可读**的结果：完成后会回到会话。
- **人类可读**的日志：只在控制台展示。

两路分开，避免调试输出污染上下文。

### 缓冲区

日志输出有上限：超过 256KB 后只保留尾部，并标记截断。

最终结果的入上下文部分再单独限制为 8KB。

读取支持从偏移量增量拉取，所以界面可以「只显示新内容」。

::: warning
截断是静默的，但会打标记。

如果模型说「结果不完整」，先看看是不是触发了截断，而不是工具本身出了问题。
:::

### 完成通知

任务完成后有三种通知方式：

- **唤醒**：立刻在当前对话里插一句结果。
- **下一轮**：安静排队，等下一次对话再说。
- **静默**：只记录，不通知。

选择依据是「这个结果现在重要吗」。

### 取消

取消会通知底层任务停止，并立刻截断后续结果回流。

部分外部任务无法瞬间停止，但系统保证不会再往对话里塞过期结果。

## 持久化

定时任务会落盘，重启后恢复。

后台任务不一定：运行中的任务属于进程状态，进程重启后通常会标记为中断。

这是有意的取舍：定时任务是承诺，要守住；后台任务是正在进行的工作，重启意味着它已经不在了。

## 与权限的关系

定时任务经常在无人值守时执行工具。

工具调用的审批流程照常生效。没人回答时，按未批准处理。

所以，一个需要审批的命令放进定时任务，实际效果往往是「每次都失败」。

::: warning
设计自动化任务时，优先选择只读操作。

需要写入或执行的，提前在权限规则里给对应的自动化场景授权，而不是指望有人半夜审批。
:::

## 排查

**任务到点了没执行。**

检查状态、宽限、每日上限、任务数量上限；确认实例在计划时间附近是否停机过。

**关注条件一直不成立。**

先用最简单的条件验证；确认条件里引用的字段确实存在；检查轮询间隔是否过长。

**判定模型没有调用。**

检查判定间隔与每日预算；确认判定模型可用。

**后台任务一直运行。**

看日志输出是否还在滚动；确认底层是慢而不是死锁；必要时取消。

**后台结果没回到对话。**

检查通知方式。静默模式不会出现在聊天里，只会在控制台记录。

**重复任务突然停了。**

可能已经达到重复上限，或者被标记为完成。检查重复设置。

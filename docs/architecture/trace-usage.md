# 轨迹与用量记录

::: tip
轨迹用于回答「这一轮对话中究竟发生了什么」，而用量则用于回答「这些操作总共消耗了多少资源与成本」。两者并非割裂的两套机制，而是共享同一套底层数据来源：`span`。
:::

对开发者而言，大语言模型的调用在很多时候就像一个黑盒。

它为什么会给出这样的回答？为什么单次交互耗时这么久？又为什么消耗了远超预期的 Token？仅凭最终展示在聊天框中的文本内容，我们很难还原背后的完整执行细节。

轨迹系统的核心目标，就是把每一次复杂的调用拆解为清晰、可观测的执行片段：完整的一轮对话、单个执行步骤、一次具体的工具调用，乃至一次子代理的独立运行。

## Span

一条完整的轨迹在内存与存储中表现为一棵层次分明的 `span` 树：

| 类型 | 代表什么 |
| --- | --- |
| `turn` | 一轮完整对话 |
| `step` | 一次模型请求及其工具执行 |
| `model` | 一次模型调用 |
| `tool` | 一次工具调用 |
| `subagent` | 一次子代理执行 |
| `chat` | 一次对话请求 |

每个 `span` 均会记录自身的关键元数据：开始时间、结束时间、执行状态、上下文属性、资源用量以及所包含的子 `span` 列表。

其中，属性是以键值对形式存在的上下文信息，通常记录了目标模型、服务提供商、调用的工具名称、参数摘要以及异常报错等详细诊断数据。

### 生命周期

`span` 的生命周期主要包含两个关键的时间广播节点：

- **开始时广播**：在 `span` 初始化并进入执行时向外广播一次通知。
- **结束时广播**：在 `span` 运行结束时再次广播，并附带最终的完整快照。

事件载荷中传递的数据均经过深拷贝处理。订阅者无法直接持有或修改内部的可变引用——这种设计有效避免了异步持久化或界面渲染与核心写入流程之间的互相干扰。

### 用量

`span` 支持向上逐级累计用量，涵盖输入 Token、输出 Token、缓存读写 Token 以及推理（Reasoning）Token。

需要明确的是，Token 的累计与聚合发生在 `span` 树本身，而不是由下游的各个汇聚端各自独立计算。这样可以保证所有消费者在不同视图下看到的统计数字严格保持一致。

## 消费者

`span` 派发的生命周期事件可以同时被多个彼此解耦的消费者订阅：

- **会话存储**：将执行轨迹持久化写入数据库，供控制台与界面查询展示。
- **文件输出**：以追加写入的形式保存为 JSONL 文件，非常适合离线归档与外部分析。
- **计费**：提取用量数据并根据单价规则折算为具体的费用成本。
- **自定义**：扩展插件可以根据业务需要订阅事件，构建专属的监控与统计面板。

各个消费者之间完全相互独立。单个消费者内部发生的异常或写入阻塞，绝不会扩散影响到其他消费者的正常运转。

## 轨迹页

控制台中的「轨迹」页面直接基于持久化后的数据进行呈现，主要包含以下视图维度：

- 按会话维度按序罗列最近的交互活动。
- 点击特定会话即可下钻查看某一轮对话的完整 `span` 调用树。
- 支持展开任意节点，查看详细的属性配置、输入输出摘要及报错堆栈。

在日常开发与排查过程中，轨迹页提供了几项非常实用的功能：

- **回放**：严格按照时间轴顺序单步复现这一轮对话中发生的所有事情。
- **草稿重调**：抓取当时生成的请求快照并重新发起一次模型调用，便于对比调试提示词改动。
- **进程视图**：将并发执行的步骤与工具调用在时间线上并排铺开，耗时瓶颈一目了然。

::: tip
在排查模型「为什么答非所问」时，最有价值的往往不是最终生成的回复文本，而是请求发出那一刻实际装配的上下文内容。在轨迹详情中，你可以清晰查看到当时的提示词摘要、可见工具列表与模型推理参数，这才是定位问题的根本依据。
:::

## 用量

如果说轨迹展示的是单次请求的微观切片，那么用量就是轨迹数据的宏观聚合视图。

### 记什么

系统在每一次模型调用结束时，都会记录以下核心指标：

- 服务提供商与具体模型名称。
- 调用的业务用途（如常规对话、条件判定、信息提取、上下文摘要等）。
- 输入 Token、缓存读取 Token、缓存写入 Token、输出 Token 与推理 Token。
- 调用是否采用了流式传输。
- 单次调用的总耗时。
- 最终折算的费用成本。

对于执行失败的模型调用，系统同样会记录调用流水；但只有在能够明确识别出提供商与具体模型时，才会进一步生成计费行。

### 成本从哪来

计费系统中的单价数据主要来源于两个渠道：

- **配置的价格**：开发者在计费插件或全局配置中手动填写的单价。
- **模型目录的价格**：服务提供商元数据清单中自带的官方基准价格。

在计费结算时，系统会优先采用「配置的价格」。如果两处均未声明该模型的价格，则本次调用的成本将记为 `0`，并将价格来源明确标记为「无」。

价格通常按每百万 Token 计，并分别针对输入、缓存读取与输出三项单独配置计费单价。

::: warning
用量系统计算出的成本仅为理论估算值，并不直接等同于实际账单。服务商的计费中转、阶梯用量折扣、限时促销以及私有缓存策略均可能导致实际扣费与估算存在偏差。如需精确对账，请以服务商官方后台账单为准。
:::

### 聚合

用量数据采用了分级保留与聚合策略：详细的单次调用明细会保留一段时间（默认 90 天），而每日生成的汇总数据则永久保留。

汇总统计主要支持以下几个维度的切分与下钻：日期、模型、用途以及会话。

通过这种设计，开发者既能在宏观上掌握「今天整体花费了多少额度」，也能精准回溯「是哪个模型、哪个业务功能消耗了最多成本」。

### 导出

为了方便团队进行成本审计与报表制作，系统支持将用量数据导出为 CSV 格式，便于接入外部的财务与对账系统。

## 界面

在控制台的用量看板中，通常包含以下模块：

- **概览卡片**：直观展示今日总花费、总请求数以及缓存命中率。
- **趋势图**：按时间维度绘制的费用与用量波动曲线。
- **分组表**：支持按模型、会话与用途进行多维拆分统计。
- **明细**：单次模型调用的原始流水记录。

此外，在控制台首页的仪表盘中，也会放置一张精简的今日用量卡片，方便快速了解当天的调用概况。

## 与其他子系统的关系

用量与轨迹的统计并不是孤立存在的，它与框架内部的多个子系统紧密协同：

- **缓存**：直接决定了 Token 的计费类型。命中前缀缓存的上下文将按相对低廉的缓存价计费，而非全额输入单价。
- **压缩**：上下文修剪与压缩会动态改变历史消息长度，从而直接降低后续轮次的 Token 消耗。
- **子代理**：子代理属于独立的执行会话，其用量会单独统计，但在总账上会汇总到同一个租户或账户视角下。
- **判定模型**：轻量判定逻辑（如意图识别、合规审查、唤醒判定等）同样会产生用量，通常推荐走轻量小模型以节约开销。

## 采样与开销

可观测性本身并非毫无代价。轨迹与用量的收集过程同样需要占用序列化、数据库写入以及事件广播等系统开销。

在调用极其高频的极端场景中，我们可以通过以下方式控制开销：

- 仅持久化关键类型的 `span`。
- 适当调低属性记录的详细粒度。
- 适度缩短单次调用明细的保留期限。

切记不要盲目为了「留存所有证据」而无限期保留所有底层的微观明细。

## 排查

在排查轨迹与用量相关的异常时，可以按照以下条目进行核对：

- **轨迹页是空的**：请先确认轨迹插件已正确加载并启用；检查后端数据库连接是否正常可用；最后确认对应的交互轮次中确实触发了实际的模型请求。
- **用量对不上**：优先核对当前模型的单价配置；再检查缓存 Token 是否被底层适配器正确提取与记录；最后排查是否存在部分调用走了未配置用量收集的第三方实例。
- **成本一直是 0**：说明既没有在配置中指定模型单价，模型目录元数据中也缺少价格定义。只需在计费配置中补充该模型的单价即可。
- **某次调用没有被记录**：检查该次请求是否在进入执行管线之前就已抛出异常；同时检查轨迹消费者在处理事件时是否有未捕获的报错。
- **数据太多，查询很慢**：建议缩短明细数据的保留周期，或者在日常查询中仅使用预聚合的汇总视图。轨迹数据重在实时排查定位，不建议替代专门的长期冷数据归档。

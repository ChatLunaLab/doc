# 轨迹与用量记录

::: tip
轨迹用于回答「这一轮对话中究竟发生了什么」，而用量用于回答「这些操作总共消耗了多少资源与成本」。两者并非割裂的两套机制，而是共享同一套底层数据来源：`span`。
:::

大语言模型调用在很多时候像一个黑盒。

为什么会给出这样的回答？单次交互为什么耗时这么久？又为什么消耗了远超预期的 Token？如果只看聊天框里的最终文本，很难还原背后的执行细节。

轨迹系统的目标，就是将每次调用拆解为清晰、可观测的执行片段：一轮完整的对话、单个执行步骤、一次具体的工具调用，乃至一次子代理的独立运行。

## Span

一条完整的轨迹在内存与存储中表现为一棵层次分明的 `span` 树：

| 类型 | 代表什么 |
| --- | --- |
| `turn` | 一轮完整对话 |
| `step` | 一次模型请求及其工具执行 |
| `model` | 一次模型调用 |
| `tool` | 一次工具调用 |
| `subagent` | 一次子代理执行 |
| `chat` | 一次对话请求 |

每个 `span` 都会记录自身的关键元数据：开始时间、结束时间、执行状态、上下文属性、资源用量，以及包含的子 `span` 列表。

其中，属性是以键值对形式存在的上下文信息，通常记录目标模型、服务提供商、调用的工具名称、参数摘要以及报错信息等诊断数据。

### 生命周期

`span` 的生命周期包含两个关键的广播节点：

- **开始时广播**：`span` 初始化并进入执行时向外广播一次通知。
- **结束时广播**：`span` 运行结束时再次广播，并附带最终的完整快照。

事件载荷中传递的数据均经过深拷贝处理。订阅者无法直接持有或修改内部的可变引用，避免异步持久化或界面渲染影响核心写入流程。

### 用量

`span` 支持向上逐级累计用量，包括输入 Token、输出 Token、缓存读写 Token 以及推理（Reasoning）Token。

Token 的累计与聚合发生在 `span` 树本身，而不是由下游各端独立计算。这保证了所有消费者在不同视图下看到的统计数字完全一致。

## 消费者

`span` 派发的生命周期事件可以同时被多个相互解耦的消费者订阅：

- **会话存储**：将执行轨迹写入数据库，供控制台和界面查询展示。
- **文件输出**：以追加写入的形式保存为 JSONL 文件，适合离线归档与外部分析。
- **计费**：提取用量数据，并根据单价规则折算为具体的费用。
- **自定义**：扩展插件可以按需订阅事件，构建自定义的监控与统计面板。

各消费者之间完全独立。单个消费者内部发生异常或写入阻塞时，不会影响其他消费者的正常运行。

## 轨迹页

控制台中的「轨迹」页面直接基于持久化后的数据展示，主要包含以下内容：

- 按会话顺序展示最近的交互记录。
- 点击特定会话，即可下钻查看某一轮对话的完整 `span` 调用树。
- 展开任意节点，查看详细的属性配置、输入输出摘要及报错堆栈。

在日常开发与排查时，轨迹页提供了几项实用的功能：

- **回放**：按时间轴顺序单步复现这一轮对话中的全部过程。
- **草稿重调**：抓取当时的请求快照并重新发起模型调用，方便对比调试提示词改动。
- **进程视图**：将并发执行的步骤与工具调用在时间线上并排铺开，耗时瓶颈一目了然。

::: tip
排查模型「为什么答非所问」时，最有价值的往往不是最终生成的回复文本，而是请求发出时实际装配的上下文内容。在轨迹详情中，你可以直接查看当时的提示词摘要、可用工具列表与模型推理参数，这也是定位问题的关键依据。
:::

## 用量

如果说轨迹展示的是单次请求的微观切片，那么用量就是轨迹数据的宏观聚合视图。

### 记什么

每次模型调用结束时，系统都会记录以下核心指标：

- 服务提供商与具体模型名称
- 调用的业务用途（如常规对话、条件判定、信息提取、上下文摘要等）
- 输入 Token、缓存读取 Token、缓存写入 Token、输出 Token 与推理 Token
- 是否采用流式传输
- 单次调用的总耗时
- 最终折算的费用成本

对于执行失败的模型调用，系统同样会记录流水；但只有在能明确识别提供商与具体模型时，才会进一步生成计费行。

### 成本从哪来

计费系统中的单价数据主要来自两个渠道：

- **配置的价格**：在计费插件或全局配置中手动填写的单价。
- **模型目录的价格**：服务提供商元数据清单中自带的官方基准价格。

结算时，系统会优先采用「配置的价格」。如果两处均未声明该模型的价格，本次调用的成本将记为 `0`，并将价格来源标记为「无」。

价格通常按每百万 Token 计算，针对输入、缓存读取与输出分别配置计费单价。

::: warning
用量系统计算出的成本仅为理论估算值，并不直接等同于实际账单。服务商的中转计费、阶梯折扣、限时促销以及缓存策略均可能导致实际扣费与估算存在偏差。如需精确对账，请以服务商官方后台账单为准。
:::

### 聚合

用量数据采用分级保留与聚合策略：单次调用明细会保留一段时间（默认 90 天），每日汇总数据则永久保留。

汇总统计支持按以下维度切分与下钻：日期、模型、用途以及会话。

通过这种设计，既能从宏观上了解「今天整体花费了多少额度」，也能精准回溯具体是哪个模型、哪项业务功能消耗了最多成本。

### 导出

系统支持将用量数据导出为 CSV 格式，方便进行成本审计或接入外部财务系统。

## 界面

控制台的用量看板包含以下模块：

- **概览卡片**：展示今日总花费、总请求数以及缓存命中率。
- **趋势图**：按时间维度展示费用与用量的波动曲线。
- **分组表**：支持按模型、会话与用途进行多维拆分统计。
- **明细**：单次模型调用的原始流水记录。

此外，控制台首页的仪表盘中也放置了一张精简的今日用量卡片，方便快速查看当天的调用概况。

## 与其他子系统的关系

用量与轨迹的统计并非孤立存在，它与内部多个子系统紧密协同：

- **缓存**：直接决定 Token 的计费类型。命中前缀缓存的上下文按相对低廉的缓存价计费，而非全额输入单价。
- **压缩**：上下文修剪与压缩会动态缩减历史消息长度，从而直接降低后续轮次的 Token 消耗。
- **子代理**：子代理属于独立的执行会话，用量单独统计，但在总账上会汇总到同一租户或账户下。
- **判定模型**：轻量判定逻辑（如意图识别、合规审查、唤醒判定等）同样会产生用量，建议选用轻量小模型以节约开销。

## 采样与开销

可观测性本身并非毫无代价。收集轨迹与用量同样需要占用序列化、数据库写入以及事件广播等系统开销。

在调用频率极高的场景下，可以通过以下方式控制开销：

- 仅持久化关键类型的 `span`
- 适当调低属性记录的详细粒度
- 适度缩短单次调用明细的保留期限

无需为了「留存所有记录」而永久保存所有底层的微观明细。

## 排查

排查轨迹与用量相关的异常时，可以按照以下条目进行核对：

- **轨迹页是空的**：先确认轨迹插件已正确加载并启用；检查后端数据库连接是否正常；最后确认对应的交互轮次中确实触发了实际的模型请求。
- **用量对不上**：优先核对当前模型的单价配置；检查缓存 Token 是否被底层适配器正确提取与记录；排查是否存在部分调用使用了未接入用量收集的第三方实例。
- **成本一直是 0**：说明既未在配置中指定模型单价，模型目录元数据中也缺少价格定义。只需在计费配置中补充该模型的单价即可。
- **某次调用没有被记录**：检查该次请求是否在进入执行管线前就已抛出异常；同时检查轨迹消费者在处理事件时是否有未捕获的报错。
- **数据太多，查询很慢**：建议缩短明细数据的保留周期，或在日常查询中仅使用预聚合的汇总视图。轨迹数据重在实时排查定位，不建议替代专门的长期冷数据归档。

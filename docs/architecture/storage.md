# 存储

::: tip
ChatLuna 的数据分三类：数据库里的结构化数据、数据目录里的文件、以及加密保存的凭据。三者用途不同，备份和排查方式也不同。
:::

会话、记忆、用量、权限、定时任务——这些东西都要落地。

但它们的形态不一样：会话是追加日志，权限是规则表，凭据是敏感文件。

所以存储没有做成一个大桶，而是分了几层。

## 数据库

默认用 SQLite，文件在实例数据目录下。

数据库服务本身是通用的：换一个驱动器就能换成别的库，上层只依赖表结构。

### 表

| 表 | 内容 |
| --- | --- |
| `chatluna_conversations` | 会话键与元信息 |
| `chatluna_sessions` | 会话日志的索引与分页 |
| `chatluna_files` | 内容寻址的文件（图片、附件） |
| `chatluna_user` | 平台用户与等级缓存 |
| `chatluna_channel` | 频道信息 |
| `chatluna_peers` | 路由用到的对端资料 |
| `chatluna_permission_user` | 用户等级 |
| `chatluna_permission_role` | 角色与继承 |
| `chatluna_permission_rule` | 权限规则 |
| `chatluna_permission_log` | 权限判定审计 |
| `chatluna_config_changes` | 配置变更记录 |
| `chatluna_registrations` | 运行时注册信息 |
| `chatluna_replay_experiments` | 轨迹重放的实验记录 |
| `chatluna_trace_spans` | 轨迹 span |
| `chatluna_usage` | 用量明细 |
| `chatluna_usage_daily` | 用量每日汇总 |
| `chatluna_character_state` | 角色状态变量 |
| `chatluna_schedule` | 定时任务 |
| `chatluna_schedule_run` | 定时任务执行记录 |

表会随插件启用而创建。

::: tip
看不到某张表，通常说明对应插件没启用。

数据库只在插件运行时扩展，不是预置的固定 schema。
:::

### 主键与索引

大多数表用自增整数主键，少数用字符串键。

索引按查询模式设计：会话按会话键与时间、用量按日期与模型、权限按动作与主体。

这决定了「按时间翻会话」「按月看花费」这类操作是否顺畅。

## 会话日志

会话表不存完整消息正文，而是存索引与分页位置。

正文在会话存储里，按追加日志组织。

这样做的原因是：

- 日志会不断增长，不适合每次全量读。
- 分页读取只需要知道位置。
- 压缩与分支是「位置操作」，不是「内容修改」。

## 文件

图片、附件这类二进制内容放在 `chatluna_files`。

写入时按内容哈希去重：同样的图片只存一份，多处引用指向同一条记录。

删除时不一定立刻清理，因为可能还有其他地方引用。清理通常由后台任务完成。

## 凭据

凭据不在数据库里。

它们存在数据目录下的一个 JSON 文件里，权限收紧（目录 0700，文件 0600）。

配置里只保存引用，例如 `{$credential: "xxx"}`。读取时再解析成真实值。

::: warning
凭据文件是明文 JSON。

它的安全性依赖文件权限与主机安全，而不是加密。备份时要么一起加密，要么单独处理。
:::

写入采用「临时文件 + 原子替换」：

1. 写一个新文件。
2. 落盘。
3. 重命名覆盖。

这样即使中途崩溃，也不会留下半截文件。

## 配置变更与快照

配置修改会留下记录。

部分插件（例如适配器）可以额外保存配置快照：每次修改前备份一份，改坏了可以回退。

快照目录是可选的，默认不开启。

## 向量存储

记忆与检索可能用到向量。

向量服务本身是抽象的：注册一个后端，才能使用。

没有后端时会明确报错，而不是静默退化为关键词搜索。

## 一致性与迁移

数据库 schema 由插件在启动时声明。

升级插件时，新字段会被补齐；旧数据保持兼容。

::: warning
跨大版本升级前先备份。

自动迁移通常只处理「加字段」这类兼容变化，结构性调整可能仍需要手动处理。
:::

## 备份

需要备份的是三个部分：

1. 数据库文件。
2. 数据目录（凭据、技能、工作区、快照）。
3. 配置清单。

做法：

- 停实例。
- 复制整个实例目录。
- 启动。

运行中直接复制数据库可能拿到不一致的状态。

## 清理与保留

数据会增长，需要策略：

- **用量明细**：默认保留 90 天，每日汇总永久保留。
- **轨迹**：按会话清理，或缩短保留期。
- **文件**：按引用计数清理。
- **会话**：删除会话时一并清理其日志。

::: tip
清理是排查「磁盘满了」时的第一站。

先看用量与轨迹的明细，它们通常是增长最快的。
:::

## 诊断

系统提供诊断命令，可以检查：

- 数据库能否打开。
- 表结构是否完整。
- 会话日志是否满足不变量。
- 凭据文件是否可读。

会话级诊断能发现「日志断档」「索引与正文不一致」这类问题。

## 排查

**数据没了。**

确认看的是正确的实例目录；确认没有被安全模式或恢复流程换过数据库。

**数据库被锁。**

通常是有另一个进程在用同一个文件。确认没有同时启动两个实例。

**磁盘增长很快。**

检查用量明细与轨迹保留期；检查文件表是否有大量未清理的附件。

**凭据读不出来。**

文件损坏或权限不对。看日志里的解密/读取错误；必要时重新配置凭据。

**升级后旧数据不兼容。**

从备份恢复，或者按发布说明做手动迁移。

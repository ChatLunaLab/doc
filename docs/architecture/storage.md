# 存储

::: tip
ChatLuna 的数据主要分为三类：数据库中的结构化数据、实例数据目录下的文件，以及凭据信息。三者的用途截然不同，备份策略与排查方式也各有侧重。
:::

在 ChatLuna 中，会话、记忆、用量统计、权限规则与定时任务等核心功能都需要持久化存储。

这些数据的形态与访问模式差异很大：会话本质上是顺序追加的日志，权限是关系型的规则表，而凭据则是需要严格保护的敏感文件。

因此，ChatLuna 没有将所有数据混在同一个存储中，而是划分了职责分明的多层存储结构。

## 数据库

ChatLuna 默认使用 SQLite 作为底层数据库，数据文件统一保存在实例数据目录下。

数据库服务采用了通用与解耦的设计：只需更换底层数据库驱动，即可自由迁移至其他受支持的数据库，上层业务逻辑仅依赖规范的表结构定义。

### 表

| 表 | 内容 |
| --- | --- |
| `chatluna_conversations` | 会话键与元信息 |
| `chatluna_sessions` | 会话日志的索引与分页 |
| `chatluna_session` / `chatluna_session_header` / `chatluna_session_entry` | 会话日志的存储实现 |
| `chatluna_files` | 内容寻址的文件（图片、附件） |
| `chatluna_peers` | 路由用到的对端资料 |
| `chatluna_permission_user` | 用户等级 |
| `chatluna_permission_role` | 角色与继承 |
| `chatluna_permission_rule` | 权限规则 |
| `chatluna_permission_log` | 权限判定审计 |
| `chatluna_config_changes` | 配置变更记录 |
| `chatluna_registrations` | 运行时注册信息 |
| `chatluna_replay_experiments` | 轨迹重放的实验记录 |
| `chatluna_trace_spans` | 轨迹 span |
| `chatluna_usage` | 用量明细 |
| `chatluna_usage_daily` | 用量每日汇总 |
| `chatluna_character_state` | 角色状态变量 |
| `chatluna_schedule` | 定时任务 |
| `chatluna_schedule_run` | 定时任务执行记录 |

数据库中的表不是一次性全部创建好的，而是由各插件在启用时按需动态创建。

::: tip
如果你在数据库中看不到某张表，通常说明提供该功能的插件尚未启用。

数据库只在插件运行时按需注册并扩展，不会在启动前预设固定的表结构。
:::

### 主键与索引

在主键设计上，大多数表使用自增整数作为主键，少数自带业务标识的表则采用字符串键。

所有索引均围绕核心查询场景设计：例如会话表基于会话键与时间戳建立索引、用量表基于日期与模型建立索引、权限表基于动作与主体建立索引。这些索引能够确保「按时间检索会话记录」「按月份统计模型调用花费」等高频操作高效响应。

## 会话日志

会话主表不直接存储完整的消息正文，仅记录索引与分页游标位置。

消息的实际正文保存在会话存储中，底层按追加日志（Append-only Log）的形式组织。这种设计主要出于以下考量：

- **避免全量读取**：日志会随交互持续增长，全量读取会带来极大的 I/O 与内存开销。
- **高效分页访问**：流式加载与分页读取只需知道起始和结束位置，即可按需截取。
- **轻量维护历史**：上下文压缩与会话分支本质上是游标层面的位置操作，无需高成本地修改实际内容。

## 文件

图片、音频及附件等富媒体二进制内容统一保存在 `chatluna_files` 表中。

写入文件时采用基于内容哈希的去重机制：即使同一张图片在多个会话中被多次发送，底层也只会保存一份文件实体，所有引用均指向同一条文件记录。

因此，删除消息时并不一定会立即清理物理文件，因为其他地方可能仍在引用该内容。物理文件的清理通常交由后台定时任务异步完成。

## 凭据

敏感的 API 密钥与凭据不会保存在数据库中。

它们独立保存在实例数据目录下的专属 JSON 文件中，并通过严格的文件权限进行保护（目录权限为 `0700`，文件权限为 `0600`）。

插件配置中仅保存对凭据的引用占位，例如 `{$credential: "xxx"}`。只有在运行时发起网络调用时，系统才会将其动态解析为真实密钥。

::: warning
凭据文件本身为明文 JSON 格式。

它的安全性完全依赖于宿主机的文件系统权限与主机安全，而非应用层的可逆加密。在备份实例时，你可以将其与整个数据目录一同加密备份，或者将其单独妥善处理。
:::

为了防止写入过程中断电导致配置损坏，凭据写入流程采用了标准的「临时文件 + 原子替换」方案：

1. 先在同一目录下写入临时新文件。
2. 将数据完整同步落盘。
3. 通过文件系统的原子重命名操作覆盖旧文件。

这样一来，即使写入过程中发生意外崩溃，也不会留下损坏的半截文件。

## 配置变更与快照

系统会记录所有的配置修改。

部分核心插件（例如平台适配器）还支持保存配置快照：在每次配置修改前自动备份快照，若因误配置导致故障，可以随时回退。

快照目录属于可选特性，默认不开启。

## 向量存储

在处理长期记忆与外部知识库检索时，往往需要依赖向量检索能力。

ChatLuna 的向量服务本身是纯抽象接口层：只有在运行时注册了具体的向量后端，上层功能才能正常工作。

如果在没有可用后端时调用了向量能力，系统会明确报错，而不是静默降级为简单的关键词搜索，确保行为符合预期。

## 一致性与迁移

数据库表结构由各插件在启动阶段主动声明。

在升级插件时，底层数据库框架会自动检测并补齐新字段，同时保持与现有旧数据的兼容。

::: warning
在执行跨大版本升级前，请务必先做好数据备份。

自动迁移机制通常仅处理「追加字段」这类向后兼容的增量变更。如果涉及表结构重构或破坏性调整，可能仍需根据版本指引手动处理。
:::

## 备份

为了完整恢复一个 ChatLuna 实例，通常需要备份以下三部分内容：

- **数据库文件**：保存结构化数据、表索引与会话游标。
- **数据目录**：包含敏感凭据、技能扩展、工作区及快照等文件。
- **配置清单**：包含实例全局配置与插件启停列表。

推荐的冷备份流程如下：

1. 停止当前运行的实例进程。
2. 完整复制整个实例目录。
3. 重新启动实例。

在实例运行过程中直接复制数据库文件（尤其是 SQLite），可能会因为 WAL 写入或未落盘缓存而获取到不一致的损坏数据。

## 清理与保留

随着机器人持续运行，持久化数据会不断增长，因此需要配合合理的生命周期策略：

- **用量明细**：默认保留 90 天，每日汇总数据则永久保留。
- **轨迹**：按会话定期清理，或根据配置缩短保留期。
- **文件**：基于引用计数机制定期清理无引用的孤立附件。
- **会话**：删除会话时，系统会一并级联清理底层关联的会话日志。

::: tip
清理历史明细是排查「磁盘空间耗尽」时的第一步。

排查时建议优先查看用量明细与轨迹数据，它们通常增长最快、占用空间也最大。
:::

## 诊断

ChatLuna 提供了内置的存储诊断工具与命令，可以自动检查以下健康指标：

- 数据库文件能否正常打开与读写
- 已注册插件的表结构与字段是否完整
- 会话日志是否满足追加与游标的不变量约束
- 凭据文件路径与权限是否可读

通过深入到会话级别的诊断，能及时发现「日志断档」「索引游标与日志正文脱节」等潜在的数据一致性问题。

## 排查

在日常维护与开发过程中，如果遇到存储相关的问题，可以参考以下清单进行排查：

**数据丢失**

请首先确认当前启动加载的是否为正确的实例数据目录；检查实例是否曾因意外崩溃触发了安全模式，或在恢复流程中被自动切换为了备用数据库。

**数据库被锁**

通常是因为有另一个进程正在占用同一个数据库文件。请检查后台是否有残留的旧进程尚未退出，并确认没有同时启动两个使用相同数据目录的实例。

**磁盘增长过快**

检查用量明细与调用轨迹的保留期限设置；检查 `chatluna_files` 表中是否存在大量未被引用的过期附件尚未清理。

**凭据读取失败**

通常是文件损坏或文件系统访问权限不正确。请查看控制台与运行日志中的读取或解密报错信息；必要时可在管理界面中重新配置并保存凭据。

**升级后旧数据不兼容**

建议先从先前创建的备份中恢复数据，并对照对应版本的发布说明（Release Notes）手动进行数据迁移或结构修复。

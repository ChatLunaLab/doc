# 接口与 SDK

::: tip
ChatLuna 完全可以脱离聊天平台独立运行并供外部程序调用。其底层暴露了标准的 HTTP 接口与实时流，而官方 SDK 则是基于这些接口的一层轻量薄封装。
:::

细心的小伙伴可能会发现，ChatLuna 自带的 Web 控制台本质上也是这套接口的调用者之一。

正因如此，你完全可以在脚本、CI 自动化流水线或是自建的业务应用中完成相同的操作：创建会话、投递消息、读取回复、统计用量以及管理预设。

## 认证

所有受保护的接口都需要在调用时提供有效的访问令牌（Token）。

ChatLuna 目前支持两种鉴权传递方式：

- **请求头**：在 HTTP 请求头中直接携带令牌进行身份认证。
- **会话**：先使用令牌换取短期有效的会话凭据，再将其附加到后续的接口请求中。

在服务端，包含接口与管理界面的路径前缀默认受到安全中间件的保护，任何未通过认证的请求都会被直接拒绝。

::: warning
访问令牌拥有与控制台相同的管理权限。

请切勿将令牌硬编码在前端代码、提交到公开仓库或发送至聊天记录中，否则相当于将整个实例的控制权拱手相让。所有外部调用均建议部署在受信的服务端环境中执行。
:::

## 会话接口

会话（Session）是外部调用时的核心概念：它代表了一次独立的对话，也是持久化上下文的承载单元。

ChatLuna 提供了以下会话相关的核心接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/agents` | 列出可用的 Agent 分组 |
| GET | `/api/sessions` | 分页列出会话 |
| POST | `/api/sessions` | 创建会话 |
| DELETE | `/api/sessions/:id` | 删除会话 |
| GET | `/api/sessions/:id/messages` | 读取消息 |
| POST | `/api/sessions/:id/messages` | 发送消息 |
| POST | `/api/sessions/:id/steer` | 在回合中途补充输入 |
| POST | `/api/sessions/:id/cancel` | 取消当前回合 |
| POST | `/api/sessions/:id/fork` | 从当前会话分叉 |
| POST | `/api/sessions/:id/compact` | 压缩上下文 |
| GET | `/api/sessions/:id/events` | 事件流 |
| GET | `/api/sessions/:id/live` | 实时流 |

### 创建会话

调用创建会话接口时，你可以根据需要显式指定会话标题、使用的预设以及目标模型。

如果请求中未提供这些参数，系统将会回退并使用当前全局配置中的默认值。

### 发送消息

向会话发送消息的操作是异步进行的：接口在成功接纳消息后会立即返回响应，而模型生成的回复则需要通过实时流或事件流获取。

因此在调用时，切勿把「接口已返回 HTTP 响应」当成「模型已经回答完毕」。

### 分页

所有的列表查询接口均采用游标分页，而非传统的页码分页。

这样设计的目的是为了确保在数据动态变动时依然保持结果一致：在分页拉取时，即使有新记录写入，翻页过程也不会出现重复或遗漏。

## 实时流

针对长连接与实时数据推送场景，系统提供了两条独立的流通道：

- **事件流**：专注于会话级别的细粒度事件，包含当前状态变化、回合推进以及工具调用等完整的运行时信息。
- **实时流**：面向外部应用程序设计的简化版数据流，适合轻量消费，但暴露的能力相对有限。

采用流式响应最大的好处在于无需客户端持续轮询，模型生成的部分 Token 一旦到达便能立即获取。

需要注意的是，流连接会定期发送心跳以维持存活；若连接长时间无响应，服务端将主动将其断开。

## 幂等

所有涉及资源变更的写接口均支持传入幂等键。

当携带同一个幂等键重复提交时，服务端会直接返回首次处理的结果，而不会再次触发执行。

这在网络超时与故障重试场景下非常关键：当客户端因网络超时无法确定请求是否成功时，可以安全地发起重试而不用担心产生重复副作用。

## 错误

服务端返回的错误响应拥有统一的 JSON 数据结构：

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "invalid input: model"
}
```

值得注意的是，成功的接口调用不会包裹额外的状态信封，返回体就是请求的目标资源本身（例如会话列表、会话详情或压缩结果等）。

常见的业务错误码如下：

| 码 | 含义 |
| --- | --- |
| `INVALID_ARGUMENT` | 参数不合法 |
| `UNAUTHORIZED` | 未认证或令牌失效 |
| `FORBIDDEN` | 已认证但无权执行 |
| `NOT_FOUND` | 资源不存在 |
| `PRECONDITION_FAILED` | 状态不允许，例如插件未安装 |
| `CONFLICT` | 并发冲突，例如会话被别处修改 |

系统将 HTTP 状态码与业务错误码进行了明确分离：状态码负责反映 HTTP 传输层面的成败，而错误码则清晰指明具体的业务原因。

## SDK

官方 SDK 是对底层接口的一层轻量薄封装：

```ts
const sdk = new ChatLunaSDK({
  baseUrl: 'http://127.0.0.1:5028',
  token: process.env.CHATLUNA_TOKEN,
})

const { sessionId } = await sdk.createConversation('脚本任务')
await sdk.sendMessage(sessionId, '帮我总结一下这个文件')
const conversations = await sdk.listConversations()
const usage = await sdk.getUsage()
```

细心的小伙伴可能会发现，SDK 的实现非常纯粹，它主要只做了三件事：拼接 API 地址、附加认证令牌、以及统一解析错误。

SDK 内部不维护隐藏状态，也没有内置本地缓存——所有的状态数据均严格以服务端为准。

### 能力探测

在发起调用前，SDK 支持先向服务端查询当前环境所支持的具体能力（如实时流协议版本、流地址以及帧类型），以此决定采用哪条路径。

这种基于特性探测的设计，比直接假设「服务端一定存在某个接口」更加稳健。

需要说明的是，虽然客户端 SDK 声明了会话、路由与用量等一系列方法调用，但服务端是否实际提供对应的 SDK 路径取决于具体的版本与启用的插件组合。接入前建议通过能力协商进行确认，而不要仅凭客户端方法名推断接口一定可用。

## 典型用法

### 脚本与自动化

你可以在 CI 流水线中调用接口跑一次测试对话，用于自动化检查输出内容。

也可以配合定时任务定期触发总结，并将结果自动发送到其他下游服务。

### 自定义前端

如果你不想使用自带的控制台，完全可以基于这套接口自行构建个性化的聊天界面。

会话管理、消息交互以及流式输出能力都是现成的，直接对接即可。

### 桥接其他平台

你还可以将其他平台的消息桥接转发进来，并将处理后的回复再转发展出。

需要注意，这种接入方式会绕过 ChatLuna 原生的平台适配器，像消息编辑、撤回等平台特定特性需要由你自行实现。

### 数据导出

通过接口读取会话记录、用量统计以及执行轨迹，你可以轻松对接自有系统并制作报表。

## 安全

在部署与使用接口时，建议遵循以下安全规范：

- 仅在局域网内网或本机回环地址暴露接口。
- 公网环境下的访问务必置于反向代理与 HTTPS 加密之后。
- 遵循最小权限原则妥善管理访问令牌。
- 对外部输入的会话 ID、文件名等参数进行严格校验，切勿直接拼接路径。

::: warning
这套接口具备创建会话以及触发工具调用的完整能力。

切勿将其当成无害的「只读 API」暴露给不可信的调用方。
:::

## 排查

在对接或调用过程中遇到异常时，可参考以下要点排查：

**401 状态码**
令牌错误或已过期。检查请求头中的传递格式是否正确，并核对令牌来源（配置项、环境变量或数据目录中的凭证）。

**403 状态码**
认证已通过但无权执行当前操作。检查请求路径是否处于受保护前缀之下，以及对应动作是否被权限系统拒绝。

**创建会话失败**
检查请求中指定的预设与模型是否可用，并确认相关依赖插件是否均处于正常加载状态。

**发送消息后没有回复**
确认实时流或事件流连接是否已正常建立；检查该轮次是否被中间件规则判定为忽略；必要时查看轨迹日志排查流转断点。

**收到重复消息**
请求未携带幂等键，导致重试被服务端执行了多次。请在写操作请求中补上唯一的幂等键。

**列表翻页时出现重复数据**
翻页时使用了基于偏移量的页码，而非游标。请使用服务端返回的游标继续请求后续分页。

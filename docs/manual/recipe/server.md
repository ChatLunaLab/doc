# 公网部署

::: tip
先说结论：千万不要直接将实例端口暴露在公网上！稳妥的做法是将其置于反向代理之后，开启 HTTPS 加密，并配置足够强度的访问口令。
:::

在完成了本地环境的部署与测试后，很多小伙伴会迫不及待地想要将控制台开放到公网，以便在任何地方随时管理机器人。

然而，在默认情况下，控制台只允许来自本地回路地址的访问请求。

这并非疏忽，而是出于安全考虑的刻意设计。控制台拥有极高的权限：它可以自由安装插件、修改系统配置、调用底层接口乃至执行命令。换句话说，拥有控制台权限在很大程度上等同于直接掌控了这台服务器本身。

如果将这样一个高权重的管理界面毫无防护地直接暴露给外部网络，无异于将服务器的 root 密码张贴在公共公告板上。

因此，在对外提供远程访问服务之前，请务必花几分钟读完这一页，为你的机器人构筑一道可靠的安全屏障。

这也是为什么我们在默认状态下对外部请求抱有极高警惕的原因。
为了确保部署过程条理清晰，我们不妨先理清整体脉络：

## 三道门

对外开放控制台并不是简单地做一次端口映射，而是需要同时构建三道相互依存的防线：

1. **谁能访问**：来源限制与访问令牌。
2. **怎么访问**：反向代理与 HTTPS 加密传输。
3. **访问了能做什么**：权限等级划分与敏感操作审批。

这三道防线层层递进：只要其中任何一项缺位，另外两项的保护能力都会大打折扣。

举例来说，哪怕口令设得再长再复杂，一旦缺乏 HTTPS 保护，凭据就会在明文网络传输中被轻易窃听；而哪怕网络边界把控得再严密，倘若访问令牌过于脆弱，攻击者也能轻而易举地暴力破解进入。

因此，只有把三道门全部妥善关好，公网上的控制台才能真正让人安心。

## 访问令牌

先说结论：登录控制台必须使用访问令牌，它是进入系统的首要钥匙。为了兼顾灵活性与安全性，系统提供了三种令牌来源，其生效优先级从高到低依次为：

- **配置项指定**：在服务插件配置中填写的令牌具有最高优先级。一旦在此处设定，系统便只认该令牌。
- **环境变量指定**：当配置项中未显式填写时，系统会尝试读取环境变量 `CHATLUNA_TOKEN`。
- **自动随机生成**：若前两者均未提供，实例在首次启动时会自动生成一个高强度的随机令牌，将其安全地写入本地数据目录，并在启动日志中打印一次带该令牌的快速登录链接。

自动生成的令牌只会在首次启动的运行日志中打印一次，日志中也会同时附带完整的快速登录地址。

初次登录成功后，我们强烈建议你前往「设置」页面，将其修改为一个便于记忆且强度达标的自定义强口令。

::: warning
系统内置了严格的令牌强度校验规则，弱口令会被直接忽略。

如果你在配置项或环境变量中填入了一个过于简单、无法满足强度规则的弱口令，系统不仅不会采用它，还会自动回退到数据目录中保存的旧令牌，并在运行日志中打印一条错误提示。

看到该错误时，千万不要误以为新令牌已经生效，请务必以日志提示为准。
:::

这里有一个容易被忽略的细节：**一旦令牌由配置项或环境变量固定，就无法在控制台界面中直接修改**。

此时如果在界面上尝试保存新口令，系统会明确提示该令牌已被外部来源固定并拒绝修改。

想要更换此类固定令牌，你必须去修改对应的配置文件或外部环境变量，随后重启实例才能生效。

另外需要特别注意：每次修改访问令牌都会使之前所有已建立的登录会话全部失效。

这是我们特意设计的安全机制——一旦怀疑口令在某个渠道泄露，改掉它就能在第一时间强制踢掉所有在线访客，确保系统安全。

那么，既然可以通过配置来控制访问，为什么我们平时还是反复强调令牌的安全管理呢？

::: tip
访问令牌在权限上等同于主人权限，但这并不代表它「永远安全」。

切勿将令牌随手写在公开脚本、代码仓库、CI 环境变量或聊天记录中。实际使用时应当通过受保护的安全变量读取，避免硬编码带来不必要的泄露风险。
:::

## 允许远程访问

先说结论：光配置好访问令牌还不够，实例在默认状态下依然会坚决拒绝来自非本机的任何访问请求。

这是因为配置项 `allowRemote` 的默认值为 `false`。系统秉持安全默认原则，即便你的端口已经映射到了外部网卡，只要该项未开启，所有远程连接依然会被一视同仁地阻断。

为了让外部网络能够顺利连接，你需要在服务插件配置中显式将「允许远程访问」开关打开，或者在启动时通过环境变量启用该选项。

如果不打开该开关，即便外部反向代理配置完全正确，实例也会直接拒绝该请求，并向客户端返回明确的禁止访问提示。

::: danger
在打开远程访问开关之前，请务必在心中完成两项重要确认：

第一，当前使用的访问令牌是一串经过验证的强口令，且绝非默认值。  
第二，所有涉及核心管理与接口调用的路径，均已明确包含在受保护前缀中。

控制台拥有安装 npm 包与调用底层系统的能力，这意味着它具备执行任意代码的可能。向公网暴露一个未受周全保护的控制台，无异于直接向外部交出服务器的掌控权。
:::

### 受保护前缀

为了区分公开内容与受限资源，服务在默认情况下保护两个路径前缀：接口路径 `/api` 与控制台管理路径 `/console`。

所有落在这两个前缀之下的网络请求，都必须携带合法有效的访问令牌或认证状态。除此之外的路径则属于公开访问区，例如用于加载前端界面静态资源的静态文件路径。

如果你在后续使用中通过插件扩展了自定义的管理页面或专属接口，请务必记得将新的路径前缀也一并追加到受保护前缀列表中，否则它们将在公网中处于裸奔状态。

更严格的是，系统的内置自检机制还会对此类风险进行强校验。

一旦实例加载了控制台相关插件，却未将控制台路径纳入受保护前缀，执行诊断命令时将直接报错。系统正是用这种强硬的方式，阻止因一时疏忽而酿成的严重安全隐患。

## 反向代理

先说结论：千万不要把实例监听的真实端口直接暴露在公网上。最推荐的做法是在前端架设一层反向代理（例如 Nginx、Caddy 或 Traefik），由反代统一负责证书管理与 TLS 终止，再将请求转发给本地运行的实例。

在为控制台配置反向代理规则时，必须同时满足以下四个核心要素：

- **转发真实客户端地址**：务必在转发请求中带上 `X-Forwarded-For` 与 `X-Real-IP` 等请求标头。否则在实例看来所有访问都来自本地回环地址，导致日志审计与来源访问控制彻底失效。
- **支持协议升级机制**：控制台的动态轨迹、运行日志以及聊天流式推送高度依赖长连接。代理服务器必须正确透传协议升级标头，把标准 HTTP 请求平滑升级为 WebSocket 长连接。
- **配置充裕的超时时间**：控制台的长连接在用户待机时可能会长时间处于空闲状态。代理端的读取与发送超时时间必须设置得足够长，防止空闲长连接被反代机制提前掐断而引发重连风暴。
- **关闭代理响应缓冲**：实时消息推送要求产生的数据即刻下发。代理端必须显式关闭响应缓冲，否则原本流畅的流式打字输出会被缓冲机制积攒成大块内容一次性蹦出。

::: warning
在反向代理配置中，最常见的问题往往不是页面彻底打不开，而是「登录一切正常，界面也能加载，但聊天不出新消息、轨迹和日志不刷新」。

如果遇到这种现象，请优先排查协议升级标头是否被正确透传，以及代理响应缓冲是否已经彻底关闭。
:::

反向代理配置完毕后，还有一个我们必须直面的核心问题：传输加密。

### HTTPS

先说结论：所有的 TLS 证书申请、加载与自动续签工作都应当交由反向代理统一管理，切勿让实例自身去处理繁琐的证书逻辑。

这样做的好处非常明显：证书轮换、现代加密套件协商以及 HTTP/2 等协议优化全部收敛在反向代理这一层处理，实例只需在本地保持标准明文监听，专注于核心业务逻辑。

如果你觉得手动申请和配置证书较为繁琐，可以考虑选用自带自动证书申请能力的代理工具。

这类工具能够全自动完成证书的签发与续期，大大减轻后续的运维负担。

解决了证书问题之后，有些小伙伴可能还会遇到特殊的网络架构需求：

### 子路径部署

如果你希望将控制台部署在域名的某个子目录之下（例如挂载在特定的 URL 子路径后），则需要同时对反向代理的重写规则与实例的基础路径配置进行协同修改。

完成配置调整后，请务必仔细验证静态资源文件、API 接口调用以及实时长连接能否在新的子路径下和谐工作。

::: tip
子路径部署最容易踩坑的地方在于路径前缀的拼接。

部署完成后如果在浏览器中遇到页面白屏或样式缺失，只需按下 F12 打开开发者工具的网络面板，观察到底是哪个资源文件请求返回了 404，往往就能一眼看出路径拼接偏差的位置。
:::

## 不开放的替代方案

先说结论：如果你只是个人偶尔需要远程查看机器人状态或排查问题，完全没有必要大费周章地向公网开放端口。借助以下两种替代方案，同样可以安全高效地完成远程访问。

接下来让我们逐一看看后两者的具体用法。

### SSH 隧道

在本机终端中建立一条简单的本地端口转发通道，就能把远程服务器上实例监听的内部端口，安全地映射为你本地机器上的一个端口。

此时，在本地浏览器中直接访问该端口，使用体验与在服务器本机打开控制台完全一模一样。

这种方式的优点极其突出：不需要域名，不需要配置证书，也不需要修改实例的远程访问开关与安全组端口策略。

排错完毕后随手断开 SSH 会话即可，干净利落且不留任何安全隐患。对个人用户而言，这是性价比最高的方案。

如果觉得每次打开终端输入隧道命令还是有些繁琐，或者设备都在内网中，我们还可以考虑第二种方式：

### 内网访问

如果你的管理设备与机器人实例原本就处于同一个家庭局域网或公司内网中（例如部署在家用 NAS 或本地软路由上），直接使用内网局域网 IP 进行访问即可，完全无需暴露在公网上。

如果需要出门在外时也能访问，更推荐的做法是在局域网内搭建私有 VPN 节点（如 WireGuard 或 Tailscale）。

在外网时先接入安全隧道，再像在家中一样直接发起访问，既能从容满足移动访问需求，又能将外部公网扫描工具彻底隔绝在外。

## 与其他安全措施的关系

先说结论：控制台只是整个系统的入口大门。一旦用户通过鉴权进入系统内部，具体能够执行哪些敏感操作，则由底层的权限系统全权把关。

在将控制台推向外部网络时，建议与以下几项安全策略做好联动检查：

- **权限等级模式**：为不同角色的访问者划分严谨的权限等级，切勿默认将最高控制权限赋予普通访客账号。
- **敏感工具策略**：对于命令执行、文件写入等具备破坏力的工具调用，务必保持处于需要人工审批确认的状态。
- **审批责任人**：确认系统中至少存在一位具备足够权限的管理员账号能够正常接收并处理审批请求。
- **审计日志追踪**：保持运行日志处于记录状态，确保关键操作均有迹可循，以便在发生非预期行为时能够快速回溯排查。

关于权限等级的具体划分方式以及工具调用的审核流转机制，请参阅[权限与安全](../usage/permissions)与[工具](../usage/tools)两节的专门说明。

## 上线检查清单

在正式向外部网络提供访问服务之前，请对照以下清单逐条核对，确认每一项防御措施均已妥善就位：

1. 访问令牌是一串高强度密码，且其配置来源清晰明确（配置项、环境变量或数据目录三选一）。
2. 已显式将 `allowRemote` 选项开启，允许接收经由外部转发的访问请求。
3. 接口路由 `/api` 与控制台路由 `/console` 均已被纳入 `protectedPrefixes` 受保护前缀中。
4. 反向代理服务已正确配置并启用了合规的 HTTPS 加密证书。
5. 反向代理正确传递了真实的客户端来源地址标头与 WebSocket 协议升级标头。
6. 长连接超时时间设置充裕，且代理端的响应缓冲机制已明确关闭。
7. 执行系统诊断命令确认整体运行状况良好，未出现受保护路由缺失等配置警报。
8. 已借助手机移动网络或另一台外网机器，完整模拟并成功通过了一次真实的远程鉴权与登录测试。

## 排查

在公网部署与反代对接的过程中，偶尔可能会遇到一些连接与鉴权异常。我们整理了几个最具有代表性的故障场景与排查方向：

**打开域名后浏览器直接提示 403 Forbidden。**

遇到这种情况时，请首先确认是否在服务插件配置中开启了「允许远程访问」（即 `allowRemote`）。如果确认已经开启，接着检查反向代理是否正确透传了真实来源 IP 标头——因为实例的来源判定逻辑高度依赖这一信息。

**控制台登录一直失败，提示口令错误。**

请检查访问令牌的实际来源与运行日志。如果你此前在配置项或环境变量中填入了一个过于简单的弱口令，系统会在启动日志中提示「忽略弱令牌」并自动回退至数据目录下的随机令牌，导致你自以为生效的口令实际上未被采用。

**页面能够顺利打开，但聊天数据与轨迹完全不刷新。**

这几乎一定是反向代理在长连接环节出现了差错。请检查反向代理配置中是否遗漏了长连接协议升级标头，或者代理响应缓冲处于开启状态，导致推送数据滞留在了代理层。

**修改访问令牌后，所有正在使用中的用户都被登出。**

不必担心，这属于符合预期的正常设计。修改令牌会自动作废之前签发的所有会话凭证，通知相关成员使用新配置的高强度口令重新登录即可。

**在子路径模式下访问时遭遇白屏或样式混乱。**

这通常是静态资源路径拼接错误造成的。请打开浏览器网络面板检查加载失败的文件地址，对比实例配置的基础路径与反向代理中的路由重写规则，确保两者对前缀的约定完全一致。

**担心公网开放后被恶意自动化脚本扫描探测。**

即便已经部署在公网上，我们依然强烈建议你在反向代理层额外叠加防护手段。例如在代理端设置来源 IP 白名单、前置 HTTP Basic 认证，或是配合 VPN 接入，尽可能将可能遭受攻击的暴露面降到最低。

# 多实例与多机器人

::: tip
这一页回答一个部署问题：想要多个机器人时，是开多个 ChatLuna 进程，还是在一个进程里接多个账号？
:::

答案取决于你想隔离什么。

如果你只是想让同一个机器人换不同的人设、在不同群里用不同的模型，一个进程就够。

如果你要的是两套完全独立的记忆、数据和配置，比如一个给公司用、一个给自己用，那就该开两个实例。

## 两种做法的区别

| 做法 | 适合 | 代价 |
| --- | --- | --- |
| **单实例多账号** | 同一个主人、不同群不同角色；多平台共用一套配置 | 数据共享，误操作会互相影响 |
| **多实例** | 不同业务、不同主人、完全隔离 | 每个实例都要单独启动、升级和占端口 |

单实例是最常见的做法。你在「聊天平台」页接几个账号，在场景规则里按账号分流，就完成了。

多实例更像「两个机器人公司」：各自有独立的目录、独立的数据库、独立的 WebUI 端口。

## 多实例是怎么组织的

ChatLuna 的命令行工具会把所有实例放在用户目录下的 `.chatluna/instances` 里，每个子目录就是一个实例。

一个实例目录里至少有两样东西：一份依赖清单和一份配置清单。它们决定了这个实例装了什么、加载了什么。

除此之外，每个实例还有自己的数据目录，里面装着会话、记忆、凭据和插件配置。

所以「隔离」是目录级的：删掉一个实例目录，不会影响另一个。

### 常用命令

- `chatluna create <名字>`：创建一个实例。
- `chatluna start <名字>`：在后台监管进程下启动。
- `chatluna list`：列出所有实例及其运行状态。
- `chatluna stop <名字>`：停止。
- `chatluna restart <名字>`：重启。
- `chatluna dev <目录>`：以开发模式启动某个目录，带热更新。

不带名字直接运行时，会启动默认实例。默认实例的名字记录在用户目录下的启动器配置里，创建第一个实例时会自动写入。

::: tip
`chatluna list` 会显示每个实例的进程号、版本和目录。

排查「到底是哪个实例在响」时，这条命令比翻日志快。
:::

### 端口必须错开

每个实例的 WebUI 都需要一个端口，默认都是 5028。

同时启动两个实例时，第二个会因为端口被占用而启动失败。所以多实例部署的第一步，是给每个实例指定不同的端口。

端口在实例自己的配置清单里改，不需要动全局设置。

::: warning
端口冲突的表现不一定很直观：有时实例启动了，但 WebUI 打不开；有时直接在启动日志里报错退出。

多实例部署时，先确认每个实例的端口互不相同，能省掉很多排查。
:::

## 安装、升级与修复

命令行工具不只负责启动，还负责维护实例：

- **安装插件**：往指定实例里安装依赖。
- **移除插件**：卸载依赖。
- **链接本地插件**：开发时把本地目录链接进实例。
- **更新**：更新启动器和实例插件，会先做快照、健康检查，失败自动回滚。
- **修复**：实例起不来时，收集诊断信息并尝试一次本地修复。
- **报告**：查看最近一次修复的报告。

这套机制的价值在于「可回退」。改配置或升级插件把实例弄坏了，先看修复报告，再决定是回滚还是手改。

::: tip
`update` 和 `repair` 都会在实例目录里留下记录。真出问题时，这些记录比你的记忆可靠。
:::

## 数据备份

多实例部署时，最容易忽略的是备份。

需要备份的东西都在实例目录里：

- 配置清单与依赖清单。
- 数据目录（会话、记忆、凭据）。

备份的方式很简单：停掉实例，把目录整体复制一份，再启动。

::: warning
不要在实例运行中直接复制数据目录。

数据库可能有未落盘的内容，复制出来的备份不一定完整。停实例再备份，是最稳妥的做法。
:::

## 怎么选

### 同一个人，多个群

用单实例。

在场景规则里按群配置模型、角色和工具，比养多个实例省事得多。

### 多个平台账号

用单实例。

聊天平台页可以同时接多个账号，场景规则能按平台和账号分流。

### 公司和自己

用多实例。

两边的人、数据、权限完全不同，共享一个进程只会让权限配置越来越难维护。

### 测试与正式

用多实例。

测试实例可以随便装插件、改配置，甚至跑坏；正式实例保持干净。

### 给不同客户交付

用多实例。

每个客户一份目录、一个端口、一套数据，互不可见。

## 推荐配置

### 单人维护两个实例

给它们起能看懂的名字，比如 `family` 和 `work`。

端口分别设成 5028 和 5029，把各自的启动命令写进系统服务，避免忘记启动。

设置里各用各的口令，别图省事共用。

### 实例很多

按业务分组，每组一个实例，不要「一个群一个实例」。

实例本身的启动开销不大，但升级、排错、备份的成本会随数量线性上升。

### 开发与生产并存

开发用 `dev` 模式启动，主目录和正式实例分开。

开发实例可以链接本地插件源码，正式实例只装发布版本。

## 排查

**启动报端口被占用。**

改这个实例的端口，或者先停掉占用端口的进程。多实例部署时这是最常见的启动失败原因。

**WebUI 打开的是另一个实例。**

端口串了。回到命令行确认这个实例实际监听的端口。

**实例列表里有，但启动不起来。**

先看启动日志，再运行修复。多数情况是依赖没装全，或者配置清单被改坏。

**两个实例的数据混在一起了。**

检查它们是否真的指向不同的数据目录。用 `--dir` 参数启动时，尤其容易指错目录。

**更新后行为全变了。**

更新会升级插件版本，行为变化是正常的。想回到旧版本，用更新时留下的快照回滚。

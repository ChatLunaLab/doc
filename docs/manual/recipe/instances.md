# 多实例与多机器人

::: tip
本节将解答一个常见的部署疑问：当你需要多个机器人时，究竟是启动多个 ChatLuna 进程，还是在一个进程里接入多个账号？
:::

答案取决于你想隔离什么。

如果你只是希望同一个机器人在不同群里扮演不同角色、使用不同模型，单进程便完全够用；但如果你需要两套完全独立的人设记忆、凭据数据与运行配置（例如一个供个人娱乐、一个供团队办公），则应当创建独立的实例。

运行 `chatluna list` 会列出 `~/.chatluna/instances` 下的所有实例，每行依次显示名称、运行状态与所在目录：

```text
$ chatluna list
default	running (pid=41522) @chatluna/cli@2.0.0-alpha.0	/home/me/.chatluna/instances/default
work	stopped	/home/me/.chatluna/instances/work
```

## 两种做法的区别

我们可以先通过下表对比两种方案：

| 做法 | 适合场景 | 代价与注意事项 |
| --- | --- | --- |
| **单实例多账号** | 同一个管理者；不同群需要不同人设；多平台共用同一套配置 | 数据全局共享，误操作或崩溃会波及所有账号 |
| **多实例** | 独立业务线；不同归属人；需要彻底的数据与环境隔离 | 每个实例都需要单独启动、升级并占用独立的系统端口 |

单实例是最常见也最省心的做法。你只需要在「聊天平台」中添加多个平台账号，再配合「场景规则」按账号或频道分流即可。

而多实例则像是两个独立运行的工作室：它们各自拥有独立的目录结构、数据库文件与 WebUI 服务端口。

## 多实例是怎么组织的

ChatLuna 的命令行工具会将所有实例存放在当前用户主目录下的 `.chatluna/instances` 中，每个子目录都对应一个完整的运行实例。

打开任意一个实例目录，你至少会看到两份核心清单：一份记录环境依赖，另一份记录运行配置。这两份文件共同决定了当前实例安装了哪些扩展、启动时加载哪些能力。

除了清单文件外，每个实例还会单独维护自己的数据目录，用来持久化存储聊天会话、长期记忆、账号凭据以及各插件的运行状态。

得益于这种目录级隔离，各个实例之间互不干涉：即便彻底删除某个实例目录，也不会对其他实例产生任何影响。

### 常用命令

日常维护中，你可以通过命令行工具管理各个实例的生命周期：

- `chatluna create <名字>`：创建一个新的实例。
- `chatluna start <名字>`：在后台监管进程下启动指定的实例。
- `chatluna list`：列出当前所有实例及其运行状态。
- `chatluna stop <名字>`：停止指定实例的运行。
- `chatluna restart <名字>`：平滑重启指定实例。
- `chatluna dev <目录>`：以开发模式启动某个目录，支持代码热更新。

如果执行启动命令时不带实例名称，系统会自动启动默认实例。默认实例的名称保存在用户目录下的启动器全局配置中，在创建第一个实例时会自动写入。

::: tip
执行 `chatluna list` 可以清晰查看各个实例的进程号 (PID)、当前版本以及所在物理目录。

多实例同时运行时，如果遇到机器人响应异常，用这条命令快速确认是哪个实例在工作，往往比翻阅日志更高效。
:::

### 端口必须错开

每个 ChatLuna 实例在启动时都需要绑定一个 WebUI 控制台端口，默认均为 `5028`。

如果你在同一台机器上同时启动两个实例，第二个实例会因端口冲突而无法正常启动。因此，多实例部署时必须为每个实例分配互不冲突的独立端口。

端口直接在实例自身的配置清单中指定即可，无需修改全局系统设置。

::: warning
端口冲突引发的问题往往不太直观：有时进程虽然成功启动，但网页端却始终打不开；有时则会在启动日志中报错并直接退出。

排查启动故障时，建议先确认各实例端口配置是否唯一。
:::

## 安装、升级与修复

除了生命周期管理，命令行工具还内置了一套针对实例的维护机制：

- **安装插件**：向指定实例的依赖环境中安装功能扩展。
- **移除插件**：从指定实例中卸载不再需要的插件。
- **链接本地插件**：在开发调试阶段，将本地源码目录软链接到实例中。
- **更新**：同时更新启动器与实例插件。执行前会自动创建状态快照并进行健康检查，一旦失败便会自动回滚。
- **修复**：当实例意外损坏无法启动时，自动收集运行诊断日志并尝试进行本地自愈。
- **报告**：查看最近一次修复操作生成的详细排查报告。

这套机制允许你随时退回。如果你在修改配置或升级插件后发现实例无法运行，可以先查看修复报告，再决定是依赖快照回退还是手动排查修复。

::: tip
所有的 `update` 与 `repair` 操作都会在实例目录下保留完整的记录。遇到突发状况时，查阅这些日志往往比回忆修改过程更可靠。
:::

## 数据备份

在管理多个实例时，备份同样是重要的一环。

多实例的隔离特性让备份变得非常直接，需要备份的关键资产均保存在实例目录内：

- 实例专属的配置清单与依赖清单。
- 存放会话记录、记忆向量与登录凭据的数据目录。

最稳妥的备份流程如下：

1. 通过命令停止目标实例。
2. 将整个实例目录完整复制到归档路径。
3. 确认无误后，重新启动服务即可。

::: warning
切记不要在实例运行过程中直接复制数据目录。

运行中的嵌入式数据库往往存在尚未落盘的内存缓冲，动态热拷容易导致备份文件损坏或缺失。请养成「先停后拷」的习惯，确保数据安全。
:::

## 怎么选

面对不同的使用场景，你可以参考以下建议进行选择：

### 同一个人，多个群

推荐使用单实例。

直接借助「场景规则」按群聊或频道分配不同的提示词人设、模型调用和技能工具，维护成本远低于独立维护多套实例。

### 多个平台账号

推荐使用单实例。

平台接入管理支持同时挂载多个平台的机器人账号，场景规则也能依据消息来源精准分流，没有必要切分底层进程。

### 公司和自己

推荐使用多实例。

两者的使用群体、私密数据与操作权限存在根本区别。强行塞进同一个进程，往往会导致配置混乱与复杂的权限负担。

### 测试与正式

推荐使用多实例。

测试实例可以随时安装前沿插件、修改调试参数，甚至允许它跑崩；而正式生产实例则只需保持干净与稳定。

### 给不同客户交付

推荐使用多实例。

为每一位客户分配独立的运行目录、独立的数据盘与访问端口，从物理层面确保彼此间数据完全隔离。

## 推荐配置

结合日常运维经验，我们总结了几套常见的搭配方案：

### 单人维护两个实例

建议为实例赋予清晰的命名，例如 `family` 与 `work`。

将两个实例的端口依次规划为 `5028` 与 `5029`，并分别将启动指令注册到系统的进程守护服务中，防止机器重启后遗漏。同时，后台管理口令也请务必单独设置，避免共用同一套密码。

### 实例很多

应当严格按照业务线划分实例边界，避免演变成「一个群开一个实例」。

虽然单独运行一个实例的内存开销并不大，但随着实例数量增加，版本升级、环境排错以及定时备份的维护成本都会显著上升。

### 开发与生产并存

日常开发建议直接使用 `dev` 模式运行，并将开发根目录与正式运行目录隔离开来。

开发环境中可以随意通过软链接挂载本地插件源码实时调试，而生产实例则严格保持只从官方源安装经过验证的正式版本。

## 排查

**启动报端口被占用。**

先检查当前实例的端口配置是否与其他服务冲突，或者提前排查并结束占用该端口的旧进程。在多实例刚部署完毕时，这是最普遍的启动失败原因。

**WebUI 打开的是另一个实例。**

说明浏览器访问的端口发生混淆。请回到终端通过命令行重新核对该实例实际绑定的监听端口。

**实例列表里有，但启动不起来。**

优先检查终端控制台的报错日志，随后执行修复命令。大部分启动失败的原因集中在第三方依赖下载不完整，或是配置清单格式存在笔误。

**两个实例的数据混在一起了。**

检查两个实例是否不小心指向了同一个数据存储路径。尤其是在手动使用 `--dir` 参数指定工作目录时，容易因路径拼写错误导致数据目录共享。

**更新后行为全变了。**

执行全量升级会同步更新第三方扩展插件，产生新特性或交互调整属于正常现象。如需紧急恢复原有业务体验，可以直接利用更新前留存的环境快照进行一键回滚。

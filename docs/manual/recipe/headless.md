# 无控制台运行

::: tip
这一页写给「只有终端」的场景：服务器、容器、CI，或者单纯不想开浏览器。ChatLuna 本身完全解耦，不依赖控制台也能稳定跑起来。
:::

控制台固然直观好用，但它并不是运行机器人的必需品。

一个机器人真正需要的只有三样核心要素：一个能连上的聊天平台、一个可调用的模型，以及一份描述行为的配置。这三样东西都不需要通过浏览器设置，在纯终端环境下同样能轻松搞定。

细心的小伙伴可能会发现，在很多特定环境下，无控制台运行反而是更高效的选择：

- 部署在只开放 SSH 的远端服务器上。
- 跑在受限的容器里，只映射了聊天平台所需的端口。
- 用脚本自动化批量创建与分发多个实例。
- 在 CI 流程中快速运行冒烟测试。

## 第一次启动

用命令行启动实例后，终端会打印出基础加载日志。初次启动时，建议优先留意以下几行关键输出：

- 实例监听的端口。
- 自动生成的访问令牌。
- 带令牌的登录地址。

即使你眼下不打算使用浏览器，也强烈建议把自动生成的令牌抄下来——后续排查故障或者临时需要连入控制台调试时，它是最直接的凭据。

如果不想每次重新生成随机令牌，也可以在启动前通过环境变量固定一个明确的值。

::: warning
控制台令牌代表着整个实例的主人级管理权限。

在多人共享的服务器上，请务必留意日志文件的读取权限；若将日志转发到外部监控或告警平台，请先确认里面没有泄露敏感令牌。
:::

## 没有控制台怎么设主人

绝大多数敏感操作与管理指令都要求执行者具备「主人」身份。图形界面通常依赖绑定码，而在纯终端环境下，我们可以直接把主人信息写进配置。

配置清单里内置了一份主人列表，每一项都需要写清楚平台标识、用户账号，以及一个方便辨认的名字备注。

填好之后重启实例，指定的用户就会自动以主人身份出现：不仅可以发送管理指令、发起人设配置，还能直接审批高危敏感操作。

::: tip
主人列表原生支持跨多个平台同时配置。

如果你同时接入了 QQ 和 Discord，并希望在两边都拥有管理能力，记得把两边的账号都完整写进列表。漏填了其中某个平台的账号，调用指令时就会直接提示权限不足。
:::

## 配置改在哪

脱离了图形界面，所有的调整其实都落在实例目录的几个静态文件里。结构十分清晰，主要分为三部分：

- **依赖清单**：记录当前实例装了哪些功能插件。
- **配置清单**：决定加载哪些插件，并声明各插件的具体参数。
- **数据目录**：保存会话历史、长期记忆与平台凭据等运行时数据。

变更配置的具体方式就是编辑对应文件，保存后重启实例（或使用命令行热重启）。

这里有几个行之有效的实践建议：

- 动手修改前，先备份原有的配置清单。
- 尽量单点改动，改完一处就重启验证一次，避免积累过多改动增加排查难度。
- 多用诊断命令检查配置是否合法，这往往比等待实例启动报错再翻堆栈快得多。

::: warning
配置文件中的密钥字段是明文保存还是密文引用，完全取决于你的书写方式。

能加密保存的凭据，优先启用框架的加密能力；实在要以明文形式保存，请至少通过文件系统限制所在目录的访问权限。
:::

## 环境变量

除了修改配置文件本身，还有若干环境变量会直接影响实例的启动行为：

- **令牌**：用来固定访问令牌，设置后优先于随机自动生成。
- **允许远程访问**：在容器等隔离网络场景下，需要开启该项才允许外部网络穿透访问。
- **时区**：直接决定定时任务的触发时刻与日志时间戳。容器镜像默认往往是 UTC 时区，一旦配置偏差，就会导致「早上八点的提醒在下午才触发」的现象。

::: tip
采用容器部署时，时区往往是最容易被忽视的隐形坑。

排查「定时任务时间对不上」时，建议先检查容器本身的时区环境变量，再回过头去看任务自身的规则配置。
:::

## 用聊天指令管理

没有控制台，并不意味着我们失去了对机器人的掌控。事实上，聊天窗口里的管理指令照样功能齐全：

- 查看实例运行状态、动态切换生效的模型底座。
- 新建与终止对话、手动触发上下文压缩。
- 增删查改后台的定时任务。
- 一键撤销误操作引起的文件修改。

需要二次确认的高危审批同样走聊天渠道：系统会以提问形式将待确认操作与选项发到会话里，主人直接回复对应编号即可完成审批。

换句话说，纯终端部署下的日常运转非常完整：聊天平台负责全部交互与管理，而终端只需要负责启动和查看日志。

## 日志与诊断

实例在后台启动运行时，所有输出都会按规则记录到对应的日志文件里。

遇到异常时，诊断命令能帮我们检查插件安装、底层数据与配置语法的常见问题；它甚至支持针对某个具体会话执行一致性校验。

如果需要深入复盘，还可以利用会话导出功能把一整段会话日志导出成标准的 JSONL 文件，方便拷贝到本地细细分析或存档备份。

推荐的排查节奏通常是：先查阅启动日志确认基础状态，再执行诊断命令定位配置隐患，最后按需导出会话深入复盘。

## 容器部署

容器化是无控制台运行最为常见的落地场景。

在构建与运行容器时，建议重点留意以下几个注意点：

- **数据要挂载出来**：务必把数据目录挂载到宿主机，否则一旦容器销毁重建，历史数据将全部丢失。
- **端口要按需映射**：通常至少映射 WebUI 端口以便外部连通；机器人连接聊天平台多属于出站请求，通常不需要额外映射平台端口。
- **令牌通过环境变量注入**：访问令牌应在容器运行时注入，切勿直接烘焙进镜像层。
- **时区显式设置**：在容器配置中明确指定时区，保障日志时间与定时调度准确一致。
- **首启日志里找令牌**：未配置固定令牌时，请在容器首次启动打印的日志中记录自动生成的凭据；如果配置了固定令牌，系统则不会生成随机值。

::: warning
切勿为容器配置不必要的高权限。

尤其是直接挂载宿主机 Docker 套接字这类操作，实际上等同于将整台宿主机的控制权拱手相让。只有在确实需要调用容器沙箱能力时才允许挂载。
:::

## 批量创建实例

当需要借助自动化脚本批量创建多个实例时，可以按需指定模板来源、包管理器类型以及目标存储目录。

模板实例化完成后，依次为各个实例修改端口、写入预置配置并启动即可。

如果所有实例的基础配置完全相同，先完整配置好第一个实例，随后直接复制其配置文件，会比每个实例逐一手写更加高效可靠。

::: tip
批量部署时，强烈建议为每个实例制定统一且清晰的命名规则，例如带上业务线与自增序号。

后期在查阅日志、过滤系统进程或执行自动化备份时，规范的命名能省去大量逐一核对的时间成本。
:::

## CI 里的冒烟测试

在 CI 流水线中进行自动化验证时，接入一个本地的虚拟假模型提供商是极佳的选择。

它不产生任何真实网络请求、不需要填写 API 密钥，却能完整走通消息链路：接收输入消息、匹配触发规则、生成回复并最终投递。

这种方式非常适合作为合入前的质量门禁，用来快速验证「本次代码提交是否破坏了实例启动与基础调用链路」，但它自然不适合用来评判实际的模型回答质量。

## 推荐配置

根据不同场景的侧重点，我们总结了三种典型的推荐配置方案：

### 个人服务器

对外只开放 SSH 安全端口，控制台仅监听本机回环地址；需要临时访问界面时，通过 SSH 端口转发建立隧道连接。

访问令牌建议直接通过环境变量固定，同时开启日志轮转归档，防止长期运行撑满服务器磁盘。

### 容器化交付

采用多租户隔离模式：每个客户对应一个容器、一个持久化挂载目录以及一个独立映射端口。

令牌随部署环境动态注入，运行区时按客户所在地区配置，配置清单则随镜像版本统一进行版本管理。

### 纯聊天管理

彻底不暴露控制台端口，仅保留与聊天平台的网络长连接。

提前在配置中配置好主人列表，日常巡检全靠聊天指令，敏感操作审批也直接在聊天会话中闭环完成。

## 排查

遇到非预期情况时，可以先按照下面的常见现象快速排查：

**启动后连不上平台。**

先查看日志中对应平台适配器的具体报错。常见诱因包括访问令牌填错、反向代理或服务网关地址写错，或者容器网络限制导致无法正常出站。

**所有指令都提示权限不足。**

通常是主人列表未配置，或是填写的平台标识与账号写错了。仔细核对平台名称与具体用户账号是否与实际完全一致，保存后重启实例。

**定时任务时间不对。**

绝大多数属于时区偏差引起。请重点检查容器环境的时区设置，以及任务自身定义的时间规则。

**改了配置没生效。**

绝大多数配置项都需要重启进程才能生效。少数参数虽然支持在线热加载，但在纯终端无界面环境下很难直观判定，统一重启是最稳妥的方式。

**找不到访问令牌。**

自动生成的临时令牌通常只在首次启动的日志中打印一次。如果遗失且没有备份，可以删除数据目录下的令牌凭据文件并重启实例，系统会自动重新生成一个。

**诊断报配置错误。**

依照诊断报错中明确指出的插件名与字段属性进行针对性修改。修改完毕后再次执行诊断，直到全部通过再启动。

# 工具

::: tip
工具是模型可以主动调用的各项能力：读写文件、执行指令、搜索网页、查询数据或是发送消息。本章将带大家了解「能力 → 工具」页面如何使用、怎样为工具制定执行策略，以及在工具数量较多时如何节省上下文消耗。
:::

在与大语言模型对话时，如果我们只让模型单凭训练学到的知识回答问题，它往往只能给出宽泛的解释，甚至可能出现「一本正经胡说八道」的幻觉。

要是能让模型在需要的时候去查查最新的网页、读一读本地的数据文件，甚至是在系统沙箱里跑一段计算脚本，回答的准确度与实用性就会发生质的飞跃。

这些能够被模型在对话中主动挑选并调用的外部技能，在 ChatLuna 中就被称作**工具**。

在 ChatLuna 中，工具并不是写死在模型底层的固定逻辑，而是由各个插件动态注册到运行上下文中的实用能力。只要系统中启用了某个插件，它所附带的工具就会立刻注入进来供模型调遣；一旦停用了对应插件，这些工具也会随之卸载，干净利落。

不过，随着安装的插件越来越多，新的管理问题也会随之而来：

- 模型怎么知道在什么时候该调用哪一个工具？
- 涉及修改本地文件、执行系统终端命令等高风险动作时，万一模型误判了怎么办？
- 工具数量成百上千时，如果把每项工具的使用手册都塞给模型，会不会让对话开销变得难以承受？

为了让大家既能享受丰富工具带来的便利，又能把控好安全与成本，ChatLuna 提供了专门的可视化工具管理界面。

我们可以通过该界面轻松「看清」并「管住」它们：清楚掌握当前有哪些可用工具、它们分别来自什么插件、调用时需要传入哪些参数；并针对不同场景灵活把控哪些工具可以直接运行、哪些动作必须等待人工审批，以及哪些功能应当对模型彻底隐藏。

## 工具页

打开控制台，在左侧导航栏中点击「能力 → 工具」，映入眼帘的就是当前实例中已注册的所有工具。

在这里，你可以一目了然地看到系统中当前挂载的全部能力。无论是系统内置的文件读写，还是刚接入的第三方功能，都会集中陈列于此。

为了方便日常查看与批量管理，页面右上角提供了「卡片」与「列表」两种视图的切换按钮。你可以根据自己的阅读喜好自由挑选：卡片视图图文并茂，更适合快速浏览；列表视图信息密集，更适合条目繁多时的批量排查。

不仅如此，视图切换按钮旁还支持按插件、按规则或不分组来组织列表：

- **按插件分组**：工具会按照其所属的插件归类折叠，方便按功能模块定位。如果你想集中查看某个新插件究竟带来了哪些能力，选这个分组最合适不过。
- **按规则分组**：根据工具当前的生效策略（如自动、询问或禁用）进行分组，一览安全防线。所有高危待审的工具都会聚在一起，方便集中复核。
- **不分组**：平铺展示所有工具，一滑到底，适合配合搜索进行快速查阅。

如果你的环境里安装了大量扩展插件，工具列表可能会非常可观。此时直接使用顶部的搜索框输入关键字，或者点击排序菜单调整展示顺序，就能在数秒内精确定位到想要配置的目标工具。

点击列表中任意一个工具卡片，页面右侧会滑出抽屉式详情面板，这里清晰展示了该工具的全部关键属性：

- **工具名称与功能说明**：用通俗的文字解释该工具具体负责什么工作。不仅方便管理员了解功能，模型也是通过这段说明文字来理解工具意图并在恰当时机主动调用它的。
- **注册插件与作用域**：标明该工具是由哪一个插件注册进来的，并直观提示它属于全局生效的公用工具，还是仅隶属于某个具体 Agent 的局部专属工具。
- **参数规格**：详细拆解了调用该工具时需要的参数结构。每一项入参都会标明名称、数据类型、取值范围，以及它是必须提供的必选参数还是允许留空的可选参数。
- **当前策略**：显示当前正在生效的控制策略，例如「自动」、「询问」或「禁用」。点击即可呼出下拉菜单进行就地切换。
- **来源标记**：如果该工具来自外部 MCP 服务，详情区域还会明确标注其所对应的 MCP 服务器名称，方便溯源。

在工具详情页中对策略所做的任何修改，系统都会在后台自动保存至工具策略插件中，并对随后的所有新对话交互即时生效。

如果在我调整策略的这一瞬间，正好有用户正在和机器人对话，正在执行的任务会不会突然被打断？

答案是完全不用担心。当前正在运行中的对话回合不会中途改变已经下发的工具列表，会平稳走完本次既定流程；新的策略变更只会在随后的新一轮对话中无缝接管。

为了让大家在配置时心中有数，这里把详情面板中几个关键字段的含义与操作建议整理如下：

| 属性名称 | 界面位置 / 呈现形式 | 作用说明 | 常见操作与建议 |
| :--- | :--- | :--- | :--- |
| **工具名称与说明** | 详情顶部标题与描述 | 解释工具职责，供管理员查阅及模型意图匹配 | 若模型总在不恰当场景调用，可核验说明是否准确清晰 |
| **注册插件与作用域** | 详情信息标签 | 标明提供该工具的插件，以及全局生效或专属 Agent | 排查工具来源；停用对应插件即可卸载该工具 |
| **参数规格** | 详情参数列表抽屉 | 拆解调用入参，标明类型、取值范围及必选 / 可选 | 遇到调用卡死或失败时，在此核对模型入参是否合规 |
| **当前策略** | 策略切换下拉菜单 | 实时控制当前工具策略（自动、询问、禁用） | 对读写、命令等高危工具建议就地调整为「询问」 |
| **来源标记** | 详情附加标签 | 标明外部 MCP 服务器归属名称 | 方便追溯第三方工具链路与关联服务器状态 |

### 三种策略

既然工具的能力有大有小、风险有高有低，我们自然不能用同一套标准对待它们。针对每一个工具，平台提供了三种不同力度的控制策略：

- **自动**：模型发起调用时直接在后台执行并返回结果，无需人工干预（除非全局权限模式另有强制审批要求）。适合无害的查询、计算或只读类操作。
- **询问**：模型在真正调用该工具前会主动暂停执行，并在界面弹出确认提示，等待管理员或用户手动核准。非常适合具有副作用、产生额外资费或涉及隐私安全的操作。
- **禁用**：将该工具从模型的视野中完全隐去，模型既看不到它的说明，也无法在对话中调用它。

除了可以在工具详情页逐个手动调整策略外，工具策略插件的配置项中还支持使用通配符进行批量规则匹配。

工具名称支持使用星号 `*` 代表任意多个字符，问号 `?` 代表单个字符。

例如，你可以简单配置一条规则，统一把所有外部引入的 MCP 工具一键设为「询问」，免去了挨个点击的繁琐操作。

又或者，你可以将某类只读查询工具统一匹配设为「自动」，把潜在的高危动作统一拦截待审。

::: warning
需要格外注意的是，「禁用」只是将工具对模型进行界面与上下文层面的隐藏，并不是从底层物理卸载。插件本身依然处于正常运行状态，随时可以在需要时重新开启。如果希望彻底移除某个工具，应当去插件市场卸载对应的插件；但对于命令执行、写入磁盘等高风险操作，直接设为「禁用」往往是更稳妥、更便捷的选择。
:::

## 工具从哪里来

前面我们提到，工具并不是固化在系统底层的。那么在日常使用中，这些工具到底是从哪些渠道汇聚而来的呢？

了解工具的来源，有助于我们在需要新功能时快速找到正确的扩充方向。

整个运行环境中的工具，主要由以下几种途径汇聚而来：

- **内置工具插件**：系统自带的基础能力，涵盖文件读写、命令执行、代码运行、网页请求与搜索、定时任务、配置管理以及运行时自省等。
- **技能**：将用户编写的技能目录与专属执行脚本封装暴露出来的扩展工具。
- **MCP 服务器**：通过模型上下文协议（Model Context Protocol）将第三方外部服务投影接入的外部工具。
- **子代理**：系统将任务委派与调度动作包装成工具，让主模型能够像调函数一样把复杂子任务派发给指定的子代理。
- **机器**：将远端主机、本地环境或容器沙箱的操作接口映射成的底层工具。
- **业务插件**：各类拓展应用插件注册的专属功能，如群组管理、AI 绘图、语音合成、记忆库检索等。

既然工具来自不同的插件与服务，那它们在同一个会话里能互相配合吗？

答案是完全可以。无论是哪一种来源注册的工具，在同一个对话回合里都可以自然混合使用。

模型可以先调用网络插件搜索最新的文档，再调用文件工具将要点记录到工作区，最后调用通知工具向你发送提醒。底层的权限校验、人工审批与可见性规则对所有来源一视同仁。

### 工具可见性

并不是所有安装的工具都会无条件塞给模型。如果系统里有一百个工具，一股脑全发给模型，不仅提示词会变得极其臃肿，模型挑选工具时也容易挑花了眼。

一个工具最终能否在某个具体会话中被模型感知到，是由下面几道关卡自上而下层层决定的：

- 插件自身注册时声明的前置过滤条件。
- 当前所选 Agent 配置的局部工具过滤。
- 「场景规则」中针对特定群聊或私聊会话配置的允许与禁用工具清单。
- 「工具页」与工具策略插件中设置的全局禁用状态。
- 对应技能或 MCP 服务器自身的开启与关闭状态。

这里的过滤机制遵循「逐步收窄」原则：靠后的规则只能进一步缩小工具范围，而无法强行让前序规则已经隐藏的工具重见天日。

换句话说，如果某个工具已经在全局策略中被设为了禁用，那么即便你在群聊的场景规则中把它列入允许清单，模型也是无法调用它的。

因此，如果在聊天中发现模型找不到某个预期中的工具，不妨顺着上述几道关卡自顶向下逐一排查。

## 工具模式

搞清楚了工具的来源与可见性，接下来我们来看看模型到底是如何使用这些工具的。

不同的对话任务对工具的使用方式有着不同的诉求。有时我们只需要模型简单执行一两次搜索，有时却需要模型编写脚本把多个工具串联起来跑批处理。

打开控制台，点击进入「场景规则 → 能力 → 工具」，会看到一个名为「工具模式」的核心设置项。

它决定了工具以怎样的形态呈现在模型的提示词上下文中：

- **直接给全部**：将当前可见工具的全部参数定义与功能描述完整填入提示词中。在工具总数不多时，这种方式最为直接可靠，模型理解起来也最轻松。
- **先搜再用**：在提示词中仅保留少数高频常驻工具以及一个专用的工具搜索器。模型遇到需要调用的功能时，先通过搜索获取该工具的完整参数规范，然后再执行调用。在挂载工具成百上千时，能大幅削减无谓的上下文占用。
- **写代码调用**：为模型提供一个代码解释环境，引导模型编写代码片段来组合编排并批量调用多个工具。非常适合数据多步流转、结果批处理或需要精确逻辑控制的场景。
- **交给子代理**：模型不直接在当前会话下调用工具，而是将整个子任务完整指派给子代理，由子代理在独立的隔离上下文中按需使用工具并汇总反馈。特别适合步骤冗长、逻辑复杂的长链路任务。

默认选用哪种模式通常取决于当前配置的模型引擎类型。普通的对话引擎默认采用「直接给全部」；而在处理较重的工作流或特定引擎时，系统可能会默认推荐走子代理委派。具体请以当前场景规则界面中展示的默认选项为准。

::: tip
工具模式并不是层级越复杂就越好。当手头只有十来个工具时，「直接给全部」响应最快、表现最稳；只有当挂载了大量外部 MCP 服务使得工具库膨胀到数十上百个时，「先搜再用」才能真正体现出节省 Token 费用的优势；而在需要批量做复杂数据清洗与调用的场合，编写代码调用才是正解。
:::

## 工具搜索

当引入的工具琳琅满目时，将每个工具厚重的参数定义全部塞给模型不仅成本高昂，还容易分散模型的注意力。

为了兼顾功能丰富度与上下文开销，ChatLuna 引入了工具搜索机制。

该机制巧妙地将所有工具划分为两大类别：

- **常驻工具**：完整的使用说明与参数架构始终驻留在提示词中，模型随时可以无需前置步骤直接调用。
- **按需工具**：在基础提示词中仅保留工具名称与简短一句话说明；只有当模型通过搜索工具主动查询并命中该工具后，系统才会动态补全并注入其完整参数说明。

这样一来，常用的核心工具依然能够随叫随到，而那些偶尔才用一次的长尾工具则不会平白无故占据昂贵的输入空间。

如果你想调整搜索的具体行为，可以前往控制台打开「场景规则 → 能力 → 工具」，在搜索配置区域细致调整以下几个参数项：

- **搜索模式**：提供「自动」、「始终搜索」以及「关闭」三种选项。其中「自动」模式仅对支持工具延迟加载特性的模型提供商生效。
- **自动启用阈值**：设定一个临界数量（默认值为 20）。只有当当前会话可用的工具总量超过此数值时，系统才会自动把按需工具转入延迟检索机制；低于该数值时则自动回退为直接全部展开。
- **按需加载列表**：配置哪些工具需要被归入按需范畴。系统默认会将所有通过 MCP 接入的外部工具包含在内，同样支持使用通配符匹配。
- **单次搜索返回数量**：控制模型在执行工具搜索时，一次最多返回几个匹配候选工具，默认设置为 5 项。

值得一提的是，如果你希望某几个核心 MCP 工具跳过搜索直接可用，也可以直接前往「能力 → 工具」详情页，将单个工具的模式由跟随全局覆盖标记为「常驻」；反之，也可以把某个冗长的内置工具单独指定为「按需」。

::: warning
延迟检索机制也存在固有开销：模型必须先耗费一次交互轮次去检索工具列表，确认格式后再发起二次调用。因此在工具总数较少的小型实例中盲目开启搜索，反而会导致响应变慢并白白消耗交互次数。请务必结合实际挂载的工具体量来权衡阈值。
:::

## 执行与审批

当模型在对话中觉得该用某个工具了，它并不是直接在你的电脑上悄悄跑一段程序。从产生想法到得出结果，系统在底层会按序流经以下处理阶段：

1. **意图输出**：模型根据对话上下文判断需要使用某项能力，生成指定的工具名称与调用参数。
2. **结构校验**：系统内置的校验层拦截输出，严格对照该工具声明的参数规范核对类型、字段与取值。
3. **权限判定**：交由安全与权限系统审查，评估这次调用是否落在需要确认的规则或风险策略上。
4. **运行处理**：工具正式在指定环境下运转，并将执行细节整理为机器可读的结构化数据以及便于模型理解的文本反馈。
5. **写回上下文**：把工具的返回结果追加记录进会话上下文与轨迹日志中，推进模型进入下一阶段的解答。

整个流程环环相扣，既确保了模型传入的参数格式准确无误，又在关键时刻把住了安全大门。

不仅如此，安装的扩展插件还可以在工具调用的前后关键节点进行灵活介入：

- **调用执行前**：插件可以动态补全或修正传入的参数内容，若识别出异常操作，也可以直接中止本次调用。
- **调用执行后**：插件能够为工具结果追加背景补充、对敏感字段做脱敏处理，或是插入辅助模型判断的额外上下文。

这些介入逻辑均严密附着在插件的生命周期内，一旦停用或卸载相应插件，所有介入钩子都会自动撤回，不会在系统中残留无用逻辑。

### 审批与权限模式

需要说明的是，在「能力 → 工具」详情页中把策略设为「询问」只是安全防御的第一道关卡。在工具真正被触发前，全局设定的权限模式还会执行第二层综合裁定。

打开全局安全与权限配置页面，系统提供了四种不同的权限模式：

- **只读**：最为严格的保护伞。全系统只允许执行无害的只读查询类操作，任何写文件、改数据或执行指令的行为都会被直接拒绝或拦截待审。
- **文件**：针对日常文件处理场景放开限制，允许正常的文件读取与保存写入，但系统底层的终端命令等高风险操作依旧强制弹窗审批。
- **自动**：引入轻量级审查器模型进行智能研判，对判定安全的常规调用自动予以放行，仅在遇到边界模糊或高危动作时才推给人工决策。
- **完全放行**：最高信任模式，通常仅向具备高权限等级的受信任用户开放；普通或低权限用户在该模式下仍会自动降级并按「自动」模式严格审查。

当触发审批时，交互界面中会明确浮现审批卡片，完整呈现将要调用的工具名称、入参细节与潜在风险提示。

面对弹出的审批卡片，你可以根据当前情况做出选择：

- 点击「仅本次允许」让这次调用立刻放行；
- 如果觉得参数不对或操作可疑，点击「拒绝执行」即可安全中止；
- 在权限允许时，还可以勾选「记住此选择」以避免后续重复确认。

如果审批卡片弹出后长时间未做响应，系统在超时后将默认按拒绝流程处理，避免会话无限期挂起。

为了方便大家快速对照，以下是四种权限模式在不同场景下的具体表现与适用建议：

| 模式名称 | 核心表现 | 高危操作（如 Shell / 写文件） | 推荐适用场景 |
| :--- | :--- | :--- | :--- |
| **只读** | 全系统仅允许查询与数据检索 | 统统一刀切拒绝或强制拦截 | 公开群聊、只供信息查询的问答机器人 |
| **文件** | 允许普通文件读写与保存 | 终端命令等底层系统操作强制弹窗待审 | 日常文档编写、报表整理等轻度协作场景 |
| **自动** | 审查器模型智能研判安全等级 | 判定安全则放行，边界模糊或高危动作推人工 | 个人日常使用、轻量级自动化助理 |
| **完全放行** | 最高信任级别，全自动放行执行 | 对受信任管理员免审批；低权限用户自动降级 | 开发者本地调试、超级管理员专属环境 |

::: tip
请根据使用定位合理划分两者的边界：「询问」适合那些有用但存在操作风险、担心模型误判的动作；而「禁用」则适用于那些本就不希望该场景碰触的功能。切忌把工具设成了询问，却在日常使用中每一次都直接拒绝——这只会导致模型在反复确认中卡住流程。
:::

## 常见工具家族

根据注册插件的不同，我们可以在工具页看到形态各异的工具家族（具体以自己控制台内实际加载的列表为准）：

- **文件家族**：提供本地或工作区文件的查看、编辑写入、增量修改、目录浏览以及关键字检索能力。平时让模型帮忙改文章、读代码时少不了它们。
- **命令家族**：在受限的系统终端中运行 Shell 指令。属于高权限、高风险类别，生产中建议默认开启审批。
- **代码家族**：在隔离解释器中执行一段指定代码并取回标准输出，常用于复杂数学运算、正则处理或批量文本转换。
- **网络家族**：提供主流搜索引擎检索、网页抓取与解析、原始 HTTP 请求发送以及对接外部 OpenAPI 接口的能力。
- **运行时家族**：允许查看 ChatLuna 自身的系统状态、查看实时日志输出、检查已启用的插件与配置项，涉及核心配置修改时通常需要超级主人权限。
- **记忆家族**：负责向量记忆或长期记忆的检索查阅、条目更新与持久化存储。
- **技能家族**：负责枚举当前已加载的技能包、提取技能指引正文，以及按需执行技能专属脚本。
- **MCP 家族**：连接外部各大 MCP 服务所映射出来的扩展工具，在列表中通常带有清晰的服务器前缀标识。
- **子代理家族**：提供任务外包派发能力，主代理可借此唤起专业子代理独立运算并回传最终解答。
- **机器家族**：将本地执行器、远端 SSH 主机、Docker 实例或云端沙箱的操作端口暴露为可调用的系统工具。
- **业务家族**：各种垂类扩展插件带来的趣味功能，包括 AI 绘图生图、文本转语音、闹钟定时器以及社群自动化管理等。

## 推荐配置

面对如此多样的选项，新上手时该如何权衡？如果你一时间不知道该怎么搭配，不妨参考下面几套针对不同运行场景的经典配置组合：

### 个人小实例

如果你搭建 ChatLuna 主要是个人日常私聊使用，建议在「场景规则 → 能力 → 工具」中将「工具模式」保持默认的「直接给全部」。

因为在个人环境中工具基数通常并不大，直接全部提供响应最灵敏，也无需增加工具搜索的等待环节。

在「能力 → 工具」页面中，把命令执行与文件改写类工具的「当前策略」设为「询问」，其余常规查询工具保持「自动」即可。

这样配置既省心顺手，又能有效防范模型在关键时刻产生误操作。

### 接了多个 MCP 的实例

一旦接入了诸如 GitHub、数据库等多个 MCP 服务，工具总量往往迅速突破几十个甚至上百个。

此时推荐在「场景规则 → 能力 → 工具」中开启「工具搜索」功能。

具体操作上，将「自动启用阈值」保持在默认的 20 上下，并确认「按需加载列表」中已包含 MCP 来源的工具。

日常将最常使用的两三个基础工具在「能力 → 工具」详情页单独设为「常驻」；对于涉及外部数据增删改的高危 MCP 工具，在工具详情页中单独配置为「询问」。

这样既能大幅降低每轮对话的输入 Token 开销，又能把控好外部数据写入的安全边界。

### 多人群聊

在群聊等多人公开环境下，安全性应当放在首位。

强烈建议利用「场景规则 → 能力 → 工具」为各个公开群聊单独设立工具白名单。

在群聊中，建议仅保留信息查询、网络搜索与趣味互动等只读类业务工具；

涉及敏感配置变更、文件读写及 Shell 终端的高风险工具，则统一限制在管理员私聊或特定的受控管理群中使用，防止群内普通成员诱导模型执行破坏性指令。

### 自动化 / 编码

当需要让模型协助编写大型项目或执行复杂的批处理自动化任务时，推荐在「场景规则 → 能力 → 工具」中将模式切换为「写代码调用」，或者选用专属的编码引擎。

为模型配齐文件读写、目录检索与解释器工具，同时将高危指令执行设为审批，或将其执行范围严格限定在隔离沙箱工作区内，以兼顾生产力与宿主机环境的安全。

在这种模式下，模型可以灵活编写脚本自行批处理多个工具的返回结果，大大减少了繁琐的往返对话交互。

## 排查

在日常使用工具的过程中，如果你遇到了预期之外的状况，可以参考以下步骤进行排查：

**模型在回答中声称自己「没有某个工具」**  
遇到这种情况请勿慌张，建议顺着可见性链路逐项确认：首先在「能力 → 工具」页面查看该工具是否已成功加载并注册；其次排查插件是否设置了环境过滤；再前往「场景规则」确认该聊天场景是否将其加入了禁用黑名单；最后查看该工具是否处于「按需加载」状态而模型在当前轮次尚未发起针对性的搜索。在工具详情页中可以直观查验其在当前上下文的综合可见状态。

**模型界面显示发起了工具调用，但后续一直没有进展**  
通常是因为触发了安全机制正在等待人工放行，或是模型生成的入参未能通过结构校验。建议点击控制台侧边栏前往「轨迹」页面，找到卡住的这一个会话回合，仔细核验这一步的具体报错或等待状态；如果是询问，请检查聊天窗口下方的审批交互槽位中是否有尚未处理的确认弹窗。

**工具返回的文本内容过长，导致上下文直接爆满**  
当工具（例如检索全文或大文件输出）返回的内容过长时，极易占满窗口限额。此时可以开启大文本结果自动转存机制：当返回体量超出设定的安全阈值时，系统会自动将内容写入临时存储，转而只向模型提示文件前缀概要与读取路径；也可以针对此类工具切换为按需检索模式。大部分专业的编码与文件类工具都已在底层自带了这一转存阈值保护。

**工具调用总是提示被系统自动拒绝**  
请优先检查当前会话所处的权限模式是否被误设为了「只读」，导致一切写入与调用请求被一刀切驳回；另外请核对触发调用的用户其自身权限等级是否达标。高危的「完全放行」策略仅对管理员等高权限用户生效，低权限普通用户即便匹配到了放行规则，系统在底层依然会退回「自动」模式并拦截高危请求。

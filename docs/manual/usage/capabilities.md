# 工具、技能与 MCP

::: tip
这一页是能力体系的总览：带你快速理清工具、技能与 MCP 分别解决什么问题、三者如何协同配合，以及它们共用的那套安全规则。具体的操作细节请前往各自的专题页面。
:::

刚开始接触 ChatLuna 时，很多小伙伴容易把工具、技能和 MCP 这三个概念混在一起。在控制台界面里，它们不仅挨在同一个导航分组下，日常对话中也常常成双成对地出现，但它们各自分管的职责其实完全不同。

如果你觉得概念太多记不住，不妨先记住这一句简单直观的对应关系：

- **工具**是动作，解决「能做什么」；
- **技能**是方法，解决「具体怎么做」；
- **MCP** 是通道，解决「外面的能力怎么接进来」。

<!-- 截图占位：能力分组 · 工具/技能/MCP 三个页面入口 -->

打开控制台，在左侧导航栏的 ChatLuna 分组下，你就能看到「工具」、「技能」和「MCP」三个独立的管理页面。接下来，让我们逐一看看它们在机器人内部到底是如何工作的。

## 三者各自是什么

### 工具

工具是模型可以直接调用的一个个具体动作，每一个工具都有明确的名字、参数和返回值。

日常生活中的读写文件、执行终端命令、搜索网络、查询数据库、向群里发送消息，在 ChatLuna 内部其实全都是工具。

在每一轮对话开始时，ChatLuna 会整理出一份工具清单交给模型。清单中详细列出了当前有哪些工具可用、它们分别做什么、调用时需要传入哪些参数。当模型判断需要某种外部能力时，就会主动发起调用请求，系统执行完后将结果反馈给模型。

简单来说，工具就是整个体系中的**执行层**。

### 技能

技能则是写给模型阅读的「业务操作说明书」。

很多复杂的实际任务往往无法通过一步调用就能搞定。比如修一个 Bug，通常需要先检查运行环境，再按顺序修改对应的几个文件，最后运行测试套件跑一次验证。这种需要多步协作的场景，光给模型一把螺丝刀（工具）是不够的，模型还需要一套操作指南，明确知道在什么时候、按什么顺序来配合使用这些工具。

技能的作用正是把这套成熟的办事流程记录下来，并在需要时供模型临时翻阅。

更棒的是，技能不会一直霸占宝贵的上下文窗口。平时模型只能看到技能列表中的一句话简介，只有当对话真正命中某个技能时，系统才会把详细的正文加载进来。

因此，技能充当的是知识与流程沉淀的**知识层**。

### MCP

MCP（Model Context Protocol）是一套通用的开放协议，专门用来无缝连接外部系统与服务。

如果你手头已经有了现成的外部系统，例如本地的 GitHub 客户端、远程数据库查询服务或者公司内部的业务系统，完全不需要大费周章地为 ChatLuna 单独重写插件。只要对方原生支持 MCP 协议，就能以统一的方式直接接入。

接入成功后，外部服务提供的各项功能就会整齐地出现在 ChatLuna 的工具清单里，模型调用它们时的体验和使用本地内置工具毫无二致。

换句话说，MCP 是帮助我们打破系统孤岛的**接入层**。

## 它们怎么汇到一起

虽然三者的定位各异，但在机器人的视野里，它们的最终形态殊途同归，都是**模型可调用的工具**。

让我们看看这三股力量是如何汇入同一处江海的：

- 工具插件直接向系统注册可用工具；
- 技能可以自带配套的专用脚本工具，也可以指导模型组合调用现有的其他工具；
- MCP 服务则会把远端的能力映射投射进来，名字前面通常带有统一的服务前缀，防止命名冲突。

当所有能力就绪后，模型拿到的就是一张扁平的清单。它根本不需要关心某个工具究竟是本地内置的还是通过 MCP 远端拉取的，只要在清单里，就能以统一的方式调用。

这也是 ChatLuna 能够实现全系统统一权限治理的前提：无论工具来自哪里，只要发生调用，都会被拦截并送入同一套安全流水线。

## 模型能看到什么

随着安装的插件和接入的服务越来越多，可用工具的数量也会成倍增长，全部堆给模型会让上下文压力剧增。因此，系统对「模型能看到什么」划分了清晰的两个层级。

第一层是**能不能用**。这一层直接决定工具的去留：插件自身的条件限制、场景规则中的允许或禁用名单，以及你在控制台工具页手动勾选的禁用状态，会第一时间把不符合条件的工具过滤掉。

第二层是**什么时候看到**。哪怕一个工具通过了第一层筛选、确认处于可用状态，它也不一定会一股脑儿全塞进模型的即时提示词里。

- **常驻工具**：完整的功能说明和参数描述始终留在提示词里，模型一抬手随时都能调用。
- **按需工具**：提示词中仅保留工具名称和一行极短的概要，模型必须先发起一次工具搜索，才能获取到完整的参数结构。

当系统挂载了数十上百个工具时，按需加载能为每轮对话省下惊人的上下文 Token。这也正是 MCP 工具默认采用按需加载模式的原因。

::: tip
如果你发现模型在对话中似乎「不知道某个工具的存在」，不妨先检查该工具是否配置成了按需加载模式。如果是按需工具，模型在当前对话轮次尚未执行主动检索前，确实看不到它的参数细节。
:::

## 安全规则是共用的

不管一个工具最初来自哪款插件还是哪台 MCP 服务器，只要它试图运行，就必须经过 ChatLuna 统一的安全治理：

- **工具策略**：打开「工具」页面，点击具体工具即可查看设置。你可以为每个工具单独配置为自动执行、需要审批或是直接禁用。
- **场景规则**：在权限设置中，针对不同的群聊环境或不同身份的用户，可以灵活圈定各自开放的工具范围。
- **权限模式**：控制台提供只读、文件、自动和放行四档全局模式，专门用来管控高危操作的处理尺度。
- **等级**：依托用户自身的权限等级，严格限定只有高权限管理者才能触发涉及敏感数据的危险动作。

得益于这套机制，第三方 MCP 服务完全无需重复开发鉴权逻辑——服务只管安心提供能力，是否放行、何时放行统统交由 ChatLuna 把关。

反过来说，接入一个功能极其强大的外部 MCP 平台，并不会凭空增加系统的安全风险，只要你在「工具」与「权限与安全」页面中做好细粒度的限制即可。

## 怎么选

在实际搭建自己的机器人助手时，并不是所有业务都要把工具、技能和 MCP 一口气全配齐。你可以根据当下的核心诉求来选择合适的路径：

**只是想调用一个外部的 HTTP 接口或云端服务？**
先去生态里找找有没有现成的 MCP 服务。如果有，直接接入即可，连一行适配代码都不用写。

**需要机器人掌握一套严谨固定的操作流程？**
编写技能。把步骤拆解清楚写进说明书，相比在系统提示词里长篇大论，能大幅节省每轮对话的上下文开销。

**需要让机器人在本机或远程服务器上执行命令、读写文件？**
直接使用内置的基础工具，配合机器管理机制将执行环境限定在安全受控的沙箱中。

**需要模型根据复杂上下文，自主决策并串联多个操作以完成综合任务？**
这时才是综合施展三者威力的时刻，你可以同时搭配基础工具与操作技能，并视情况开启工具搜索或代码调用模式。

## 常见误解

**「只要安装了技能，机器人就自动获得了对应的工具？」**
并不一定。技能的核心是传授流程和方法，具体的敲砖打底依然要依托工具完成。少数技能会打包自带专属的辅助脚本工具，但绝大多数技能还是在指导模型如何更好调用现有的基础工具。

**「接入的 MCP 服务越多越好吗？」**
并不是。每一个接入的 MCP 服务都会带来一整套工具定义，并产生持续的上下文检索成本。对于已经不用的外部服务，及时在控制台将其停用，比长期挂在后台吃灰要划算得多。

**「在控制台把工具设为禁用，等于把插件卸载了吗？」**
完全不是。禁用只是将该工具对模型临时隐藏，底层插件依然在后台正常运转，随时可以一键恢复启用。

**「需要审批的弹窗太繁琐，干脆把工具全改成放行好不好？」**
不建议这么做。审批机制的核心价值是拦截模型偶然的推理幻觉与误操作，而不是阻碍正常业务。如果你发现某个工具每次都能顺利通过人工审批，将其策略调整为自动执行会更舒适；反之，如果某个工具频频被拒绝，说明它打一开始就不该暴露在该场景中。

## 推荐起点

如果你刚刚接手 ChatLuna 的配置工作，面对众多功能不知道从何下手，不妨按照这套节奏来起步：

1. 首先打开「工具」页面，整体浏览一遍清单，把命令执行、文件写入这类涉及系统变更的高危工具手动设为需要审批；
2. 挑选一两个平时最常用的核心 MCP 服务接入，并保持其工具的按需加载默认设置；
3. 暂时不需要急着编写技能文件，先观察日常对话，直到发现「模型总是记不住操作步骤、容易忙中出错」时，再针对性地补上技能。

一口气添加过多能力，不仅容易让模型在选择时陷入迷茫，一旦排查起问题来也更难定位根因。

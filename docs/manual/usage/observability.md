# 轨迹与用量

::: tip
这一页讲两件事：一次回复到底发生了什么（轨迹），以及这些回复花了多少钱（用量）。出问题时先看轨迹，算账时先看用量。
:::

当机器人不仅用于日常闲聊，还接入了网络搜索、长期记忆或外部工具调用等复杂功能时，单看聊天窗口中的最终回复，往往很难了解背后的具体执行过程。

如果某次回合出现答非所问、响应迟缓，或者月底账单超出预期，我们往往需要知道：到底具体卡在哪一步？又是哪些功能消耗了最多的额度？

为了解决这些问题，ChatLuna 会将每一次模型调用、工具执行与提示词装配完整记录为执行轨迹。

这里的轨迹不是无序的纯文本日志，而是一棵结构化的树状链路：一个对话回合可以包含多个步骤，每个步骤包含具体的模型或工具调用，工具内部还可以嵌套子代理。

用量统计则直接基于这些轨迹数据进行汇总。系统会按模型、用途、插件和平台等维度，将资源消耗折算为 Token 数量与预估成本，方便你随时了解运行开销。

## 轨迹页

进入控制台，点击左侧导航栏的「观测 → 轨迹」，即可查看当前会话的历史执行记录。

页面顶部提供了三泳道时间轴总览视图，自上而下分别对应回合、步骤以及底层的模型/工具调用。时间轴以毫秒为单位展开整个执行过程，直观呈现每一步的耗时与资源开销。

### 记录表

时间轴下方是按回合与步骤归类的调用记录表。

在列表中点击任意一条调用记录，右侧会展开对应的检查器面板。你可以在这里查看本次调用的详细信息：

- **提供商与模型**：本次请求使用的 Provider 实例与具体模型名称。
- **响应速度与耗时**：包括首 Token 返回时间（TTFT）、整体请求耗时以及每秒 Token 解码速度。
- **Token 消耗**：输入 Token、输出 Token 以及提示词缓存命中的 Token 数量。
- **上下文与提示词归属**：请求拼接的系统提示词片段与挂载的工具，以及各部分分别来自哪个已安装插件。
- **工具调用细节**：模型传入的参数、工具返回的原始内容、执行耗时以及权限安全判定结果。
- **异常诊断信息**：请求失败时的错误原因与具体错误代码。

借助检查器面板，你可以快速定位回复缓慢、工具未被调用或提示词异常等具体问题。

### 时间线回放

除了检查器面板，你还可以切换到「时间线回放」视图。

时间线回放将单次回合内部发生的所有事件，按时间先后顺序自上而下平铺展开：

- 用户的消息何时进入接收队列。
- 模型在什么时间开始接收输入并开始生成，何时结束。
- 外部工具在何时被触发、执行了多长时间、何时返回结果。
- 上下文压缩、人工审批与子代理切入等特殊动作在主流程中的具体时机。

时间线回放直接展示已记录的落盘事件，不会在后台重新发起请求。它适合用来梳理并行或嵌套事件的因果顺序，定位阻塞环节。

### 把某一步改成草稿重新调用

排查问题时，我们常需要验证修改某句提示词或更换模型后的效果。

轨迹页支持原地调试。在记录表中选中任意一步模型调用，点击右上角的「作为草稿重新调用」按钮，系统会将当时的上下文、提示词与参数配置复制到草稿编辑抽屉中。

<!-- 截图占位：轨迹页 · 草稿重放与参数调试抽屉 -->

在抽屉中，你可以修改提示词内容、临时切换其他提供商的模型，或微调温度等生成参数，然后点击「重新调用」发起测试。

重新调用会直接与模型对话，脱离原有的 Agent 循环。返回的结果会作为实验记录保存在抽屉中，不会写回或污染现有的聊天会话。

这一功能通常用于：

- 调整提示词措辞，对比不同表达下的回复效果。
- 临时切换轻量模型或高规格模型，比较质量与 Token 消耗。
- 复现偶现的异常回复，验证属于模型幻觉还是提示词诱导。

::: warning
实验调用依然会向模型提供商发起真实请求并产生 Token 费用；若允许了工具执行，也会实际产生副作用。进行测试前，请确认当前权限模式，或在面板中手动禁用相关工具。
:::

### 进程视图

除了与具体聊天会话直接关联的交互轨迹，轨迹页顶部还提供了「进程」视图标签。

切换到「进程」视图后，可以查看在日常会话之外静默执行的后台调用：

- **后台维护任务**：对话历史自动压缩、会话标题智能生成、长期记忆提炼与提取、文本向量化（Embedding）以及实例启动设置等后台调用。
- **系统生命周期**：插件动态注册上线与配置项热变更的历史轨迹。
- **安全审批流**：工具权限审批请求的发起、审批人操作与最终裁决结果。

这些后台调用同样会消耗 Token 并占用资源。如果对账时发现费用超出预期，或者会话空闲时仍有系统负载，可以在进程视图中排查明细。

## 用量页

了解单次回调的细节后，我们再来看整个实例的资源消耗与成本核算。

点击控制台左侧导航栏的「观测 → 用量」，系统会将轨迹中的用量数据聚合为统计报表。

### KPI

用量页顶部展示了一组核心指标卡片：

- **请求数**：选定时间范围内发起的模型请求总次数。
- **输入 / 输出 Token**：输入端与输出端累计消耗的 Token 数量。
- **成本**：根据配置单价计算出的累计预估费用。
- **平均首 Token 时间**：模型起步响应的平均耗时。
- **P95 耗时**：反映长尾延迟的关键指标，表示 95% 的请求在该时间内完成。
- **成功率**：整体请求成功的百分比。

这些指标支持通过右上角的时间范围选择器进行筛选。控制台仪表板中的「今日用量」卡片，就是基于今日时间范围展示的精简统计。

### 分组

在核心指标下方，用量页提供了多维分组视图。你可以通过下拉菜单按不同维度汇总查看数据：

- **模型 / 提供商**：统计每个具体模型或 Provider 占用的资源。
- **用途分类**：按对话交互、上下文压缩、记忆提炼、意图判定、标题生成、向量化等分类汇总。
- **插件来源**：查看各个插件分别带来的资源消耗。
- **平台渠道**：对比不同聊天平台群组或频道的调用量与开销。
- **会话或用户**：定位具体会话或活跃用户的消耗情况。

通过分组筛选，可以快速了解成本主要集中在哪些模型、插件或会话中。

### 调用明细

页面下半部分提供了按时间倒序排列的「调用明细」列表：

- 每一行展示了发生时间、调用模型、用途分类、Token 开销、折算成本、执行耗时以及最终状态。
- 因网络中断或配额不足而失败的调用也会完整记录，并附带错误描述。
- 点击右上角的「导出 CSV」按钮，可将明细数据导出为本地表格文件。
- 点击任意一行记录，可直接跳转到轨迹页中对应的具体步骤。

注意，失败的调用往往同样会产生计费或占用并发配额。排查异常开销时，也应当重点检查失败记录。

### 成本怎么算

用量页展示的成本金额，是由各项 Token 消耗量乘以对应单价计算得出的。系统支持两种单价配置方式：

- **使用模型目录里的默认价格**：直接使用系统内置的模型基准费率。
- **在用量插件中自定义单价**：在用量插件的配置界面中，针对具体的提供商与模型，分别为普通输入、缓存读取和输出配置单价。

通常情况下，缓存读取单价低于常规输入单价，而首次写入缓存可能略高。若未单独配置缓存价格，系统会采用统一规则进行估算。

::: tip
用量页展示的成本属于基于配置单价核算的预估值，并非服务商账单。各提供商通常包含阶梯折扣、限时活动或币种结算差异；实际核算请以提供商控制台的账单为准，用量页主要用于观察长期趋势与插件消耗分布。
:::

## 插件怎么标注用量

为了便于统计，插件在发起模型调用时，可以主动标注用途标签（例如「记忆提取」「标题生成」或「判定」）。用量页的分类汇总便基于这些标签进行归类。

在插件运行过程中：

- 插件可以在配置面板中声明全局默认的用途与标签。
- 发起特定调用时，可以覆盖并指定单次调用的用途与标签。
- 未走统一调用入口的特殊调用，也可以通过标准接口手动上报用量数据。

如果调用时未指定标签，系统会将其归入「未分类」一栏。

合理的用途标注有助于更清晰地分析报表，但在配置时无需过度细化，避免增加不必要的记录开销。

## 缓存看板

在仪表板界面中，你可以通过 KV 缓存看板卡片监控各会话的 Epoch 代数演变与前缀复用情况。

正常运行状态下的会话通常具有以下表现：

- 对话回合数随聊天平稳增长。
- Epoch 代数维持在较低水平。
- 前缀作废次数接近于 0。

如果 Epoch 代数增长接近回合数，说明提示词前缀在几乎每一轮对话中都被重新构建。

导致缓存频繁作废的常见原因包括：

- **把易变动态内容塞进系统提示词**：例如将精确到秒的系统时间或实时变动的状态标记放入前置提示词中。
- **每一轮对话都在动态增删工具**：工具列表频繁变动导致前缀不一致。
- **频繁跨模型切换**：同一会话在不同回复间来回切换模型。
- **预设或人设频繁切换**：人设模板变动导致系统设定被整体重写。

排查时，可以在轨迹页中查看请求的提示词片段来源，并结合缓存看板记录的 Epoch 突变时间点，定位破坏前缀缓存的具体插件。

## 命令行诊断

当网络波动、配置异常导致 WebUI 无法访问，或者服务无法正常启动时，可以使用 ChatLuna 内置的命令行离线诊断工具：

- `chatluna doctor config`：全方位检查系统配置合法性、插件清单以及认证守卫的运行状态。
- `chatluna doctor session <id>`：针对指定的会话 ID，深入校验其会话日志的不变量与数据完整度。
- `chatluna doctor cache <id>`：专项检查指定会话的前缀缓存健康度与 Epoch 代数演变。
- `chatluna doctor providers`：实时检测各个已配置提供商的网络连通性与服务响应能力（需要后台服务进程处于存活状态）。
- `chatluna export <id>`：将指定会话的完整轨迹与上下文无损导出为 JSONL 文件，专门用于向官方或社区反馈问题。

命令行诊断工具独立于 WebUI 运行，适合在无图形界面的服务器环境下进行排障。

## 日志页

在控制台侧边栏中，你可以打开「日志」页面。

日志页按时间流输出系统底层的运行日志。相比业务视角的轨迹，日志更适合观测基础服务状态：

- 系统的启动与关闭流程。
- 插件的动态加载、卸载与热重载记录。
- 接口连接失败、网络超时重试与速率限制提示。
- 权限系统的安全拒绝事件与人工审批超时记录。

日志与轨迹的分工非常明确：日志按时间记录底层系统的运行流水，轨迹按结构呈现单次人机交互的完整因果。

排查单次回复异常时建议查看轨迹，排查系统报错或网络问题时建议查看日志。

## 推荐用法

面对常见问题时，可以参考以下排查步骤：

### 回复变慢

当机器人回复延迟明显拉长时：

1. 打开「观测 → 轨迹」，查看顶部时间轴上的回合和步骤耗时，判断是模型响应慢、工具执行慢还是排队等待时间长。
2. 点击具体模型调用的检查面板，查看「首 Token 时间」和「解码速度」。若首 Token 时间过长，多与网络延迟或提供商排队有关；若首 Token 正常但总耗时长、解码速度低，多为输出文本较长或模型生成较慢。

### 费用突然上涨

当用量账单出现异常增长时：

1. 进入「观测 → 用量」页面，按「模型」与「用途」维度查看分布，确认高额消耗对应的模型或后台功能。
2. 切换至「插件」分组，排查近期新增或更新的插件是否存在高频调用。
3. 查看底部的「调用明细」列表，检查是否有单次输入过长或失败后频繁重试的记录。

### 缓存不命中

当缓存复用率较低、调用成本偏高时：

1. 前往仪表板的「缓存看板」，观察各会话的 Epoch 代数走势，找到代数异常升高的会话。
2. 打开「观测 → 轨迹」中该会话对应的步骤，比对各次请求装配的提示词来源。
3. 检查是否有插件将动态时间或易变变量拼入了系统提示词，或是否存在频繁增删的工具列表。

### 模型没调用工具

当已配置的工具未被模型触发时：

1. 在轨迹页中打开对应步骤的模型调用详情，检查右侧面板中的「可见工具列表」与工具定义。
2. 若工具未列出，请检查控制台中该工具的策略开关、场景规则权限或可见性过滤配置。
3. 若工具已正常列出但未被调用，通常是由于工具的自然语言描述不够明确，或入参定义过于复杂导致模型无法准确识别。

## 排查

遇到常见异常时，可参考以下建议：

**轨迹页没有记录。**
请确认轨迹插件本身是否已开启，并检查对应的输出汇（会话存储、JSONL 文件或 OpenTelemetry 链路）配置是否已启用。轨迹服务在内存中独立运作，但如果没有挂载任何持久化汇，执行完毕的数据将不会写入磁盘。

**用量和 provider 账单对不上。**
用量页展示的费用纯属估算；请确认用量插件里的单价配置是否与提供商一致，并检查缓存读取单价的计算策略。另外，失败的调用与频繁的后台任务也会产生开销，请务必切到用量页的「进程」视图中核对会话之外的调用明细。

**轨迹里看不到提示词全文。**
提示词内容在展示时可能触发了长度截断或敏感信息脱敏规则。请前往系统设置中检查轨迹与隐私相关选项；在多用户共享的实例部署中，管理员往往会出于隐私安全考虑有意隐去完整的上下文提示词。

**导出文件很大。**
由于导出的完整 JSONL 包含了深度的会话历史日志与工具执行返回的原始数据块，体积通常较为庞大。在导出前，可以先在终端中通过 `chatluna doctor session <id>` 检验不变量健康度，或者针对性地仅导出存在问题的单个特定会话。

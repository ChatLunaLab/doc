# 轨迹与用量

::: tip
这一页讲两件事：一次回复到底发生了什么（轨迹），以及这些回复花了多少钱（用量）。出问题时先看轨迹，算账时先看用量。
:::

当机器人的能力越来越丰富，不仅能陪大家日常闲聊，还会主动搜索网络、检索长期记忆、甚至调用外部工具执行复杂操作时，单凭聊天窗口里最终呈现的文字，往往很难看清背后的真实过程。

如果某次回话明显答非所问，或者迟迟没有反应，究竟是模型本身的理解出现了偏差，还是某个外部工具卡住了？又或者，到了月底查看账单，发现调用费用比预期高出一大截，到底又是哪一项功能在默默消耗额度？

为了帮大家理清这些疑问，ChatLuna 把每一次模型调用、工具执行和提示词装配，都完整记录成了可供回溯的执行轨迹。

这里的轨迹并不是杂乱无章的纯文本控制台日志，而是一棵层次分明的树状因果链路：一个完整的对话回合往往包含多个执行步骤，一个步骤又包含了具体的模型调用与工具调用，而工具调用内部甚至还可能嵌套着负责特定子任务的子代理。

至于用量统计，则是直接从这些细致的轨迹数据中自动汇总提炼出来的。系统会按照模型、用途、插件以及平台等多个维度，将所有的资源消耗折算成 Token 数量与预估成本，让你对整个实例的运行开销一目了然。

## 轨迹页

打开控制台，在左侧导航栏中点击「观测 → 轨迹」，映入眼帘的就是当前会话的历史执行记录。

页面顶部是一张直观的三泳道时间轴总览视图，自上而下分别对应着：回合、步骤以及底层的模型/工具调用。时间轴以毫秒为单位将整个执行过程完全拉平，让你一眼就能看出哪一步耗时最长、哪一次调用花费的资源最多。

### 记录表

在时间泳道下方，呈现的是按回合与步骤层层归类、整齐排列的调用记录表。

在日常使用中，如果你发现某一次回复表现异常，直接在列表中点击对应的调用条目，右侧面板就会立刻滑出详尽的检查器面板。在这里，你可以逐一核对：

- **提供商与模型**：本次请求具体指向了哪个 Provider 实例，使用的是哪一款模型。
- **响应速度与耗时**：包括首 Token 返回时间（TTFT）、整体请求耗时以及每秒 Token 的解码速度。
- **Token 消耗**：清晰区分输入 Token、输出 Token 以及提示词缓存命中的 Token 数量。
- **上下文与提示词归属**：这次请求到底拼接了哪些系统提示词片段，又挂载了哪些外部工具，并且每一段内容分别来自哪个已安装的插件。
- **工具调用细节**：模型给工具传递了哪些具体参数、工具返回了怎样的原始内容、工具执行消耗了多久，以及它在权限体系中触发了怎样的安全判定。
- **异常诊断信息**：如果请求不幸遇到阻碍，面板会直接标红给出失败原因和具体的错误代码。

借助这一块检查面板，诸如「为什么刚才那句话回复那么慢」「为什么模型明明能联网却没调用搜索工具」「这段奇怪的提示词到底是谁塞进来的」等疑问，都能在几秒钟之内找到明确的答案。

### 时间线回放

如果你觉得静态查看单个步骤还不够直观，不妨切换到「时间线回放」视图。

时间线回放将单次回合内部发生的所有细碎事件，严格按照时间先后顺序从上至下平铺展开。顺着这条时间线，你可以清楚地看到：

- 用户的聊天消息是在哪个确切的时间点进入收件箱的。
- 模型在什么时候开始接收输入并开始生成，又在什么时候彻底结束。
- 外部工具在哪个间隙被触发，中间执行了多久，何时交还了执行结果。
- 对话上下文压缩、管理员人工审批、子代理切入等特殊动作，是在什么位置插入主流程的。

需要说明的是，时间线回放并不是把刚才的请求在后台重新跑一遍，而是将已落盘记录的事件按时间轴完整展开呈现。它非常适合用来理清各种并行或嵌套事件的先后因果，帮助你快速判断到底是谁在阻塞下游链路。

### 把某一步改成草稿重新调用

排查问题时，我们经常会萌生这样的想法：如果我把当时的提示词改掉一个词，或者换一个理解能力更强的大模型，它会不会就能给出正确的答案了？

轨迹页为你提供了非常贴心的原地调试能力。在记录表中选中任意一步模型调用，点击右上方醒目的「作为草稿重新调用」按钮，系统就会把当时的全部上下文、提示词和参数配置完整复制到草稿编辑抽屉中。

<!-- 截图占位：轨迹页 · 草稿重放与参数调试抽屉 -->

在这里，你可以自由修改提示词措辞、临时更换为其他提供商的模型，或者微调温度等生成参数，然后直接点击「重新调用」发起测试。

这次调用会脱离原本的 Agent 自动循环直接与模型对话，返回的结果会作为独立的实验记录单独保存在抽屉中，完全不会污染或写回你现有的聊天会话。

这项功能非常适合用来：

- 尝试换一种提示词引导方式，现场对比模型回复的语气与准确度。
- 一键切换到更轻量或更昂贵的新模型，横向比较回复质量与 Token 成本。
- 稳定复现某个偶现的诡异回答，快速验证这到底是模型本身的幻觉还是提示词诱导所致。

::: warning
请注意，实验调用仍然会向模型提供商发起真实的请求，并产生真实的 Token 费用；如果测试中允许了工具执行，也可能会真正触发生效。在执行带有副作用的实验前，请先确认当前的权限模式，或在面板中手动禁用相关工具。
:::

### 进程视图

除了与具体聊天会话直接挂钩的交互轨迹之外，轨迹页顶部还提供了一个名为「进程」的视图标签。

点击切换到「进程」视图后，你将看到一系列在日常会话之外静默执行的系统后台调用：

- **后台维护任务**：对话历史自动压缩、会话标题智能生成、长期记忆提炼与提取、文本向量化（Embedding）以及实例启动设置等后台调用。
- **系统生命周期**：各个插件动态注册上线，以及配置项发生热变更的历史轨迹。
- **安全审批流**：工具权限审批请求的发起、审批人操作以及最终的处理裁决结果。

这些调用虽然在聊天窗口里完全隐形，但同样会在后台默默消耗 Token，也可能短暂占用系统资源。如果你在对账时发现「费用对不上」，或者觉得机器人在没聊几句时也有后台负载，先切到进程视图里看一看，通常就能真相大白。

## 用量页

理清了一次回复内部的细枝末节后，我们再来看看实例整体的资源消耗与成本核算。

点击控制台左侧导航栏的「观测 → 用量」，系统就会把所有分散在轨迹里的用量数据聚合汇总成清晰美观的分析报表。

### KPI

刚进入用量页，页面顶部首先陈列着一组核心指标卡片：

- **请求数**：选定时间段内发起的模型请求总次数。
- **输入 / 输出 Token**：直观展示输入端与输出端各自累计消耗的 Token 数量。
- **成本**：系统基于配置单价自动换算出的累计预估费用。
- **平均首 Token 时间**：衡量模型起步响应快慢的平均耗时。
- **P95 耗时**：反映长尾请求延迟的关键指标，即 95% 的请求都在此时间内完成。
- **成功率**：整体请求执行成功的百分比。

这些核心指标支持通过右上角的时间范围选择器进行自由筛选。你在主界面仪表板中看到的「今日用量」卡片，本质上就是这套统计数据在今日范围下的精简版本。

### 分组

在关键指标下方，用量页提供了强大的多维分组与数据透视能力。你可以通过下拉菜单自由切换视角，按以下维度进行归类查看：

- **模型 / 提供商**：统计每一款具体模型或 Provider 占用了多少资源。
- **用途分类**：按对话交互、上下文压缩、记忆提炼、意图判定、标题生成、向量化等分类汇总。
- **插件来源**：清晰洞察各个功能插件分别带来了多少消耗。
- **平台渠道**：对比不同聊天平台群组或频道的活跃度与开销。
- **会话或用户**：精确锁定到底是哪一个具体会话或哪一位活跃用户用得最多。

借助这些细致的分组维度，你可以轻而易举地解答「钱究竟花在哪个模型上」「最近新装的插件是不是太贵了」「哪一个群聊消耗了最多预算」等管理难题。

### 调用明细

如果你需要定位某笔异常消费的具体出处，可以在页面下半部分查看详尽的「调用明细」列表。

明细表格按照时间倒序完整列出了每一次调用流水：

- 每一行都清晰呈现了发生时间、调用模型、用途分类、Token 开销、折算成本、执行耗时以及最终的状态结果。
- 即便某次调用因为网络中断或接口配额不足而失败，系统也会完整予以记录，并附带明确的错误描述。
- 如果需要配合电子表格进行深入分析，点击右上角的「导出 CSV」按钮，即可一键下载全量报表。
- 点击任意一行流水记录，页面就会立刻精准跳转到轨迹页中对应的那一步，方便你无缝切入当时的执行现场。

需要特别提醒的是，失败的调用往往同样会产生计费，或者至少占据了你的请求并发额度。因此在排查异常开销或服务波动时，千万不要只看成功记录，失败条目同样需要仔细审视。

### 成本怎么算

用量页上展示的成本金额，是由消耗的各项 Token 数量乘以对应的单价自动计算得出的。系统支持两种灵活的单价配置方式：

- **使用模型目录里的默认价格**：直接继承系统内置的模型基准费率。
- **在用量插件中自定义单价**：在用量插件的配置界面中，针对具体的提供商与模型名称，单独为普通输入、缓存读取以及输出分别配置单价。

在当前的大模型生态中，缓存读取通常比常规输入便宜许多，而首次写入缓存可能会略微偏贵。如果你并未单独指定缓存价格，系统会采用保守的方式统一进行估算。

::: tip
用量页所展示的成本属于基于配置单价核算出的估算值，并不是服务商给出的最终账单。不同模型提供商通常拥有复杂的阶梯优惠、时限活动或币种转换规则；在实际对账时请始终以提供商控制台的账单为准，用量页的核心价值在于观测长期趋势与各插件间的相对消耗比例。
:::

## 插件怎么标注用量

为了保证用量报表井然有序，插件在发起模型调用时，可以主动为这次调用打上用途标签，例如「记忆提取」「标题生成」或是「判定」。用量页在汇总数据时，正是根据这些标签来进行精准归类的。

在实际使用与插件运行中：

- 插件可以在自身的配置面板中声明全局默认的用途和标签。
- 在运行时发起特定动作时，单次调用也可以随时覆盖并指定新的用途和标签。
- 对于那些没有走统一模型调用入口的特殊调用，插件也可以通过标准接口手动记录其用量数据。

如果某个调用在发起时完全没有指定标签，系统会将其归入「未分类」一栏。

归类做得越细腻，用量页的统计报表就越有参考价值；但也不必走向极端给每次调用打上密密麻麻的标签，标签本身也是需要占用存储与检索资源的。

## 缓存看板

在仪表板界面中，你可以看到专门的 KV 缓存看板卡片。它主要负责监控各个会话的 Epoch 代数演变以及前缀复用情况。

在一个处于良性运行状态的会话中，你所看到的理想指标应当是：

- 对话回合数伴随着聊天正常平稳增长。
- Epoch 代数始终保持在一个极低的数值。
- 前缀作废的发生次数无限接近于 0。

相反，如果你发现 Epoch 代数几乎追平了回合数，这就意味着提示词前缀几乎每一轮都在被全盘摧毁并重新构建。

导致缓存频繁作废的常见诱因通常包括：

- **把易变动态内容塞进系统提示词**：例如把精确到秒的当前系统时间、实时变动的状态标记写进了前置提示词。
- **每一轮对话都在动态增删工具**：工具列表频繁变动破坏了前缀的一致性。
- **频繁跨模型切换**：同一会话在不同回复之间来回变更模型。
- **预设或人设频繁切换**：频繁切换人设模板导致系统设定发生翻天覆地的变化。

排查这类问题其实非常简单：轨迹页能清楚看到每一次请求中提示词片段的完整来源，而缓存看板则准确记录了 Epoch 发生突变的时间节点。两者结合起来对照查看，通常不出几分钟就能精准定位到是哪一个插件破坏了前缀缓存。

## 命令行诊断

当网络波动、配置损坏导致 WebUI 打不开，或者整个服务甚至无法启动时，我们该怎么办呢？

ChatLuna 内置了强大的命令行离线诊断工具，无需依赖图形界面，在服务器终端中直接运行命令即可快速完成系统体检：

- `chatluna doctor config`：全方位检查系统配置合法性、插件清单以及认证守卫的运行状态。
- `chatluna doctor session <id>`：针对指定的会话 ID，深入校验其会话日志的不变量与数据完整度。
- `chatluna doctor cache <id>`：专项检查指定会话的前缀缓存健康度与 Epoch 代数演变。
- `chatluna doctor providers`：实时检测各个已配置提供商的网络连通性与服务响应能力（需要后台服务进程处于存活状态）。
- `chatluna export <id>`：将指定会话的完整轨迹与上下文无损导出为 JSONL 文件，专门用于向官方或社区反馈问题。

这些命令行诊断工具完全独立于 WebUI 运行，极为适合在没有桌面环境的 Linux 服务器或生产机上快速开展排障。

## 日志页

在 WebUI 控制台的侧边栏中，你同样可以找到熟悉的「日志」页面。

日志页按照时间流连续输出系统最原始的运行日志。相比于业务视角的轨迹，它更适合用来观测底层基础设施层面的状态：

- 系统的完整启动与安全关闭过程。
- 各功能插件的动态加载、卸载与热重载流水。
- 远程接口连接失败、网络超时重试以及速率限流警告。
- 安全系统的权限拒绝事件以及人工审批超时记录。

我们可以把它们的分工简单概括为：日志是一条线性的纯文本流，忠实记录系统运行的底层脉搏；轨迹则是一棵立体的结构化树，生动还原每一次人机对话的完整因果。

排查具体某一次回复的表现时看轨迹，排查系统服务级异常或网络连接故障时看日志。

## 推荐用法

为了让你在面对各种偶发异常时心中有数，这里总结了几种最典型场景的标准化排查建议：

### 回复变慢

当群聊或私聊中机器人的回复明显变卡、延迟拉长时：

1. 打开「观测 → 轨迹」，首先查看顶部时间轴上的回合和步骤总耗时，一眼区分到底是模型请求慢、外部工具执行慢，还是在任务队列中排队过久。
2. 随后点开具体模型调用的检查面板，重点观察「首 Token 时间」和「解码速度」。如果首 Token 时间很长，通常说明网络链路不畅或提供商排队严重；如果首 Token 很快但总耗时长、解码速度低，则往往是因为输出内容过长或是模型本身推理算力吃紧。

### 费用突然上涨

如果你在检查用量时发现账单出现了异常飙升：

1. 进入「观测 → 用量」页面，按「模型」与「用途」维度展开透视，确认到底是哪一款模型、哪一项后台功能在集中消耗额度。
2. 切换到「插件」分组，排查是不是最近新启用的某款插件调用频率过高。
3. 检查底部的调用明细列表，看看是否存在输入内容异常庞大的单次请求，或者模型报错后频繁发起的无限自动重试。

### 缓存不命中

如果你发现缓存复用率极低，调用成本居高不下：

1. 前往仪表板的「缓存看板」，观察各个会话的 Epoch 代数递增趋势，找出 Epoch 异常偏高的会话。
2. 根据时间点打开「观测 → 轨迹」中该会话的对应步骤，比对每次请求装配的提示词来源。
3. 检查是否有插件将动态时间、随叫随变的环境变量注入到了系统提示词中，或者是否存在频繁变动的工具列表。

### 模型没调用工具

明明为机器人配置好了好用的能力工具，但它在对话中却偏偏不肯使用：

1. 在轨迹页中点开该步骤的模型调用详情，仔细检查右侧面板里的「可见工具列表」与对应的工具定义。
2. 如果该工具根本没有出现在列表中，请回到控制台检查工具本身的策略开关、场景规则中的权限约束，或者是否存在可见性过滤规则。
3. 如果工具稳稳地存在于列表中但模型依然选择视而不见，多半是因为该工具的自然语言功能描述不够清晰，或者入参要求过于晦涩复杂导致模型无法准确识别调用时机。

## 排查

在日常运维与观测实践中，如果遇到以下困扰，请按以下提示进行排查：

**轨迹页没有记录。**
请确认轨迹插件本身是否已开启，并检查对应的输出汇（会话存储、JSONL 文件或 OpenTelemetry 链路）配置是否已启用。轨迹服务在内存中独立运作，但如果没有挂载任何持久化汇，执行完毕的数据将不会写入磁盘。

**用量和 provider 账单对不上。**
用量页展示的费用纯属估算；请确认用量插件里的单价配置是否与提供商一致，并检查缓存读取单价的计算策略。另外，失败的调用与频繁的后台任务也会产生开销，请务必切到用量页的「进程」视图中核对会话之外的调用明细。

**轨迹里看不到提示词全文。**
提示词内容在展示时可能触发了长度截断或敏感信息脱敏规则。请前往系统设置中检查轨迹与隐私相关选项；在多用户共享的实例部署中，管理员往往会出于隐私安全考虑有意隐去完整的上下文提示词。

**导出文件很大。**
由于导出的完整 JSONL 包含了深度的会话历史日志与工具执行返回的原始数据块，体积通常较为庞大。在导出前，可以先在终端中通过 `chatluna doctor session <id>` 检验不变量健康度，或者针对性地仅导出存在问题的单个特定会话。

# 轨迹与用量

::: tip
这一页讲两件事：一次回复到底发生了什么（轨迹），以及这些回复花了多少钱（用量）。出问题时先看轨迹，算账时先看用量。
:::

ChatLuna 把每次模型调用、工具执行和提示词装配都记录成可回看的轨迹。轨迹不是简单的日志文本，而是一棵有因果关系的树：一个回合包含多个步骤，一个步骤包含模型调用和工具调用，工具调用还可能属于某个子代理。

用量则从这些轨迹里汇总出来，按模型、用途、插件、平台分组，折算成 token 和成本。

## 轨迹页

侧边栏「观测 → 轨迹」按会话展示执行记录。顶部通常有三条泳道：回合、步骤、模型/工具调用。时间轴让你一眼看出哪一步慢、哪一步花得多。

### 记录表

记录按回合和步骤分组。点开一次调用，可以看到：

- 请求使用的模型和 provider。
- 首 token 时间、总耗时、解码速度。
- 输入、输出、缓存命中的 token。
- 这次请求用到了哪些工具、哪些提示词片段，分别来自哪个插件。
- 工具调用的参数、结果、耗时和权限判定。
- 如果失败，失败原因和错误码。

这些信息足够回答「为什么这次回复很慢」「为什么模型没调用工具」「这段提示词是谁加的」。

### 时间线回放

时间线把一次回合内的事件按发生顺序排开。你可以看到：

- 消息什么时候进入收件箱。
- 模型什么时候开始、什么时候结束。
- 工具什么时候执行，执行了多久。
- 压缩、审批、子代理在什么位置插入。

回放不是重新执行，只是把已记录的事件按时间展开。它适合理解「先后关系」和「谁阻塞了谁」。

### 把某一步改成草稿重新调用

轨迹页可以取任意一步的请求，修改后作为草稿重新调用模型。这次调用不经过 Agent 循环，结果作为实验保存，不会写回原来的会话。

适合：

- 换一个提示词，看看模型会怎么回。
- 换一个模型，比较质量和成本。
- 复现某个奇怪输出，确认是不是提示词的问题。

::: warning
实验调用仍然会产生真实费用，也可能触发工具。做危险实验前先确认当前权限模式，或把工具禁用。
:::

### 进程视图

除了按会话看，轨迹还有一个「进程」视图，展示会话之外的调用：

- 压缩、标题生成、记忆提取、embedding、setup 等后台调用。
- 插件注册和配置变化的历史。
- 审批请求和处理结果。

这些调用没有直接对应的聊天消息，但同样花 token，也会影响延迟。排查「费用对不上」时，先看这里。

## 用量页

侧边栏「观测 → 用量」把轨迹里的 usage 汇总成可读的报表。

### KPI

顶部通常展示：

- 请求数。
- 输入 / 输出 token。
- 成本。
- 平均首 token 时间。
- P95 耗时。
- 成功率。

这些指标可以按时间范围筛选。仪表板的「今日用量」卡片是同一套数据的简版。

### 分组

用量可以按这些维度分组：

- 模型 / provider。
- 用途：对话、压缩、记忆提取、判定、标题、embedding 等。
- 插件。
- 平台。
- 会话或用户。

分组帮助你回答「钱花在哪个模型上」「哪个插件最贵」「哪个群用得最多」。

### 调用明细

明细表列出每次调用：

- 时间、模型、用途、token、成本、耗时、状态。
- 失败的调用也会记录，并带错误信息。
- 可以导出 CSV。
- 点开一条可以跳到轨迹页对应的那一步。

失败调用也计费或至少计入请求数，所以排查异常时不要只看成功记录。

### 成本怎么算

成本由 token 数乘以单价得出。单价可以：

- 使用模型目录里的默认价格。
- 在用量插件里为某个 `provider:model` 单独配置输入、缓存读取、输出单价。

缓存读取通常比普通输入便宜，缓存写入可能更贵。没有配置缓存价格时，系统会按保守方式估算。

::: tip
成本是估算值，不是账单。不同 provider 的计费规则、阶梯价、缓存折扣可能和配置不一致；对账时以 provider 的账单为准，用量页用于趋势和相对比较。
:::

## 插件怎么标注用量

插件在发起模型调用时，可以标注这次调用的用途和标签，例如「记忆提取」「标题生成」「判定」。用量页据此分组。

- 插件可以在配置里声明默认用途和标签。
- 运行时可以覆盖单次调用的用途和标签。
- 不经过统一模型调用入口的调用，可以手动记录用量。

没有标注的调用会归到「未分类」。归类越细，用量页越有用；但也不要为了归类给每次调用加太多标签，标签本身也会占空间。

## 缓存看板

仪表板里有 KV 缓存看板，展示会话的 epoch 和前缀复用情况。理想状态是：

- 回合数在增长。
- epoch 数保持很少。
- 前缀作废次数接近 0。

如果 epoch 数接近回合数，说明有东西每轮都在变。常见原因：

- 把时间、状态等易变内容放进了系统提示。
- 每轮都在增删工具。
- 频繁切换模型。
- 预设或人设频繁切换。

轨迹页能看到每次请求的提示词来源，缓存看板能看到 epoch 变化的时间点。两者结合，通常能定位到是哪个插件在破坏前缀。

## 命令行诊断

服务起不来或 WebUI 打不开时，可以用命令行离线诊断：

- `chatluna doctor config`：检查配置、manifest、认证守卫。
- `chatluna doctor session <id>`：检查会话日志不变量。
- `chatluna doctor cache <id>`：检查前缀缓存和 epoch。
- `chatluna doctor providers`：检查 provider 连通性，需要活进程。
- `chatluna export <id>`：导出完整 JSONL，用于上报问题。

这些命令不依赖 WebUI，适合在生产机上直接跑。

## 日志页

WebUI 的日志页展示运行日志。它适合看：

- 启动和关闭过程。
- 插件加载、卸载、重载。
- 连接失败、重试、限流。
- 权限拒绝和审批超时。

日志是文本流，轨迹是结构化树。排查具体一次回复用轨迹，排查系统级问题用日志。

## 推荐用法

### 回复变慢

先看轨迹的回合和步骤耗时，定位是模型慢、工具慢，还是排队。再看首 token 时间和解码速度；首 token 慢通常是网络或 provider 排队，解码慢通常是输出太长或模型本身慢。

### 费用突然上涨

看用量页的趋势和分组，确认是哪个模型、哪个用途、哪个插件在涨。再看调用明细里有没有异常长的输入，或者失败的重复重试。

### 缓存不命中

看缓存看板的 epoch 变化，结合轨迹里的提示词来源，找出每轮变化的部分。常见是时间变量、工具列表、模型配置。

### 模型没调用工具

在轨迹里看这一步的可见工具列表和工具 schema。如果工具不在列表里，检查工具策略、场景规则和可见性过滤；如果在列表里但模型没调用，可能是描述不清楚或参数太复杂。

## 排查

**轨迹页没有记录。**
确认轨迹插件和对应的汇（session/jsonl/otel）是否启用。轨迹服务本身在，但没有汇时不会持久化。

**用量和 provider 账单对不上。**
成本是估算；检查单价配置、缓存价格、失败调用和后台调用。用量页的「进程」视图包含会话外调用。

**轨迹里看不到提示词全文。**
提示词可能被截断或脱敏。检查轨迹配置和隐私设置；有些部署会有意不记录完整提示词。

**导出文件很大。**
导出包含完整会话日志和工具结果。可以先用 `doctor session` 检查不变量，或只导出需要的会话。

# 权限与安全

::: tip
权限系统回答一个核心问题：这次操作到底能不能执行？它负责管辖的是工具调用、文件读写、命令执行等具有实际影响的行为，而不是日常聊天的文字内容。
:::

当机器人的能力越来越强大，不仅能陪大家闲聊，还能调用工具修改文件、执行系统命令甚至管理服务时，安全防护就成了最重要的一环。

如果管理过群聊或服务器，大家一定遇到过这种纠结：既想让机器人帮我们处理事务，又担心误操作损坏文件或泄露敏感信息。ChatLuna 的权限系统并不是简单的「管理员」与「普通用户」二选一，而是会在每次操作发生时，同时综合「谁发起的」、「想做什么」、「影响范围」与「危险程度」，再由权限模式、精准规则与人工审批共同裁决。

这样一来，你在私聊里可以放手调用高级工具，而把机器人拉进公开群聊时，也能把危险行为牢牢收紧。

<!-- 截图占位：权限页 · 用户、角色与待审批列表 -->

打开控制台，在左侧导航栏中点击「权限与安全」，就能看到实例当前的权限管理全貌。

在这里，页面直观地呈现了用户列表、自定义角色以及实时的待审批事件。你可以随时掌握每个账号的能力边界，按需调整它们在不同环境下的权限。让我们从最基础的用户等级开始了解。

## 等级

在 ChatLuna 中，每个用户都会被赋予一个 0 到 5 级的权限等级：

| 等级 | 典型身份 | 默认模式 |
| --- | --- | --- |
| 0 | 未登记或受限用户 | 只读 |
| 1 | 普通群成员 | 只读 |
| 2 | 活跃成员 / 受信任用户 | 只读 |
| 3 | 群管理员 | 自动 |
| 4 | 群主 / 主人 | 自动 |
| 5 | 实例主人 | 全部允许 |

系统是怎么知道某个用户该算几级呢？在日常使用中，用户的权限等级主要有以下几个来源：

- **主人列表**：在控制台权限设置中直接填入的各平台用户账号。主人直接享有 5 级权限与最高信任。
- **平台身份**：针对群聊场景，系统会自动映射平台原生身份。群主映射为 4 级，群管理员映射为 3 级，普通成员映射为 1 级，无需手动录入。
- **角色**：你可以创建自定义角色并设定等级。一个用户可以同时拥有多个角色，判定时系统会自动取其中的最高等级。
- **手动指定**：在权限页的用户列表中直接点击某个用户，就能在详情面板中手动为他指定独立的权限等级。

需要注意的是，权限等级本身并不是一键通行的通行证。具体操作能不能执行，还要看当前生效的模式与具体规则。

## 四种模式

在等级之上，系统通过「权限模式」来划定用户在当前环境下的基础行为边界：

| 模式 | 允许什么 | 适合谁 |
| --- | --- | --- |
| 只读 | 读取、查询类操作；写入和执行一律拒绝或询问 | 普通群成员、未信任用户 |
| 只改文件 | 允许文件读写；命令执行等高风险操作仍需审批 | 需要改文件但不该执行命令的用户 |
| 自动 | 由审查器模型判断，能放行的放行，拿不准的再问 | 管理员、受信任用户 |
| 全部允许 | 大部分操作直接执行；危险和高危操作仍受限制 | 实例主人、5 级用户 |

这里有一个关键的安全机制：`全部允许` 仅对 5 级的实例主人真正生效。如果给低于 5 级的用户配置了该模式，系统底层会自动将其降级为 `自动` 模式运行，防止出现意外越权。

权限模式可以配置在不同的层级上：

- 插件配置中的全局默认模式。
- 各权限等级绑定的默认模式。
- 在「场景规则」中针对单个群聊或用户设置的覆盖模式。
- 单次特定调用所允许的模式上限。

当多个层级的模式同时出现时，系统始终遵循「取更严格者」的原则。

换句话说，就算你在某个群聊的场景规则中放宽为自动模式，但只要用户的自身等级限制在只读模式，最终依然按只读模式执行；反过来，场景规则也无法突破底层等级的安全上限。

::: warning
请勿将 `全部允许` 设为全局默认模式。对于多人公开群聊，请务必让成员保持在 `只读` 或 `只改文件` 模式。
:::

## 风险等级

即使同样是允许调用的动作，不同操作背后的潜在破坏力也大不相同。

为了防止误操作引发危险，系统将所有动作的风险清晰划分为三档：

- **普通**：例如读取本地文件、查询记忆库、搜索网页等纯读取类操作。只要符合当前模式就能直接放行，不需要额外确认。
- **危险**：例如写入并保存文件、执行终端命令、修改配置、读取技能密钥等具有实际影响的操作。即使处于允许写入的模式，系统依然可能要求审批。
- **高危**：例如删除文件目录、批量修改关键数据、重启或终止实例等核心操作。此类操作仅限 3 级及以上用户申请，并且始终需要人工确认，即便配置了「一直允许」规则也一律无效。

动作的风险等级并不是死板固定的。

工具在注册时会声明基准风险，权限系统在运行时还会结合操作目标做出动态评估。例如同样是读写文件，修改普通文本是普通或危险动作，而试图覆盖系统关键配置文件则会被立即升级为高危动作。

## 规则

当预设的等级与模式不能满足特定群聊或特殊成员的需求时，添加定制规则是最灵活的方式。

打开「权限与安全 → 规则」，点击右上角的「添加规则」按钮即可创建一条新规则。规则包含以下几个核心字段：

- **动作**：具体执行的操作类型，例如读取文件、写入文件、执行命令、读取记忆或使用技能密钥。
- **目标**：动作施加的对象范围，例如特定的文件路径、允许执行的命令前缀或记忆主题，支持通配符匹配。
- **谁**：规则适用的主体，可以精确指定到具体用户、角色、等级、群组、会话、路由、Agent 乃至平台。
- **效果**：命中后的裁定结果，分为允许、询问或拒绝。
- **有效期**：规则的生效周期，支持本次调用、本轮对话、当前会话、特定时间段或永久生效。
- **是否最终**：指定该规则在命中后是否立即终止判定，不再继续比对后续规则。

当模型发起操作时，系统会严格按照自顶向下的顺序进行比对：

1. 首先检查是否存在匹配的明确「拒绝」规则。一旦命中任何一条拒绝规则，请求立即终止。
2. 其次依次检索是否存在明确的「允许」或「询问」规则。
3. 当没有任何规则命中时，系统会自动回退到当前主体的权限模式与等级进行兜底判定。

如果一个请求里包含多个复合子操作，系统会将其拆解为独立部分分别判定。只有每一个子操作都顺利通过时整个请求才会执行，任意一处被拒都会整体验退。

::: tip
规则非常适合用来处理「允许某人修改指定目录」这类特殊需求。在日常管理中，建议用等级覆盖绝大多数场景，把规则留给个别例外。
:::

## 审批

<!-- 截图占位：权限页 · 审批弹窗与授权选项 -->

当权限模式拿不准操作意图，或者命中规则的结果为「询问」时，系统会主动暂停当前操作并触发人工审批。

此时，系统会同时在两条通道中推送审批提示：

- 在当前的聊天窗口中直接发送一条审批消息，写明谁发起的请求、具体要做什么、操作目标、风险等级以及调用原因。
- 在控制台 WebUI 右上角的专属审批通知槽位中，同步亮起待办徽标并展示相同的审批卡片。

审批并不是任何人都能点击的。审批人自身的权限等级必须达到该操作要求的最低门槛，只有合规的管理者才能裁决。审批卡片上提供了以下几种处理方式：

- **允许这一次**：仅放行眼前的这一回操作，后续再有新动作时仍会重新发起询问。这是最推荐、最稳妥的日常选项。
- **这一轮都允许**：在当前对话回合的全部后续交互中放行该动作，进入下一轮新对话后恢复审批保护。
- **这个会话都允许**：在当前整个会话窗口期间均不再重复询问，适合集中调试代码或处理任务。
- **一直允许…**：为该操作自动生成一条持久的放行规则（高危操作出于安全考虑不提供该选项）。
- **拒绝**：直接驳回本次操作请求，模型会收到拒绝反馈并尝试调整后续策略。
- **一直拒绝…**：驳回请求并沉淀一条永久拒绝规则，杜绝后续重复骚扰。

系统内置的审批等待超时时间默认为 120 秒，若超时未获批复将自动按「拒绝」处理。

如果审批过程中被用户主动取消，同样按拒绝处理。每一次审批结束后，系统都会把申请人、批准人、操作对象与生效时限完整记录到审计日志中备查。

::: warning
点击「一直允许…」时请格外留意。对于终端命令类调用，系统记住的往往是命令前缀而非单一完整指令。在批准前请看清提示中的范围；一旦拿不准，请优先选择「允许这一次」。
:::

## 审查器

在「自动」模式下，系统并不会盲目放行操作，而是将请求交给「审查器模型」进行前置评估。

审查器模型就像是一位数字安全专员。它会审阅模型打算调用的动作、目标路径、风险评级，并结合前后的对话上下文，智能推断这次操作是否合理、是否存在越权隐患，进而决定是直接放行还是转交人工审批。

在控制台的「权限与安全 → 审查器」配置区域中，你可以调整以下几项核心参数：

- **审查器模型**：默认选用当前系统配置的决策角色，你也可以指定一个推理能力更强的专有模型。
- **审批超时**：控制审批卡片等待人工处理的最长时限，系统默认设置为 120 秒。
- **各等级默认模式**：灵活调节 0 到 5 级用户所绑定的预设权限模式。

需要提醒的是，审查器并不是万无一失的读心神探。

它的主要作用是替管理员过滤掉大量无害的常规读取操作，减轻频繁弹窗的负担。对于绝对不能发生的危险操作，请务必在控制台中添加明确的「拒绝」规则或直接禁用对应工具，切莫单纯依赖审查器拦截。

## 权限页

打开控制台的「权限与安全」页面，你会看到顶部整齐排列着四个标签页，分别负责不同的管理任务：

- **待审批**：集中处理等待人工答复的操作请求。点击该标签页后，你将看到实时的待办卡片列表，每张卡片都清楚展示了申请人、具体动作、目标对象、风险等级以及审批所需的最低权限门槛，右侧则配有快捷审批按钮。
- **谁能做什么**：查看与管理所有用户与角色的权限边界。点击进入后，左侧会列出当前已记录的用户与自定义角色列表，点击任意用户可以直接调整其权限等级与指定模式；点击任意角色则能配置其基准等级、生效模式以及继承关系。
- **规则**：管理自定义的精准权限匹配规则。点击后会呈现当前所有规则的详细列表表格，清晰展示动作、目标、主体、效果与有效期等字段，右上角还提供了「添加规则」按钮用于快速新建放行或拒绝策略。
- **记录**：查看系统最近 24 小时的权限判定足迹。点击后可以看到操作判定日志与统计图表，系统将按允许、询问、拒绝与审查放行等状态分类归纳，点击单条记录还能展开查看详细的判定依据与当时匹配的上下文信息。

页面上方的「缺省模式」决定没有命中任何规则时的兜底行为，旁边会列出单独设置过的对象，方便你确认哪几个人或角色不跟随缺省值。

### 审批选项

在审批卡片或弹窗中，系统提供了以下几种回答方式：

- **允许这一次**、**这一轮都允许**、**这个会话都允许**、**一直允许…**
- **拒绝**、**一直拒绝…**

其中，「一直允许…」与「一直拒绝…」会自动沉淀为一条持久规则，后续命中相同条件的请求将直接生效而不再询问。「这个会话都允许」则仅在当前会话窗口内有效。同时请记住，审批人自身的权限等级必须达到卡片上标明的门槛，否则将无法执行放行操作。

## 常见场景

为了帮助大家快速上手，这里梳理了日常维护中最常见的几种典型场景与配置建议：

### 群里只允许查询

在日常群聊中，我们通常希望群友能够自由提问、查资料或让机器人搜索网页，但不希望机器人随意修改主机文件。

此时只需让普通群成员保持默认的 `只读` 模式，将群管理员设为 `自动` 模式。随后在「场景规则」中，针对该群聊将命令执行与文件写入的权限效果统一设为「询问」。

这样一来，群友在群里正常聊天、查资料完全不受影响；但只要有人尝试诱导模型生成脚本写入磁盘或执行 Shell 命令，系统就会立刻捕获并弹出审批通知，群管理员点击拒绝即可化险为夷。

### 私聊放开

与群聊相比，私聊通常更具隐私性与专属感。

你可以在权限页为经常私聊的用户单独指定更高的等级或权限模式。对于你本人的私聊会话，直接配置为最高信任的 `全部允许`；而对于其他私聊协作者，则建议维持在 `只改文件` 或 `自动` 模式，确保涉及系统底层的危险操作依然需要经过你的把关。

如果你需要让协作者在私聊里协助维护某个插件的配置文件，分配 `只改文件` 模式是极佳的选择：他可以自由读写指定数据，但依然无法越权执行宿主机系统命令。

### 给某个群管理员放权

如果你希望某位群管理员能够独立管理本群的机器人特性，但又不想给全群放权，千万不要盲目提升整个群的基准等级。

正确的做法是打开该群的配置面板，在群成员规则列表中定位到该成员，单独将其权限等级提升为 3 级或 4 级，并为其开启 `自动` 模式。

这样既能满足协同管理的需要，又不会将多余权限误发给其他群成员。当普通群友试图调用管理指令时，系统依旧会坚决拦截。

### 技能密钥

很多外部技能在调用第三方 API 时都需要依赖专属的访问凭证。

在权限体系中，读取与注入「技能密钥」属于明确的「危险」动作，需要较高的权限等级才能调取。你可以在场景规则中按群直接禁止技能调取密钥，这样即使在群聊中有人触发了对应技能，系统也会拒绝下发核心凭据，避免敏感变量遭到泄露。

对于某些需要付费 API 额度的高级技能，这种控制尤为有用：你可以仅在专属管理群中放开密钥使用，而在普通公开群里将其设为禁用。

### 子代理

当主代理将复杂任务拆解并指派给子代理去并发执行时，子代理会自动继承发起者的全部权限上下文，并在执行链条中完整附带委派链路信息。

当子代理需要发起审批时，审批卡片中会清晰标注委派链条（例如显示「子代理：A → B」），帮助审批人一眼看清真正的任务源头。需要注意的是，子代理的权限永远不会超出初始发起者的权限上限，无法通过多层委派完成越权突破。

## 排查

在日常使用权限系统的过程中如果遇到未达预期的情况，可以对照以下条目快速排查：

**工具调用一直被拒绝。**
首先确认当前会话生效的权限模式是否处于只读状态，其次检查当前用户的权限等级是否达到工具要求的门槛，最后排查规则列表中是否存在明确的拒绝规则命中该动作。此外，审批超时未处理也会默认作为拒绝记录。

**主人也无法执行。**
删除重要文件、影响实例运行等高危操作始终需要人工确认，即便配置了始终放行规则对其也一律无效。请检查界面是否已弹出审批卡片，并确认当前操作账号的实际等级是否满足高危授权门槛。

**审批消息没收到。**
请检查即时通讯平台的审批插件是否处于启用状态、审批人账号是否处于机器人可达的私聊或管理会话中，以及审批通知是否被平台侧的消息过滤器拦截。审批超时后系统按拒绝处理，不会自动顺延给别人。

**批准了但下次还要问。**
说明在上次弹出审批提示时，点击的是「允许这一次」而非「这个会话都允许」或「一直允许…」。此外对于高危操作，系统出于安全考量本就只提供单次允许选项，下回调用自然会继续发起审批。

**规则改了不生效。**
请检查是否存在层级更高、限制更严的模式或等级约束；当多个层级模式叠加时，系统始终以更严格的限制为准。场景规则虽然能够替换基础运行模式，但不能打破底层等级设定的硬性上限。

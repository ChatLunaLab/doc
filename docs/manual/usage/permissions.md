# 权限与安全

::: tip
本节介绍权限系统的运作机制：用户等级、会话权限模式与工具批准流程，用于控制机器人执行操作的边界与审批要求。
:::

每次工具调用或敏感操作执行前，系统都会经过权限判定管线，输出以下三种判定效果（Effect）之一：

- `allow`：直接放行并执行。
- `ask`：挂起当前执行，向用户发送批准请求，确认后方可执行。
- `deny`：直接拒绝执行。

## 用户等级与默认权限

每个平台用户对应一个 `0`–`5` 的权限等级（User Level）。用户等级决定了该用户触发操作时默认采用的权限模式：

| 等级 | 默认模式 | 说明 |
| --- | --- | --- |
| `0`–`2` | `read-only` | 只读权限，禁止任何修改操作 |
| `3`–`4` | `auto` | 常规操作自动放行，敏感操作仍需批准 |
| `5` | `allow` | 完全放行（主人级） |

你可以在「权限」页面中管理用户等级与对应角色，配置数据会持久化保存至数据库中。对于未识别身份的用户，系统一律按最低等级（`0`）处理。

## 配置会话权限模式

权限模式（Permission Mode）是作用于会话级别的总控开关。系统支持以下四种模式：

- `read-only`：仅允许只读操作。
- `files`（系统默认）：允许读写工作区文件；执行系统命令等敏感操作仍需批准。
- `auto`：常规操作自动放行，超出常规范围的操作需批准。
- `allow`：放行所有操作。

::: warning
`allow` 模式会完全跳过敏感操作的安全拦截。请谨慎在生产群组或不可信环境中开启此模式。
:::

如果需要针对特定群组或单独会话覆盖默认权限，可以在对应的路由规则中配置 `permissions.mode`。当路由中未显式指定 `permissions.mode` 时，系统将自动回落（Fallback）至当前触发用户的等级默认模式。

## 处理批准请求（ask）

当判定结果为 `ask` 时，当前工具调用将被挂起，系统会向对应用户发送交互式批准请求，等待确认后再继续执行。

你可以通过以下配置项控制批准行为：

- `tool-policy`：在其 `ask` 列表中指定默认必须经过批准的工具名称（例如 `bash`、`session_reference_list`）。
- `askTimeout`：设置批准请求的等待超时时间。

所有批准操作均属于权限判定的一部分并会被完整审计。你可以在「权限」页面与「轨迹」页面中审查相关日志，包含以下信息：
- 批准人身份
- 命中的判定规则
- 最终执行结果

## 能力调用的安全边界

无论能力来源是技能（Skill）、MCP（Model Context Protocol）、子代理（Sub-agent）还是后台任务，它们向模型投影出的所有工具均必须接入同一套权限判定管线，没有任何隐式提权通道。

为某个会话启用更多扩展能力，仅代表扩充了该会话可见的工具集，不会自动赋予该会话更高的执行权限。

# 权限与安全

::: tip
权限系统回答一个核心问题：这次操作，到底该不该让它做？它负责管辖的是工具调用、文件读写、命令执行、技能密钥这些具有实际影响的动作，而不是对日常聊天内容的过滤与审核。
:::

当机器人的能力越来越丰富，不仅能陪大家日常闲聊，还能主动调用工具去执行终端命令、修改配置文件、甚至读写宿主机的本地数据时，安全防护就成了不可忽视的一环。

如果你曾经管理过社群或服务器，一定明白「既要放手让工具发挥威力，又担心意外操作损坏环境」的纠结。ChatLuna 的权限设计并不是粗暴的「管理员」与「普通用户」两档切分。在每一次工具调用发生时，系统会将「谁在发起请求」、「试图做什么动作」、「作用在哪个具体范围」以及「动作本身潜藏着多高的风险」细致拆开进行综合评估，最后交由权限模式、精准规则以及人工审批这三道防线协同裁决。

这样一来，既能保证你在私聊中拥有完全自由的掌控权，也能确保机器人在人多嘴杂的群聊环境中把危险行为牢牢收紧。

<!-- 截图占位：权限页 · 用户、角色与待审批列表 -->

打开控制台，在左侧导航栏中点击「权限与安全」，就能看到当前实例的权限管理全貌。

在这里，页面直观地呈现了用户列表、自定义角色以及实时的待审批事件。你可以清晰地掌握每一个账号的权限水准，并根据实际需要随时调整其在不同环境下的能力范围。接下来，让我们从最基础的用户等级开始逐层了解。

## 等级

在 ChatLuna 的安全体系中，每一个用户都会被赋予一个介于 0 到 5 级之间的权限等级：

| 等级 | 典型身份 | 默认模式 |
| --- | --- | --- |
| 0 | 未登记或受限用户 | 只读 |
| 1 | 普通群成员 | 只读 |
| 2 | 活跃成员 / 受信任用户 | 只读 |
| 3 | 群管理员 | 自动 |
| 4 | 群主 / 主人 | 自动 |
| 5 | 实例主人 | 完全放行 |

细心的小伙伴可能会好奇：系统是怎么知道某个用户到底该算几级呢？在日常使用中，用户的权限等级主要有以下几个常见来源：

- **主人列表**：在控制台的权限设置界面中，你可以直接填写各聊天平台的用户账号 ID。被列入主人列表的用户会直接获得最高等级的信任，享有对实例的最高支配权。
- **平台身份**：针对群聊等协同场景，系统支持将聊天平台自带的群主、管理员与普通成员身份自动映射为对应的等级。系统默认将群主映射为 4 级、群管理员映射为 3 级、普通成员映射为 1 级，无需你逐个手动录入名单。
- **角色**：你可以创建自定义角色，为每个角色单独设置权限等级并建立继承关系。例如创建「运营助手」角色并赋予 2 级权限。一个用户可以同时绑定多个不同角色，在执行权限判定时，系统会自动取其中的最高等级。
- **手动指定**：如果需要对某位特定成员进行特殊关照，也可以在权限页的用户列表中直接点击该用户，进入详情面板手动为其分配独立的权限等级。

需要牢记的是，权限等级并不是一键通行的「越权开关」，它更像是一套合理的基准默认值。每次操作是否真正被允许执行，系统依然会综合当前的运行模式、规则匹配以及操作自身的风险等级来共同定夺。

## 四种模式

在等级之上，系统通过「权限模式」来圈定用户在当前环境下的基础行为边界。你可以把它理解为整个会话的大环境防线：

| 模式 | 允许什么 | 适合谁 |
| --- | --- | --- |
| 只读 | 读取、查询类操作；写入和执行一律拒绝或询问 | 普通群成员、未信任用户 |
| 文件 | 允许文件读写；命令执行等高风险操作仍需审批 | 需要改文件但不该执行命令的用户 |
| 自动 | 由审查器模型判断，能放行的放行，拿不准的再问 | 管理员、受信任用户 |
| 完全放行 | 大部分操作直接执行；危险和高危操作仍受限制 | 实例主人、5 级用户 |

这里有一个非常关键的安全机制：「完全放行」模式仅对 5 级的实例主人真正生效。对于等级低于 5 级的其他用户，哪怕你在界面上为他配置了完全放行，系统在底层也会自动将其降级为「自动」模式进行防护，绝不给意外越权留下空隙。

在系统的运转过程中，权限模式可以配置在不同的生效层级：

- 插件配置中的全局默认模式。
- 对应权限等级所绑定的默认模式。
- 在「场景规则」中针对单个群聊或特定用户设置的覆盖模式。
- 单次特定调用所允许的模式上限。

当多个层级的模式同时出现时，系统始终遵循「取更严格者」的原则。

就像进入机场需要经过层层安检一样：即使在场景规则中将某个群聊放宽为自动模式，但如果某位进群的新成员本身等级被严格限制在只读模式，那么当他发起操作时，系统仍然会坚守只读的安全防线；反之，若全局模式要求审批，场景规则也无法将其实质放宽为无条件执行。场景规则可以替换当前会话的基础模式，但绝不能突破底层等级设定的严格限制。

::: warning
切记不要因为图省事而将「完全放行」作为全局默认模式。它只应当赋予你绝对信任的主人账号；对于公开群聊里的普通群友，请务必让其保持在「只读」或「文件」模式。
:::

## 风险等级

即使同样是处于「允许」状态的操作，不同动作背后的危险程度也是截然不同的。例如查看帮助信息与格式化本地硬盘，显然不能相提并论。

为了杜绝误操作引发灾难，系统将所有动作的风险清晰划分为三档：

- **普通**：例如读取本地文件、查询记忆库、访问公网网页等纯读取类交互。这类操作只要符合当前模式与规则即可顺利通行，通常无需任何多余的确认弹窗。
- **危险**：例如写入并保存文件、执行终端命令、修改实例配置、读取技能密钥等具有明确副作用的操作。即使当前处于允许写入的模式，系统依然可能要求经过人工审批。
- **高危**：例如删除文件目录、批量修改重要数据、重启或终止实例运行等伤筋动骨的操作。此类操作仅限 3 级及以上权限的用户申请；并且它始终需要人工确认，即便配置了「始终允许」规则对高危操作也一律无效。

在 ChatLuna 中，风险等级并非单纯根据工具名称死板固化在系统底层的。

各个能力工具在注册时会声明自己的基准风险属性，权限系统在运行时还会结合具体的动作意图与操作目标做出动态评估。例如同样是文件读写工具，读取公开帮助文档会被识别为普通风险，而试图修改系统关键配置则会立刻被升级为危险甚至高危动作。

## 规则

如果说等级与模式构成了权限的安全底色，那么「规则」就是实现精细化裁量的不二法宝。当默认的模式不能满足特定群聊或特定用户的特殊需求时，前往控制台添加一条定制规则就是最优雅的解决办法。

打开「权限与安全 → 规则」，点击右上角的「添加规则」按钮，即可创建一条新的权限规则。一条完整的权限规则通常涵盖以下核心要素：

- **动作**：具体要进行的操作类型，例如读取文件、写入文件、执行命令、读取记忆或使用技能密钥。
- **目标**：动作施加的对象范围，例如特定的文件路径、允许执行的命令前缀，或是某个记忆主题。支持使用通配符进行模糊匹配。
- **谁**：规则适用的主体，可以精确指定到具体用户、角色、等级、群组、会话、路由、Agent 乃至平台。
- **效果**：命中后的裁定结果，分为允许、询问或拒绝。
- **有效期**：规则的存活周期，支持本次调用、本轮对话、当前会话、特定时间段或永久生效。
- **是否最终**：指定该规则在命中后是否立即终止判定，不再继续向下比对后续规则。

当模型发起一项操作时，系统内部会严格按照以下顺序自顶向下进行规则比对：

1. 首先检查是否存在匹配的明确「拒绝」规则。只要有任何一条拒绝规则被命中，整个请求会立即宣告失败。
2. 其次依次检索是否存在明确的「允许」或「询问」规则。
3. 当没有任何规则能够命中该请求时，系统才会自动回退到主体当前的权限模式与等级进行兜底判定。

如果一次操作属于复合请求，例如一条指令中串联了多个子命令，系统会将其拆解为若干独立部分逐一进行判定。

只有当其中的每一个子操作都顺利通过时，整个复合请求才会被放行。只要其中任意一环被拒绝，系统就会整体验退，确保操作的原子安全性。

::: tip
规则非常适合用来满足「允许该成员修改指定目录」、「某群仅能调用特定查询命令」这类精准需求。在日常管理中，不建议滥用规则来取代等级机制；等级应当负责管好绝大多数情况，而规则只用来处理个别例外。
:::

## 审批

<!-- 截图占位：权限页 · 审批弹窗与授权选项 -->

当权限模式判断拿不准，或者规则判定结果为「询问」时，系统便会主动暂停当前操作并触发一次人工审批流程。

此时，系统会同时在两条通道呈现实时审批提示：

- 在当前的聊天窗口中直接推送一条审批消息，详细列出本次请求由谁发起、要执行的具体动作、操作的目标范围、评估出的风险等级以及发起原因。
- 在控制台 WebUI 右上角的专属审批通知槽位中，也会同步亮起待办徽标并展示相同的审批卡片。

审批并不是任何人都能随手点击的。系统要求审批人的权限等级必须达到该操作所要求的最低授权等级，只有合规的管理员才能做出裁决。在审批弹窗或交互按钮中，你可以根据现场情况从容选择以下几种处理方式：

- **允许本次**：仅放行眼前的这一次动作调用，后续产生新的动作时依旧会重新发起询问。这是最推荐、最稳妥的日常选项。
- **允许本轮**：在当前对话回合的全部后续交互中，均放行该动作。当前回合结束后若发起新轮次，将重新恢复审批保护。
- **允许本会话**：在当前整个会话窗口未关闭期间，均不再重复打扰，非常适合集中连续调试代码或处理任务的场景。
- **始终允许**：为该操作自动生成一条持久的放行规则（高危操作出于安全考虑不提供该选项）。
- **拒绝**：直接驳回本次操作请求，模型会收到操作被拒的反馈并尝试调整策略。
- **始终拒绝**：不仅拒绝本次请求，还会沉淀一条永久拒绝规则，杜绝后续重复骚扰。

系统内置的审批等待超时时间默认为 120 秒，若超时未获批复将自动按「拒绝」处理。

如果当前会话中的预设审批人处于离线或不可达状态，请求还会自动顺延交由下一个可用审批人处理；中途主动取消审批同样不代表允许。

每一次审批流程结束后，无论是批准还是驳回，系统都会把申请人、批准人、批准对象以及生效时限完整收录至审计日志中备查。

::: warning
选择「始终允许」时务必保持警惕。系统在记录可复用规则时，针对命令类调用往往会沉淀该命令的前缀范围，而非单一完整指令。在点击批准前，请务必看清界面提示中写明的「将记住」范围；一旦拿不准，坚决选择「允许本次」。
:::

## 审查器

在「自动」模式下，系统并不会盲目放行所有动作，而是会将请求先行递交给「审查器模型」进行前置评估。

审查器模型就像是一位不知疲倦的数字安全专员。它会细致审阅模型打算调用的具体动作、目标路径、风险评级，并结合前后的对话上下文，智能推断这次操作是否合理、是否存在越权隐患，进而果断决定是直接放行还是转交人工审批。

在控制台的「权限与安全 → 审查器」配置区域中，你可以针对审查器调整以下几项核心参数：

- **审查器模型**：默认会直接选用当前系统配置的决策角色，你也可以根据需求单独指定一个推理能力更敏锐的专有模型。
- **审批超时**：控制审批卡片等待人工处理的最长时限，系统默认设置为 120 秒。
- **各等级默认模式**：灵活调节 0 到 5 级用户所绑定的预设权限模式。

需要明确的是，审查器并不是万无一失的读心神探。

它旨在替管理员过滤掉大量无害的常规操作，减少繁重的弹窗确认负担，绝不应该被当成明确禁止规则的廉价替代品。对于那些绝对不容许发生的危险操作，应当在控制台中直截了当地添加「拒绝」规则或直接禁用对应工具，切莫寄希望于审查器每次都能准确拦截。

## 权限预设

逐项配置等级映射、模式覆盖与规则细节可能会让新手用户感到眼花缭乱。为此，系统贴心地提供了「权限预设」功能，将一套套经过实战检验的常用模式、规则库以及等级映射模板一键打包，供你随取随用：

- **严格**：普通群成员一律限制在只读模式，任何文件的写入与命令执行都需要提交人工审批，适合面向公众开放的各类公开大群。
- **标准**：管理员采用自动模式以保证操作连贯性，普通成员默认只读，适合内部团队或多数常规交流群。
- **宽松**：受信任的普通用户也能享有自动模式的便利，仅在触及高危动作时才暂停等待审批，适合私密好友群或可信的研发环境。

当你进入权限设置面板切换权限预设时，系统会快速替换现有的基础权限方案。

不过无需担心你的个人定制：只要你自己手动创建的自定义规则未被预设明确覆盖，它们依然会以更高的优先级继续生效。预设只负责刷上一层坚实可靠的底漆，而你的专属规则才是最终成型的装潢。

## 常见场景

为了帮助大家快速上手，这里梳理了日常维护中最常碰到的几种典型场景与配置建议：

### 群里只允许查询

在日常群聊中，我们通常希望群友能够自由提问、查资料或让机器人搜索网页，但不希望机器人随意修改主机文件。

此时只需让普通群成员保持默认的「只读」模式，将群管理员设为「自动」模式。随后在「场景规则」中，针对该群聊将命令执行与文件写入的权限效果统一设为「询问」。

这样一来，群友在群里正常跟机器人聊天、咨询知识完全不受影响；但只要有人尝试诱导模型生成脚本写入本地磁盘或执行 Shell 脚本，系统就会立刻捕获并弹出审批通知，群管理员点击拒绝即可化险为夷。

### 私聊放开

与群聊相比，私聊通常更具隐私性与专属感。

你可以在权限页为经常私聊的用户单独指定更高的等级或权限模式。对于你本人的私聊会话，直接配置为最高信任的「完全放行」；而对于其他私聊用户，则建议维持在「文件」或「自动」模式，确保涉及系统底层的危险操作依然需要经过你的把关。

如果你需要让某位协作者在私聊里协助维护某个插件的配置文件，给他分配「文件」模式是极佳的选择：他可以自由读写指定数据，但依然无法越权执行宿主机系统命令。

### 给某个群管理员放权

如果你希望某位群管理员能够独立管理本群的机器人特性，但又不想给全群放权，千万不要盲目提升整个群的基准等级。

正确的做法是打开该群的配置面板，在群成员规则列表中定位到该成员，单独将其权限等级提升为 3 级或 4 级，并为其开启「自动」模式。

这样既能满足协同管理的需要，又不会将多余权限误发给其他潜在成员。当其他普通群友试图调用管理指令时，系统依旧会坚决拦截。

### 技能密钥

很多外部技能在调用第三方 API 时都需要依赖专属的访问凭证。

在权限体系中，读取与注入「技能密钥」属于明确的「危险」动作，需要较高的权限等级才能调取。你可以在场景规则中按群直接禁止技能调取密钥，这样即使在群聊中有人触发了对应技能，系统也会拒绝下发核心凭据，避免敏感变量遭到泄露。

对于某些需要付费 API 额度的高级技能，这种控制尤为有用：你可以仅在专属管理群中放开密钥使用，而在普通公开群里将其设为禁用。

### 子代理

当主代理将复杂任务拆解并指派给子代理去并发执行时，子代理会自动继承发起者的全部权限上下文，并在执行链条中完整附带委派链路信息。

当子代理需要发起审批时，审批卡片中会清晰标注委派链条（例如显示「子代理：A → B」），帮助审批人一眼看清真正的任务源头。需要注意的是，子代理的权限永远不会超出初始发起者的权限上限，休想通过多层委派完成越权突破。

## 排查

在日常使用权限系统的过程中如果遇到未达预期的情况，可以对照以下条目快速排查：

**工具调用一直被拒绝。**
首先确认当前会话生效的权限模式是否处于只读状态，其次检查当前用户的权限等级是否达到工具要求的门槛，最后排查规则列表中是否存在明确的拒绝规则命中该动作。此外，审批超时未处理也会默认作为拒绝记录。

**主人也无法执行。**
删除重要文件、影响实例运行等高危操作始终需要人工确认，即便配置了始终放行规则对其也一律无效。请检查界面是否已弹出审批卡片，并确认当前操作账号的实际等级是否满足高危授权门槛。

**审批消息没收到。**
请检查即时通讯平台的审批插件是否处于启用状态、审批人账号是否处于机器人可达的私聊或管理会话中，以及审批通知是否被平台侧的消息过滤器拦截。若当前审批人超时未响应，系统会自动顺延派发给下一个候选审批人。

**批准了但下次还要问。**
说明在上次弹出审批提示时，点击的是「允许本次」而非「允许本会话」或「始终允许」。此外对于高危操作，系统出于安全考量本就只提供单次允许选项，下回调用自然会继续发起审批。

**规则改了不生效。**
请检查是否存在层级更高、限制更严的模式或等级约束；当多个层级模式叠加时，系统始终以更严格的限制为准。场景规则虽然能够替换基础运行模式，但不能打破底层等级设定的硬性上限。

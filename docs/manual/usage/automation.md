# 定时与后台任务

::: tip
这一页讲三件容易混淆的事：按时间或条件触发的「定时任务」、跑得久所以放到后台的「后台任务」，以及角色自己约定的「稍后回来」。
:::

它们的共同点是「不在当前回合里完成」。区别在于谁发起、什么时候执行、结果怎么回到对话。

## 定时任务

定时任务是显式创建的、会在未来某个时间或条件满足时执行的作业。可以在「自动化」或「定时任务」页面管理，也可以由模型或插件创建。

一个任务通常包含：

- **触发方式**：某个时间点、固定间隔、cron 表达式，或一个关注条件。
- **执行内容**：唤醒对话，或运行一段提示词并把结果发回来。
- **重复规则**：执行一次、执行若干次，或直到某个时间。
- **状态**：活跃、暂停、完成、失败。
- **宽限时间**：到点后最多延迟多久仍然执行，超过就跳过。

### 触发方式

- **时间点**：在某个具体时间执行一次。
- **固定间隔**：每隔一段时间执行一次。间隔太短会触发审批，防止误配出高频任务。
- **cron**：按日历规则执行，例如每天某个时刻、每周某天。可以指定时区。
- **关注条件**：持续检查一个表达式，条件为真时执行。条件可以读消息、时间、沉默时长等。

### 执行内容

- **唤醒**：像有人叫了机器人一样触发一次对话，附带一个原因。
- **运行提示词**：用指定的引擎或子代理运行一段提示词，结果可以发送、作为通知，或不发送。

### 限制

为了避免任务失控，系统有几层限制：

- 每个会话同时活跃的任务数量上限。
- 每个会话的一次性唤醒数量上限。
- 每个会话每天的触发次数上限。
- 最短触发间隔；低于这个间隔的任务需要审批。
- 单次定时器的最长时长和最大延迟。

这些限制可以在定时任务插件的配置里调整。默认值适合大多数部署；调大之前先想清楚最坏情况。

::: warning
定时任务会在无人盯着的时候执行。给任务配置的提示词要明确、可重复，避免「看看情况再说」这种依赖即时上下文的指令。涉及写入或命令执行的任务，权限和审批仍然生效。
:::

### 关注条件

关注条件适合「等到某件事发生」而不是「等到某个时间」：

- 等人回复。
- 等群里安静下来。
- 等消息数量达到某个值。
- 等某个时间段开始。

条件可以读取最近的消息、说话人、沉默时长、当前时间、已触发次数等。读取时间的条件会定期检查；只读消息的条件在新消息到达时检查。

条件里的判断可以很灵活，但不要写得太复杂。条件越复杂，越难排查为什么没触发。

### 意图判定

有些任务需要判断「这句话是不是在说某件事」，而不是简单的数量或时间比较。定时任务可以调用一个判定模型，把最近的聊天和问题交给它，得到一个是/否的结论。

判定有频率限制和每日预算，避免在活跃群里反复调用模型。

## 后台任务

后台任务不是「定时」，而是「现在开始、稍后取结果」。它通常由工具调用触发：某个操作太久，同步等待会卡住整个回合，于是转到后台继续跑。

后台任务的特点：

- 有独立的状态：运行中、停止中、完成、失败、取消。
- 可以持续输出进度和日志。
- 可以按偏移量读取输出，不必一次拿全部。
- 可以在完成时通知：打断当前对话、排到下一轮，或只记录不通知。
- 可以取消；取消会尽量终止底层工作，但不保证立即停止。

### 什么时候会用后台

- 命令执行超过同步等待上限。
- 长时间的文件处理、下载、构建。
- 需要持续观察的外部任务。
- 子代理或工具自己决定转到后台的长任务。

工具可以声明自己的超时和是否允许转后台。超过同步等待时间后，调用会变成后台任务，先返回一个占位结果；完成后再把结果送回对话。

### 读取与取消

后台任务的输出分两路：

- **模型可读的输出**：会进入后续对话，供模型判断进度或结果。
- **人类可读的日志**：只出现在管理界面，不进入模型上下文。

输出有缓冲区上限，超出会截断并标记。读取时可以从上次的位置继续，避免重复。

::: tip
后台任务适合「慢但不需要马上知道结果」的工作。如果用户正在等一个明确答案，后台化只会让回复更慢、更难懂；这时应该缩小任务范围，而不是把它丢到后台。
:::

## 角色自己的唤醒

伪装引擎的角色可以自己约定「稍后回来」：

- 等人回复后继续话题。
- 等群里安静一段时间后重新开口。
- 到某个时间点提醒或问候。
- 持续关注一个条件，满足时再说话。

角色可以设置：

- 最早什么时候可以醒来。
- 醒来条件：等回复、等沉默、等时间、等消息数量等。
- 最多醒几次，两次之间至少隔多久。
- 最长等待时间；到期还没满足条件时，是放弃还是直接醒来。
- 是否在角色主动说话后自动取消。

唤醒默认只保留一次；需要持续关注时，设置次数和间隔。默认的最长等待时间是「最早可醒时间之后十分钟」，想等更久要显式延长。

::: warning
唤醒是条件，不是闹钟。条件写得太宽会让角色频繁醒来；写得太窄会永远不醒。先用「等回复」或「等沉默」这类简单条件，观察实际行为后再加复杂度。
:::

## 页面怎么用

定时任务页通常提供：

- 任务列表：按状态、会话、创建者筛选。
- 新建任务：选触发方式、执行内容、重复规则。
- 任务详情：下次执行时间、已执行次数、最近一次结果、错误。
- 运行历史：每次触发的时间、结果、耗时。
- 暂停、恢复、删除、立即执行。

后台任务可能在同一个页面或单独的「任务」页里，显示运行中的任务、进度、输出和取消按钮。

## 推荐配置

### 日常提醒

用时间点或 cron，执行一次或每天一次。执行内容用固定提示词，明确要做什么。宽限时间不要设太长，避免错过时间后还在补发。

### 群活跃维护

用关注条件：沉默超过一段时间、消息数量达到阈值、特定人发言。设置次数和间隔，避免角色反复刷屏。配合角色的作息和每小时发言上限。

### 长任务

把命令执行、构建、下载这类工作交给后台任务工具。设置合理的同步超时，让短任务仍然同步返回；长任务转到后台，完成后再通知。

### 多群

每个群单独建任务，或在任务目标里指定会话。不要用一个全局任务给所有群发同样的消息；不同群的活跃时间和话题不一样。

## 排查

**任务没有按时执行。**
检查任务状态是否活跃、下次执行时间是否正确、时区是否写对、是否超过每日触发上限。宽限时间太短也会导致错过。

**任务执行了但没发消息。**
检查执行内容的投递方式：发送、通知、不发送。通知可能只出现在管理界面，不进对话。

**关注条件一直不触发。**
条件可能依赖了不会更新的字段，或者读取时间的条件检查间隔太长。先用简单条件验证，再逐步加复杂度。

**后台任务一直运行。**
检查底层工作是否卡住、输出是否在持续增长。可以取消；取消不保证立刻停止，但会阻止结果继续回流。

**角色频繁醒来。**
唤醒条件太宽，或者次数和间隔设得太松。缩短最长等待时间、增加间隔，或改成「等回复」这类更具体的条件。

**任务费用很高。**
关注条件里的意图判定、运行提示词的模型调用都会产生费用。减少判定频率、降低每日预算，或改用纯时间/数量条件。

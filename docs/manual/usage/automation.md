# 定时与后台任务

::: tip
本页介绍三种容易混淆的自动化与异步机制：按时间或条件触发的「定时任务」、因耗时较长而转入后台的「后台任务」，以及由角色自主约定的「稍后回来」。
:::

机器人的日常交互通常是一问一答。但在实际使用中，许多工作无法或不适合在当前对话回合中立即完成。

例如，让机器人每天早晨定时发送问候、在群聊冷场半小时后主动发言，或者下载大文件并执行耗时较长的脚本。如果这些操作都在当前对话中同步等待，不仅会长时间阻塞聊天窗口，也会让机器人失去响应灵活性。

这些场景的共同特征是「不在当前回合中完成」。它们的核心差异在于发起者、执行时机以及结果返回对话的方式：

- **定时任务**：由用户、插件或模型显式创建，在未来指定的时间点、固定周期或特定事件发生时触发。
- **后台任务**：在当前对话中启动，由于执行耗时较长而转入后台静默运行，产生进展或最终结果后再返回通知。
- **角色自己的唤醒**：角色在对话中根据上下文或剧情设定，自主约定在特定契机下重新回到对话中发言。

## 定时任务

定时任务是系统中最基础的自动化功能。通过预设规则，机器人可以在指定时间到达或特定条件满足时，自动执行相应的操作。

你可以在控制台的「观测 → 定时任务」页面中统一查看并管理所有任务。除了管理员手动创建任务外，大模型在对话中根据需求、或第三方插件也可以向系统注册定时任务。

创建与查看定时任务时，主要包含以下五个核心要素：

- **触发方式**：决定任务何时被触发。支持精确时间点、固定时间间隔、cron 表达式，以及持续检测事件的关注条件。
- **执行内容**：决定任务触发后执行的具体动作。例如直接唤醒对话，或在后台运行指定提示词并将产出发送出来。
- **重复规则**：决定任务的执行周期。支持单次执行、重复指定次数，或在设定的截止时间之前持续重复。
- **状态**：展示任务当前的运行状态，包括等待执行的「活跃」、手动挂起的「暂停」、执行结束的「完成」以及运行出错的「失败」。
- **宽限时间**：为任务执行设置的容错缓冲区间。若因系统繁忙或网络波动导致未能准时执行，在宽限时间内仍会补发执行；一旦超过该时间，系统将跳过本次执行，避免在不适当时刻补发过期消息。

### 触发方式

在新建任务面板中，系统提供了四种触发方式：

- **时间点**：在未来的指定时间执行一次。适合设置一次性提醒（例如「今天下午 3:00 提醒开会」），执行后任务自动进入完成状态。
- **固定间隔**：按固定时长循环触发（例如「每隔 2 小时检查一次更新」）。若配置的间隔过短，系统会将其识别为高频操作并触发审批流程，以防高频发信或过度消耗资源。
- **cron**：按日历规则周期性触发（例如「每周一至周五早上 9:00 发送早报」）。支持指定时区，系统将严格依据日历时间调度。
- **关注条件**：不依赖固定时钟，而是由系统持续评估动态条件表达式。仅当条件成立时触发任务，可感知新消息、特定发言人及群聊沉默时长等上下文数据。

### 执行内容

触发条件满足后，任务支持以下两种执行模式：

- **唤醒**：模拟用户在群聊或私聊中呼叫机器人，直接发起一次对话回合。你可以附带明确的触发原因（例如「早晨定时唤醒」），模型将结合该原因生成自然的发言内容。
- **运行提示词**：不进入常规问答流程，而是调用指定的模型引擎或子代理在后台运行独立提示词。产出内容支持三种投递方式：作为普通消息「发送」到目标群聊、作为系统「通知」推送到控制台，或「不发送」仅供系统内部流转。

### 限制

为防止任务陷入循环调用或过度消耗系统资源，系统内置了多层安全限制策略：

- **同时活跃任务上限**：限制每个会话中可同时处于活跃状态的任务总数。
- **一次性唤醒上限**：限制单个会话中排队等待执行的一次性唤醒数量，避免唤醒积压。
- **每日触发上限**：限制单个会话单日允许触发任务的最大次数，超出后当日自动停止后续触发。
- **最短触发间隔**：对周期性任务设置的最小时间间隔，低于该阈值的任务需要管理员审批方可生效。
- **允许的最大延迟**：任务触发超时后允许补发的最大时长；超过该时长的任务将被跳过，避免补发陈旧消息。

上述限制项均可在定时任务插件的配置项中调整。默认配置已兼顾常规部署环境的安全与性能，调整阈值前建议先评估服务器负载能力。

::: warning
定时任务通常在无人值守环境下运行。编写任务提示词时，应保持指令清晰明确、逻辑自洽且可重复执行，避免使用模糊或过度依赖即时语境的表述。此外，定时任务中调用的工具若包含写入或命令执行等敏感操作，系统的权限检查与审批流程仍会照常触发。
:::

### 关注条件

关注条件用于处理无法仅凭时钟计算的业务场景，适用于「等待某事件发生」的需求：

- 等待群聊中特定用户回复消息。
- 等待热闹的群聊逐渐安静，进入冷场状态。
- 等待统计区间内的消息总量达到设定阈值。
- 等待指定的工作时间段开始。

在条件表达式中，可以读取上下文环境数据，包括最新消息内容、发言人身份、群聊当前沉默时长、系统当前时间以及该任务的历史触发次数等。

条件评估依据其依赖的数据类型运行：仅依赖消息内容的条件会在每次收到新消息时即时计算；依赖系统时间或沉默时长的条件，则由系统按固定周期轮询检测。

编写关注条件时，建议保持简明清晰的逻辑。过多的条件嵌套会增加后续排查未触发原因的难度。

### 意图判定

对于无法通过字数统计、发言频率或关键词简单匹配的语义场景（例如判断「群友是否正在讨论聚餐话题」），定时任务支持启用意图判定。

启用后，系统会调用轻量级判定模型，结合滑动窗口内的聊天记录与预设的核心问题，由模型给出是否成立的二元判断。

由于意图判定依赖模型调用，系统对其配置了严格的频率限制与每日调用额度，避免高活跃度群聊中因频繁触发请求而产生过高成本。

## 后台任务

后台任务与定时任务的执行逻辑不同：定时任务是等待未来某个时机再开始执行，而后台任务则是立即启动执行，因耗时较长而转入后台运行并在完成后获取结果。

后台任务多由对话中的工具调用触发。当模型调用的外部工具预计耗时超出常规等待时间时，为避免前端交互界面长时间无响应或触发超时错误，系统会自动将该操作交由后台处理。

后台任务具有以下运行特征：

- **独立的生命周期状态**：脱离主对话独立运行，包含「运行中」「停止中」「完成」「失败」和「取消」五种状态。
- **实时输出与日志**：支持在执行过程中持续推送运行进度与调试日志，便于随时查看。
- **分段增量读取**：支持基于偏移量读取已生成的输出内容，无需每次全量拉取，降低系统开销。
- **灵活的完成通知**：任务完成后支持配置结果交付方式，可直接打断当前对话发送结果、排队保留至下一回合汇报，或仅在管理界面记录而不通知用户。
- **支持安全取消**：执行过程中可随时在后台发送取消指令。系统会中止底层的异步作业，具体停止响应时间取决于外部系统的实现。

### 什么时候会用后台

常见转入后台执行的操作包括以下几类：

- 执行复杂的终端命令或脚本，且耗时超出系统的同步等待上限。
- 耗时较长的本地或网络文件处理，例如大文件下载、解压、视频转码或项目构建。
- 需要在外部环境中持续观察或轮询状态的监听任务。
- 复杂的子代理执行流程，由子代理或工具自身根据任务复杂度决定转入后台。

工具可自行声明「同步等待超时时间」并配置「允许转后台」开关。当工具调用的耗时达到同步等待阈值时，系统会将其无缝转为后台任务，先在对话中返回临时占位结果，待后台执行完毕后再将最终输出回传至会话。

### 读取与取消

后台任务运行期间，系统将输出流划分为两个独立通道：

- **模型可读的输出**：经过结构化处理的内容。在任务完成或汇报时注入对话上下文，供模型理解执行结果并回复用户。
- **人类可读的日志**：包含底层执行细节、标准错误与耗时统计等信息。该部分日志仅在控制台界面展示，不会进入模型的对话上下文。

为避免异常脚本无限打印日志占用内存，系统设置了缓冲区上限，超出阈值的日志会被截断并标注截断标识。在控制台或通过接口查看日志时，系统支持基于偏移量进行增量拉取。

::: tip
后台任务适合处理运行耗时较长且无需即时获得回复的工作。若用户需要即时交互结果，将任务转入后台可能会拉长等待链路。此时应优先考虑精简单次任务处理范围。
:::

## 角色自己的唤醒

在伪装引擎下，角色具备更高的主动行为能力。除被动响应用户呼叫外，角色可以根据对话语境和设定，自主约定重新发言的契机：

- 在提出探讨性问题后暂时等待，待有群友回复时继续跟进交流。
- 在群聊讨论热烈时保持静默，待群聊出现较长时间沉默后再发起新话题。
- 按照日常作息规律，约定在特定时间点（如清晨或傍晚）主动发送问候或备忘内容。
- 自主注册关注条件，持续观察群聊走势并在满足条件时主动接话。

角色发起唤醒时，支持配置以下控制参数：

- **最早可醒时间**：设定保护时段，在此时间到达之前无论外部发生何种事件均不触发唤醒。
- **醒来条件**：指定唤醒触发的依据，例如等待他人回复、等待群内持续沉默达到设定时长、到达指定时刻，或群消息累积到指定条数。
- **最大唤醒次数与最小间隔**：限制角色的主动唤醒次数上限及相邻两次唤醒之间的最小时间间隔，避免过于频繁发言。
- **最长等待时间与超时处理**：设定唤醒的有效期限。若超过最长等待时间条件仍未满足，可配置为放弃唤醒或直接触发发言。
- **主动说话后自动取消**：若在等待期间因其他原因（如被用户 @ 提问）提前发言，是否自动清理当前挂起的等待计划。

默认情况下，角色约定的唤醒仅生效一次；如需持续生效，需显式配置唤醒次数与间隔。此外，系统默认的最长等待时间为「最早可醒时间之后的十分钟」，如需跨较长时间等待，需相应调大该配置项。

::: warning
唤醒机制基于条件触发，并非严格意义上的准时定时器。唤醒条件设置过宽容易导致角色频繁发言打扰交流，设置过窄则可能使角色无法正常触发。建议初期从「等回复」或「等沉默」等简单条件入手，观察稳定后再按需扩展。
:::

## 页面怎么用

打开控制台，在左侧导航栏的「观测」分组中点击「定时任务」，即可进入任务全生命周期管理页面。

该页面主要包含以下功能区域：

- **任务列表**：集中展示当前的自动化任务。支持按「任务状态」（活跃、暂停、完成、失败）、「目标会话」（私聊或具体群聊）及「创建者」（人工创建、插件创建或模型创建）进行筛选。
- **新建任务**：点击右上角的新建按钮打开配置抽屉。在抽屉中依次选择「触发方式」、配置触发参数、指定「执行内容」与目标会话，并为周期任务配置「重复规则」。
- **任务详情**：点击具体任务可查看其「下次执行时间」、「已执行次数」、最近一次执行结果摘要及错误堆栈信息。
- **运行历史**：切换至历史记录标签页，可以以时间线方式查看历次触发的时间戳、执行状态、终端结果及执行耗时。
- **快捷控制**：在列表操作列或详情页顶部，提供了「暂停」「恢复」「删除」等操作按钮，也可以点击「立即执行」手动进行触发测试。

<!-- 截图占位：定时任务页 · 任务详情与运行历史 -->

后台任务的管理页面位于左侧导航栏「观测」分组下的「后台任务」。

在后台任务页面中，可以查看所有处于「运行中」的任务状态，展开查看实时更新的进度与日志，并在需要时直接执行取消操作。

## 推荐配置

结合具体业务场景合理配置参数，能够使自动化机制更加稳定高效。以下是几种常见场景的配置建议：

### 日常提醒

配置每日早报、定时下班提醒或固定日程时，建议选用「时间点」或「cron」触发方式，并将重复规则配置为单次或每日重复。

在「执行内容」中填入明确的提示词（例如「向大家播报今天的天气与重点日程」），清晰指示模型的执行目标。同时将「宽限时间」设置为较短区间（如 5 到 15 分钟），避免因系统重启或网络延迟导致在不适当时刻补发过期提醒。

### 群活跃维护

若希望机器人在群聊冷场时主动发言活跃气氛，建议优先选用「关注条件」模式。

可将条件组合设置为：群内「沉默时长」达到阈值（如 45 分钟）、前一阶段发言消息数达到一定基数，或特定活跃成员发言。务必设置合理的每日触发上限与最小间隔，防止频繁发言打扰群聊。此外，建议配合角色的作息时间与每小时发言上限共同生效。

### 长任务

当机器人需要执行系统命令、网络抓取、大文件处理或代码构建等重度任务时，应将其封装为支持后台执行的工具。

在工具配置中设置合理的「同步等待超时时间」（如 5 到 10 秒）。对于短时间内可完成的请求，机器人仍保持同步响应；对于超出阈值的长耗时任务，则自动转入后台执行并在完成后通知会话，保证对话交互的流畅度。

### 多群

当机器人同时服务多个群聊时，应避免配置向所有会话全局广播的单一任务。

不同群聊的成员偏好、作息规律与活跃时段各不相同。建议在创建任务时明确绑定目标会话，或针对重点群聊分别创建独立的定时任务，根据各个群的具体节奏配置针对性的触发策略与提示词。

## 排查

当自动化任务未按预期运行时，可参考以下排查方向：

**任务没有按时执行。**
在控制台中检查任务状态是否为「活跃」，处于暂停或失败状态的任务不会触发。检查「下次执行时间」计算是否正确、时区配置与服务器系统时间是否一致，并确认该会话是否已达到「每日触发上限」。若系统负载较高且配置的「宽限时间」过短，任务可能会因超出宽限期而被系统跳过。

**任务执行了但没发消息。**
在任务详情或运行历史中确认任务是否成功触发。若任务已执行但会话未收到消息，检查「执行内容」中的投递方式配置是否误设为「不发送」，或配置成了仅向控制台输出的「通知」模式。通知类内容仅记录在控制台后台，不会推送给前端对话。

**关注条件一直不触发。**
检查条件表达式中引用的变量名是否正确、字段数据是否正常更新。若条件依赖系统时间或沉默时长，确认轮询检测周期是否合理。排查时建议简化条件，先通过单一基础规则（如纯沉默时长判断）测试通过，再逐步叠加复合条件。

**后台任务一直运行。**
在控制台后台任务页中打开任务实时日志，查看输出流是否仍在更新，判断底层任务是仍在处理中还是处于卡死状态。可在操作列中点击「取消」按钮终止任务。取消后系统会立即停止将后续结果回传给对话，底层资源将在作业退出后释放。

**角色频繁醒来。**
通常是由于唤醒条件设置过于宽泛（例如任意消息均触发唤醒），或最大唤醒次数与最小间隔配置过小。可通过缩短「最长等待时间」、调大触发间隔，或将条件限定为「特定用户回复」等具体事件来降低唤醒频率。

**任务费用很高。**
自动化任务的开销主要来自两部分：在关注条件中频繁调用「意图判定」模型，以及在执行内容中频繁调用大模型「运行提示词」。可以通过降低意图判定的检测频率、设置更严密的每日调用预算来控制成本；对于规则明确的场景，建议改用纯时间或消息条数等无模型调用的判定条件。

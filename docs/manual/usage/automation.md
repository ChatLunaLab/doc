# 定时与后台任务

::: tip
这一页讲三件容易混淆的事：按时间或条件触发的「定时任务」、跑得久所以放到后台的「后台任务」，以及角色自己约定的「稍后回来」。
:::

日常使用机器人时，我们最常见的交互是一问一答。但在很多真实场景里，机器人的工作并不局限于当前这一回合。

比如你想让它每天早上八点发一句早安，或者在群里冷场半小时后主动暖场，又或者让它去下载一个大文件、跑一段耗时很长的脚本。如果这些事情全堵在当前对话里等它跑完，不仅整个聊天窗口会被卡死，机器人也失去了灵活性。

它们的共同点是「不在当前回合里完成」。区别在于到底是由谁发起、什么时候执行，以及最后的结果该怎么回到对话中：

- **定时任务**：由你（或插件与模型）显式创建，等到未来某个确切时间点、固定周期，或者特定事件发生时才触发。
- **后台任务**：在当前对话中就已经启动，但因为耗时过长，转入后台静默运行，有了进展或最终产出后再通知你。
- **角色自己的唤醒**：角色在对话中根据剧情或上下文，主动为自己约定好「稍后在什么契机下重新开口」。

## 定时任务

定时任务是系统中最基础的自动化机制。简单来说，它就像是你给机器人定下的一份备忘日程表。只要时间一到或者预设的条件满足，机器人就会自动执行预定好的动作。

你可以在控制台的「观测 → 定时任务」页面里统一查看和管理所有任务。不仅管理员可以手动新建任务，大模型在对话中根据需要、或者第三方插件也可以主动向系统注册定时任务。

在创建或查看一个定时任务时，通常需要关注以下五个核心要素：

- **触发方式**：决定任务在什么时候被唤醒。可以是一个具体的时间点、固定循环间隔、复杂的 cron 表达式，也可以是持续观察某个特定事件的关注条件。
- **执行内容**：决定任务触发后具体做些什么。例如像真人进群一样直接唤醒对话，或者在后台运行一段专属提示词并把结果发送出来。
- **重复规则**：决定任务执行的生命周期。可以只执行一次、连续执行若干次，或者在达到某个特定截止时间前持续重复。
- **状态**：展示任务当前所处的运行阶段。系统定义了四种标准状态：等待执行的「活跃」、被人工挂起的「暂停」、生命周期结束的「完成」，以及执行出错的「失败」。
- **宽限时间**：为任务执行设置的一道容错缓冲。如果因为系统繁忙或网络波动导致到点后无法准时执行，只要延迟没有超过宽限时间，系统仍会补发执行；一旦超过宽限时间，该次任务就会被安全跳过，避免在不合时宜的时刻补发无效消息。

### 触发方式

在新建任务的设置面板中，系统提供了四种不同的触发方式。你可以根据实际需求灵活挑选：

- **时间点**：在未来的某个精确时间执行一次。适合设置一次性的提醒，例如「今天下午 3:00 提醒大家开会」。执行完毕后，任务就会自动标记为完成。
- **固定间隔**：每隔一段固定时长循环执行一次，例如「每隔 2 小时检查一次更新」。需要注意的是，如果设置的触发间隔太短，系统会将其判定为高频操作并触发审批流程，以防止因为手滑误配导致机器人疯狂刷屏或耗尽资源。
- **cron**：按照日历规则精准安排周期，例如「每周一至周五早上 9:00 发送早报」。你可以根据所在地区指定具体时区，系统会严格按照日历时间进行调度。
- **关注条件**：不再依赖死板的时间表，而是让系统持续检查一个动态条件表达式。只有当条件计算为真时，任务才会真正触发。条件可以感知群聊的新消息、特定发言人、群内沉默时长等动态数据。

### 执行内容

当触发条件达成之后，任务到底该干什么？系统主要支持两种执行模式：

- **唤醒**：模拟有人在群里或者私聊中叫了机器人一声，直接触发一次正常的对话回合。你可以为这次唤醒附带一个明确的触发原因（例如「早晨定时唤醒」），大语言模型会参考这个原因组织自然的开场白。
- **运行提示词**：不走常规的聊天问答流程，而是使用你指定的模型引擎或子代理，在后台专门运行一段独立的提示词。对于产出的结果，你可以自由选择投递方式：直接作为普通消息「发送」到目标群聊、作为系统「通知」推送到控制台、或者完全「不发送」仅供系统内部流转。

### 限制

定时任务赋予了机器人脱离人工介入的自动化能力，但如果缺乏节制，容易引发意外。为了避免任务陷入死循环或消耗过多资源，系统内置了多层安全限制网：

- **同时活跃任务上限**：限制每个会话下能够同时处于运行状态的任务总数。
- **一次性唤醒上限**：限制单个会话中排队等待执行的一次性唤醒数量，防止短时间内大量唤醒挤压队列。
- **每日触发上限**：为每个会话设置单日允许触发任务的最高次数，超出后当天的后续触发将被熔断。
- **最短触发间隔**：对重复任务设定了频率红线，低于这个安全间隔的任务必须经过管理员手动审批后才能生效。
- **允许的最大延迟**：任务到点后如果系统正忙或刚好在重启，只要延迟没有超过这个时间仍会补发；超过就跳过本次，避免半夜补发白天的提醒。

这些限制项都可以在定时任务插件的配置面板中找到并根据实际硬件环境进行微调。系统预设的默认值已经兼顾了绝大多数部署环境的安全与性能；在动手调大这些阈值之前，建议先评估好最坏情况下的系统负载。

::: warning
定时任务往往是在无人值守的情况下自动跑起来的。因此，在为任务编写提示词时，务必做到指令明确、逻辑自洽且可重复执行，切忌写出诸如「看看情况再说」「根据气氛发挥」这种极度依赖当下即时上下文的模糊指令。此外，即便是在定时任务内部调用的工具，凡是涉及写入操作或命令执行的高危动作，系统的权限检查与审批流程依然会照常生效。
:::

### 关注条件

关注条件的设计初衷，是为了解决那些「无法用固定时钟衡量」的场景。它更适合「等到某件事发生」，而不是「等到某个时刻到来」：

- 等待群里特定的人回复消息。
- 等待热闹的群聊逐渐安静下来，气氛转入冷场。
- 等待一段时间内积累的消息数量达到某个预设阈值。
- 等待指定的某个工作时间段正式开始。

在条件表达式中，你可以读取上下文中的丰富环境数据，包括最近收到的消息内容、说话人的身份、群聊当前持续的沉默时长、当前系统时间，以及该任务此前已经触发过的总次数等。

值得注意的是底层的检查机制：只读取消息内容的条件，系统会在每一次收到新消息时立即进行判定；而读取了系统时间或沉默时长的条件，系统则会按照固定的时间轮询定期检查。

在编写关注条件时，尽管逻辑判断非常灵活，但通常建议尽量保持清晰简洁。条件嵌套得越复杂，后期排查「为什么任务迟迟没有触发」时的难度就会成倍上升。

### 意图判定

有时候，光靠字数比较、发言频率或简单的关键词匹配，很难准确捕捉人类复杂的表达。比如你想在「大家聊到聚餐话题时」主动提供餐厅推荐，这显然不是简单的时间或数字规则能搞定的。

为了应对这类高级需求，定时任务支持接入意图判定。系统会调用一个轻量级判定模型，把最近窗口内的聊天记录与预设的核心问题一同交给它，让模型在上下文中做出是或否的二元结论。

由于意图判定每次都需要调用大语言模型，系统专门为其设置了严格的频率限制与每日调用预算。这样能确保机器人在热闹非凡的千人大群里工作时，不会因为每来一句话都去请求判定模型，进而导致 API 账单迅速见底。

## 后台任务

许多刚接触自动化的朋友容易把「后台任务」和「定时任务」弄混。其实两者的逻辑完全不同：定时任务是「等到未来某个时间点再开始」，而后台任务则是「现在立刻开始，但我知道要跑很久，所以稍后再来取结果」。

后台任务通常是由对话中的工具调用触发的。当模型决定调用某个外部工具，而该操作预计耗时较长时，如果继续让对话在前端同步傻等，整个交互就会彻底卡住，直到超时报错。此时，系统就会顺理成章地将这个工作转到后台继续推进。

一个标准的后台任务具有以下运行特征：

- **独立的生命周期状态**：任务脱离主对话独立流转，拥有「运行中」「停止中」「完成」「失败」以及「取消」五种明确状态。
- **实时输出与日志**：支持在运行过程中持续向外抛出执行进度和调试日志，便于用户随时观察。
- **分段增量读取**：支持按偏移量读取已产生的输出内容，无需每次从头到尾拉取全部文本，节省开销。
- **灵活的完成通知**：任务跑完后，可以配置如何把结果送回对话——直接打断当前对话插播结果、安静地排队留到下一轮对话再汇报，或者仅仅在管理界面做记录而不通知用户。
- **支持安全取消**：在任务执行过程中如果发现异常，你可以随时在后台向其发送取消指令。系统会尽最大努力去终止底层的异步作业，尽管部分外部系统可能无法做到毫秒级即时停止。

### 什么时候会用后台

在日常使用中，最常转入后台运行的通常是以下几类重型工作：

- 执行复杂的终端命令或脚本，执行时间明显超过了系统设置的同步等待上限。
- 耗时巨大的本地或网络文件处理，比如大体积文件的下载、解压、视频转码或项目编译构建。
- 需要在外部环境中持续观察或轮询状态的监听型任务。
- 复杂的子代理执行流程，由子代理或工具自身根据任务复杂度，主动决定转入后台运行。

为了保证体验流畅，工具自身可以声明其同步等待超时阈值，并明确配置「允许转后台」开关。当工具调用的执行时间突破同步等待上限后，系统会自动将其升级为后台任务，并先在前端对话中返回一个占位结果安抚用户；等到后台工作彻底搞定后，再把最终产出无缝送回会话。

### 读取与取消

在后台任务的运行过程中，输出流会被系统精细地拆分成两条通道，互不干扰：

- **模型可读的输出**：这部分内容经过结构化整理，在任务完成或汇报时会重新注入对话上下文，供模型理解任务的最终产出，并据此组织语言答复用户。
- **人类可读的日志**：包含底层的执行细节、标准错误信息和耗时监控。这部分纯技术日志只会呈现在控制台的管理界面中，绝不会污染模型的对话上下文。

为了防止某个异常脚本产生死循环并疯狂打印日志撑爆内存，系统为任务输出设置了严格的缓冲区上限。一旦日志量超出阈值，超出部分会被自动截断并附上明确的截断标记。而在控制台或通过接口读取日志时，系统支持基于偏移量进行增量拉取，确保你只拉取自上次查看之后的新内容。

::: tip
后台任务最适合处理「运行较慢但用户并不急于当场拿到结果」的工作。如果用户眼巴巴地在群里等待一个即时答案，把任务生硬地扔进后台只会让体验变得更慢、更割裂。遇到这种情况，更合理的做法通常是拆分或缩小单次任务的处理范围，而不是滥用后台化。
:::

## 角色自己的唤醒

在伪装引擎下，角色拥有更高的主动性。除了被动地等待人类在群里呼叫，角色还可以根据聊天进展和剧情需要，自己约定「稍后回来看一眼」：

- 在丢出一个引人深思的问题后，暂时退场，等待有群友回复时再接着往下聊。
- 在群聊氛围热烈时主动隐身，耐心等待群里彻底安静一段时间后，再挑起一个全新的话题。
- 根据日常作息规律，约定在明天的某个具体时间点（如清晨或傍晚）主动向大家发送问候或备忘提醒。
- 在心里给自己挂上一个关注条件，静静观察群聊走向，一旦满足特定要求便主动开口接话。

当角色主动发起唤醒时，可以在内部设置一整套细致的自律参数：

- **最早可醒时间**：设定一个保护期，在这个时间点到来之前，无论外面发生什么都不会被过早吵醒。
- **醒来条件**：指定唤醒的契机，例如等待他人回复、等待群内出现指定时长的沉默、等待到达某刻、或者等待群消息累积到一定条数。
- **最大唤醒次数与最小间隔**：明确自己最多主动醒来几次，以及两次主动发言之间必须相隔多久，防止频繁冒泡。
- **最长等待时间与超时处理**：为唤醒设置一个有效期。如果在最长等待时间到期后条件依然没有达成，角色可以选择直接放弃此次唤醒，或者不再等待强行醒来发言。
- **主动说话后自动取消**：如果中途因为其他原因（比如被群友主动 @ 提问）提前开口说了话，是否自动清理掉原本挂起的等待计划。

在默认规则下，角色约定的唤醒通常只生效一次；如果你希望它能持续关注并反复醒来，就需要显式配置允许的次数与间隔。需要特别注意的是，系统预设的最长等待时间默认是「最早可醒时间之后的十分钟」。如果你想让角色在几个小时甚至几天后依然保持等待，就必须显式延长这个最长等待时间。

::: warning
唤醒本质上是基于「条件」触发的，切勿把它当成绝对准时的硬性闹钟来用。如果把唤醒条件写得过于宽泛，角色很可能会频繁跳出来打扰大家；而如果条件苛刻到脱离现实，角色就可能永远陷入沉睡。在初始配置阶段，推荐先从「等回复」或「等沉默」这类清晰明了的基础条件开始尝试，观察几轮实际表现后再酌情增加复杂度。
:::

## 页面怎么用

打开控制台，在左侧导航的「观测」分组里点击「定时任务」，你可以在这里完成任务全生命周期的可视化管理。

页面主要包含以下核心功能区域：

- **任务列表**：集中展示当前所有的自动化任务。你可以按照「任务状态」（活跃、暂停、完成、失败）、「目标会话」（私聊或具体群聊）以及「创建者」（人工创建、插件创建或模型创建）进行快速筛选过滤。
- **新建任务**：点击右上角的新建按钮即可唤出配置抽屉。在这里你可以按步骤选定「触发方式」、设定触发参数、指定具体的「执行内容」与目标会话，并为周期性任务编排「重复规则」。
- **任务详情**：点进任意一个具体任务，你可以清楚地查看该任务的「下次执行时间」、「已执行次数」、最近一次触发的执行结果摘要，以及可能发生的错误堆栈提示。
- **运行历史**：点击历史记录标签页，系统以时间线形式记录了该任务过往每一次触发的详细时间戳、执行状态、终端结果以及具体执行耗时，方便溯源审计。
- **快捷控制**：在列表操作列或详情页顶部，提供了直观的控制按钮，你可以随时对任务执行「暂停」「恢复」「删除」操作，也可以点击「立即执行」当场触发一次测试。

<!-- 截图占位：定时任务页 · 任务详情与运行历史 -->

至于后台任务，它有自己的页面：在左侧导航的「观测」分组里点击「后台任务」。

在后台任务页中，你可以实时监视所有处于「运行中」的任务，展开查看动态更新的进度与输出，并在必要时直接取消。

## 推荐配置

在不同场景下使用自动化时，合理的参数搭配往往能达到事半功倍的效果。以下是几种常见业务场景的最佳实践推荐：

### 日常提醒

在配置每天早报、下班提醒或特定时刻日程时，最稳妥的方式是选用「时间点」或「cron」触发方式，重复规则设置为执行一次或每天一次。

在「执行内容」中，建议填入语义非常明确的固定提示词，例如「向大家播报今天的天气与重点日程」，明确告诉模型要做什么。同时，将「宽限时间」控制在合理的小范围内（如 5 到 15 分钟），避免在服务器临时关机或重启后，在夜深人静时把白天错过的陈旧提醒一股脑补发出来。

### 群活跃维护

如果你想让机器人在群聊气氛低落时主动出来活跃气氛，应当优先选用「关注条件」模式。

可以把触发条件组合为：群内持续「沉默时长」达到阈值（例如 45 分钟）、上一阶段的发言消息数量达到一定基础、或者特定活跃群友发言。切记一定要为任务设置合理的单日触发次数上限与最小间隔，防止群里偶尔冷场时机器人反复发言刷屏。此外，务必配合角色的睡眠作息时间以及每小时发言上限协同工作，让机器人的作息表现更像一个真人。

### 长任务

当你的机器人需要承担执行系统命令、抓取大型网页、下载资源或进行工程构建等重活时，请务必将其封装为支持后台调用的任务工具。

在工具配置中设置一个得当的「同步等待超时时间」（例如 5 到 10 秒）。这样一来，对于那些几秒内就能快速搞定的轻量操作，机器人依然能够直接同步回复用户；而一旦遇到真正耗时的大型作业，系统便能平滑自动转入后台运行，待产出完毕后再通过会话通知用户，大幅提升交互体验。

### 多群

如果你的机器人同时加入了多个不同的聊天群，切忌简单粗暴地配置一个「向所有会话广播相同内容」的全局大任务。

不同群聊的成员结构、作息规律和日常话题存在巨大差异。推荐的做法是在创建任务时明确绑定单一目标会话，或者为每一个核心群聊单独建立专属的定时任务。针对每个群的具体活跃时间段量身定制触发策略与提示词风格，这样才能让机器人的发言显得自然而不突兀。

## 排查

自动化任务在无人值守时运行，遇到问题时可以按照以下步骤对号入座进行排查：

**任务没有按时执行。**
首先进入控制台检查任务的当前状态是否仍为「活跃」，如果处于暂停或失败状态则不会触发。其次检查「下次执行时间」计算是否符合预期、所选的时区设置是否与服务器系统时间一致。此外，检查该会话是否已经触碰了「每日触发上限」。如果系统负载较高，而任务配置的「宽限时间」设置得过于苛刻，也会导致任务因为轻微超时而被系统直接跳过。

**任务执行了但没发消息。**
在任务详情或运行历史中确认任务确实触发成功。如果任务已执行但聊天窗口毫无动静，通常是「执行内容」中的投递方式配置有误：检查是否不小心勾选了「不发送」，或者选成了仅供管理员后台查看的「通知」模式。通知类消息只会静默写入控制台，并不会推送给前端对话。

**关注条件一直不触发。**
请先检查条件表达式中所引用的变量是否存在、以及这些字段是否具备实时更新能力。如果是依赖系统时间或沉默时长的条件，确认检查轮询的检测周期是否设置过长。排查时建议采用渐进法：先将逻辑缩减为单一的简单条件（如单纯判断沉默时长），验证成功后再逐步叠加其他复合规则。

**后台任务一直运行。**
在控制台的任务页中调出该任务的实时日志，观察底层的输出流是否仍在持续滚动，确认底层进程是仍在繁忙运算还是已经彻底死锁卡死。你可以随时点击操作列中的「取消」按钮手动终止任务；尽管取消信号下发后可能需要等待底层工作自行释放资源，但系统会立即截断后续结果继续回流至对话中。

**角色频繁醒来。**
这往往是因为角色设定的唤醒条件过于宽泛（例如只要有人发任意消息就立即唤醒），或者是最大唤醒次数给得太多、两次唤醒之间的最小间隔定得太短。你可以通过缩短「最长等待时间」、强制拉大触发间隔，或者把条件精准细化为「特定用户回复」等具体场景来收紧发言频次。

**任务费用很高。**
自动化任务的开销主要集中在两处：一是在关注条件中频繁启用了「意图判定」小模型，二是在执行内容中频繁调用大模型「运行提示词」。你可以通过调低意图判定的轮询频率、设置更严密的每日调用预算来止血；对于判断逻辑相对固定的场景，推荐直接改用零成本的纯时间或消息条数等硬性条件。

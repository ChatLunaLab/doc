# MCP

::: tip
MCP（Model Context Protocol）负责把外部服务提供的工具接进 ChatLuna。连接成功后，在模型看来它们就是普通的工具，而背后的实际运算则由独立的本地进程或远程服务来完成。
:::

在很多日常场景中，我们并不需要为了接入某个外部系统而大费周章地专门编写一个插件。

如果你手头已经有了现成的服务——比如本地运行的数据库、自建的搜索引擎、GitHub 等项目管理平台，或是企业内部的业务系统，直接对接现有的标准接口往往会轻松得多。

这正是 MCP 大显身手的地方。

它是一套开放的标准协议。只要外部服务支持 MCP，你就可以用完全统一的方式把它接入 ChatLuna。

接入之后，外部服务暴露出来的工具就会直接出现在 ChatLuna 的工具箱中。

对大语言模型而言，它感知到的就像是本地原生工具一样，可以随时按需调用；而实际的任务执行与数据读写，全都在外部进程或远端服务器中安全搞定。

## MCP 页

在控制台中，点击左侧导航栏的「能力 → MCP」，就能进入 MCP 服务的统一管理页面。

这里集中展示了当前实例接入的所有 MCP 服务。

你可以根据自己的查看习惯，在页面右上角自由切换「卡片」或「列表」视图。

当接入的服务越来越多时，你还可以根据「连接状态」或者「传输方式」对服务进行分组筛选，排查问题非常直观。

在每一个服务卡片上，系统都清晰列出了几项关键信息：

- **服务 ID 和名称**：服务的唯一标识与自定义显示名称。
- **传输方式**：当前服务是通过本地命令启动，还是连接远程地址。
- **连接状态**：包括已连接、连接中、已停用、出错、缺少传输支持、空闲等。
- **工具数量**：该服务成功导入并可供使用的工具总数。
- **最近一次连接错误**：如果连接遇到问题，卡片上会直接展示具体的报错提示。

点击任意一个服务卡片，右侧就会展开详细抽屉。

在这里，你可以查看该服务的配置详情、数据来源以及底层的连接参数。

更重要的是，你可以在这里查阅完整的「工具清单」。

清单中列出了每一个工具的名称、功能说明以及所需的调用参数。

如果外部服务的某些工具参数结构不兼容，系统在解析时会自动跳过该工具，并在列表中明确标注跳过的原因，方便你针对性地进行调整。

### 添加服务

要想让外部工具为你所用，首先需要把服务添加到系统中。

在 MCP 页点击「添加服务」，系统提供了三种便捷的添加方式：

- **本地命令**：填写可执行文件、启动参数、环境变量和工作目录。适合在运行 ChatLuna 的宿主机上直接启动的服务。
- **远程地址**：填写服务端点和请求头。适合已经独立部署在服务器或容器中的 HTTP 服务。
- **粘贴导入**：直接粘贴现成的服务配置文本，系统会自动解析并批量完成导入，省去逐项填写的繁琐。

配置填写完成后，建议先别急着保存。

你可以先点击「测试连接」按钮进行验证。

点击测试连接后，系统会在后台尝试连接目标服务，拉取一次工具清单，并在校验完毕后主动断开。

这次测试仅仅是一次轻量级的握手探测，并不会真正把工具加载到实例中，完全不影响正在运行的会话。

确认各项连接正常、工具清单也顺利读取后，再点击「保存并启用」，服务便会正式上线工作。

::: warning
本地命令会以实例进程的同等权限在系统后台运行。
请切勿随意连接来源不明的命令或脚本，以免带来系统安全隐患。
如果需要运行不可信的服务，建议将其放入隔离的容器或远程主机中，通过远程地址的方式进行接入。
:::

## 两种传输方式

MCP 协议支持多种底层通信媒介。在 ChatLuna 中，你可以根据服务的部署位置自由选择适合的传输方式。

### stdio

在本地命令方式下，ChatLuna 会在宿主机上派生启动一个独立的子进程。

系统与该子进程之间完全通过标准输入输出（stdio）来收发消息。

这种方式非常适合本地轻量工具、CLI 命令行封装，或是需要直接读写本机磁盘文件的本地服务。

在配置界面中，你可以设置以下选项：

- **启动命令**：可执行文件的名称或系统中的绝对路径。
- **命令行参数**：启动程序时附加的一系列参数。
- **环境变量**：程序运行所需的环境变量。对于敏感信息，可以勾选将其作为密钥安全保存，这样不会在普通界面上明文展示。
- **工作目录**：子进程执行任务时的基准路径。
- **单次调用超时**：单个工具执行的最长等待时间，默认值为 `120` 秒。

子进程的生命周期与服务状态完全同步。

当你启用该服务时，子进程会被自动拉起；而当插件卸载或实例关闭时，子进程也会被随之安全终止。

如果运行过程中子进程意外断开，卡片会变为出错状态，你可以随时手动点击重新连接。

### http

远程地址方式则是直接向一个已有的网络端点发起通信。

它通过 HTTP/HTTPS 协议与远端的 MCP 服务连接，非常适合已经在独立服务器上部署好的服务。

如果你有多个 ChatLuna 实例需要共享同一个服务，或者网络环境中有特定的网关与安全策略，这种方式再合适不过。

在界面中，你可以配置以下内容：

- **端点 URL**：远程 MCP 服务的访问入口地址。
- **请求头**：请求外部端点时附加的 Header 内容。如果其中包含认证令牌，同样可以作为密钥进行脱敏保存。
- **单次调用超时**：等待远程服务响应的最长时间。

HTTP 方式最大的优点在于轻量，它不需要在本机创建和管理任何子进程。

不过需要注意，所连接的远程服务端必须完整支持 MCP 协议所要求的流式传输规范，否则可能无法正常交互。

## 工具是怎么投影进来的

服务连接成功后，外部的工具究竟是如何进入 ChatLuna 的体系中的呢？

为了防止外部工具与本地现有的原生工具产生冲突，ChatLuna 对所有 MCP 工具采用了统一的投影命名规范。

投影后的工具名称结构非常清晰：

固定以 `mcp__` 开头，中间拼接服务的 ID，最后附上原工具名称，整体格式形如 `mcp__服务ID__工具名`。

举个例子：如果服务 ID 是 `github`，该服务暴露了一个名为 `search_repos` 的工具，那么投影后进入系统的工具名称就是 `mcp__github__search_repos`。

在转换过程中，系统还会进行规范化处理：

如果工具原本的名字中带有非法字符，系统会自动将其替换为合规符号。

对于特别冗长的工具名，系统会自动将其截断到 `64` 个字符以内。

如果在替换或截断后不幸与系统中已有的工具重名，为了保证安全性，系统会跳过当前工具，并记录一条警告日志。

与此同时，工具的参数结构也会被自动映射转换。

系统会将外部服务提供的参数规范，转化为 ChatLuna 内部能识别的工具参数模型。

在此期间，如果不巧遇到了系统暂不支持的特殊规范参数，这部分内容会被自动忽略并写入日志；而如果某个工具的整体结构完全无法兼容解析，该工具也会被直接跳过。

::: tip
在「工具」管理页面中，只需要在过滤框输入 `mcp__` 这个前缀，就能迅速筛选出当前接入的全部 MCP 工具。
你可以借助通配符对它们进行批量管理，比如批量将所有 MCP 工具设为按需加载，或是统一要求执行前必须人工审批。
:::

## 连接与重连

在日常管理中，掌握服务的连接状态有助于快速发现并解决问题。

卡片上常见的连接状态包括以下几种：

- **已停用**：服务的配置依然保留在系统中，但你关闭了它的启用开关。
- **连接中**：系统正在尝试建立进程通道或网络握手，并同步拉取工具定义。
- **已连接**：连接建立成功，所有兼容的工具已经顺利投影就绪，随时可以响应调用。
- **出错**：连接失败或中途异常断开，卡片上会明确展示具体的出错原因。
- **缺少传输支持**：系统当前缺少处理对应传输方式的插件支持。
- **空闲**：服务开关处于开启状态，但目前尚未触发实际的连接流程。

很多小伙伴可能会担心：万一外部服务崩溃了，会不会把整个机器人带垮？

答案是完全不会。

ChatLuna 具备良好的故障隔离机制，某个服务的连接失败绝对不会影响系统的正常运转。

出现故障的服务仅仅会保持在出错状态，其他服务和功能依旧照常工作。

当你修复好外部环境或修改了配置参数后，点击卡片上的重连按钮即可恢复，无需重启整个实例。

此外，每当你修改了服务配置、安装卸载了相关插件，或是重启了 ChatLuna 实例，系统都会自动重新发起连接并刷新工具列表。

在刷新的过程中，即使当前正好有工具正在被模型调用，那次调用也不会被中途强行掐断，保证任务执行的连续性。

## 与工具页、权限的关系

经常有小伙伴会有疑问：MCP 工具接入之后，它的权限由谁管？

结论很简单：一旦 MCP 工具投影进来，它在系统眼中就是普通的工具。

它会完全融入现有的治理体系中，受到全方位的统一调度：

- **工具策略独立配置**：在「工具」页面中，你可以像对待原生工具一样，为每个 MCP 工具单独指定策略，设为自动执行、需要审批或直接禁用。
- **场景规则精细划分**：通过「场景规则」，你可以灵活控制哪些群聊可以使用某个 MCP 工具，哪些群聊则对其完全不可见。
- **全局权限机制兜底**：系统的权限模式会对高风险工具调用进行统一把控，敏感操作是否需要审批由全局权限说了算。
- **支持按需动态加载**：当开启了工具搜索时，系统支持将 MCP 工具设为按需加载模式，系统默认也是这样推荐的。

换句话说，MCP 服务本身从来不负责决定用户的访问权限。

它唯一的职责就是提供工具能力。

一个工具最终能不能被执行、要不要管理员审批，始终由 ChatLuna 的工具策略和权限规则共同决定。

## 常见服务类型

随着 MCP 生态的壮大，社区中已经有大量成熟的服务可以直接取用。

目前比较常见的服务类型包括：

- **文件与代码**：读取与修改本地文件、检索代码仓库、在隔离沙盒中执行系统命令。
- **数据库**：获取数据库表结构信息、安全执行只读查询操作。
- **搜索与网页**：调用外部搜索引擎获取最新资讯、抓取网页正文内容或生成页面摘要。
- **项目管理**：管理 GitHub 或 GitLab 等平台的 Issue、查看 Pull Request 变更、跟进任务看板。
- **内部系统**：对接企业私有的业务系统，如查询订单状态、同步库存数据或创建客服工单。

把一个新服务接进来之前，建议先花一两分钟熟悉它的工具特性：

看看工具到底是不是只读的、是否依赖外部认证凭据、调用后会不会带来不可逆的副作用。

凡是带有写入、修改或执行外部指令性质的工具，通常都建议在工具页将其设置为需要审批。

## 推荐配置

面对不同的运行环境，如何配置 MCP 服务才能既安全又好用？

我们为你总结了以下几种典型场景的配置建议：

### 个人实例

如果只是在自己的个人电脑上单人使用，建议选择本地命令（stdio）方式。

平时只需接入一两个最常用的工具服务即可，配置简单，响应也最直接。

对于涉及本地文件修改或终端命令执行的高风险工具，记得在工具页手动调成需要审批。

### 多实例共享

如果是多用户团队或部署了多个 ChatLuna 实例，建议将服务搭建为独立的远程 HTTP 服务。

让多个实例共同连接同一个远程端点，实现工具能力的集中复用。

各个实例在请求头中配置各自独立的鉴权凭据，并根据每个实例的具体使用场景单独设定工具策略。

### 工具很多

当接入的服务较多、工具总数累计达到几十甚至上百个时，一股脑全部暴露给模型容易导致上下文超限或模型注意力分散。

这种情况下，强烈建议在工具页开启工具搜索功能，让所有 MCP 工具默认保持按需加载。

只把最核心、最常用的几个高频工具设为常驻工具，其他工具则等待模型有需求时再动态检索匹配。

一般而言，将搜索阈值保持在 `20` 左右，整体使用体验最佳。

### 高风险环境

在面向公开群聊或复杂多租户的高风险环境中，安全性是首要考量。

此时应避免使用本地命令方式运行不可控的程序，建议将服务部署在安全的容器或独立主机中，通过远程地址方式接入。

对于本地命令方式，只保留绝对可信的官方或内部经过审计的命令。

在工具权限上，将所有具有写入行为的工具全部设为需要审批，而带有命令执行能力的工具则建议默认保持禁用状态。

## 排查

在接入和使用 MCP 服务时，如果遇到了非预期的情况，可以按照以下条目逐步排查：

**服务一直显示出错。**

请先仔细查看卡片上展示的错误提示文本。

常见的故障原因包括：指定的本地命令不存在、参数格式有误、远程端点无法连通、请求头鉴权失败，或是服务协议版本不兼容。

如果是本地命令，请先确认该命令脱离 ChatLuna 在本机命令行中能否正常运行；如果是远程地址，请检查网络通畅度及请求头配置是否正确。

**连上了但没有工具。**

如果状态显示连接成功但工具列表为空，说明外部服务可能本身就没有暴露任何可用工具。

另一种常见的情况是，该服务所提供的工具参数格式较为特殊，导致参数结构无法被系统识别而被全部跳过。

你可以点击卡片打开服务详情，在工具清单中查看具体的跳过原因说明。

**模型看不到某个 MCP 工具。**

当模型在对话中无法调用某个工具时，可以按照以下顺序逐项核对：

首先确认对应的 MCP 服务当前是否保持在已连接状态；

其次检查该工具是否因为参数兼容性问题在工具清单中被标记跳过；

然后前往「工具」页和「场景规则」页，查看该工具是否被全局禁用，或是在当前所在群聊中被规则过滤；

最后查看是否开启了按需加载，如果处于按需模式且当前提示词未匹配中该工具，模型暂时也是看不到的。在工具页可以查看工具的最终可见状态。

**工具名冲突。**

当两个不同的 MCP 服务导出了同名工具，或者不同工具在替换非法字符并截断后碰巧生成了相同的投影名称，就会触发名称冲突。

遇到这种情况，系统会跳过冲突的工具。

你可以在服务设置中修改该服务的 ID，从而调整投影后的前缀名称；也可以直接在工具管理页中将其中一个冲突工具手动禁用。

**调用总是超时。**

如果工具在调用过程中频繁出现超时报错，可以尝试在对应服务的配置中适当调大「单次调用超时」的设定值。

同时，建议检查外部服务内部是否存在死锁、网络阻塞或长时间无响应的问题。

如果开启了工具搜索，初次搜索匹配工具时如果网络延迟较高，也有可能因为耗时过长而触发超时，可以留意底层网络情况。

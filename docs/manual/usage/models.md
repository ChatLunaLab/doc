# 模型与提供商

::: tip
提供商负责「怎么连上模型服务」，模型负责「这次用哪一个」。把这两件事分开，换模型时不用重配密钥，换服务时也不用改对话设置。
:::

在配置聊天机器人时，我们最关心的往往是：它到底用什么模型在和我们说话？

ChatLuna 本身不内置任何模型，也不要求你只能使用某一家具体的 AI 服务商。你可以同时接入任意多个提供商，在控制台给它们起不同的名字以便区分，再根据具体的聊天场景、人设角色或者后台任务，灵活选用不同的模型。

那么细心的小伙伴可能会发现：既然都是用来生成文本，为什么系统要将「提供商」和「模型」拆成两个独立的概念呢？

让我们设想一下：如果把模型和具体的连接配置混在一起，每当你想要换一个模型体验，就得重新填写一遍服务器地址和 API 密钥；一旦哪天服务商的接口地址变了，所有相关的配置都要翻出来挨个修改。

而一旦将这两者解耦，提供商就只管服务通信，模型则只是该提供商名下的一个可选项。日常切换模型只需轻轻一点，完全不需要重复折腾连接参数。

## 提供商

提供商 (Provider) 是一次具体的服务连接。简单来说，只要你配置好了一个服务端点、一组访问凭据，以及一份可用的模型清单，就组成了一个提供商实例。

同一个服务商可以接入多次。例如你有两个不同的 OpenAI 账号，只要在添加时为它们指定不同的实例 ID，就能在系统中并存并同时使用。

在日常使用中，常见的提供商类型包括：

- **官方服务**：如 **OpenAI**、**Anthropic**、**Google**、**DeepSeek**、**阿里云** 等厂商的官方原生接口。
- **聚合网关**：如 **OpenRouter**、**Vercel AI Gateway** 这类聚合了海量模型的统一路由服务，只需一个账号就能调到多家模型。
- **云厂商托管服务**：如 **Azure OpenAI**、**Google Vertex AI**、**Amazon Bedrock** 等各大云厂商提供的企业级托管环境。
- **兼容自定义端点**：如 **OpenAI 兼容**、**Gemini 兼容**、**Claude 兼容** 等开放协议端点，非常适合中转服务、自建代理以及本地私有化推理。
- **复合路由**：在同一个提供商实例下挂载多条路由，把不同类型的请求智能分流并指向不同的后端。
- **Mock**：本地模拟假模型，专门用于界面测试和流程演示，不会发起真实网络请求，也不会产生调用费用。

### 添加提供商

在控制台中，配置提供商是一件非常直观的事情。

打开侧边栏的「配置 → 提供商」，点击右上角的「添加提供商」按钮。在弹出的面板中选择你要接入的类型，随后根据界面的表单引导填写连接参数：

- **名称 / ID**：实例的唯一标识。如果你接入了多个同类型的服务，系统在内部就是依靠这个 ID 来进行相互区分的。
- **端点地址**：服务的基础接口 URL。对于各类兼容协议端点，通常需要手动补齐基础路径（例如以 `/v1` 结尾的完整地址）。
- **API 密钥**：访问服务所需的凭证。你可以选择直接填写，也可以使用凭据引用方式。
- **模型清单**：部分提供商类型支持自动拉取模型列表；如果遇到不支持自动发现的服务，则需要在此手动填入模型 ID。
- **额外参数**：针对云厂商托管服务，表单中通常还会提供部署区域、项目 ID 或资源名称等特定字段。

在点击保存之前，请务必先点击表单底部的「测试连接」按钮。

系统会主动尝试向远端接口发送握手请求，现场验证端点地址是否可达、密钥是否有效以及模型列表能否正常获取。

只有当测试结果显示通过后，再点击「保存」按钮将实例存入系统。这样可以有效避免把一个尚未跑通或地址有误的失效实例写进配置，省去后续无谓的排查时间。

### 凭据与多密钥

在填写 API 密钥时，系统支持两种不同的存放方式：

- **直接填写**：最省事的做法，密钥会直接保存在实例的配置中。这种方式非常适合个人在本地调试或测试环境中使用。
- **凭据引用**：配置项中只记录一个凭据名称引用，真实的敏感密钥则存放在凭据库中。如果你的机器人运行在多人协作或生产环境中，这种方式更加安全可靠。

此外，为了应对服务商严格的请求并发与频次限制，系统还支持在同一个密钥字段中填入多个密钥。

输入时，只需用英文半角逗号将各个密钥隔开即可。在实际发起请求时，一旦遇到网络限流或个别密钥临时失效，系统就会自动轮换并按顺序尝试下一个密钥。

不过需要注意，多密钥轮换并不等于无限重试；当列表中的所有密钥都依次尝试失败后，当前的请求仍然会宣告失败。

::: warning
不要把包含明文密钥的界面截图发到公开交流群，也不要把含有密钥的日志和配置文件随意分享。在导出配置请求他人协助排查时，请务必提前确认里面没有留下明文密钥。
:::

## 模型

模型始终属于某一个具体的提供商实例。每一个成功接入系统的模型，都在界面中对应着一组清晰的属性描述：

- **模型 ID**：服务端用来准确识别该模型的名称，例如官方给出的具体版本号。
- **显示名称**：在控制台和聊天界面中呈现给用户的友好名称。
- **能力**：模型支持的内容格式与交互特性。包含能接受哪些输入与输出（如文本、图片、音频、视频、文件），以及是否支持工具调用、结构化输出和深度推理。
- **上下文窗口**：单次请求允许容纳的最大 token 总量，决定了模型一次能读入多长的对话历史。
- **价格**：包含输入、输出以及上下文缓存读写的单价，系统会借助这些数值进行实时的调用成本估算。
- **推理档位**：如果该模型支持思考过程，会在此声明可选的推理深度，通常包含低、中、高以及关闭等档位。

模型目录可以通过插件自动拉取，也可以在界面中手动维护。

自动获取的目录信息偶尔可能不够完整，或者对某些新特性的识别存在偏差。如果你发现某个明明支持识图的模型被错误标记成了不支持图片，可以直接在模型列表中点击进入详情页，手动勾选或修正对应的能力项并保存。

### 模型地址

在配置场景规则、分配任务或运行交互时，系统统一使用「提供商实例 ID : 模型 ID」的格式来精确定位一个模型。

例如 `openai:gpt-4o-mini`，就表示使用实例 ID 为 `openai` 的提供商下的 `gpt-4o-mini` 模型。

这个标准格式的模型地址会频繁出现在以下位置：

- 场景规则页面中的「基本 → 模型」选项。
- 聊天窗口顶部的模型下拉选择器。
- 提供商管理页中的「模型角色」配置项。
- 子代理调度、意图判定、记忆提取等各类后台任务的配置中。

需要特别说明的是：地址冒号前面的是提供商的「实例 ID」，而不是你随意填写的显示名称。

如果你在提供商页面中修改了某个实例的 ID，所有引用了该旧 ID 的场景规则和角色配置都不会自动更新，必须手动前往相应页面重新选择或更新模型地址。

### 模型角色

除了在日常对话中给机器人挑选一个主聊天模型之外，系统还在后台设计了一套「模型角色」机制。

在机器人的日常运行中，后台其实潜藏着大量细碎的辅助任务，比如提取用户画像、提取长期记忆、总结对话标题，或是判断当前用户是否在向机器人提问。如果这些后台杂项全都交给高配的大模型来处理，不仅响应迟缓，钱包也会大出血。

为此，系统抽象出了四个分工明确的模型角色：

- **小模型**：便宜又快速的轻量模型，专门用于处理判定、信息提取、对话摘要、自动起标题等轻型后台任务。
- **中模型**：性能与理解力优于小模型，适合作为通用子代理的默认模型，或者负责处理较为复杂的条件规划。
- **大模型**：综合能力最强的高阶模型，专门留给需要高质量文本生成、复杂逻辑论证的重度任务。
- **决策模型**：专门用于核心行为裁决，比如在群聊中实时判定「当前这一句话要不要搭理回复」或「这项高危操作要不要批准执行」。

你可以把每个角色分别绑定到具体的模型地址上。

那么，如果你刚配好机器人，还没来得及细分这些角色，后台任务会不会罢工报错呢？

完全不用担心。系统内置了非常贴心的回退机制：当角色未绑定时，会自动按照「大模型 → 中模型 → 小模型 → 会话主模型」的顺序向下寻找替代模型；而决策模型未绑定时，通常会默认回退到中模型。因此哪怕你从头到尾只配了一个主模型，所有后台任务也都能照常跑起来。

当你想要细化分工时，只需打开「配置 → 提供商」页面，切换到上方的「模型角色」标签页。在这里为各个角色挑选合适的模型并保存，设置就会在全局统一生效，完全不需要跑到每一个群的场景规则里重复填写。

### 视觉与多模态

模型自身所具备的能力，直接决定了它在收到不同格式的消息时能呈现出什么样的反应。

当用户在聊天中发送了富媒体内容时，系统会根据目标模型的能力标记做出针对性处理：

- **图片内容**：如果当前模型不支持视觉识别，系统会自动将图片剥离，并在对话中替换为对应的占位提示与文字描述，防止远端接口直接报参数错误。
- **音视频与文件**：对于不支持音频、视频或文件解析的模型，这些媒体内容本体不会强行塞进请求包里，只会保留基础的引用链接与元信息。
- **工具调用**：只有在能力清单中明确支持工具调用的模型，才能顺畅驱动系统的插件工具体系；若模型不支持工具调用，相关工具能力会被自动隐藏或降级。

对于模型目录中未登记的全新模型，系统通常会采取较为宽松的策略，把富媒体内容按标准格式全部提交给服务端。

但这完全取决于服务端的兼容程度，请求有可能直接失败，也有可能被服务端静默忽略。如果在日常使用中遇到「机器人坚称自己看不见图片」的情况，请先去模型详情页中检查该模型的视觉能力标记是否已被正确勾选。

## 选模型的几种方式

在实际运行中，面对一条具体的聊天消息，系统到底是怎么决定使用哪一个模型的呢？

ChatLuna 允许你在不同层级上指定模型。当多个地方的设置发生冲突时，系统会按照从高到低的优先级次序进行裁决：

1. **单次调用显式指定**：在某一次特定的指令触发或自动化脚本中，临时强制指定的专属模型。
2. **会话选择**：用户在聊天页面顶部的模型切换栏中，或者在具体会话的设置项里手动锁定的模型。
3. **场景规则**：在「场景规则」页面中，针对某个特定群聊、特定机器人账号或特定用户所覆盖配置的模型。
4. **引擎默认**：当前所选引擎（例如特定角色的独立对话引擎）自身所设定的默认模型。
5. **全局默认**：当上述所有层级都未做特殊指定时，系统最终采用的全局保底模型。

在这一套层级中，处于上层的具体配置具有更高的优先权，会直接覆盖掉处于下层的通用配置。

因此，当你发现机器人使用的模型不太对劲，想要排查「为什么这次会调用这个模型」时，只需严格按照上述五个层级由上往下逐层核对，就能迅速找到是哪里的配置覆盖了全局设定。

### 推理档位

针对支持深度思考的新一代推理模型，系统允许你在调用时进一步调节其思考深度。

打开相关设置，你会看到以下几个可选的推理档位：

- **低**：思考步骤精炼，响应速度最快，消耗 token 最少，适合处理事实明确的简单咨询。
- **中**：在推导深度与等待耗时之间取得平衡，适合绝大部分日常综合性任务。
- **高**：进行极其细致的多步逻辑推导，耗时较长且消耗较多 token，适合应对复杂分析与代码难题。
- **关闭**：彻底跳过思维链推理阶段，直接输出最终答案。

需要注意的是，可选档位完全受限于模型自身的能力声明。

虽然你可以在路由层或场景规则中自由挑选档位，但如果模型本身根本不支持推理，系统在运行时会自动将其降级为默认行为或直接丢弃该参数，并在后台日志中如实记录，确保正常回答不受影响。

## 运行时增强

在基础的提供商连接之上，ChatLuna 还提供了一套轻量且可按需插拔的「运行时增强」中间件体系。

你可以根据机器人的部署环境与网络状况，在设置中按需启用以下能力：

- **重试**：遇到偶发网络波动、服务端限流或请求超时时，系统会自动执行带退避延迟的重试，挽救当次调用。
- **回退**：当配置的主模型突发宕机或连续报错时，无缝切换到备用模型继续生成回复，保障服务不中断。
- **缓存**：对完全相同的请求内容复用历史生成结果，减少不必要的重复调用与开销。
- **预算**：按天、按月或按会话设定开销上限，一旦触碰预算红线便自动拒绝请求或降级至经济模型。
- **账本**：精确记录每一次调用的输入输出 token 数量与折算成本，方便在用量报表中随时查阅。
- **降级**：当模型缺少某项关键能力时，系统自动换用其他兼容方式完成表达与交互。
- **分组**：把多个不同的提供商或模型组合成一个逻辑入口，按照既定轮询或负载策略智能分流。

需要说明的是，这些能力在默认情况下并不会全部开启。

过多的中间件可能会对交互响应速度、费用预算以及失败处理逻辑产生连锁影响。对于生产或长期运行的环境，我们强烈建议至少开启「重试」与「账本」两项基础功能，兼顾稳定性与成本透明度。

## 首次配置

当你第一次安装好系统并登录进入控制台时，界面会自动弹出一套便捷的「设置向导」。

向导中的模型配置环节通常包含四个简短的步骤：

1. 在列表中点击选择你准备接入的提供商类型。
2. 填写你的 API 密钥与端点地址，并点击测试连接确认通信畅通。
3. 从成功拉取到的模型列表中，点选一个模型作为全局默认的主模型。
4. 确认信息无误后点击提交，将其保存为系统的第一个提供商实例。

在向导中填写的 API 密钥会安全地保存进后端的凭据库，绝不会泄露给第三方聊天平台，也不会残留在浏览器的本地临时草稿中。

只有当连接测试顺利通过的实例，系统才会将其判定为「模型就绪」状态，机器人也才能正式对外提供对话服务。

如果你在初次登录时不小心跳过了向导，也完全没关系。你随时可以打开控制台的「配置 → 提供商」页面进行手动添加；对于无法使用 Web 界面的纯命令行或容器化环境，也可以通过本地覆盖配置文件的方式提前预设好提供商和默认模型。

## 推荐配置

面对繁多的配置项，新手用户往往不知道该如何搭配。

这里我们梳理了几种常见的使用场景，供你参考：

### 个人使用

接入一家主流且稳定的大厂提供商，挑选一个综合性价比高的通用对话模型作为全局主模型。

将后台的小模型与决策模型直接绑定到同一提供商旗下的经济型模型上，既能减少跨服务商调用带来的延迟，又能保证输出风格的连贯。同时，记得在运行时增强中开启「重试」和「账本」功能。

### 多服务商

根据不同服务商的长处进行合理分工拆分。

例如，日常对话选用一家回复速度快、语义理解好的主力模型；把信息提取、意图判定等脏活累活交给另一家单价极低的轻量模型；遇到发图较多的场景，再通过规则定向路由到擅长多模态识别的提供商。务必在「模型角色」中把后台任务明确绑定到便宜模型上，避免它们在不知不觉中消耗昂贵的主模型额度。

### 本地 / 自托管

通过「OpenAI 兼容」等通用类型连接本地运行的私有化推理引擎（如 Ollama、LocalAI 或 vLLM），并在模型列表中手动补全模型 ID。

考虑到本地显卡资源的承载能力，建议关闭激进的并发重试与自动回退，防止高并发流量将本地服务挤爆。此外，本地模型的上下文窗口通常比云端模型小得多，记得在高级设置中把对话压缩阈值相应调低。

### 多群不同模型

如果你管理着多个不同属性的群聊，推荐优先使用「场景规则」来进行精细化区分。

保持全局默认模型为通用经济模型不变，只在几个特定的重点交流群或 VIP 群的场景规则中，打开覆盖开关并切换为高性能模型。千万不要在每一个群里都从头配置一遍完整的提供商信息，只要在规则里按需选模型即可。

## 排查

在使用和配置模型的过程中，如果遇到了不符合预期的情况，可以对照以下常见现象逐一排查：

**添加提供商时连接失败。**
请仔细核对端点地址、API 密钥是否准确，以及网络代理是否配置妥当。如果你使用的是兼容协议的中转端点，请注意端点地址末尾是否漏掉了版本路径（例如 `/v1`）；若是连接云厂商托管服务，检查是否漏填了区域或项目 ID 等必填参数。

**模型列表是空的。**
有些中转服务商或本地端点不提供自动拉取模型的发现接口。此时无需担心，直接在提供商配置面板的模型清单一栏手动输入服务端实际的模型 ID 即可。输入时请务必确认大小写与版本后缀完全吻合。

**回复报「模型不存在」。**
这通常是因为模型地址格式书写错误或引用了无效 ID。请仔细检查报错处填写的模型地址，冒号左侧必须是提供商页里显示的「实例 ID」，而非外部起的名字。如果你曾经修改过该实例的 ID，必须去报错的规则页重新选定一次模型。

**图片发不出去。**
如果机器人始终对发送的图片视而不见，可能是该模型在模型目录中被标记为不支持视觉能力，也有可能是当前会话的场景规则中限制了接收图片。请先进入模型详情确认视觉能力勾选项，再前往场景规则排查群聊图片设置。

**后台任务用了很贵的模型。**
请打开「配置 → 提供商」并切换到「模型角色」检查绑定情况。当后台的小模型或决策模型未做单独指定时，系统会自动向下回退至当前会话的主模型；如果主模型恰好是高价旗舰模型，就会产生意外的开销。请将这些后台角色明确绑定到小模型上。

**切换模型后缓存不命中。**
系统在构建上下文缓存时，会将具体的模型标识作为缓存键前缀的一部分。如果你在短时间内频繁在多个模型之间来回切换，原有的上下文缓存就会全部失效，导致每次请求都需要重新计算。建议尽量固定使用一个主模型，或仅在特定独立会话中选用新模型，避免频繁做全局性的来回切换。

# 技能

::: tip
技能把「做某件事的方法」写成一份可加载的说明。模型平时只看到技能目录，需要时才读取完整内容；这样既能装很多专长，又不用把每份说明都塞进每次请求。
:::

简单来说，工具解决的是「能做什么」的问题，而技能解决的则是「具体怎么做」。

在日常使用中，如果你想让机器人学会一项复杂的业务流程，最直接的想法往往是在对话的系统提示词里写满详细步骤。

但如果每一个专业任务都这么写，机器人的上下文空间很快就会被挤占殆尽，甚至严重影响日常对话的理解质量。

技能的出现，正是为了妥善解决这一矛盾。

通常情况下，一个技能的核心就是一份格式规范的 Markdown 说明文档，此外还可以根据实际需要，附带可执行的脚本、文本模板以及各类参考资源。

当用户向机器人提出需求时，模型并不会一开始就把所有技能的详细正文通读一遍。

相反，它平时看到的仅仅是一份精简的技能目录——里面只记载了各个技能的名称和一句简短的功能描述。

只有当模型判断当前对话确实需要用到某项专长时，它才会主动请求加载该技能的正文，并严格按照说明中的步骤去调用工具或运行脚本。

这种「先看目录索引、需要时再查阅正文」的方式，在系统中被称为渐进披露。

渐进披露带来的好处非常显著：

你可以放心地为实例安装成百上千个不同场景的技能，而完全不用担心它们会拖慢日常的普通对话。

只有在真正触发某项技能的具体回合里，该技能的详细内容才会产生对应的上下文成本。

## 技能页

打开控制台，在侧边栏中点击「能力 → 技能」，就能进入技能管理页面。

这里集中展示了当前实例所有可用与已发现的技能。

为了方便日常浏览与管理，技能页顶部提供了灵活的视图与筛选控制。

你可以根据个人习惯，随时在直观的卡片视图与紧凑的列表视图之间进行切换。

当技能数量较多时，你还可以按来源层级对技能进行分组查看，或者直接在搜索框中输入关键字快速检索，也可以按照技能名称或更新顺序进行排序。

在列表中点击任意一个技能，页面右侧就会展开该技能的详细信息面板。

通过这个面板，你可以清晰地了解该技能的完整状态：

- 技能名称、简介和正文预览：展示技能的标题、一句话功能概述，并提供可直接滚动的完整说明正文预览。
- 来源：明确标示该技能的具体出处，包括内置、宿主机目录、用户自定义、工作区、导入还是市场。
- 文件清单：除了核心说明文档之外，清楚列出该技能目录下还包含了哪些脚本文件、模板文件和参考资源。
- 环境变量声明：详细列出技能运行所需的配置项，明确标注哪些变量是必需填写的、哪些变量属于敏感密钥，以及各自的默认值。
- 覆盖关系：当系统中存在多个同名技能时，这里会清晰显示当前实际生效的是哪一个，以及哪些同名技能正处于被遮蔽状态。

如果你从社区获取了新的技能文件，也可以直接在技能页进行导入。

目前系统支持以下几种导入形式：

- 单个 `SKILL.md` 文件。
- 一个技能文件夹。
- 一个 `.zip` 包。

通过界面导入技能后，系统会即时完成扫描与注册。

如果你导入的新技能与已有技能同名，新技能可以直接覆盖原有的同名技能。

而对于不再需要的导入技能，你也可以在详情面板中直接点击删除将其彻底移除。

需要特别说明的是，随插件分发的内置技能通常处于只读保护状态，不能直接在界面上修改或覆盖。

如果你想调整某个内置技能的内容，最推荐的操作是在详情面板中点击复制，将其完整复制一份到用户自定义目录中，随后便可以在自定义副本上自由修改了。

::: warning
同名技能不会合并，而是按来源优先级取一个，其余被遮住。

如果你在修改了某个技能后发现实际表现没有任何变化，排查时的第一步就是打开技能页，仔细查看该技能当前生效的来源以及具体的覆盖关系。
:::

## 技能从哪来

既然技能可以来自各种不同的途径，那么当系统启动或扫描技能时，究竟是如何决定选用哪一个的呢？

在底层设计中，系统将技能划分为多个清晰的来源层。

当遇到同名技能发生冲突时，系统会自上而下按照来源层的固定优先级进行裁决：

1. **工作区**：当前 Agent 的工作目录里的技能。这一层的优先级最高，非常适合存放特定项目的专有技能。它既能精准满足单个项目的定制需求，又完全不会影响到全局的其他项目。
2. **内置**：随插件分发的技能。它们为系统提供了开箱即用的基础能力，默认受到系统的只读保护。
3. **宿主机目录**：数据目录或配置的宿主机路径下的技能。适合在宿主机层面上进行跨实例的统一维护与批量管理。
4. **用户自定义**：数据目录里的自定义技能目录。你在管理控制台中手动新建或复制出来的技能，通常都会存放在这里。

如果两个技能处于完全相同的来源层中，系统则会根据加载顺序或排名规则来处理，通常后注册或排名更高的技能优先。

但无论如何，同名技能最终只会保留一个，其他的标记为被遮蔽。

除了本地已经存在的文件之外，技能还可以来自市场（如果启用了市场）。

当你在技能市场中找到心仪的技能并下载后，市场技能下载后落在宿主机目录，和本地技能一样参与优先级排序。

## 一份技能长什么样

抛开抽象的概念，一个技能在文件结构上其实非常纯粹。

在最基础的情况下，一个技能至少包含一个 `SKILL.md`。

打开这个文件，你会发现它在结构上清晰地分为两个部分：文件头部是元数据，正文是给模型看的说明。

在顶部的元数据区域，我们通过标准字段向系统介绍这项技能的基本属性。

常见的元数据字段包括：

| 字段 | 作用 |
| --- | --- |
| 名称 | 技能的唯一标识，通常要求小写短横线格式。 |
| 描述 | 一句话说明技能做什么，会进入技能目录。 |
| 版本 / 作者 / 许可 | 可选的来源信息。 |
| 平台 | 技能适用的操作系统，例如 macOS、Linux、Windows。 |
| 环境 | 技能适用的运行环境。 |
| 环境变量 | 技能运行需要的变量，可以标记为密钥、必需或带默认值。 |

元数据下方的大篇幅内容，就是整份技能的核心：什么时候用、步骤是什么、注意什么、失败怎么处理。

这份正文的表述是否清晰准确、步骤是否严谨，直接决定了模型会不会正确使用。

除了单一的说明文档之外，技能目录里还可以放脚本、模板、参考文档和资源文件。

当模型按需加载该技能后，便可以通过技能工具读取这些文件，或运行脚本。

### 环境变量与密钥

在很多实际业务中，技能在执行时往往需要依赖外部的配置参数。

为了兼顾灵活性与安全性，技能可以声明自己需要哪些环境变量：

- **必需**：没有值就不能运行，加载时会提示缺失。
- **密钥**：值是敏感信息，不应出现在日志或模型上下文里。
- **默认值**：没有配置时使用的值。

需要特别指出的是，敏感密钥的使用并不是无条件的，它会受到场景规则的严密管控。

某个群或某个私聊可以禁止技能使用保存的密钥。

一旦受到场景规则的禁止，依赖密钥的技能在这个场景里不可用，从而彻底防范越权调用敏感凭证的风险。

::: tip
不要把密钥直接写进 `SKILL.md`。

规范的做法是用环境变量声明，让密钥留在实例的凭据或环境配置里；技能正文只引用变量名。
:::

## 模型怎么用技能

了解了技能的组织形式之后，我们再来看看在日常的人机交互中，模型究竟是如何发现并使用这些技能的。

正如前面提到的，模型不会一次性看到所有技能正文。

它平时看到的仅仅是一个技能目录：每个技能的名字、一句简介，以及怎么加载。

当用户提出的需求触及某项技能的专业范畴时，模型会根据目录指引，主动调用技能工具：

- 列出或搜索技能。
- 读取某个技能的完整说明。
- 读取技能里的某个文件。
- 运行技能脚本。

模型读取到技能的详细正文后，加载后的正文进入当前回合的上下文，不会永久留在系统提示里。

下一回合如果还需要，模型要重新加载。

这种机制保证了技能很多时也不会把前缀撑爆。

此外，技能不仅可以作为被动查阅的操作手册，还可以拥有自己的工具入口。

例如某个技能提供一个「查询订单」的工具，模型可以直接调用，而不必先读完整说明。

## 技能脚本

除了用于指导模型的文字说明之外，技能还可以带脚本。

在很多实际业务中，如果把确定性的计算或外部命令全交给模型去逐字推导，往往效率不高且容易出错。

而脚本恰恰非常适合这类确定性操作：格式转换、批量处理、调用内部命令。

最理想的分工方式是：把需要判断和解释的部分，仍然交给模型；而把确定性的操作交给脚本执行。

当模型在对话中发起运行脚本的指令时，系统会：

- 在受控的工作目录里执行。
- 注入技能声明的环境变量。
- 按权限模式决定要不要审批。
- 捕获输出并返回给模型。

通过这种方式，脚本的高效可靠与模型的灵活智能得以实现优势互补。

::: warning
技能脚本和命令执行一样有风险。

不要把来源不明的技能直接放进生产实例；导入前先看脚本内容，必要时先设成需要审批。
:::

## 技能市场与自动进化

如果启用了技能市场，可以在技能页搜索和安装社区技能。

市场技能和本地技能走同一套发现、覆盖和权限规则。

除了手动安装技能之外，还有一个可选的「技能自进化」插件（默认不装）：

- 允许模型把成功的做法写成草稿技能。
- 经过测试、审查、安装和回滚流程后才生效。
- 可以自动提议草稿，但不会跳过审查。

没有这个插件时，技能注册表是只读的：

只能通过导入、文件编辑或市场安装来增加技能。

这意味着系统本身绝不会在后台擅自生成或修改任何技能，所有技能的变更都处于管理员的明确控制之下。

## 与工具、MCP 的关系

初次接触系统的用户，往往容易混淆这几个概念。

三者经常一起出现，但职责不同：

- **工具**是模型可以直接调用的动作。它相当于机器人的手和脚，专门负责执行单一、具体的操作，例如读取文件或发送消息。
- **技能**是使用工具的方法和流程，通常以说明和脚本的形式存在。它负责教会模型按什么顺序、在什么条件下组合使用工具。
- **MCP**是把外部服务的工具接进来的协议。它的核心使命是充当开放桥梁，把外部独立服务的能力转换为可用工具。

在实际运作中，这三者构成了紧密协作的能力体系：

一个技能可以指导模型使用多个工具；一个 MCP 服务器可以提供多个工具；技能也可以调用 MCP 工具。

权限和审批对它们统一生效。

无论具体的动作来自何处，系统都会在底层进行一致的校验与把关。

## 推荐配置

在不同的部署与应用场景下，技能的配置侧重点应当有所区别：

### 个人实例

只装少量常用技能，保持技能目录简短。

把需要的环境变量配好，密钥类变量设成密钥。

技能脚本默认需要审批，避免误操作风险。

### 多人群聊

按群控制技能：在「场景规则 → 能力 → 技能」里给不同群设置允许/禁用列表，并决定是否允许使用密钥。

群里只保留查询类技能，写入和执行类技能只在管理员场景开放。

这样可以有效避免公共群聊中成员越权触发高风险操作。

### 团队 / 项目

把项目专用技能放进工作区，优先级最高，不污染全局技能。

用版本控制管理技能文件，确保每一次改动都清晰可查。

导入前先在测试实例验证，确认稳定后再部署到生产环境。

### 技能很多

依赖渐进披露，不要把所有技能都做成常驻工具。

定期清理不再使用的技能，避免目录膨胀和同名覆盖混乱。

留意技能页显示的覆盖状态，确保核心技能正常生效。

## 排查

在配置、导入或调用技能的过程中，如果遇到了未达预期的异常表现，可以对照以下常见场景进行逐一排查：

**模型不知道有这个技能。**
检查技能是否被发现、是否被同名技能遮住、是否被场景规则禁用、来源目录是否在扫描范围内。技能页会显示最终状态。

**技能加载了但模型不用。**
简介写得太模糊，或者正文步骤不清晰。把「什么时候用」写进简介和正文开头，减少模型判断成本。

**技能脚本报缺少环境变量。**
到技能详情看环境变量声明，补上必需项。密钥类变量要确认当前场景允许使用密钥。

**导入后同名技能没变。**
新技能可能被更高优先级的同名技能遮住了。看技能页的覆盖关系，删除或重命名其中一个。

**技能正文太长，加载后上下文不够。**
把技能拆成多个小技能，或把细节放到技能目录里的参考文件，正文只留步骤和入口。模型需要时再读参考文件。

# 技能

::: tip
技能把「做某件事的方法」写成一份可按需加载的操作说明。模型平时只看技能目录，需要时才查阅完整步骤；这样既能掌握大量专业本领，又不会让每次对话的上下文被说明文档挤占。
:::

在前面的章节中，我们已经了解了工具的基本用法。如果说工具解决的是机器人「能做什么」的动作问题，那么技能解决的，就是「具体怎么把一件事做好」的流程问题。

很多时候，你可能希望机器人学会一套复杂的业务操作。最直接的做法，莫过于把详细的执行指南一股脑写进系统提示词里。

但如果每个专业场景都这么写，机器人的上下文空间很快就会被大量静态文档塞满。这不仅会消耗额外的对话额度，甚至还会干扰模型对日常闲聊和基础指令的理解质量。

技能的引入，正是为了妥善化解这一矛盾。

一份技能的核心，往往就是一份条理分明的 Markdown 说明文档。如果遇到更复杂的业务场景，你还可以在技能目录中附带现成的脚本文件、文本模板以及各类参考资源。

当用户向机器人发出提问时，模型并不会直接通读所有技能的详细正文。

相反，它平时在脑海中看到的，仅仅是一份精炼的「技能目录」——里面只记录了各个技能的名字与简短的一句话描述。

只有当对话话题真正触及某项专业领域时，模型才会主动请求调阅该技能的完整说明，随后按照步骤调用工具或执行脚本。

这种「平时只翻目录，用时再查说明」的机制，在系统里被称为渐进披露。

渐进披露为日常使用带来了显而易见的好处：

你可以放心地给机器人配置成百上千个不同场景的技能，而完全不用担心日常打招呼或简单问答被拖慢。

技能正文所带来的上下文开销，只会发生在真正调阅它的那一轮对话之中。

## 技能页

想要查看和管理机器人掌握的各项本领，我们可以从控制台的技能页开始。

打开控制台，在左侧导航栏中点击「能力 → 技能」，便能进入技能管理主界面。

这里集中收录了当前实例中所有已经发现且可供调用的技能。

为了让管理和浏览更顺手，技能页在顶部提供了灵活的视图切换与筛选工具：

- **切换视图**：你可以随时在直观的卡片视图与紧凑的列表视图之间进行切换。
- **分组查看**：技能比较多时，可以按照来源层级对技能进行分组折叠，快速理清技能的出处。
- **检索与排序**：在搜索栏中输入关键字即可快速过滤，也可以按技能名称或更新时间重新排列。

在列表中点击任意一项技能，右侧就会滑出该技能的详细信息面板。

通过这个面板，你可以一步到位地了解技能的完整属性与状态：

- **名称、简介与正文预览**：展示技能的标题、一句话功能概述，并提供可直接滚动阅读的完整说明正文。
- **来源**：明确标示当前技能是从哪里加载而来的，包括内置、宿主机目录、用户自定义、工作区、导入还是市场。
- **文件清单**：清晰列出该技能目录下除了主说明文档之外，还附带了哪些可执行脚本、模板文件以及参考文档。
- **环境变量声明**：详细罗列运行该技能所需的配置项，清楚标明哪些参数是必需填写的、哪些参数属于敏感密钥，以及各自的默认值。
- **覆盖关系**：如果系统中存在多个同名技能，这里会直接告诉你当前真正生效的是哪一个，以及哪些副本正处于被遮蔽状态。

当你从社区或是其他渠道获取了一份制作好的新技能，可以直接在技能页将其导入系统。

目前技能页支持以下几种导入形式：

- 单个 `SKILL.md` 文件。
- 一个包含完整资源的技能文件夹。
- 打包好的 `.zip` 压缩包。

完成导入后，系统会立即执行扫描并将其注册到技能列表中。

要是导入的新技能与已有技能重名，新技能可以直接覆盖原有的同名技能。

对于那些后续不再需要的导入技能，你也可以在详情面板中直接点击删除按钮将其彻底移除。

需要留意的是，随插件一同分发的「内置技能」通常处于只读受保护状态，系统不允许直接在界面上对它们进行编辑或覆盖。

如果你想修改某个内置技能的内容，推荐的做法是在详情面板中点击「复制」，把它完整复制一份到用户自定义目录中，随后便能在属于你自己的副本上自由定制了。

::: warning
同名技能不会合并内容，而是按照来源优先级只保留一个生效，其余的同名项都会被遮蔽。

如果你修改了某个技能却发现机器人的实际表现没有任何改变，排查的第一步就是打开技能页，确认当前生效的究竟是哪一个来源，并仔细检查右侧面板里的覆盖关系。
:::

## 技能从哪来

既然技能可以通过多种途径进入系统，那么当机器人启动并扫描技能时，遇到名字冲突究竟该听谁的呢？

为了避免不同来源的技能互相打架，系统在底层划分了清晰的来源层级。

当遇到同名技能发生冲突时，系统会严格按照自上而下的固定优先级进行裁决：

1. **工作区**：位于当前 Agent 工作目录中的技能。它的优先级最高，专门用来存放特定项目的专属技能。它既能精准适配单个项目的定制需求，又完全不会影响全局其他项目的运作。
2. **内置**：随插件一同分发的技能。它们为系统提供了开箱即用的通用能力，默认受到系统的只读保护。
3. **宿主机目录**：存放在数据目录或指定宿主机路径下的技能。适合运维人员在宿主机层面上进行跨实例的集中维护与批量下发。
4. **用户自定义**：存放在数据目录自定义技能目录中的技能。你在控制台里手动新建、或者从内置技能中复制出来的副本，通常都保存在这里。

如果两个同名技能恰好处于完全相同的来源层级内，系统则会根据扫描加载的先后顺序或内部排名规则来决定，通常以最新注册或排名靠前的版本为准。

但无论如何，同名技能最终只会保留一个生效，其余版本均会被系统标记为被遮蔽。

除了本地已经存在的文件之外，技能还可以来自技能市场（如果当前实例启用了技能市场功能）。

当你浏览市场相中某项技能并点击下载后，下载回来的技能文件会自动落在宿主机目录中，随后便会与本地技能一样参与统一的优先级排序与生效裁决。

## 一份技能长什么样

把抽象的概念放到一边，如果从文件结构来看，一个技能其实非常朴实直观。

在最精简的情况下，一个标准技能只需要包含一个名为 `SKILL.md` 的说明文件即可。

打开这个文件，你会发现它的内部结构主要分为上下两大部分：文件头部是一组格式规范的元数据，下方则是写给模型阅读的说明正文。

在头部的元数据区域，我们通过标准字段向系统登记该技能的基本档案：

| 字段 | 作用 |
| --- | --- |
| 名称 | 技能的唯一标识，通常要求小写短横线格式。 |
| 描述 | 一句话说明技能做什么，会进入技能目录。 |
| 版本 / 作者 / 许可 | 可选的来源信息。 |
| 平台 | 技能适用的操作系统，例如 macOS、Linux、Windows。 |
| 环境 | 技能适用的运行环境。 |
| 环境变量 | 技能运行需要的变量，可以标记为密钥、必需或带默认值。 |

元数据下方的说明正文，则是整份技能最核心的灵魂：什么时候应该使用该技能、具体的执行步骤是什么、有哪些注意事项、遇到错误时该如何补救。

这份正文写得是否清晰准确、步骤引导是否严谨到位，直接决定了模型在实际对话中能不能正确掌握该技能。

在单一的说明文档之外，一个功能完整的技能目录下还可以放入辅助脚本、文本模板、参考文档以及各类素材文件。

一旦模型按需加载了该技能，便能通过技能配套工具读取这些参考文件，或是直接运行附带的脚本。

### 环境变量与密钥

在处理真实的业务时，许多技能需要依赖外部环境的配置参数才能正常运转。

为了兼顾配置的灵活性与安全性，技能可以在元数据中预先声明自己所需的环境变量：

- **必需**：缺少该变量技能就无法运行。如果加载时发现没有配置该变量，系统会明确给出缺失提示。
- **密钥**：变量的值属于敏感信息，不应出现在日志或模型的对话上下文中，避免外泄。
- **默认值**：当用户没有主动配置该参数时，系统自动兜底采用的值。

更重要的是，敏感密钥的使用并不是毫无节制的，它会受到场景规则的严格管控。

在实际使用中，管理员可以在特定群聊或私聊场景中禁止技能使用保存的密钥。

一旦受到场景规则的禁止，依赖敏感密钥的技能在对应会话里就会直接变为不可用状态，从而在根源上彻底防范非授权场景跨界调用敏感凭证的风险。

::: tip
切忌将密码、API Token 等敏感密钥直接明文写在 `SKILL.md` 的正文里。

规范的做法是在技能头部声明环境变量，将真实凭据留在实例的凭据或环境配置里；技能正文中只提及对应的变量名称即可。
:::

## 模型怎么用技能

了解了技能的存放与结构之后，我们来看看在日常交互中，模型究竟是怎样找到并施展这些本领的。

正如前面提到的，模型在对话之初并不会直接通读所有技能的完整正文。

在平时状态下，系统只会在模型的视野中呈现一份轻量级的技能目录：包含各个技能的名称、一句话功能概述以及调阅该技能的方法指引。

当用户在对话中提出了需要专业技能解决的诉求时，模型会根据目录中的简述做出判断，并像操作工具一样主动向系统发出调用请求：

- 搜索或列出当前所有可用的技能。
- 读取指定技能的完整说明正文。
- 按需查阅技能目录中附带的特定文件。
- 触发并运行技能附带的执行脚本。

当模型读取了技能的详细说明后，这份正文只会进入当前对话轮次的上下文中，而不会永久保存在系统提示词里。

如果下一回合的对话中仍然需要用到该技能，模型会根据需要再次重新查阅。

这种按需调阅的设计，确保了即便系统里装载了成百上千种专业技能，也绝对不会把初始提示词的前缀撑爆。

不仅如此，技能除了充当供模型查阅的操作手册之外，还可以拥有专属的工具入口。

举个例子，某个技能可以直接向模型提供一个「查询订单」的工具入口，此时模型可以直接发起工具调用来获取数据，甚至无需先读完冗长的前置说明。

## 技能脚本

在撰写技能时，除了引导模型思考的文字步骤，我们还可以为技能附带脚本。

在很多日常任务里，如果把纯粹确定性的计算、格式转换或系统命令调用完全丢给模型逐字推演，不仅效率不高、耗费更多算力，还容易因为模型理解偏差而出现失误。

而脚本恰好最擅长处理这类确定性的操作：诸如格式转换、批量处理或调用内部命令。

因此，最理想的分工方式是：把需要判断分析、解释说明的部分仍然交给模型，而把确定性的操作交给脚本执行。

当模型在对话中发起运行脚本的指令时，系统会按照规范的安全流程予以处理：

- 自动在受控的独立工作目录中执行该脚本。
- 安全注入该技能在元数据中所声明的环境变量。
- 根据当前的权限管控模式，决定是否需要人工审批。
- 完整捕获脚本的标准输出与错误信息，原样反馈给模型作为后续推理的依据。

借助这套机制，既保留了脚本高效可靠的确定性，又发挥了模型灵活聪慧的上下文理解优势。

::: warning
技能脚本拥有在宿主环境中执行命令的能力，与直接执行系统命令一样具有安全风险。

切勿将来源不明的第三方技能直接导入生产环境。导入前务必先仔细查看脚本内容；在不确定的情况下，最好先将其执行权限设为需要人工审批。
:::

## 技能市场与自动进化

如果你的实例开启了技能市场功能，你便能直接在技能页中检索、浏览并安装来自社区的各类丰富技能。

通过技能市场安装的技能，会自动遵循与本地技能完全一致的发现机制、层级覆盖逻辑以及权限校验规则。

除了由人工主动挑选并安装技能之外，系统还提供了一个可选的「技能自进化」插件（默认不安装）：

- 允许模型在日常对话总结出成功经验后，尝试将其整理成技能草稿。
- 草稿技能必须经过严格的测试验证、人工审查、手动确认安装与回滚流程后，才能正式投入运行。
- 模型在对话中只能提出技能草稿提议，绝对不会绕过人工审查私自上线生效。

在没有启用该插件的普通环境下，整个技能注册表始终是只读受保护的：

所有的技能新增与变动，都必须通过管理员在界面上手动导入、编辑本地文件或通过市场安装才能完成。

系统本身绝不会在后台擅自生成或修改任何技能，所有能力的扩充都牢牢掌握在你的掌控之中。

## 与工具、MCP 的关系

刚接触这一整套能力体系的用户，很容易将这几个名称相似的概念弄混淆。

在日常使用中，它们确实经常一同登场，但各自的分工有着清晰的边界：

- **工具**：是模型可以直接调用的动作。它就像机器人的手和脚，专门负责执行单一、具体的实际操作，比如读取文件或发送消息。
- **技能**：是指导模型如何运用工具的方法和流程，通常由说明文档和脚本组成。它的职责是教会模型按什么顺序、在什么条件下组合使用工具。
- **MCP**：是将外部独立服务所提供的工具接入本系统的开放协议标准。它的核心使命是充当开放桥梁，把外部独立服务的能力转换为可用工具。

在实际执行一个复杂任务时，三者往往紧密配合、环环相扣：

一份技能可以指导模型使用多个工具；一个 MCP 服务器可以提供多个工具；技能自身也可以调用由 MCP 带来的外部工具。

无论具体的动作来自何处，系统都会在底层进行一致的权限校验与审批把关，确保安全规则统一生效。

## 推荐配置

为了让技能体系在不同的应用场景中发挥出最佳效果，我们建议针对不同环境采取差异化的配置策略：

### 个人实例

在个人使用的机器人上，建议保持精简，只安装少量高频使用的技能，让技能目录保持简短清晰。

对于依赖的外部配置，在设置中把环境变量逐一配好，敏感凭据务必勾选标记为密钥。

技能脚本的执行策略建议保持默认的需要人工审批，避免在日常使用中发生误操作风险。

### 多人群聊

在公开或多人群聊环境中，务必做好精细化管控：在「场景规则 → 能力 → 技能」里为各个群单独配置允许或禁用的技能列表，并明确决定是否允许使用密钥。

在公共群聊中，通常只开放信息查询类技能，将涉及数据写入和系统执行的技能严格限定在管理员私聊等受信场景中开放。

这样可以有效避免公共群聊中普通成员越权触发高风险操作。

### 团队 / 项目

如果是面向团队协作或特定工程项目的场景，建议将项目专用技能放进工作区目录中。

工作区技能的优先级最高，不仅能精准满足单个项目的定制需求，而且完全不会污染全局其他技能。

技能文件推荐使用版本控制系统进行管理，确保每一次改动都清晰可查。在正式导入生产环境之前，务必先在测试实例中完成验证，确认流程稳定后再行部署。

### 技能很多

当系统中累积安装了大量技能时，应充分依赖系统的渐进披露机制，切忌把所有技能都做成常驻工具。

建议养成定期清理技能库的良好习惯，及时移除不再使用的技能，避免技能目录过度膨胀和同名覆盖混乱。

日常多留意技能页显示的覆盖状态，确保核心定制技能正常生效。

## 排查

在配置、导入或调用技能的过程中，如果遇到了未达预期的异常表现，可以对照以下常见场景进行排查：

**模型不知道有这个技能。**
请检查该技能是否被系统成功扫描发现、是否被同名的更高优先级技能遮蔽、当前会话是否被场景规则禁用，以及所在目录是否在扫描范围内。技能页右侧面板会展示最终状态。

**技能加载了但模型不用。**
通常是因为技能简介写得过于模糊，或者正文里的步骤不够清晰。建议把「什么时候用」明确写进简介和正文开头处，减少模型的判断与匹配成本。

**技能脚本报缺少环境变量。**
请在技能页中点击该技能展开详情面板，查阅其环境变量声明，补齐标明为必需的配置项。如果涉及密钥类变量，还需确认当前场景规则是否允许使用密钥。

**导入后同名技能没变。**
新导入的技能可能因为所处的来源层级较低，被更高优先级的同名技能遮住了。请在技能页查看具体的覆盖关系，通过重命名或删除冲突项来确保目标版本生效。

**技能正文太长，加载后上下文不够。**
如果一份技能正文篇幅过于庞大，加载后会占用过多上下文空间。建议将大技能拆分成多个小技能，或者把细节规则放入技能目录下的参考文件中，正文只保留核心步骤与入口，引导模型在需要时再去读取参考文件。
